# ADR-0047：用户可见终态解耦与内存目录树查询权威

- 状态：Accepted
- 日期：2026-08-24
- 相关预研：[R-047](../research/R-047-用户可见终态解耦与内存目录树查询预研.md)
- 实施状态：代码切片已完成并端到端实测（2026-08-25）。可见终态中位数 `20.651s` → `17.110s`，
  目录覆盖率 `92.86%`，真实 `/` 上投影与 durable 逐字段一致；`<=16s` 门禁差 `1.1s` 未达成，
  `700 MiB` 内存预算经实测证伪并已重定（见第 2.1 条）。详见
  [R-047 第 3.13 节](../research/R-047-用户可见终态解耦与内存目录树查询预研.md)。

  实现与本 ADR 假设的三处机制差异（均不改变决策，且都更省或更安全）：
  1. **投影只在内存保留记录地址与排序键**，节点事实仍从已提交数据帧经 `readNodeRecordAt` 解码——与
     durable 走同一条解码路径，一致性因此是结构性的，而不是靠测试维持；
  2. **不需要按 `parent_id` 分片**。该约束源自原型直接挂扫描器的并发 emitter；实现中投影由 writer 累加，
     `AppendBatch` 是在 store 锁下由单个 goroutine 串行调用的；
  3. **目录子项全部保留，只对文件子项做 top-K**。目录自身的 roll-up 尺寸要到扫描结束才最终确定，扫描期
     按 `owned_allocated` 选 top-K 会选错条目；文件尺寸在 emit 时已最终，可以安全裁剪。原型只保留
     `ID/Owned/Name/Kind`，碰不到这个正确性问题。

## 背景

Marmot 从 R-038 到 R-046 连续九个切片在 `FinishSnapshot` 外排结构和 Darwin 原生扫描回调内部做 CPU、
分配和 I/O 优化，产品完整终态目标一次都没有达成。当前稳定 profile 中纯原生扫描已占完整终态 `70.3%`
（`14.952s / 21.254s`），`FinishSnapshot` 占 `19.9%`，Application 收尾约占 `9.7%`。

本轮纠正了三个此前未被处理的事实：

1. **被优化了九轮的 `<15s` 门槛没有实测出处。** 它最早出现在
   [R-020](../research/R-020-macOS目录fd与openat扫描路径优化预研.md) 第 52 行和
   [R-024](../research/R-024-SQLite扫描写入并发与端到端性能复测.md) 第 22 行的推定表述；
   [R-014](../research/R-014-DaisyDisk本机实机交互复核.md) 只记录窗口尺寸和菜单项，没有耗时。
2. **同机同卷实测原版三次为 `18s` / `16s` / `15s`，中位数 `16s`**（开始 → 扫描完成进入结果页）。
   真实差距约 `5.25s` / `33%`。`15s` 这个数值本身接近原版最好一次，并不离谱；错的是**口径**——它被当成
   durable 完整终态的目标，而原版的数字是可见终态，于是九轮切片都在用错误的口径判定达成与否。
   三次结果单调下降，高度疑似 APFS cache 逐次预热，因此 Marmot 的对照测量必须使用相同的冷热次序纪律。
3. **原版终态不是「首屏 + 后台补齐」。** 实机观察其扫描完成时整张空间图可见、可连续下钻五层，说明
   该时刻全盘结构已保留在进程内存中。因此任何「只发布首层、深层等待」的方案不构成追平，只是把等待
   从进页面前挪到首次下钻时。

同时确认了一个使方案可行的事实：**扫描结束时全盘目录聚合树已经在内存中，是已付成本。** 两条扫描路径
都为每个目录持有 path、parentID 和全深度 roll-up 后的聚合尺寸——
`internal/infrastructure/scanner/scanner.go:136-138`、`:172-174`、`:337-345`，以及
`internal/infrastructure/scanner/native_darwin.go:902`、`:923-926`、`:949-964`、`:764`。它已经计入当前
峰值 RSS。缺的只有子项排序列表，和个体**文件**条目（文件只被累加进父目录 totals，而 `MapEntry` 是包含
文件条目的，见 `internal/domain/scan/model.go:79`）。

R-047 第 3.7 节已实测本机 `/` 的分布并据此定尺寸：目录 `771,265`、文件 `2,737,195`；深度分布很深
（深度 `<=4` 只覆盖 `0.9%` 目录，`50%` 的目录在深度 `>=10`），所以按深度收口不可行；子项数极度偏斜
（`p50=1`、`p90=5`、`p99=53`），所以按目录做 top-K 收口很便宜。

| 方案 | 保留条目 | 子项被完整覆盖的目录 | 估算内存 |
| --- | ---: | ---: | ---: |
| 全深度 top-8 | `1,529,545` | `93.26%` | `72.8 MiB` |
| 深度 `<=4` top-256，其余 top-8 | `1,552,980` | `93.31%` | `74.0 MiB` |
| 深度 `<=4` top-256，其余 top-16 | `1,878,049` | `95.90%` | `89.8 MiB` |

分层几乎免费（`+1.2 MiB`）且修掉了纯 top-8 会把根目录 18 个子项折掉 10 个的首屏残缺；top-16 多花
`15.8 MiB` 只换 `2.6` 个百分点，性价比明显更低。

R-047 第 3.9 节随后用真实扫描器跑了只测量的投影原型，结果替换了上面的估算并新增两条实现约束：

| 项目 | 实测 |
| --- | ---: |
| 真实节点 / 目录 / 非空目录 | `2,860,136` / `589,497` / `422,577` |
| 保留条目 | `1,159,430` |
| 扫描 wall（含累加） | `14.390s` |
| finalize（逐目录排序） | `62.3ms` |
| 仅扫描结果的 `HeapAlloc` | `72.4 MiB` |
| `+` 朴素 `map[int64]*dirProjection`（`Name string`） | `+295.1 MiB` |
| `+` compact arena | `+62.0 MiB` |

- **可见终态 ≈ `14.45s`**，低于原版中位数 `16s`，也低于 stretch `15s`；构建耗时不构成风险。
- **朴素表示超预算 3 倍，compact arena 在预算内。** `74 MiB` 的估算对朴素表示错了 4 倍，原因是每对象
  开销（`422,577` 个 map 项与结构体分配、`1,159,430` 个 string header 与独立字符串）。表示方式因此
  必须写成约束。
- **累加器必须分片。** 原型第一版单 map 直接 `fatal error: concurrent map writes`：R-045 已把 emitter
  移到全局锁外，批次 emitter 由 8 个 native worker 并发调用（`native_darwin.go:936`）。
- **剩余风险**：扫描期的可增长 per-dir 结构造成瞬时峰值（原型 `295.1 MiB`）。

R-047 第 3.10 节随后实测了「逐批 compact」原型 v2，把该风险缩小但没有完全消除。native 每次 flush 的
批次是单父目录的（实测 `multi_parent_batches=0`，`batches=422,881` ≈ 非空目录 `422,743`），所以每收到
一批就能合并进 arena 并裁到 top-K，不需要保留可增长的 per-dir 结构。

| 项目 | v1 朴素 map-of-slices | v2 逐批 compact |
| --- | ---: | ---: |
| 稳态增量 | `+295.1 MiB` | **`+58.9 MiB`** |
| 扫描期峰值贡献 | — | **`+117.1 MiB`** |
| finalize | `62.3ms` | `3.8ms`（加 clip `97.0ms`） |

- 稳态 `63.6 MiB` 在第 2.1 条 `<=160 MiB` 预算内；正确性自检 `sum(Total) = nodes-1` 精确通过。
- 峰值贡献在默认 `GOGC=100` 下为 `+103`–`127 MiB`，在第 2.1 条 `<=160 MiB` 预算内。第 3.11 节已证明
  这是 GC 锯齿余量而非结构性瞬时占用：chunked arena 峰值反而更高，该假设被推翻。
- 时间成本已用稳定指标量化：**`+0.29s` user CPU（`+9.4%`）**，`sys` CPU 无变化（投影不产生系统调用），
  对 `16s` 门槛可忽略。
- 两个实现陷阱已实测定量：名称必须**排序裁剪后**才复制进 arena（否则被裁子项的名称成为垃圾，名称字节
  从 `19,179,851` 涨到 `62,028,760`）；分片 map 的预分配容量必须按实测定（`64` 个各 `1<<13` 槽位的空
  map 就占 `26.7 MiB`，降到 `1<<10` 只占 `3.3 MiB`）。
- **wall 时间在本机实时 `/` 上不可测**：控制组与投影组的分布完全重叠；六对交替中五对显示投影组「更快」，
  而增加工作量不可能加快扫描，说明噪声不是慢漂移、配对抵消无效。测量时 `WindowServer` 占 `33%`、
  终端 `11%`、浏览器 `10%`。改用 `user` CPU 后信号立刻稳定（三对全部一致）。
- 测量纪律：`50ms` 采样在大堆下把扫描 wall 从 `14.410s` 抬到 `22.869s`，**峰值与 wall 必须分两次运行
  测量**。

但 [ADR-0027](0027-DaisyDisk扫描中窗口状态边界.md) 把前台切页绑定在任务终态且最终 Map 成功之上，
而终态当前隐含要求 `store.FinishSnapshot(...)` 已完成、reader 索引可用。用户因此要为已经在内存中的
结构额外等待约 `6.3s`。

## 方案

### 方案 A：可见终态由内存目录树投影应答，durable 发布转后台（采用）

扫描结束即进入用户可见可查询终态，空间图由内存投影应答；`store.FinishSnapshot(...)` 在后台完成，
就绪后 `SnapshotStore` 恢复为唯一查询权威。投影为全盘目录聚合树加每目录 top-K 子项，`K` 分层取值。

- 优点：可见终态约等于扫描结束加投影排序，即 `15s` 量级，对原版中位数 `16s` 持平或略快；`93.31%` 的
  目录在可见终态即可无等待下钻；全盘目录树是已付成本；不改变快照格式、checksum、manifest 原子发布和
  恢复语义；复用已有的 `MapQuery` / `MapResult` 和 `Remaining` 语义，不扩展契约。
- 必要性：中位数 `16s` 下，仅实施 R-046（其自身目标 `<=20.50s`）仍慢 `4.5s`。方案 A 因此是追平的
  必要条件，不是可选加分项。余量很薄——`15s` 量级对 `16s` 只有约 `1s`。
- 代价：查询权威在一次生命周期内切换一次，必须保证切换前后同一层结果逐字段一致；top-K 新增
  `62.0 MiB` 常驻内存（compact arena，已实测）。
- 首要剩余风险：扫描期的可增长 per-dir 结构造成瞬时峰值（原型 `295.1 MiB`）。这是目前唯一可能让方案 A
  失败的因素，缓解方向已定但未实测。

### 方案 B：全量事实常驻内存，取消二进制快照（拒绝）

`285` 万节点的完整对象、路径、子项和索引会把 RSS 推到远高于当前峰值，并失去取消后的部分结果、重启
恢复和快照缓存复用，同时仍要为分页、Map 和子项排序重建内存索引。与 ADR-0028/0030 的内存边界冲突。
与方案 A 的区别是量级：方案 A 复用的是**目录级**聚合，比全量节点小一到两个数量级。

### 方案 C：只在内存保留根与首层，或只保留深度 `<= D` 的 top-N（拒绝）

前者被实机观察否掉：原版终态可下钻五层，首层投影不构成追平，只是把等待挪到首次下钻，用加载态掩盖成本。
后者被深度分布否掉：深度 `<=4` 只覆盖 `0.9%` 的目录，深度 `<=5` 只覆盖 `2.6%`。收口必须按目录做，
不能按深度做。

### 方案 D：扫描期间提前切换到结果页（拒绝）

违反 ADR-0027 第 1 条，也与 R-014/R-025 复核的原版行为不一致。方案 A 保持窗口只在扫描结束后切换一次。

### 方案 E：继续在 `FinishSnapshot` 内部优化以达标（拒绝作为达标路径）

九轮证据表明该路径 wall time 收益不可预测。R-046 的正确性和 CPU 收益保留并继续实施，但不再作为门槛
达成路径——按其自身目标 `<=20.50s`，相对原版中位数 `16s` 仍慢 `4.5s`。

### 方案 F：扫描期按 `parent_id` 分桶增量构建索引（本轮不采用）

`node_id` 由 native 层单调分配（`marmot_native_reserve_ids`），`parent_id` 在 emit 时已知
（`marmot_native_flush_batch`），child/directory section 原则上可在扫描期间分桶追加，`FinishSnapshot`
退化为封口、checksum 和 manifest 发布。它改动 durable 发布路径和临时索引布局，风险显著高于方案 A，
且缩短的是后台窗口而非可见终态。留作 R-048 独立预研。

## 决策

### 1. 分离「用户可见可查询终态」与「durable 快照发布完成」

两者成为 `ScanJob` 上两个独立的状态事实，均在领域层建模，不得只存在于 Presentation。不变量：durable
未发布完成时，不得宣称快照可复用、可恢复或已发布；`SnapshotVersion`、缓存准入和重启恢复仍只承认已原子
发布的 manifest。

### 2. 内存投影的内容、应答范围与权威切换

- **投影内容**：
  - 全盘目录聚合树（任意深度）——复用扫描结束时已在内存的 `directories` / `dirSizes`，不新建副本；
  - 每个目录的 top-K 子项（含文件条目），按 `owned_allocated DESC, node_id` 排序，`K` 分层取值：
    深度 `<=4` 用 `K=256`（与 `MapQuery` entries 上限一致），其余深度用 `K=8`；
  - 超出 top-K 的部分折叠进已有的 `MapResult.Remaining` 与 `ProjectionTruncated` 语义，不新增契约字段。
- **表示方式是约束，不是实现者的选择**：top-K 必须使用 compact arena——扁平条目切片、名称字节 arena、
  `parent -> (offset, count, total)` span 索引。朴素的 `map[int64][]childEntry` 明确拒绝
  （实测 `+295.1 MiB`，超预算 3 倍）。
- **累加器必须按 `parent_id` 分片**：批次 emitter 由 native worker 并发调用，单 map 会
  `concurrent map writes`，单锁会把 ADR-0045 消除的争用加回来。一个目录的全部子项落在同一分片，
  不需要跨分片合并。
- **累加必须逐批 compact**：native flush 是单父目录批次，收到即合并进 arena 并裁到 top-K；不得保留
  可增长的 per-dir 结构（实测差 5 倍：`+58.9 MiB` 对 `+295.1 MiB`）。
- **名称只在排序裁剪之后复制进 arena**；被裁掉的子项不得留下名称字节。
- **峰值必须在明确的 GC 设置下测量并记录**（默认即 `GOGC=100`）。R-047 第 3.11 节实测：峰值随 GC 锯齿
  余量与活跃堆等比放大，与 arena 表示无关——固定块链式（chunked）arena 的峰值（约 `+127 MiB`）反而略高于
  `append`（约 `+103 MiB`），该假设已被推翻。默认设置下的峰值已在第 2.1 条预算内，无需调整 GC 参数。
- **分片 map 与分片 arena 的容量按实测定**：`64` 个各 `1<<13` 槽位的空 map 占 `26.7 MiB`；分片块大小会被
  分片数放大 `64` 倍（`1 MiB` 名称块造成 `64 MiB` 地板）。
- **每分片的排序 scratch 必须释放或设上限**：一个批次可携带 `8192` 个子项，`64` 个未释放的 scratch 占
  数十 MiB。
- **扫描期瞬时峰值与稳态同受内存预算约束**：不得以「稳态达标」为由接受扫描期的高峰值。
- **应答范围**：目录级信息在任意深度无等待可用；top-K 覆盖范围内的下钻（含文件条目）无等待；需要
  top-K 之外的子项或分页超出 top-K 时等待 durable 就绪并显示加载态。不得返回空结果、截断结果或与
  durable 不一致的结果。
- **权威切换**：任务进入 `completed` / `completed_with_issues` / `cancelled` 即为用户可见可查询终态，
  Presentation 按 ADR-0027 触发一次首屏 Map；durable 就绪后 `SnapshotStore` 恢复为唯一查询权威，
  投影释放。当前在 `FinishSnapshot` 之前串行执行的 `UpdateDirectorySizes` 和 `InsertIssues` 一并移入
  后台，它们属于 durable 侧工作。
- 投影容量必须设硬上限；超过预算时按 `owned_allocated` 降序裁剪并置 `ProjectionTruncated`，
  不得无界增长。

### 2.1 新增显式终态内存预算（以实测原版峰值为标尺）

[ADR-0030](0030-应用持久化队列上限与终态内存.md) 没有给出数值内存上限，它约束的是事件队列容量
（`scanPersistQueueCapacity = 2`）与背压语义；这些保持不变。但常驻投影需要一个此前不存在的显式预算。

> **实测修正（2026-08-25）**：本条最初以原版观察到的 `700M+` 作为总峰值上限，但那是「用别人的标尺量
> 自己」。同 harness 的 A/B 实测显示，Marmot 在引入投影**之前**的控制臂最大 RSS 中位数就是
> `~1013 MiB`，投影臂反而更低（`~893 MiB`）。因此总峰值上限改为以自身同口径基线表述：
> **不得高于控制臂基线（当前 `~1013 MiB`）**，投影新增部分实测为负值（不增加峰值）。
> 原 `700 MiB` 上限作废；`<=160 MiB` 的投影增量上限继续有效但已无约束力。
> 下面保留原始推导作为记录。

**标尺由实测原版给出，不再凭空设定。** 本机观察原版扫描期内存从 `300M+` 一路升到 `700M+`，且扫描完成后
维持在该量级（全盘结构常驻内存）。对照 Marmot 的最大 RSS：

| 配置 | 扫描期最大 RSS | 终态之后 |
| --- | ---: | --- |
| 原版（活动监视器口径） | `700M+` | 维持 `700M+` |
| Marmot 当前（无投影） | `383`–`402 MiB` | — |
| Marmot `+` 投影（默认 `GOGC=100`） | `499`–`523 MiB` | durable 就绪后释放投影 |

即带投影的 Marmot 峰值仍比原版低约 `200 MB`，且终态后会释放投影而原版不会。因此预算定为：

- **总峰值 RSS 上限 `<=700 MiB`**（不超过实测原版量级）；
- **投影新增部分（top-K 子项）上限 `<=160 MiB`**：R-047 实测稳态 `63.6 MiB`，默认 `GOGC=100` 下峰值贡献
  `+103`–`127 MiB`，均在此预算内；
- 该预算同时约束扫描期瞬时峰值与稳态；
- **不要求 `GOGC=50`**。它能把峰值贡献压到 `+91.2 MiB`，但在 `700 MiB` 的标尺下没有必要，而其自身的
  CPU 代价未量化；若将来需要收紧内存再单独评估。
- 历史 RSS 记录互不一致（ADR-0030 三次约 `584 MiB`、R-045 单次约 `420 MiB`），不可沿用为基线；
  内存类指标在本机可稳定复现，按第 4 条口径重测即可。

### 3. 用实测基线取代无出处的 `15s` 门槛

- 对标基线以同机同卷实测为准：原版「开始 → 扫描完成进入结果页」三次为 `18s` / `16s` / `15s`，
  中位数 `16s`。
- 产品门槛改为：**用户可见终态固定样本三次中位数 `<=16s`**（追平原版中位数）；`<=15s` 为 stretch
  目标（原版最好一次），不作为达成/未达成的判定线。
- 测量必须与原版同样的冷热次序纪律：连续三次、不清缓存、记录每次而非只记中位数。
- 门槛不只是时间：**首屏五环图必须在可见终态零等待，且投影完整覆盖 `>=90%` 目录的全部子项**。
  只满足时间不满足覆盖率不算达成。
- R-020 / R-024 lineage 中的 `<15s` 推定失效，不得再作为后续 ADR 或预研的依据。
- 原版基线已由三次实测确立；它混入 cache 预热且原版节点口径未知，是当前最好的可用基线，但不是无偏基线。

### 4. 冻结性能测量口径

- **固定只读样本在本机不可行**（R-047 第 3.11 节）：APFS 本地快照可以创建，但 Data 卷 `95%` 占用下
  `deleted(8)` 会在一轮测量结束前把它回收；同样的空间约束也排除了复制一份只读语料。因此本条改为：
  - **相对成本判定使用 `user` / `sys` CPU 时间，不使用 wall**。实测 `user` CPU 三次配对完全一致，
    而 wall 在 `14`–`25s` 间随机跳、配对交替无法抵消（六对中五对方向与物理事实相反）；
  - **绝对 wall 门槛（`<=16s`）必须在静默环境下测量**：测量期间不得有显著的 CPU / I/O 竞争进程，
    并记录竞争情况；无法满足时只能记录为「未验证」，不得用噪声数据宣称达成或未达成；
- 真实 `/` 继续测量，但只作为量级参考和正确性 smoke；内存类指标在本机可稳定复现（`72.4 MiB` 基线每次
  精确一致），wall 类指标不可；
- 每次记录必须同时包含：纯扫描、用户可见终态、投影目录覆盖率、投影外首次下钻可用、durable 发布
  完成、`FinishSnapshot`、节点数、问题数、首屏查询、checksum、恢复和最大 RSS；
- 判定一律使用同口径串行三次中位数，单次 smoke 不构成达标证据。

### 5. 不变边界

本 ADR 不改变 `formatVersion`、快照 section 布局、数据帧与 index checksum、manifest 同步与原子 rename、
尾部恢复语义、`SnapshotStore` 公开方法返回契约、`MapQuery` / `MapResult` 契约、scanner worker 预算、
`scanPersistQueueCapacity = 2` 的背压语义、`scanBatchSize` 提交阈值、APFS 共享块归属、硬链接计数与
空间语义，以及清理授权边界。

durable 发布失败必须传播为任务级失败并对用户可见，不得因为可见终态已展示而被静默吞掉。durable 完成前
崩溃的语义不变：无可复用快照。

该决策更新 [ADR-0027](0027-DaisyDisk扫描中窗口状态边界.md) 中「终态」隐含要求 durable 快照发布完成这一
前提；ADR-0027 的「扫描中保持源页」「终态只触发一次最终首屏查询」「失败不用空 Map 伪装成功」全部保留。
[ADR-0013](0013-DaisyDisk空间图与渐进查询数据契约.md) 与 [ADR-0017](0017-有界多层空间图投影.md) 不变，
本决策复用其语义而非扩展。

## 后果

正面后果：

- 用户可见终态预期进入 `15s` 量级，对原版中位数 `16s` 持平或略快，且 `93.31%` 的目录在该时刻即可
  无等待下钻；不牺牲快照耐久性、取消部分结果或重启恢复；
- 结束九轮在 `FinishSnapshot` 内部追虚构门槛的优化循环，把该路径回归为纯正确性与 CPU 改善；
- 性能判定第一次建立在实测基线和固定样本之上，后续 ADR 不再在噪声上做 `3%` 级决策。

代价和风险：

- 查询权威在一次生命周期内切换，需要额外的一致性测试面；
- 全盘目录树在 durable 窗口内延长持有，叠加 top-K 的 `63.6 MiB` 稳态；扫描期最大 RSS 从 `383`–`402 MiB`
  升到 `499`–`523 MiB`，仍低于实测原版的 `700M+`，且终态后释放；
- 本机不具备可验证 wall 门槛的测量环境（实时 `/` 扫描 wall 在 `14`–`25s` 间跳，冻结样本不可行）。
  这不是方案缺陷，但它意味着 `16s` 门槛在静默环境就绪前只能记为「未验证」；
- top-K 之外的子项和分页在 durable 就绪前会等待（约 `6.7%` 的目录）；
- 领域状态新增一个事实，`ScanJob` 状态机和 Wails DTO 可能需要 durable 就绪标志；
- 实测差距为 `5.25s` / `33%`，且方案 A 的时间余量只有约 `1s`。若一致性或 RSS 代价超出验收门禁，
  可以回退到仅实施 R-046，但必须如实记录为「未追平原版」——不能再像基于单次 `18s` 时那样写成「与原版
  持平」。

## 验收门禁

1. scanner、binary snapshot、application 的窄测试、race、全仓 Go 测试和 `go vet` 通过；
2. 一致性：同一层的投影 Map 与 durable Map 逐字段一致，覆盖 `owned_allocated DESC, node_id` 排序、
   分页、`Remaining`、`ProjectionTruncated`、空目录、部分结果和问题状态；
3. 边界：top-K 外下钻与分页的等待态、durable 就绪后的权威切换、扫描中不切页（ADR-0027）、取消、
   durable 失败传播、崩溃恢复全部回归通过；
4. 性能（固定样本同口径串行三次中位数）：
   - 用户可见终态 `<=16s`，stretch `<=15s`；
   - 首屏五环图在可见终态零等待，且投影完整覆盖 `>=90%` 目录的全部子项——不满足则不算达成；
   - 开始 → top-K 外首次下钻可用 `<=21.254s`（当前完整终态），即任何路径都不得变慢；
   - durable 发布完成相对 R-046 实施后同口径不回退超过 `3%`；
   - 内存按第 2.1 条判定：投影新增 `<=160 MiB`，总峰值 RSS `<=700 MiB`（实测原版量级）；
   - 纯扫描不回退超过 `3%`；
5. 原版基线补足两次同条件复测并记录中位数；
6. 未达到以上目标时只能记录为「正确性通过、性能目标未达成」；回退到仅实施 R-046 时必须同时记录
   「未追平原版中位数 `16s`」。

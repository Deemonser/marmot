# ADR-0063：直接删除，与不可恢复守卫的硬边界

- 状态：**Accepted**（2026-08-31 使用方要求：「我需要删除是能直接删除释放空间的，
  而不是移动到废纸篓」）
- 日期：2026-08-31
- 相关预研：无新增预研。依据是本机实测（见背景）。
- 关系：**取代 [ADR-0009](0009-清理计划与macOS废纸篓执行.md) 的"第一阶段不永久删除"**。
  ADR-0009 的其余部分（计划生命周期、逐条校验、执行后必须重新扫描、不承诺原子回滚）
  全部保留，本 ADR 只增加一种执行方式。
  **不修改** [ADR-0061](0061-AI清理建议边界与证据装配.md) §1：AI 仍然只产出建议，
  绝不产出授权，更不能选择删除方式。

## 背景

AGENTS.md 写的是"**默认**移入废纸篓，不做永久删除"，ADR-0009 写的是
"**第一阶段**不永久删除、不安全擦除"。两处都是默认与阶段，不是绝对禁止。

促成本决策的是一次真实执行。使用方删除了约 33 GB（Gradle 转换产物、Gradle 构建缓存、
Go 构建缓存、VS Code 更新包残留），执行成功，然后**磁盘可用空间没有变化**：
数据卷 228 GB 里可用 1.3 GB，删除前后一样。

原因不是 bug：**废纸篓在同一个卷上，移进去只是改名，字节一个都没释放。**
一个以回收空间为目的的工具，无法回收任何空间——这不是保守，是没做完。

## 决策

### 1. 直接删除是一种**逐次显式选择**的执行方式，不是偏好

- `CleanupPlanRequest.Permanent` 随每一次计划传递，**不落盘、不记忆**。
  一个不可逆的动作应当在每次发生时被选择，而不是打开一次之后被忘掉。
- 界面上是收集区里的一个复选框，不是第二个按钮：**并排放两个破坏性按钮，
  就是按错那个的标准做法**。勾选后删除按钮改文案为"直接删除"并换成更重的配色。
- 执行后立即复位。
- 计划回传 `Permanent`，确认与结果都必须说清楚发生的是哪一种——
  这两件事只有一件可以撤销。

### 2. 不可恢复守卫在这条路径上从建议变成拒绝

`recommendation.IrreplaceableReason` 此前的作用是**更正模型的错误主张**
（ADR-0061 §7）：因为走的是废纸篓，判错了也只是一次还原。直接删除没有这个退路，
所以同一层守卫在这条路径上是**硬拒绝**：

> **凡是删了无法重建的东西，一律不能直接删除，只能移入废纸篓。**

拒绝发生在建立计划时，理由原文告知用户。`cleanup.DeleteBlock` 的既有拒绝
两条路径都照旧适用。

这条边界是本决策能够成立的前提。没有它，"直接删除"只是把工具的最坏情况
从"可还原"变成"没了"。

### 3. 守卫的覆盖范围必须先补上（同批修复）

实现时发现：`IrreplaceableReason` 里 `**/` 开头的模式——`**/.git`、`**/.ssh`、
`**/.gnupg`、`**/Local Storage`、`**/IndexedDB`、`**/LocalHistory` 等——
**只在路径成功解析为某个家目录的相对路径之后才被检查**。于是：

| 路径 | 此前 |
| :-- | :-- |
| `/Volumes/Work/app/.git` | **不受保护** |
| `/opt/service/.git` | **不受保护** |
| `/Users/Shared/team/project/.git` | **不受保护**（`Shared` 不算账户） |

**一条"任意深度、任意位置"的模式，如果只在一个家目录里生效，就不是它看起来的那个守卫。**
扫描根是整盘，这个洞一直在；直接删除只是让它从"建议可能不准"变成"东西真的没了"。

已拆为 `anywhereIrreplaceable`（对完整路径匹配，先于家目录判断）与
`homeRelativeIrreplaceable`（`Documents`、`Library/Mail` 等确实与家目录绑定的）。
`tmp_pack_*` / `tmp_idx_*` 的豁免在任何位置同样适用。

### 4. 执行仍然是逐条的，语义不变

`ExecuteCleanupPlan` 对每一项分别校验、分别执行、分别记录结果。直接删除只替换
"移动"这一步（`os.RemoveAll`），**逐条校验一字未改**——
`matchesSnapshotNode` 与 `validateCleanupItem` 保持原样。

平台层的 `RemovePermanently` 不做任何"什么能删"的判断，只拒绝空路径与 `/`。
该判断属于应用层策略，不属于适配器。

### 5. 门禁

| # | 门禁 | 判定方式 |
| :-- | :-- | :-- |
| 1 | `go test` / `-race` / `vet` / `tsc` / `vite build` / `npm test` / `wails3 package` | 现有门禁 |
| 2 | 直接删除的计划走 `RemovePermanently`，**完全不碰废纸篓** | 单测 |
| 3 | 不可恢复路径的直接删除被拒，且**同一路径仍可移入废纸篓** | 单测 |
| 4 | `Permanent` 不在两次计划之间继承 | 单测 |
| 5 | `**/` 模式在 `/Volumes`、`/opt`、`/Users/Shared` 下同样命中 | 单测 |
| 6 | 结果文案区分"已直接删除"与"已移入废纸篓" | 单测 + 人工复核 |

## 后果

**得到**：工具能真正释放空间；不可恢复守卫的覆盖范围从一个家目录扩大到整盘
（这一条独立于本功能，本身就是修 bug）。

**付出**：产品最坏情况从"可还原"变为"在守卫允许的范围内不可还原"。
这是使用方在知情下的选择，边界由 §2 承担。

**风险**：

- **守卫的正确性从"影响建议质量"升级为"影响数据存亡"。** 守卫漏掉的任何一类，
  以前的代价是一次还原，现在是永久丢失。§3 已经暴露过一个这样的洞。
- 逐条校验只保证"和扫描时是同一个对象"，**不保证对象里没有你在意的东西**——
  规则判断错了，直接删除就没有退路。
- 本决策**不做**安全擦除，删除后的数据仍可能被取证工具恢复；ADR-0009 的这条不变。

## 后续工作

1. 守卫覆盖范围的复核：§3 的洞是实现时偶然发现的，说明缺少一个"守卫在扫描根的各类
   位置下是否都生效"的系统性检查。应补一份按位置分类的用例表。
2. 直接删除的失败半路中断时，已删除的部分无法回滚（ADR-0009 本就不承诺原子性），
   但逐条结果必须让用户看清删到哪一条——已实现，需人工复核一次真实中断。

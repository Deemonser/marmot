# ADR-0064：删除后就地更新快照

- 状态：**Accepted**（2026-08-31 使用方指出：「如果不做实时更新，那么删除后自动重扫需要
  花费大量时间，这个体验就非常糟糕了。那为什么不只更新删除的那部分呢，这应该是一瞬间的
  事情吧」）
- 日期：2026-08-31
- 相关预研：无。依据是本机实测（全盘 `1,823,061` 节点重扫 `9.5s`）。
- 关系：**取代 [ADR-0009](0009-清理计划与macOS废纸篓执行.md) 的"清理执行结果不能回写为
  扫描事实，执行后需要提示用户刷新或重新扫描"**。ADR-0009 其余部分不变。
  依赖 [ADR-0055](adr/0055-取消快照持久化与内存唯一事实源.md) 的内存唯一事实源，
  以及 [ADR-0063](0063-直接删除与不可恢复守卫的硬边界.md) 的直接删除。
  不修改 [ADR-0056](0056-内存事实源的结构与发布峰值.md) 的内存布局与分配契约。

## 背景

ADR-0063 让清理变成真删除。删除后视图必须与磁盘对上，此前的做法是**自动全盘重扫**，
本机实测 **9.5 秒**。使用方指出这个体验不可接受，并直接给出了正确的问题：
**为什么不只更新删掉的那一部分？**

### 为什么 ADR-0009 当初禁止回写，以及它的前提已经不在了

ADR-0009 写的是"清理执行结果不能回写为扫描事实"。这条在当时是对的，理由和废纸篓绑在一起：
**移进废纸篓时字节仍在同一个卷上**。从快照里减掉它们，会得到一张声称磁盘变空了、
而磁盘并没有变空的图——那是谎报。

ADR-0063 之后删除是真的删除。**同一个减法从"谎报"变成了"准确陈述"。**
禁令的前提消失了,结论必须重算——这是我上一轮直接引用 ADR-0009 拒绝时犯的错:
**引用了结论，没有复核它的前提。**

## 决策

### 1. 每一条成功删除的路径，从内存树上就地摘除

`Store.RemoveSubtree(snapshotID, path)`：

1. 从父节点的子索引里摘掉该节点（子组是连续且按体积降序的，左移补洞即保持顺序）；
2. **同时把该记录的 `parentID` 置 0**；
3. 沿祖先链把 `ownedAllocated` / `logicalSize` 扣减掉；
4. 走一遍被摘子树，得到节点/文件/目录数，修正树的计数器；
5. `version++`，前端据此重绘。

代价是 `O(深度 + 父的子节点数 + 被删子树的节点数)`，最后一项只是计数遍历。
对照全盘重扫的 `O(整块磁盘)`。

**第 2 步不是冗余。** `group()` 只从 `parentID` 重建子索引，只改索引的话，
下一次任何操作让 `grouped` 失效，被删的子树就会**复活**——几个月后再出现，看起来像内存损坏。
两处都改，并有一条专门的回归测试重建索引后确认它没回来。

被摘节点的后代仍指向它，**刻意不动**：从根出发已经到不了它们，
为了证明这一点去改写几十万个父指针是为改而改。

路径解析（`nodeIDByPath`）本身就是从根走子索引的，所以摘除后该路径自然无法解析——
这同时意味着它不会被再次放进收集区。

### 2. 树的数字来自算术，卷的数字来自 statfs

两者刻意分开：

| | 来源 | 精度 |
| :-- | :-- | :-- |
| 各级目录 roll-up | 对扫描测得的值做减法 | **和当次扫描一样准** |
| 卷 总量/已用/可用 | 删除后重新 `statfs` | **精确** |

所以用户最关心的那个数字（实际可用空间）是操作系统给的，不是我们算的。

**已知的不精确**：扫描与删除之间，若子树深处有文件变化，顶层目录的 mtime 不会变
（`validateCleanupItem` 因此也不会拦），减掉的值可能与实际释放量略有差异。
差额限于那段时间内的变化量，且用户随时可以重新扫描。**这是取舍，不是 bug**，写在这里。

### 3. 能力可选，缺失时诚实降级

`subtreeRemovingStore` 是可选存储能力（与既有的 `snapshotIssueStore` /
`snapshotVolumeStore` 同一约定）。做不到就地更新时返回 `Removed == 0`，
前端**回退到重新扫描**——宁可慢，不可显示一张错的图。
单条路径摘除失败只记日志、不中断：**删除已经发生了，落后的只是视图。**

### 4. 实时更新（FSEvents）仍然不做

理由与本决策一致而非相反：空间图的价值来自它是**某一时刻的一致快照**——
residue 分区、证据下限、项目活跃度分级全部建立在"同一时刻"之上。全盘监听在一台正常使用
的机器上是不间断的事件流，图会永远在抖，读不出结论。

**就地更新与实时更新是两件事**：前者是把一次由本工具发起、结果已经确知的变化反映进去；
后者是追踪任意外部变化。前者不损害快照的一致性，后者会。

### 5. 门禁

| # | 门禁 | 判定方式 |
| :-- | :-- | :-- |
| 1 | `go test` / `-race` / `vet` / `tsc` / `vite build` / `npm test` / `wails3 package` | 现有门禁 |
| 2 | 摘除后祖先各级 roll-up 精确减少，兄弟不受扰动 | 单测 |
| 3 | 摘除后路径及其后代都无法解析 | 单测 |
| 4 | **重建子索引后被删子树不复活** | 单测 |
| 5 | 拒绝摘除扫描根 | 单测 |
| 6 | `version` 变化 | 单测 |
| 7 | 存储不支持时回退重扫，且不显示错图 | `Removed == 0` 分支 |

## 后果

**得到**：删除后视图瞬间接上，不再有 9.5 秒空等；ADR-0009 那条禁令的前提被显式复核。

**付出**：内存树多了一个可变操作（此前只在扫描期写入，完成后只读），
`removeSubtree` 必须与 `group()` 的重建语义保持一致——这是新的耦合点，
门禁 4 就是为它设的。

**风险**：

- **树从"完成后只读"变成"可就地修改"。** ADR-0056 的布局假设是扫描期写、完成后读；
  本决策打破了后半句。目前只有一个修改入口，且有回归测试，但这类耦合会随时间腐化。
- §2 的不精确差额没有量化过，只论证了它有界。
- 就地更新会让快照与磁盘的实际状态**在其他方面**继续漂移（其他进程的写入），
  而现在少了一次"反正要重扫"的兜底。用户可随时手动重扫。

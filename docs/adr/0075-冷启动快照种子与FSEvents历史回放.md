## 背景

每次启动都要冷扫 17–20 秒（R-077：17.3 s 纯扫描；R-078：经 application 19.6 s），即使磁盘和上次相比只变了几百个目录。
OpenDisk（MIT，与 Marmot 同形）的做法是：扫描前记下 `FSEventsGetCurrentEventId()`，与树一起落盘；下次用它作
`FSEventStreamCreate` 的 `sinceWhen`，回放 macOS 按卷持久化、跨重启保留的目录级事件日志，只重读变过的目录。

R-078 在本机量了这条路的每一段：

| 项 | 数值 |
| --- | --- |
| 树落盘（记录页 + 名字 arena 原样） | 227.5 MiB，写含 `fsync` 0.30 s |
| 读回 + 重建分组 | **0.25 – 0.30 s**，抽样 2,786 节点 0 处不一致 |
| 回放：闲置 1 h / 6 h | 0.6 s（~850 个目录）/ 1.5 s（~1,600 个目录） |
| 回放：闲置 24 h | 7 – 11 s（~8,150 个目录） |
| 回放：闲置 7 天 | 178 s，`UserDropped`，且回放中途停止——**不可用** |
| latency 参数（0 / 1 ms / 50 ms） | 对回放耗时无影响；速度由 fseventsd 决定，约 0.2 – 0.3 ms / 事件 |
| 新鲜度 | 回放前刚写的标记目录被回放到；回放确实覆盖到"现在" |

所以收益是真的，但比借来的数字窄：**闲置半天内约 1 – 2.5 秒热启动；隔天只快一倍；隔一周必须全扫。**

必须正视的一件事：ADR-0055 是产品决策，理由是"产品是磁盘清理工具，应用自己长期占着接近 1 GB 是自身价值的反面"。
种子是 227 MiB——比当年的 843 MB 小，但不是零。本 ADR 不假装这个矛盾不存在，把它写进方案让决策者选。

## 预研依据

- R-078 §4.1–4.3：按闲置时长的回放事件量、耗时、可靠性标志；latency 无关；新鲜度自检。
- R-078 §4.5：落盘体积、写入与加载耗时、一致性。`record` 实为 64 B（`table.go` 注释写 56 B，待改）。
- R-078 §4.3：回放到的最后 ID 落后于当前 ID 是正常的——ID 按原始事件分配，目录级事件约每 80 – 200 个 ID 一个；
  本机约每 130 个 ID 一个目录事件，所以 **ID 跨度在回放前就能给出预计回放时间**。
- R-078 §4.4：变化集中在 `~/Library`、`/private/var`、构建产物目录，几乎不在用户自己的文件夹——与 R-074 一致。
- R-074 / ADR-0072：拼接一批目录的成本（浅刷新 1 – 2.5 µs/条，`group()` 约 70 ms）；事件路径与树路径同形。
- R-078 §6：**拼接成本未实测**（8,150 个目录的浅重读没量），是实施切片的第一个数。
- 构件已就位：`internal/platform/fileevents_history_darwin.{c,go}`（自指定 ID 回放、`HistoryDone`、丢失标志、
  当前 ID、时刻前最后 ID、日志 UUID）；ADR-0072 的拼接路径；`memtree` 的页式布局。

## 方案

### 方案 A：种子 + ID 跨度预判 + 回放拼接（采用）

**种子**：扫描以 `completed` / `completed_with_issues` 结束后，异步把树写到应用缓存目录下**一个固定文件名**
（每个扫描根一份，文件名取根路径的稳定散列），临时文件写完 `fsync` 再 `rename` 替换。头部：格式版本、
扫描**开始前**取的 eventID、根路径、设备号、FSEvents 日志 UUID、根节点 ID、四个编码表、卷数字、issue 列表；
正文：记录页、名字 arena 页原样。子节点分组数组不落盘（`group()` 0.2 s 重建）。

**启动**：源页选中一个根时，若存在种子且头部四项（根、设备、UUID、格式版本）全部匹配：

1. 算 `span = FSEventsGetCurrentEventId() − 种子.eventID`。`span > 跨度上限` → 不回放，删种子，全扫。
2. 否则并行做两件事：读种子（0.3 s）；从 `种子.eventID` 回放到 `HistoryDone`，硬超时。
3. 回放出现 `EventIdsWrapped / UserDropped / KernelDropped / RootChanged` 任一、或超时、或变更目录数超上限
   → 丢弃已读的种子，全扫。
4. 全部通过 → 种子升级为内存树；回放得到的目录清单作为**一批**交给 ADR-0072 §3 的拼接路径
   （按路径长度父先于子；`MustScanSubDirs` 走深读；找不到的路径跳过）；一次 `group()`、一次 `statfs`；
   进入结果页；随后照 ADR-0072 §1 开实时监听。
5. 升级为内存树的那一刻起，种子文件在逻辑上作废——下一次扫描终态会覆盖它。

**跨度上限**：定义为"预计回放耗时不超过全扫的三分之一"。本机换算约 3 – 4 M 个 ID（≈ 15 – 20 小时）。
比例是本机的，所以上限取保守值并**在运行时自校准**：每次回放实际测得的（事件数 / ID 跨度）与（耗时 / 事件数）
写回种子头部，下次用实测值算预计。硬超时（默认 6 s）兜底。

**淘汰**：只保留最近一次扫描的根对应的种子；切换根时旧种子删除。上限一份、最大 512 MiB；超过即不写。
应用启动时清理缓存目录里本 ADR 命名规则之外的种子残留（`.tmp`）。

优点：闲置半天内 1 – 2.5 s 出结果；放弃判断在回放前、免费；所有构件都已存在或已量过。
代价：磁盘 227 MiB（一份）；扫描终态后多 0.3 s 后台写；启动路径多一个分支；一个新的失效来源（种子坏了 → 全扫，不是错误）。
风险：拼接成本未量；ID 跨度与事件数的比例因机器而异（自校准缓解）；日志 UUID 在卷组内两卷相同的原因未查。

### 方案 B：压缩种子

记录页与 arena 用 LZ4/zstd 压缩后落盘。名字压缩率高，记录页里大量零字段也可压。
优点：磁盘占用可能降到 60 – 100 MiB。代价：加载多一次解压（预计 0.1 – 0.3 s，未量）；一个新依赖。
**未量**，作为方案 A 门禁不过时的加法，不单独采用。

### 方案 C：不做（维持 ADR-0055）

每次 17 – 20 s。R-078 的结论是收益只在闲置半天内明显——如果决策者认为"应用不留任何缓存"比"当天再开秒开"重要，
这是正当的选择，而且是 ADR-0055 已经做过一次的选择。

### 方案 D：回放但不落盘树（拒绝）

没有种子就没有可拼接的对象，回放无意义。

## 决策

**采用方案 A。** 使用方已接受"应用在缓存目录留一份 ≤ 512 MiB 的种子"（见状态栏）。

1. **种子不是事实源。** 它不可被查询、不出现在 UI、不参与清理计划的任何校验；只能整份升级为内存树或整份丢弃。
   内存树一旦建立，与冷扫得到的树在契约上**不可区分**——同一个 `SnapshotStore`、同一套查询、同一个实时监听。
2. **接受条件**（全部满足）：头部根、设备、UUID、格式版本匹配；ID 跨度低于上限；回放 `HistoryDone` 且无任何丢失标志；
   变更目录数低于上限；回放在硬超时内完成。任一不满足：删种子、全扫，不报错，只记日志。
3. **eventID 在扫描开始前取。** 扫描期间的变化因此会在下次回放里出现并被重读——多读一点，不漏。
4. **拼接复用 ADR-0072 §3**，不写第二套。回放清单转成与实时监听同形的一批事件。
5. **一份种子，固定文件名，`rename` 替换，`.tmp` 启动清理。** 不用模式匹配删除（ADR-0054 §3 的约束沿用）。
6. **UI 上不出现"上次结果"、"恢复"、"缓存"字样。** 用户看到的只是"这次扫得快"。进度条在种子路径上不显示扫描进度，
   显示"正在核对变化…"一类中性文案，因为它不是扫描。
7. **实施顺序**：先量拼接成本（8k 目录的一批），再写种子格式，再接启动分支。拼接成本若使 24 h 情形超过全扫的一半，
   把跨度上限收到 6 – 8 小时，不改方案。

### 门禁

| # | 门禁 | 通过标准 |
| --- | --- | --- |
| 1 | 闲置 ≤ 1 h 热启动到结果页 | 三次中位数 `<= 2.5 s`（含读种子、回放、拼接、`group()`） |
| 2 | 闲置 ≈ 24 h | 三次中位数不超过全扫中位数的 `70%`，否则收紧跨度上限 |
| 3 | 一致性 | 热启动后的树与同一时刻冷扫的树，根层总量差 `<= 0.1%`，随机 1,000 个目录的 `allocated` 一致 |
| 4 | 放弃路径 | 人为制造 `UserDropped`（7 天前的 ID）、改设备、改 UUID、超跨度：四种都走全扫且无错误对话框 |
| 5 | 磁盘 | 缓存目录里种子文件恰好一份，`<= 512 MiB`，切换根后旧的消失，`.tmp` 不残留 |
| 6 | 内存 | 热启动峰值 `phys_footprint` 不超过冷扫峰值（ADR-0058 门禁 3）；读种子不产生第二份树 |
| 7 | 不留暗示 | 冷启动源页与 ADR-0055 门禁 3 相同：没有"查看上次结果"，按钮仍是"扫描" |

## 后果

- 收益：当天第二次打开 1 – 2.5 s；隔天约 9 – 13 s（比 17 – 20 s 快但不再是"秒开"）；隔周不变。
  这个收益曲线要写进 README，不许写成"秒开"。
- 代价：磁盘一份 227 MiB 种子——这是对 ADR-0055 产品立场的**有限回退**，已由使用方认可（见状态栏）。
- 新约束：种子格式版本必须随 `record` 布局、编码表、目录尺寸语义的任何变化递增；忘记递增会让旧种子被接受——
  所以 `TestRecordStaysPacked` 之外再钉一条"格式版本与记录布局一致"的测试。
- 新的失效来源被设计为静默退回全扫。日志里必须能看出"为什么这次没走种子"（跨度 / 标志 / 头部 / 超时）。
- R-078 §4.3 的 ID 跨度 → 事件数比例进入运行时自校准，成为一个持久化的经验参数。

  §7 快照与查询：种子不是查询源；§12 体验：种子路径的中性进度文案。
- README "当前状态"：热启动的收益边界（半天内 1 – 2.5 s，隔天快一倍，隔周全扫）。
- ADR-0055 的实施状态栏补一行："跨会话存活的绝对形式已由 ADR-0075 收窄"。

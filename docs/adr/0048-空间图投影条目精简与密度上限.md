# ADR-0048：空间图投影条目精简与密度上限

- 状态：Accepted
- 实施状态：代码切片已完成并实测（2026-08-25）。**两条门禁均达标，密度目标 `2000` 弧达成**：
  真实 `/` depth 4 下 `2021` 弧载荷 `235.2 KB`（门槛 `<=256 KB`）、装配 p95 `66.2ms`（门槛 `<=150ms`）。
  R-049 第 3.5 节的路径重建假设**被证实**：`533` 弧 p95 从 `137.2ms` 降到 `36.6ms`，`2021` 弧从
  `346.9ms` 降到 `66.2ms`。

  实施中撞到两处本 ADR 未预见的问题，均已处理：
  1. **`maxPageSize` 有第二处守卫**。除 `normalizePageLimit` 外，`readChildIDs` 也按 `maxPageSize` 拒绝
     大页，预算过 `1000` 即报 `child page exceeds limit`。按第 3 条解耦，但**保留守卫本身**——只是把界
     从分页上限换成投影预算，防止索引损坏时申请巨额分配（新增 `readChildIDsBounded`）。
  2. **载荷首测为 `321 KB`，不是 R-049 预估的 `132.8 KB`**。R-049 的原型用单字母 JSON key，而真实 DTO
     用完整字段名，且每个叶子都携带 `childrenTotal:0` 与 `childrenHasMore:false`。两步修正：这两个字段
     加 `omitempty`（`321`→`282 KB`），键名改为 `id`/`name`/`kind`/`size`/`children`/`total`/`more`
     （`282`→`235 KB`）。未采用单字母键——更省但契约可读性代价过大，短而可读已足够过线。

  一处语义收紧：投影后代不携带路径，因此**深层弧不再可点击或可拖拽**（`role="presentation"`）。
  这本就是 ADR-0017 第 2 条的规定，此前实现越权。副作用是无法直接点深层弧下钻；将来若要支持，必须按
  节点 ID 回查完整节点，不得把路径塞回投影。
- 日期：2026-08-25
- 相关预研：[R-049](../research/R-049-空间图投影密度与载荷成本预研.md)

## 背景

结果页版式已按 [ADR-0018](0018-DaisyDisk视觉版式与窗口状态重做.md) 与原版对齐，但空间图的**扇区密度**
仍有明显差距：原版每个顶层楔形都长满细齿，Marmot 只在最大的楔形上有 3–4 环。

密度由 [ADR-0017](0017-有界多层空间图投影.md) 锁定：`projectionLimit` 默认 `384`、硬上限 `512`，且它是
**整个投影共享的总节点预算**（`map_assembly.go` 的 `projectChildrenFrom` 以 `*budget` 递减）。最大的楔形
先吃光配额，其余楔形没有余量。

R-049 实测真实 `/` 快照后，把这件事的性质改了——它不是"把 `512` 调大"能解决的问题：

1. **`256 KB` 载荷上限一直在被突破。** ADR-0017 第 4 条的这个数从未实测过。实测默认 `384` 预算即
   `274 KB`，硬上限 `512` 预算达 `384 KB`（超 `50%`）。这与 R-047 里 `<15s` 属同一类错误：无实测出处的
   数值被当作门槛长期沿用。
2. **载荷的成本在每条弧的 DTO，不在弧数。** 投影后代当前是完整 `MapEntry`，内嵌完整 `scan.Node`
   （`Path`、`Device`、`Inode`、`ModifiedAt`、`VolumeID`，以及逐条重复的 `Confidence`/`SizeBasis`
   字符串和 JSON 字段名）。改用"绘制一条弧实际需要的字段"后载荷稳定小 `11` 倍。
3. **JSON 编码不是瓶颈**（`1.4 MB` 仅 `2.48ms`），**服务端装配才是**。
4. **存在第二条独立上限**：`format.go` 的 `maxPageSize = 1000` 使预算无法抬过 `1000`，宽目录会直接报
   `page limit 5747 exceeds 1000`。

关键实测（depth 4，真实 `/`）：

| budget | arcs | 完整载荷 | 精简载荷 | 装配中位 | 装配 p95 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| `384` | `405` | `288.1 KB` | — | `88.4ms` | `130.1ms` |
| `512` | `533` | `384.0 KB` | `33.6 KB` | `105.1ms` | `137.2ms` |
| `1000` | `1021` | `747.7 KB` | `69.2 KB` | `140.1ms` | `159.1ms` |
| `2000` | `2021` | `1467.5 KB` | **`132.8 KB`** | `257.7ms` | `346.9ms` |
| `5000` | `5021` | `3604.1 KB` | `314.0 KB` | `906.0ms` | `1191.5ms` |

前端侧的核对：空间图与目录列表实际只使用投影条目的 `node.id`、`node.kind`、`name` 和
`ownedAllocated`（`App.tsx` 中对 `.node.*` 的全部引用只有 `id` 与 `kind`）。因此精简形态不会削减任何
已实现的前端能力。

## 方案

### 方案 A：投影后代改用精简条目，再按实测抬密度（采用）

当前层 `entries` 保留完整 `MapEntry`；**只有** `children`（投影后代）改用精简形态，并跳过其路径重建。
先拿回载荷与延迟，再把密度抬到目标值。

- 优点：`2021` 弧的载荷从 `1467.5 KB` 降到 `132.8 KB`，重新落回 `256 KB` 之内；同时**结构性地**加强了
  DDD 不变量 17（投影后代不携带路径，无法被当作文件操作授权）；前端无能力损失。
- 代价：`MapResult` 的 `children` 形态变更，Wails 绑定、前端类型与 ADR-0047 的差分测试需同步。
- 风险：装配延迟能否随之下降，取决于 R-049 第 3.5 节的**未验证假设**（路径重建是主因）。若假设不成立，
  密度目标必须让步，见第 4 条。

### 方案 B：直接抬高 `projectionLimit` 上限（拒绝）

`2000` 弧在当前 DTO 下是 `1467.5 KB` 载荷与 p95 `346.9ms`，同时突破 ADR-0017 的两条门槛，且 `>1000`
会被 `maxPageSize` 直接拒绝。这是把已经违规的载荷再放大一个数量级。

### 方案 C：前端按需逐扇区补齐深层（拒绝）

ADR-0017 已拒绝"每个扇区单独调用 `GetMap`"：造成 N+1 请求与快照版本漂移。本 ADR 不重开该选项。

### 方案 D：二进制或并行数组传输（本轮不采用）

比精简 JSON 更省，但需新增编码与前端解码路径。精简 JSON 已把 `2021` 弧压到 `132.8 KB`，够用；
若第 6 条的门槛在精简形态下仍不达标，再单独评估。

## 决策

### 1. 投影后代使用精简条目形态

`MapEntry.Children` 中的条目改为精简形态，只携带：节点 ID、名称、`owned_allocated`、种类
（目录/文件/聚合）、`children`、`childrenTotal`、`childrenHasMore`。

**不携带**：`Path`、`Device`、`Inode`、`ModifiedAt`、`VolumeID`，以及逐条的 `Confidence` 与
`SizeBasis`——后两者由所在层的 `MapResult` 继承。

当前层 `entries` **不变**，继续携带完整 `scan.Node`：它们驱动预览、Finder 定位和清理，需要完整节点身份
（ADR-0013/0015、DDD 不变量 17）。

### 2. 投影后代跳过路径重建

装配投影后代时不得调用路径重建。这既是延迟优化，也是第 1 条的必然结果——不携带路径就不该为它付读取
成本。当前层条目继续重建路径。

### 3. 解除投影内部读取与 `maxPageSize` 的耦合

`projectChildrenFrom` 读取子项时不得受 `maxPageSize = 1000` 约束，否则密度无法抬过 `1000`。分页查询
（`Children`、`Map` 的 `Limit`）的 `maxPageSize` 保持不变。

### 4. 密度目标与门槛的优先级

- **密度目标：`2000` 弧**（产品决策）。`projectionLimit` 的默认值与硬上限按该目标重新给定。
- 深度上限保持 `4`（当前层加 4 层投影，对齐 R-016 第 4 节的 5 个深度与原版可见的五环）。
- 当前层 `entries` 上限保持 `256`。
- **门槛优先于密度。** 若在精简形态下 `2000` 弧仍无法满足第 6 条的延迟门槛，**下调密度目标**到能满足
  门槛的值，而不是放宽延迟门槛。理由：延迟是用户直接感知的，密度是观感增益；R-049 第 3.5 节的收益是
  假设而非实测，本 ADR 不预支它。

### 5. 载荷上限保持 `256 KB`，并首次成为真实约束

ADR-0017 第 4 条的 `256 KB` 保留，但必须按 R-049 的口径（`json.Marshal(MapResult)` 的真实字节数）实测
核对。该数此前从未被测量，现已知在默认预算下即被突破；精简形态使 `2000` 弧为 `132.8 KB`，因此它第一次
成为一条真正可满足的约束，而不是纸面数字。

### 6. 延迟门槛按实测重定，不沿用未实测的数

ADR-0017 的"三层投影 p95 `<=150ms`"同样没有实测出处。本 ADR 按 R-049 的实测基线重述：

- 现行基线（完整 DTO）：`533` 弧 p95 `137.2ms`，`1021` 弧 p95 `159.1ms`，`2021` 弧 p95 `346.9ms`。
- **门槛：目标密度下装配 p95 `<=150ms`**。该值与现行 `512` 弧的实测 p95（`137.2ms`）同量级，因此不是
  放宽，而是要求密度提高后延迟不劣化。
- 测量口径：进程内、页缓存命中、同一快照、预热后取 11 次以上样本的中位数与 p95；冷缓存另行记录，
  不作为判定依据。

### 7. 不变边界

- `MapQuery` 的参数语义、`Remaining` 与 `ProjectionTruncated` 语义、聚合项与虚拟项的能力集合、
  "投影不扩大文件操作能力"（ADR-0017 第 2 条）全部不变；
- 不引入逐扇区查询；投影仍是一次查询返回的有界结果；
- 内存投影与 durable reader 必须继续共享同一装配（ADR-0047），精简形态对两者同时生效；
- 不改变快照格式、索引布局或 `SnapshotStore` 的其他方法。

该决策更新 [ADR-0017](0017-有界多层空间图投影.md) 第 1 条的预算数值、第 4 条的载荷与 p95 表述，以及
投影后代的条目形态；ADR-0017 的其余部分（投影不扩大操作能力、共享快照版本与口径、拒绝逐扇区查询与
完整树传输、截断必须可见）继续有效。

## 后果

正面后果：

- 空间图密度可达产品目标，同时载荷首次真正落在 `256 KB` 之内；
- 投影后代不再携带路径，DDD 不变量 17 从"约定"变为"结构性无法违反"；
- 前端无能力损失：它对投影条目只使用 `node.id`、`node.kind`、`name` 与 `ownedAllocated`。

代价和风险：

- `MapResult.Children` 是对外契约的一部分，Wails 绑定、前端类型定义与 ADR-0047 的投影/durable 差分
  测试都必须同步更新；漏改会在类型层暴露，但差分测试必须显式覆盖新形态；
- 延迟收益依赖一个未验证的假设。若假设落空，按第 4 条下调密度，本 ADR 的密度目标即未达成——这必须
  如实记录，不得通过放宽延迟门槛来"达成"；
- 精简形态使投影后代无法直接用于任何需要路径的功能。若将来空间图要支持"从扇区直接预览"，必须先按
  节点 ID 回查完整节点，而不是把路径塞回投影。

## 验收门禁

1. 全仓 Go 测试、`-race`、`go vet`、前端 `tsc` 与 `vite build` 通过；
2. ADR-0047 的投影/durable 差分测试更新到新条目形态后继续逐字段通过（内存投影与 durable 的
   `children` 必须一致）；
3. 聚合项、虚拟项与 `stale` 的能力集合在精简前后不变；投影后代不得获得预览、定位或清理能力；
4. 载荷：目标密度下 `json.Marshal(MapResult)` 实测 `<=256 KB`；
5. 延迟：目标密度下装配 p95 `<=150ms`，口径按第 6 条；
6. 记录 R-049 同口径的对照表（arcs、完整/精简载荷、装配中位与 p95、编码耗时），并注明
   第 3.5 节假设被证实还是推翻；
7. 未达到第 4/5 条时，按第 4 条下调密度目标并如实记录"密度目标未达成"，不得放宽延迟门槛。

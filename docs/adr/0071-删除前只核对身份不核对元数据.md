# ADR-0071：删除前只核对身份，不核对元数据

- 状态：Accepted（2026-09-08 使用方在读过 R-073 的论证后答复「按照你的建议来改」）
- 日期：2026-09-08
- 相关预研：[R-073](../research/R-073-删除前校验的内容复核.md)
- 关系：
  - **修订 SDD §10** 由 [ADR-0009](0009-清理计划与macOS废纸篓执行.md) 落地的校验内容：ADR-0009 要求"每项执行前
    再次校验 `lstat` 身份"，SDD §10 实现时加上了大小与修改时间；本文去掉后者，身份校验与"执行前重新校验"的
    硬约束不变。
  - **依赖 [ADR-0070](0070-目录就地重读.md)**：用户看到的大小改由创建计划前的目录重读保证。
  - **不修改 [ADR-0063](0063-直接删除与不可恢复守卫的硬边界.md)**：`DeleteBlock` 与倒计时三次确认仍是仅有的两道
    用户侧保护。

## 背景

删除前的校验比三层：设备号 + inode、类型、大小 + mode + 修改时间。第三层对活缓存几乎必发（目录 mtime 随直接
子项增删变化），拦下的几乎都是用户最想删的东西，拦下之后唯一的出路是重扫整盘。使用方问：为什么删除前要做这个
比对？R-073 把三层拆开：前两层回答"删的是不是那个东西"，第三层回答"那个东西有没有变"——用户的意图是删这个对象，
不是删扫描那一刻的字节快照。

## 预研依据

R-073 §2 的三层对照表；§3 实测 APFS inode 号单调不复用，身份层无需加固；§4 说明第三层为什么几乎必发而其想防的
场景几乎不会发生；§5 指出硬约束只要求"重新校验"，ADR-0009 原文写的就是身份。

## 方案

### 方案 A：去掉元数据层，创建计划前重读所涉目录（采用）

校验只核对身份与类型；"看到的数字要准"由重读承担。

### 方案 B：保留元数据层，校验失败时自动重读并重试一次（拒绝）

效果接近但多一次往返，且把"内容变了"继续当成拒绝理由——它不是。

### 方案 C：全部保留（现状，拒绝）

活缓存删不掉，唯一出路是重扫整盘。

## 决策

### 1. `validateCleanupItem` 只核对身份与类型

- 设备号 + inode 不等：拒绝，"对象已被替换（不是扫描时的那一个）"；
- 类型（文件 / 目录 / 符号链接）不等：拒绝，"对象类型已变化"；
- 大小、mode、修改时间：**不比对**。
- 校验点不变：创建、确认、执行前整体校验，每项执行前再校验一次（ADR-0009）。`DeleteBlock` 不变。

### 2. 创建计划前重读所涉目录

前端在 `CreateCleanupPlan` 之前，对收集区选中项所在的目录（目录项即自身，文件项取父目录，嵌套者折进最外层）
逐个调用 `RereadDirectory`（ADR-0070）。读完后按保留下来的节点 ID 刷新收集区行：仍在的行取新条目（新大小），
已消失的行移出并提示数量。计划用刷新后的条目创建，随后照常校验、倒计时、三次确认。

被拒绝的重读（`too_large`、`busy`、`scan_root` 等）跳过，不阻塞：执行前的身份核对仍钉住每个对象。

### 3. 边界

- 删除仍按**当前内容**执行；扫描之后新出现在该目录下的子项也会被删——这是"删这个对象"的字面含义，重读让用户
  在倒计时前看到它现在有多大。
- 不引入任何新的拒绝理由；不改倒计时时长与确认次数。

## 后果

正面后果：

- 活缓存可以删了，不再需要为一次删除重扫整盘；
- 倒计时前显示的大小是当前值，而不是扫描时的值；
- 校验的语义变清楚：它回答"是不是那个东西"，只回答这一个问题。

代价和风险：

- 创建计划前多了 0.5-1.5 s 的重读（按目录大小），收集区里目录多时按个累加；
- 用户在看图与点删除之间若有人往该目录放了新东西，它会一起被删。这与在 Finder 里删一个文件夹的语义相同，
  由倒计时承担确认；R-073 §4 判断此场景极少。

## 验收门禁

1. 全仓 Go 测试、`go vet`、前端 `tsc`、`vite build` 无错误；
2. 单测：计划创建后文件内容变长、目录新增子项、目录 mtime 改到未来，校验仍通过；同路径换成另一个对象，校验仍拒绝；
3. 既有 `TestValidateCleanupPlanDetectsReplacement` 不变通过；
4. 真实窗口：向一个仍在写入的缓存目录发起删除，倒计时前收集区显示的是当前大小，删除成功。

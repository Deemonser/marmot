# ADR-0003 全盘扫描与快照架构

状态：Accepted（本机性能门槛已验证；真实全盘仍需发布前回归）

日期：2026-08-19

## 背景

全盘扫描可能产生百万级节点。成熟产品不会把完整结果一次性传给 UI，而是使用后台扫描、渐进展示、受限并发、缓存、增量刷新和按需展开。

## 预研依据

- [R-001 成熟产品与扫描策略](../research/R-001-成熟产品与扫描策略.md)
- [R-004 百万级节点性能与快照存储](../research/R-004-百万级节点性能与快照存储.md)

## 决策

### 扫描流水线

采用分阶段、可取消的扫描流水线：

```text
卷/权限探测
  -> 顶层汇总
  -> 受限并发遍历
  -> 大小和链接处理
  -> 分批写入快照
  -> 更新目录汇总
  -> 事件推送进度
```

### 数据口径

每个节点至少保留逻辑大小、实际占用、去重后占用、可信度和计算口径版本。默认可视化使用去重后占用；不可得时必须降级并说明。

### 查询和前端

- 快照按目录和父节点查询。
- 子节点分页、排序、过滤和懒加载。
- 不向 WebView 一次发送百万级节点。
- 事件只发送批次进度、目录汇总和问题摘要。

### 资源控制

- worker、队列、事件批次和缓存有明确上限。
- 缓存带 schema 版本、TTL、容量上限和失效策略。
- 硬链接按卷内身份去重。
- APFS 部分克隆无法可靠计算时标记未知，不伪造精确值。

### 快照存储

定义 `SnapshotStore` 端口，第一实现使用 SQLite，以支持百万级节点的本地分层查询和增量保存。
具体驱动、批次和门槛由 ADR-0007 锁定；若未来不达标，只替换存储实现，不改变领域和用例契约。

## 不在本 ADR 中锁定

- APFS 部分克隆的精确归属仍不承诺；
- 本地快照第一阶段只展示，不执行清理；
- 真实签名应用和全盘样本的发布回归。

## 后果

- UI、扫描器和存储必须围绕快照查询契约协作。
- 初期实现比“递归后返回完整 JSON”复杂，但能避免百万级数据导致的返工。
- 本机合成基准不等于真实全盘性能目标；发布前仍需真实只读样本回归。

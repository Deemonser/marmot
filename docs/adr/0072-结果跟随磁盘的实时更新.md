# ADR-0072：结果跟随磁盘的实时更新

## 背景

R-071 修掉了陈旧误报，ADR-0070 让陈旧有了出路，ADR-0071 去掉了删除前的元数据比对。使用方随后问：原版会隔
一段时间刷新，对象变化本来就正常，为什么不做全盘监听、把这一整套"发现变化再补救"都省掉？

ADR-0064 §4 拒绝监听的两条理由：

1. **"分析建立在同一时刻的快照上，监听会破坏一致性。"** 分析（residue 分区、证据下限、活跃度分级）是在触发时
   读当前的树算一遍；树更新得更勤，分析拿到的只是更新的"那一刻"。一次分析内部读同一个版本靠店锁保证，
   与是否监听无关。这条混淆了"树是否变"与"一次读取是否一致"。
2. **"事件流不间断，图会永远在抖。"** R-074 量出空闲机器每秒 1-1.5 个事件、落在十来个目录；突发集中在极少目录。
   攒批 2 s、按目录去重、用户操作期间不重绘，这是常规界面手段。使用方观察到的原版行为——隔一段时间刷新一次——
   正是"批量应用"的样子。

所以拒绝该推翻。剩下的问题是代价与边界，R-074 给了数字。

## 预研依据

R-074 §2：300 s 全盘监听 81,924 事件 / 1,460 目录，每次回调最多 32 个事件（系统只按时间合并，不按数量），
每次回调不同目录中位数 1，无丢事件与重扫标志。§3：浅刷新 1-2.5 µs/条，一批几十个目录个位数毫秒，成本由
`group()` 约 70 ms 主导。§4：事件路径与树路径同形（firmlink 形态、`/private/tmp`），带结尾斜杠。
R-072 §2-§5：接入新节点的规则与深读代价。

## 方案

### 方案 A：目录级 FSEvents，浅刷新 + 新目录深读，2 s 一批（采用）

### 方案 B：文件级事件（`FileEvents` 标志）逐文件更新（拒绝）

事件量成倍增加，而目录级事件到来时本来就要重列该目录一次，逐文件事件不省任何读取。

### 方案 C：定时全盘重扫（拒绝）

17-25 s 一次，且期间树不可用；这是把"刷新"做成"重来"。

### 方案 D：维持不监听（现状，拒绝）

理由已在背景中推翻。

## 决策

### 1. 结果完成后跟随扫描根

扫描以 `completed` / `completed_with_issues` 结束时，对扫描根开一条 FSEvents 流（目录级、`NoDefer`、latency 2 s，
专用串行 dispatch queue）。新扫描开始前、进程退出时停止。缺任何一项能力（无监听端口、店不支持浅刷新、
扫描器不支持浅读）时静默不开，行为退回 ADR-0070。

### 2. 应用层再攒一批

回调只记录（去掉结尾斜杠，`MustScanSubDirs` 按目录取或，`Dropped` 按批取或），2 s 后一次应用。应用在
`rereadMu` 下进行——与 ⌘R 同一把锁，一棵树只有一个写者；扫描进行中丢弃整批（结果即将被替换）。

### 3. 一个目录一次浅刷新，新目录一次深读

按路径长度排序（父先于子），逐个：`NodeByPath` 找不到即跳过（另一卷、边界外、或它自己已被删——其父的刷新
会摘掉它）；非目录跳过；`MustScanSubDirs` 走 ADR-0070 的深读，被拒绝（超上限、含挂载卷）计入 `dirty`；
否则 `DirectoryReader.ReadDirectory` 浅读 + `Store.RefreshDirectory`：

- 同名同类：文件取新大小、身份、mtime，差值上滚；目录只更新身份与 mtime，**子树总量不动**；
- 新名字：文件直接加；目录以空目录加入并立刻深读（新目录一般很小）；
- 消失的名字：连子树摘下（ADR-0064 的方式），空间从祖先扣除；
- 挂载卷节点（`kind=volume`）不在列表里但**保留**，否则一次 `/System/Volumes` 的事件会让卷组成员消失。

一批结束：一次 `group()`（约 70 ms）、一次 `statfs` 刷新卷数字、一个 `snapshot-updated` 事件。

### 4. 前端：批量重绘，用户操作时让路

收到事件后至多每 1.5 s 重查一次当前层；拖拽、倒计时、删除进行中、Map 忙时不重绘，事后补一次。收集区的行按
保留的 ID 刷新，已消失的行移出并提示数量。创建计划前：若 `GetLiveUpdateStatus` 报告跟随中且无丢事件，
跳过 ADR-0071 §2 的重读；否则照旧。

### 5. 保留什么

- **删除前的身份核对不变**（ADR-0071 §1）。监听是异步的、可能丢事件，"删的是不是你点的那个对象"只能在
  动手那一刻由一次 `lstat` 回答。
- `⌘R` 仍是手动深读，处理 `dirty` 的目录与用户想立刻看到的情况。
- 丢事件（`Dropped`）记入状态并写日志；前端据此在创建计划前退回重读。不自动重扫整盘。

### 6. 不变边界

- 不引入文件级事件；不做后台全盘重扫。
- 每个目录是它自己最近一次事件时刻的状态，全树不承诺同一时刻——这在 ADR-0064 §4 被当作缺陷，本文把它明确为
  产品语义：图跟着盘走。
- 加入收集区不触发文件操作；`CleanupPlan` 仍在执行前重新校验。

## 后果

正面后果：

- 图跟着磁盘走，陈旧几乎不再出现；删除前不需要额外重读。
- 事件、去重、攒批的成本在正常使用下不可感知（R-074）。

代价和风险：

- 每批一次 `group()` 分配约 12 B/节点的临时数组；2.7M 节点约 33 MB 的短命分配，2 s 一次。
- 硬链接文件在浅刷新里按全量计（走的链表是每次扫描一份），与扫描时的去重口径有出入，直到下次扫描或深读。
- 未在 Time Machine 备份、大规模 `rsync` 期间测过事件量；`MustScanSubDirs` 对超上限目录只能标 `dirty`。
- 真实窗口里"是否还抖"待验证。

## 验收门禁

1. 全仓 Go 测试、`go vet`、前端 `tsc`、`vite build`、绑定重新生成后无编译错误；
2. `RefreshDirectory` 单测：仅动直接子项、子目录子树不动、新目录空进并上报、消失者连子树摘除、祖先差值、
   计数器与版本、无变化幂等、保留挂载卷节点、拒绝文件与未知节点；
3. Application 单测（假监听端口）：扫描完成即开始跟随；一批事件后文件新大小、新文件、新目录（深读到内容）、
   消失的 ID、目录与根的差值一致；一批一个事件；停止恰好一次；
4. 真实窗口：往一个可见目录里放文件，2-4 s 内轮盘与列表更新；拖拽期间不重绘。

# ADR-0056：内存事实源的结构与发布峰值

- 状态：Accepted（由决策者接受）
- 实施状态：已实施（2026-08-26）。一处与本文数值不符，如实记录：**节点记录是 64 字节，不是 56。**
  第 1 条只算了 `kind` 与 `flags` 两个字节，实际还需要 `volume`/`basis`/`confidence` 三个码，合 5 字节，
  加对齐后是 64。因此定长部分是 `170 MiB` 而不是 `148.6 MiB`。`TestRecordStaysPacked` 用
  `unsafe.Sizeof` 把这个数字钉住：它就是内存预算，改动必须是有意的。

  实测（真实 `/`）：**留存堆 `257.8 MiB`**（强制 GC 后采样），可见终态 `15.2s`，
  目录覆盖率 `589191/589191`，空间图载荷 `123.7 KiB`、装配 p95 `4.34ms`，ADR-0052 的两条恒等式仍精确成立
  （`Σ子项 = 已用`、`已用 + 可用 = 容量`）。存储本身的吞吐单独测过：`2.8M` 次插入 `0.71s`（`255 ns/节点`），
  分组 `0.04s`。

  两处偏离设计的实现细节：

  1. **子项分组是按需构建的，不是扫描期维护的。** 第 4 条要求"扫描期直接写入按父分组的数组"，但
     ADR-0014/0027 规定 `TopLevelPublish` 之后后端就应可查询，而那时分组还不存在。改为：插入与改写
     roll-up 使分组失效，查询时用计数排序重建一次（`O(n)`，实测 `0.04s`）。这既满足"可查询"边界，
     又不需要扫描期维护一份按父分组的副本——那份副本正是第 4 条要消除的 2× 峰值。
  2. **`allocatedSize` 与 `ownedAllocated` 合成一个字段**，`node()` 返回时两者取同值。第 3 条要求的
     "留出扩展位"以 `flags` 的空闲位实现；引入 `privatesize`（ADR-0052 §2）需要新增字段，不得复用此字段。

  第三处修正（2026-08-26 复测后）：初版实现让节点表与名字 arena 靠 `append` 的 `~1.25×` 增长长起来，
  把一个终态 `178 MiB` 的数组累计复制约五倍，单这两处就贡献 `1209 MB` 的瞬时垃圾。改为翻倍增长，但翻倍
  会长期持有最多 2 倍容量（留存堆一度升到 `368 MiB`，直接违反门禁 2 的稳态部分），故在 `finish()` 里加
  `trim()` 裁到精确长度。净效果：留存堆 `276.0 → 257.8 MiB`，扫描期分配量 `2794 → 2478 MiB`。
  **增长策略是内存预算的一部分，不是实现细节**：翻倍换吞吐、裁剪换稳态，两者必须成对出现。

  门禁 2 的峰值部分未达成，原因与 ADR-0055 的实施状态同一条：扫描管线仍逐节点构造完整路径。剩余
  `1324 MB` 的分配量（`addNodes` `968 MB` + `joinNativePathAndName` `356 MB`）全部来自那里，占 churn 的
  `53%`。R-057 第 4c 节另外证实：Darwin 上这部分高水位**不可回收**——Go 的 `MADV_FREE_REUSABLE` 返回成功
  却不降 `phys_footprint`，只有 `munmap` 能降而 Go 从不 `munmap` 堆 arena。因此门禁 2 的峰值只能靠"不分配"
  达成，`GOMEMLIMIT` 不是替代方案（`400MiB` 比 `500MiB` 的峰值与耗时都更差）。

## 背景

R-057 测出内存事实源的结构成本，并指出现行 `projectionEntry`/`projectionDirectory` 的开销大部分来自
"能从盘上重读"这个已经不需要的能力：

| 现行开销 | 大小 | 原因 |
| :-- | --: | :-- |
| `dataOffset` + `stringBase`（`16 B/节点`） | `42 MiB` | 定位盘上记录 |
| 单独存的 `nodeID`（`8 B/节点`） | `21 MiB` | 可以是数组下标 |
| `allocatedSize`（`8 B/节点`） | `21 MiB` | 与 `ownedAllocated` 恒等（R-053） |
| 每目录两个 Go string（`32 B`） | `19 MiB` | 真实基数只有 `2` 和 `1`（R-057 §3.2） |
| 每目录三个切片头（`72 B`） | `42 MiB` | 发布后只用其中一个 |

另有一处峰值问题：发布阶段把 `directoryChildren` + `fileChildren` **append 进一个新切片**再排序，两份同时
存在，实测峰值 `500 MiB` 对稳态 `340 MiB`。

## 决策（若被接受）

### 1. 定长节点表，nodeID 即数组下标

> **本条已由 [ADR-0057](0057-扫描到装配的分配契约.md) 第 3 条替代**：连续数组与其增长策略改为分页，
> 实施中引入的 `trim()` 一并移除。定长记录本身与 `unsafe.Sizeof` 钉住预算的做法保留。

```
parentID       int64   (8)
ownedAllocated int64   (8)
logicalSize    int64   (8)
device         int64   (8)
inode          int64   (8)
modifiedAt     int64   (8)
nameOffset     uint32  (4)
nameLength     uint16  (2)
kind           uint8   (1)
flags          uint8   (1)   // hasChildren 等位标志
= 56 字节
```

`nodeID` 不存储——它是下标。扫描器已经从 1 开始连续编号且无空洞（R-053 第 3 节据此推断
`result.Nodes` 即最大 ID），本 ADR 把这条从"推断"变成**结构前提**：编号一旦出现空洞，节点表就会错位，
因此必须由测试守住"ID 连续无空洞"。

### 2. `kind` / `volumeID` / `sizeBasis` / `confidence` 一律 1 字节码

实测基数分别是 `3 / 1 / 2 / 1`（R-057 §3.2）。码表按 scope 保存一份，不进节点表。
**禁止**再以 Go string 形式逐节点或逐目录保存这四个字段。

### 3. 去掉 `allocatedSize`，但保留扩展位

`allocatedSize` 与 `ownedAllocated` 恒等（R-053），只存后者。

**但必须留出退路**：ADR-0052 第 2 条把 `privatesize`（"删了能释放多少"）留作未来选项，那时需要第二个
独立的尺寸字段。`flags` 里保留位，并在文档中写明"引入第二种尺寸口径需要扩展节点表"——不得因为现在恒等
就假设永远只需一个尺寸。

### 4. 发布阶段就地排序，消除 2× 峰值

不再把两组子项 append 进新切片。子项在扫描期直接写入一个按父分组的全局子项数组，发布阶段**就地**排序
每个父的区间。目标：峰值不超过稳态的 `1.2` 倍（现状是 `1.47` 倍）。

### 5. 目录表只保留 roll-up 与子项区间

```
childStart uint32, childCount uint32, ownedAllocated int64, logicalSize int64,
confidence uint8, sizeBasis uint8  (+ 对齐)
= 40 字节
```

不再有三个切片头，不再有 Go string。

### 6. 名字用单一 arena，不得逐节点分配

一个连续 `[]byte`，节点表存 `offset`+`length`。实测名字总量 `55.7 MiB`（均长 `21`，最长 `178`），
`uint32` 偏移与 `uint16` 长度足够，且必须校验上界。R-047 第 3.9 节已实测朴素 per-node 分配的代价
（`+295 MiB` 对 `+62 MiB`），不得回退到那个形态。

### 7. 不变边界

- ADR-0049 的全保留不变：每个目录的全部子项都在内存里，**不得**借结构压缩之名退回 top-K；
- 空间图契约、密度上限、载荷与 p95 门槛（ADR-0048/0053）不变；
- 清理计划的 device+inode 复核链不变（第 1 条已把这两个字段放进节点表）；
- 不改变扫描器的输出契约。

## 后果

正面后果：

- 结构成本从推算 `340–385 MiB` 降到 `~237 MiB`；
- 峰值从稳态的 `1.47` 倍降到目标 `1.2` 倍以内；
- 四个字段的 1 字节码同时消除了盘上 30% 的重复（若 ADR-0055 未被接受，这一条对 durable 格式同样成立）。

代价和风险：

- **nodeID 下标化把"编号连续无空洞"从推断变成硬前提**。这是本 ADR 最脆的假设：扫描器将来若并行分配 ID
  或跳号，节点表会静默错位。必须有测试守住，且该测试要能在 ID 出现空洞时失败；
- `uint32` 名字偏移把 arena 上限定在 `4 GiB`，`uint16` 长度上限 `65535`。实测值离上限很远，但必须显式校验
  而不是假设；
- 去掉 `allocatedSize` 会让"引入 privatesize"变成一次结构扩展（第 3 条已留位并写明）；
- 就地排序会让子项数组在扫描期就必须按父分组，扫描期的写入路径比现在复杂。

## 验收门禁（若被接受）

1. 全仓 Go 测试、`-race`、`go vet` 通过；
2. 内存实测：稳态 `<=280 MiB`、峰值 `<=400 MiB`，且峰值 `/` 稳态 `<=1.2`；口径同 R-047

   > **峰值两条已由 [ADR-0058](0058-扫描内存上限与峰值门禁.md) 替代。** `<=1.2` 不可实现：
   > `GOGC=100` 的定义就是堆涨到活跃量的 `2×` 才回收，R-059 实测 churn 降 `74%` 而该比值纹丝不动。
   > 新门禁是峰值 `<=700 MiB` 且峰值 `-` 稳态 `<=350 MiB`——加法而非比例，因为比例门禁在更大的卷上
   > 会自动放宽。稳态 `<=280 MiB` 这一条不变，实测 `254.7 MiB`。
   （堆用 `runtime/metrics`，RSS 用 `/usr/bin/time -l`，峰值与 wall 分轮测量）；
3. "节点 ID 连续无空洞"由测试守住，且该测试在人为跳号时失败；
4. 名字 arena 的偏移与长度上界有显式校验与对应测试；
5. 全保留不变：真实 `/` 上目录覆盖率仍为 `100%`（ADR-0049 门禁 2）；
6. 空间图的载荷 `<=256 KB`、装配 p95 `<=150ms` 仍达标（ADR-0048）；
7. 可见终态中位数无回退。

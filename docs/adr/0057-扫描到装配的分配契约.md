# ADR-0057：扫描到装配的分配契约

- 状态：Accepted
- 实施状态：已实施（2026-08-26）。七条门禁全部通过：

  | 门禁 | 结果 |
  | :-- | :-- |
  | 1 测试 / `-race` / `vet` / `tsc` / `vite build` | 通过 |
  | 2 契约测试在旧行为下失败 | 通过（关掉复用后 `TestEmitBatchIsValidOnlyDuringTheCallback` 失败，恢复后通过） |
  | 3 扫描期总分配量 `<= 800 MB` | **`650.1 MiB`**（现状 `2530 MB`，推算 `~626 MB`） |
  | 4 留存堆 `<= 260 MiB` | **`256.7 MiB`** |
  | 5 峰值三口径 | `ps rss` `581.2` / `phys_footprint` `569.0` / 活跃堆 `256.7 MiB` |
  | 6 可见终态 `<= 17s` | **`14.259s`**（现状 `15.2s`，基线 `16.5s`） |
  | 7 覆盖率与 ADR-0052 恒等式 | `586173/586173`，`balance_gap = 0.00 GB`，`used + free = total` |

  四处如实记录：

  1. **`scan.Result.DirectorySizes` 仍是 map**，只是从"扫描期逐条长大"改成"结束时按已知条数一次建好"
     （`directorySizeMap`，`65.93 MB`，原先 `160 MB`）。第 3 条的字面要求是扫描器的两个持久 map 都变稠密——
     内部状态确实变了（`dirOrdinal` ＋ 两张按序号分页的表），但**边界类型没变**。把 `scan.Result` 改成
     并行切片还能再省约 `56 MB`，代价是同时改动进度路径上的 `UpdateDirectorySizes`。门禁 3 已有 `19%` 余量，
     没有承担这个风险。
  2. **实施中途我把分配量做到了 `19934 MiB`**，比改之前差 20 倍。原因是消费侧缓冲耗尽时按下限容量新建，
     而自由链表**基本总是空的**（扫描器跑在写入端前面），于是每批次分配 `754 KB`。正确做法是**等**一个
     缓冲而不是新建。这条写进决策第 1 条的实现要求：**在回收路径上"分配一个新的"就等于没有回收**。
     它是被测量抓到的，不是被评审抓到的。
  3. **我自己的契约测试犯了 R-058 §3 记录的同一个错**——emitter 里写 map 没加锁，先跑通过是靠运气，
     换了分页实现后立刻 `concurrent map writes`。挂在 emit 回调上的一切都必须先假定并发，包括测试。
  4. **应用层 `topLevelDirectory`（按节点 ID 索引的 map，`44.26 MB`）未处理**，理由同第 4 条"不在本 ADR
     内决定的事"：改成 `[]int32` 只省约 `11 MB`，不值得。

  改后的分配构成基本贴着下界：节点表分页 `166.47 MB`（表本身就是 `178 MiB`）、文件名 `73 MB`、
  目录路径 `68.01 MB`、边界 map `65.93 MB`、名字 arena 分页 `53.20 MB`。

## 背景

[ADR-0055](0055-取消快照持久化与内存唯一事实源.md) 门禁 4 与 ADR-0056 门禁 2 的**峰值**部分至今未达成，
两次实施报告都把原因记为"扫描管线逐节点 materialise `scan.Node` 加完整路径"，并注明需另立 ADR。

现在必须决定，因为 R-057 第 4c 节补上了缺失的前提：**这个峰值在 Darwin 上事后无法回收**。Go 的
`sysUnusedOS` 调用 `MADV_FREE_REUSABLE`，该调用在 macOS 26.5 上返回成功却既不降脏页也不降
`phys_footprint`（独立最小样本实测）；只有 `munmap` 能降，而 Go 从不 `munmap` 堆 arena。因此使用方在活动
监视器里看到的数字是**单调高水位**，`debug.FreeOSMemory()` 只能拿回约 `300 MiB`，`GOMEMLIMIT` 有拐点
（`400MiB` 的峰值与耗时都劣于 `500MiB`）。

结论是：**峰值只能靠不分配来降**。而 R-058 表明，先前记录的原因只覆盖了一半。

## 预研依据

R-058 的关键证据：

1. **批次极小。** 扫描器发出 `421,701` 个批次，平均 `6.6` 个节点，**`45.7%` 只有 1 个节点**，
   `90%` 不超过 8 个。所有"每批次一次"的固定分配要付 `42` 万次——这是先前判断完全遗漏的一头。
2. **契约成本 `813.0 MiB`，信息下界 `55.7 MiB`，倍率 `14.6×`。** 存储保留的唯一文本是名字
   （`55.7 MiB`）；文件路径 `263.4 MiB` 建完即弃；父前缀被复制 278 万次共 `269.1 MiB`，
   而这份信息已经在父记录里。
3. **三个按 ID 索引的 map 合计 `428.95 MB`**，其中 `directoryDeltas` 一项 `210.61 MB`——一个每批次新建、
   平均只装几条的 map，建了 42 万次。
4. **ADR-0056 实施引入的翻倍增长＋`trim()` 是一笔方向相反的交换**：花 `737.54 MB` 分配量换 `110 MiB`
   留存下降（`growRecords` `511.99 MB` ＋ `trim` `225.55 MB`）。在"高水位不可回收"前提下不成立。
5. **隔离测量**（实测批次分布下）：每批次分配 `831.1 → 0.6 MiB`；两个持久 map `224.2 → 55.5 MiB`；
   文件路径 `267.8 → 50.2 MiB`。与生产剖析交叉校验，三项均在 `±10%` 内。

约束证据：`scan.BatchEmitter` 当前文档**明确转移所有权**，消费侧把批次送进 `scanPersistQueueCapacity = 2`
的 channel 交给写入 goroutine；且 emit 回调**并发调用**，实测峰值并发 `2`。

## 方案（评估记录）

### 方案 A：只改扫描器的路径构造（先前记录暗示的范围）

不再为文件构造完整路径。

- 优点：改动面最小，只动 `joinNativePathAndName` 与 `addNodes` 的调用点；
- 代价：省 `217.6 MiB`，占 `2530 MB` 的 `8.6%`；
- 风险：**达不到任何门禁**，且会让人误以为问题已经处理过。R-058 第 5 条第 1 点已经证明这个范围建立在
  不完整的归因上。

### 方案 B：改契约所有权 ＋ 去路径 ＋ 稠密数组（本 ADR 采纳）

三条一起做，理由是它们服务同一个门禁，拆开后门禁无法归属到任何单独一条。

- 优点：推算合计 `2530 → ~626 MB`（`-75%`），且第 3 条顺带修掉 ADR-0056 实施引入的翻倍＋裁剪缺陷；
- 代价：改 `scan.BatchEmitter` 的所有权语义，消费侧必须在回调返回前复制出去；扫描器需要按 worker 持有
  缓冲；memtree 记录表改分页后，`nodeID` 到记录的寻址多一次页内偏移计算；
- 风险：**所有权语义是内存安全边界**。改错就是数据竞争或读到被覆写的批次，而且不一定稳定复现。
  缓解见"决策"第 1 条的强制要求。

### 方案 C：方案 B ＋ 设置 `GOMEMLIMIT`

- 优点：可能把峰值再压一档；
- 代价与风险：R-057 第 4c.4 节实测 `GOMEMLIMIT` 有拐点且拐点位置随被扫卷规模移动，`400MiB` 在 RSS 与耗时
  上都劣于 `500MiB`。**在 churn 修复前设置软上限是掩盖症状并引入一个规模相关的失效点。**
  修复后重测才有意义，因此不在本 ADR 内决定。

## 决策

采纳方案 B。（2026-08-26 接受，按本文实施。）

### 1. 扫描器输出契约改为"仅回调期内有效"

`scan.BatchEmitter` 的语义从"转移所有权"改为：**切片及其中的 `string` 字段仅在回调返回前有效，
消费方必须在返回前复制出所需内容。** 扫描器按 worker 复用缓冲。

强制要求，不得省略：

- 缓冲**按 worker 分配**。emit 回调并发调用（实测并发 `2`），单一全局缓冲是数据竞争；
- 消费侧（`internal/application` 的 `enqueueBatch`）**不得**再把扫描器的切片送进 channel。
  必须先复制进自己拥有的批次缓冲；
- 新契约必须有一个**会在旧行为下失败**的测试：一个 emitter 保留切片、在下一批到达后读取，
  用 `-race` 跑；以及一个"复用后内容被覆写"的正向断言。没有这个测试不算实施完成。

### 2. 文件节点不再携带完整路径

- `scan.Node.Path` 对 `kind != "directory"` 的节点为空，`Name` 单独分配；
- **目录仍然携带路径**——walk 需要它来 `opendir`，`native.directories` 也需要它构造子项路径；
- 需要文件路径的调用方一律按 ID 回查存储（`memtree` 的 `path(id)` 已经从父链重建，这是现成能力）。

本条**加强 DDD 不变量 17**：文件节点在扫描流里结构性地不再携带路径，因此不可能拿一个流中节点去授权
文件操作。这与 `ProjectedEntry` 已有的设计一致。

### 3. 按节点 ID 索引的 map 一律改为稠密数组

节点 ID 由单一计数器分配（C 侧 `state->next_id`，根为 `1`），**稠密**，因此：

- 扫描器的 `native.directories` 与 `native.dirSizes` 改为"节点 ID → 目录序号"的 `[]int32` 索引
  加两个按序号紧凑排列的数组；
- 每批次的 `directoryDeltas` map 改为按 worker 复用的两个并行切片；
- **memtree 的记录表与名字 arena 改为分页**（固定大小的页，扩容只追加一页，永不复制）。
  本条**替代 ADR-0056 第 1 条的连续数组与增长策略，并移除本次实施引入的 `trim()`**：
  分页同时消除翻倍的累计副本与裁剪的整份复制，留存端的余量上限是一个半空页。

页大小必须是显式常量并有测试钉住，理由同 ADR-0056 对 `unsafe.Sizeof(record{})` 的处理：**它是内存预算，
改动必须是有意的。**

### 4. 不在本 ADR 内决定的事

- `GOMEMLIMIT` / `GOGC` 策略（理由见方案 C）；
- 应用层 `runScan` 的 `176.29 MB`（占比 `7.0%`，改动收益不足以承担风险）。

## 后果

- **收益（推算）**：扫描器 `1363.8 → ~170 MB`，memtree `946.4 → ~280 MB`，合计 `2530 → ~626 MB`。
  留存堆预期不变或略降（分页去掉 `trim` 的整份复制，余量上限一个半空页）；
- **代价**：`scan.BatchEmitter` 是跨三层的契约，所有实现与所有消费方必须同步修改；
  `memtree` 的每一处 `records[id]` 寻址变成页内寻址；
- **新约束**：任何新的批次消费方默认**不拥有**批次。这条必须写进 SDD，否则以后加消费方就会踩；
- **对门禁的影响，如实记录**：本 ADR **不承诺** ADR-0056 门禁 2 达成。留存堆 `258 MiB` 不变，
  而 `GOGC=100` 的定义就是堆涨到活跃量的 `2×` 才回收，即峰值堆约 `516 MiB`。
  门禁 2 写的"峰值/稳态 `<=1.2`"**在 `GOGC=100` 下由构造决定就达不到**，与 churn 多少无关。
  这是门禁本身的规格问题，见"后续工作"第 1 条。**不得**通过放宽数值来"达成"。

## 验收门禁

1. `go test ./... -race`、`go vet`、`tsc`、`vite build` 全通过；
2. **契约测试**：保留切片的 emitter 在 `-race` 下失败；缓冲复用后内容被覆写有正向断言；
3. **扫描期总分配量 `<= 800 MB`**（现状 `2530 MB`；推算 `~626 MB`，留 `28%` 余量）。
   口径：`/gc/heap/allocs:bytes`，真实 `/`，与 R-058 同机同法；
4. **留存堆不回退**：`<= 260 MiB`（现状 `257.8 MiB`）；
5. **峰值 footprint 报告值必须同时给出三个口径**（`ps rss`、`phys_footprint`、活跃堆），
   理由见 R-057 第 4c.5 节：不写口径的内存数字没有意义；
6. **可见终态不回退**：`<= 17s`（现状 `15.2s`，基线 `16.5s`），且在静默环境测量、
   未被权限对话框阻塞（R-057 第 4b 节的测量纪律）；
7. 目录覆盖率仍为 `100%`，ADR-0052 的两条恒等式仍精确成立。

## 文档同步

- **DDD**：不变量 17 下补一条结构性说明——文件节点在扫描流中不携带路径，操作必须按 ID 回查；
- **SDD**：重写 `scan.BatchEmitter` 的所有权语义（"仅回调期内有效"）与扫描器→应用层→存储的数据流；
  内存布局一节改为分页描述；
- **BASELINE**：更新分配量、峰值三口径、留存堆；
- **ADR-0056**：标注第 1 条被本 ADR 替代；
- **`docs/adr/README.md`**、**`docs/research/README.md`**：新增条目。

- 状态：Accepted

  | 门禁 | 结果 |

  | 1 测试 / `-race` / `vet` / `tsc` / `vite build` | 通过 |
  | 2 三条退出路径的还原断言 | 通过（去掉 `defer s.memoryLimiter.hold()()` 后三个子用例全部失败） |
  | 3 峰值 `phys_footprint` `<= 700 MiB`；峰值 `-` 稳态 `<= 350 MiB` | 通过：峰值 `486.2 / 487.8 / 526.8`，差值 `231.5 / 233.1 / 272.2` |

  | 7 覆盖率 `100%` 与 ADR-0052 恒等式 | 通过：`576777/576777`，`balance_gap = 0.00 GB` |

  三口径峰值：`ps rss` `532.4` / `phys_footprint` `487.8` / 活跃堆 `254.7 MiB`（各取三次中位数）。
  较本 ADR 之前：峰值 footprint `568.5 → 487.8 MiB`。

  **双峰**——四次约 `13.7s`，两次约 `20s`，后者超过门禁。这不是本 ADR 引入的：把
  `defer s.memoryLimiter.hold()()` 摘掉后同样跑六次，得到
  `13.528 / 13.635 / 13.733 / 14.408 / 20.240 / 20.370`，**同样双峰、同样 6 次里 2 次慢**。

  | | 中位数 | 慢模式 |
  | :-- | --: | :-- |
  | 限流器开 | `13.727s` | `2/6` |
  | 限流器关 | `13.983s` | `2/6` |

  这个 A/B 同时证实了两件事：自适应上限**没有可测的耗时代价**（比 R-059 §4.3 的单配置采样强得多，
  那里的耗时还是在采样循环下测的）；以及**测量环境存在一个约 `20s` 的慢模式，与本改动无关**。
  慢模式的成因未查明，列入后续工作第 5 条。在查明之前，门禁 6 按中位数判定为通过，
  但**不宣称它干净通过**。

  一处实现上的改进，优于本文第 1 条写的做法：上限在 `hold()` 里**立即应用一次**，而不是等第一个
  `100ms` tick。这让短于一个 tick 的扫描也运行在上限之下，并且让还原测试能区分"持有过又还原了"
  与"从未持有"——否则那条断言会平凡通过。R-059 §6 里"比轮询间隔更短的扫描拿不到任何调整"这条限制

## 背景

[ADR-0057](0057-扫描到装配的分配契约.md) 把扫描期分配量从 `2530 MB` 降到 `650 MiB`，峰值
`phys_footprint` 从 `1126 → 568 MiB`。**峰值门禁仍然不通过**，但原因换了，这一点在 ADR-0057 的实施状态里
已经指出并留给决策者裁决。

门禁写的是"稳态 `<=280 MiB`、峰值 `<=400 MiB`，且峰值/稳态 `<=1.2`"。R-059 验证了那个判断：
churn 降了 `74%` 而峰值/稳态**纹丝不动**，仍是 `2.2`。因为它不由 churn 决定——`GOGC=100` 的定义就是
堆涨到上一轮活跃量的 `2×` 才回收。**`<=1.2` 在 `GOGC=100` 下由构造决定就达不到。**

同时 R-059 重测了 R-057 §4c.4 里那个让 `GOMEMLIMIT` 被判定为"危险旋钮"的拐点：**它随 churn 一起消失了。**
所以这条路重新打开了，需要一并决定。

## 预研依据

R-059 的关键证据：

1. **比值是构造性的。** 留存堆 `255.3 MiB`、峰值 footprint `568.5 MiB`、比值 `2.2`，正是 `GOGC=100`
   的目标值加运行时开销。
2. **拐点消失。** churn `2478 MB` 时 `400MiB` 的峰值（`889.7`）**高于** `500MiB`（`797.1`）；
   churn `650 MiB` 后峰值随上限**单调下降**：`577.2 → 570.8 → 520.4 → 486.2 → 473.2`。
   代价只在 `300MiB` 出现（耗时 `+18%`），`400MiB` 及以上落在噪声带内。
3. **固定上限不安全。** 活跃集约 `92` 字节/节点，所以超过约 `4.3M` 节点的卷会顶穿 `400MiB`，
   上限落到活跃集之下。Go 把 GC CPU 封在 `50%`，那是退化不是死锁，但意味着**本机调好的固定值
   会在更大的盘上变成纯粹的性能损失**。
4. **自适应上限更好也更安全。** 同一探针各 3 次中位数：无上限 `549.0 MiB`、固定 `400MiB` `521.9`、
   `live + 100 MiB` **`499.5`**，耗时无可测代价。它把峰值与稳态的关系从**比例**变成**加法常数**。

一条影响结论可信度的方法学纠正，如实记录：自适应实验的第一版用
`/memory/classes/heap/objects:bytes` 当活跃集，**该指标含未清扫的死对象**，导致上限永远落在堆的当前
位置之上、四档 headroom 全部"无效果"，我差点据此判定方案不可行。正确指标是 `/gc/heap/live:bytes`。
同一个错误也解释了此前"扫描刚结束时留存堆 `434.9 MiB`、静置后 `256.7 MiB`"的异常——不是真的多留，
是指标选错。两处探针已改正，改后两个读数一致（`255.3 MiB`）。

## 方案（评估记录）

### 方案 A：只改门禁数值，不设上限

- 优点：零实现风险；
- 代价：峰值停在 `568 MiB`，是稳态的 `2.2` 倍；
- 风险：门禁变成"把线画到实测值之上"，失去约束力。而且**这个比例在更大的卷上照样是 `2×`**——
  一个 `10M` 节点的卷会峰值约 `1.8 GB`，门禁数值再改一次。

### 方案 B：固定 `GOMEMLIMIT = 400MiB`

- 优点：本机峰值 `521.9 MiB`，实现只是一行；
- 代价：无可测耗时代价（本机）；
- 风险：**只在活跃集低于 `400MiB` 时成立**。超过约 `4.3M` 节点就落到活跃集之下，退化为 `+18%` 耗时
  （R-059 §4.2 的 `300MiB` 行就是这个形态）而且拿不到任何峰值收益。这是一个**在别人的机器上会反向生效**
  的常量。

### 方案 C：扫描期自适应上限 `live + 100 MiB`（本 ADR 采纳）

- 优点：本机峰值 `499.5 MiB`（三种里最低），无可测耗时代价，且**在任何卷规模上都不会落到活跃集之下**；
  把峰值/稳态从比例变成加法常数，这才让门禁在不同卷上都有意义；
- 代价：一个每 `100ms` 轮询的 goroutine；`debug.SetMemoryLimit` 是进程全局的，必须在扫描结束还原；
- 风险：**`-9%` 是中等收益且有方差**（`459.0 / 499.5 / 516.3`）。采纳它的主要理由是规模安全性，
  不是这 `50 MiB`。规模安全性本身是**推理，不是实测**——只测了一个卷，见"后续工作"第 2 条。

## 决策

采纳方案 C，并按它重写门禁。（2026-08-26 接受，按本文实施。）

### 1. 扫描期自适应内存上限

扫描运行期间，每 `100ms` 读一次 `/gc/heap/live:bytes`，设
`debug.SetMemoryLimit(live + scanMemoryHeadroom)`，`scanMemoryHeadroom = 100 MiB`。

强制要求：

- **扫描结束（含取消与出错）必须还原为 `math.MaxInt64`**。这个旋钮是进程全局的，留下它会影响应用
  其余部分的 GC 行为。还原走 `defer`，不走正常返回路径；
- **不得读 `/memory/classes/heap/objects:bytes`**。它含未清扫的死对象，用它推出的上限等于没设上限。
  这条写进代码注释，因为它是一个会静默失效、且测起来"看着像没效果"的错误；
- **`scanMemoryHeadroom` 是内存预算，不是调参**。改它要有测量依据；
- 并发扫描时上限由最后一次写入决定。这是可接受的：所有扫描共享同一个堆，上限本来就该跟随全局活跃集。

### 2. 峰值门禁

替代 ADR-0055 门禁 4 与 ADR-0056 门禁 2 的峰值条款：

| 项 | 旧 | 新 | 依据 |
| :-- | --: | --: | :-- |
| 稳态留存堆 | `<=280 MiB` | `<=280 MiB`（不变） | 实测 `255.3`；数据下界 `92` 字节/节点 |
| 峰值 `phys_footprint` | `<=400 MiB` | **`<=700 MiB`** | 实测 `499.5`（自适应）/ `568.5`（无上限），留余量 |
| 峰值 / 稳态 | `<=1.2` | **改为加法：峰值 `-` 稳态 `<=350 MiB`** | 比例在 `GOGC=100` 下由构造决定，不可用作门禁 |

**为什么改成加法而不是换一个更大的比例**：比例门禁在更大的卷上会自动放宽（`10M` 节点的卷，`2×`
就是 `1.8 GB`），加法门禁不会。这正是方案 C 要建立的性质，门禁必须能验证它。

**报数口径**：峰值必须同时给出 `ps rss`、`phys_footprint`、`/gc/heap/live:bytes` 三个值
（R-057 §4c.5）。门禁判定用 `phys_footprint`——那是活动监视器和 macOS 内存压力系统用的口径。

## 后果

- **收益**：峰值 `568.5 → 499.5 MiB`（中位），且该余量在更大的卷上是常数而不是比例；
- **代价**：生产代码里多一个运行时旋钮和一个轮询 goroutine；
- **新约束**：任何在扫描期设置进程级运行时参数的代码，都必须在结束时还原，且还原走 `defer`；
- **门禁不再是"画在实测值上方的线"**：加法余量 `350 MiB` 对实测的 `244 MiB`（`499.5 - 255.3`）
  留 `43%`，对无上限的 `313 MiB` 留 `12%`。它能验证方案 C 是否真的生效——如果自适应上限被误删，
  峰值会回到 `2×` 稳态，在更大的卷上立刻越线。

## 验收门禁

1. `go test ./... -race`、`go vet`、`tsc`、`vite build` 全通过；
2. **还原测试**：扫描结束、取消、出错三条路径各有一个断言，检查 `debug.SetMemoryLimit` 已还原；
3. 峰值 `phys_footprint` `<= 700 MiB`，且峰值 `-` 稳态 `<= 350 MiB`，三口径同时报出；
4. 稳态留存堆 `<= 280 MiB`，口径 `/gc/heap/live:bytes`；
5. 扫描期总分配量不回退（ADR-0057 门禁 3 的 `<= 800 MB` 继续有效）；
6. 可见终态 `<= 17s`，在静默环境、不采样 RSS 的运行里测量；
7. 目录覆盖率 `100%`，ADR-0052 的两条恒等式仍精确成立。

## 后续工作

1. 实施后用**不采样**的运行测一次干净耗时，确认自适应上限没有可测的耗时代价——
   R-059 §4.3 的耗时是在采样循环下测的，只可横向比较；
2. **在一个明显更大的卷上验证规模安全性。** "固定上限会在超过约 `4.3M` 节点时反向生效"是由
   `92` 字节/节点外推得到的**推理**，没有实测过。这是采纳方案 C 的主要理由，理由本身还欠一次验证；
3. `scanMemoryHeadroom = 100 MiB` 只在本机一个卷上扫过 headroom（`100/150/200/300`）。
   `200` 以上无效果这个边界在别的规模上会移动；
4. 应用层 `runScan` 的 `topLevelDirectory`（按节点 ID 索引的 map，`44.26 MB`）仍未处理，
   继承自 ADR-0057 第 4 条；
5. **查明可见终态的约 `20s` 慢模式。** 六次里两次，与本改动无关（A/B 已证），成因未知。
   在查明之前，任何耗时门禁的判定都必须给出多次采样而不是单次数字，否则结论取决于运气。

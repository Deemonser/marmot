# ADR-0053：扫描进度条真实分母

- 状态：Accepted
- 实施状态：已实施并复测（2026-08-25）。实测曲线见 [R-054](../research/R-054-扫描进度条真实分母预研.md)
  第 3.6 节：偏差 `-0.116`–`+0.032`，`deep_scan` 全程在 `±0.105` 内，封顶 `0.959`，终态 `counted == bytes`
  （前置计数无重复）。

  两处实施中的记录：
  1. **条纹必须行进，同时必须固定 `background-size`**。第 2 条"条纹动画"的表述是对的——原版实测是
     蓝白相间的斜条纹持续行进，整体进度不前进时纹样也在走。实施中先撞到一个陷阱：斜向
     `repeating-linear-gradient` 若不给 `background-size`，渐变会按元素盒铺开，相位随盒宽变化，宽度每变
     一次（5 Hz）整个纹样横向平移，条纹蠕动。**错误的修法是去掉倾斜或去掉动画**（本 ADR 曾一度如此实施，
     已纠正）；正确的修法是把 `background-size` 固定为纹样的水平周期（`105deg` 下为 `6px / sin(105°)
     = 6.21px`），纹样即以左边缘为原点平铺、与宽度无关，行进完全由 `background-position` 提供。
  2. 第一轮实施漏接 `countedBytesLocked`，UI 上进度条恒为空而分母正常。只有端到端采样 UI 实际收到的
     字段才能发现（R-054 第 3.6 节）。
- 日期：2026-08-25
- 相关预研：[R-054](../research/R-054-扫描进度条真实分母预研.md)

## 背景

原版扫描时显示有进度的条；我们显示不确定条。此前不做进度是因为没有可信分母，
[ADR-0027](0027-DaisyDisk扫描中窗口状态边界.md) 第 4 条与
[ADR-0050](0050-扫描中源页反馈与原版一致.md) 第 3 条据此禁止显示百分比。

[ADR-0052](0052-空间数值口径与卷组覆盖对齐.md) 之后前提变了：快照在创建时就记录了卷的容量/已用/可用，
分母成为**有实测出处、随快照存下来的真实值**。R-054 以它为分母实测了整条曲线：单调，与挂钟偏差
`<=12` 个百分点，封顶 `95.9%`；若不把卷组辅助卷做前置计数，末尾会有 `12` 个点的可见跳变。

R-054 还解开了 R-051 第 5 节那个悬案：原版的条纹段占轨道 `36%`，**条纹是"正在扫描"的质感、宽度是真实
进度**，两者不是二选一。

## 方案

### 方案 A：确定进度 + 条纹填充，前置计入辅助卷（采用）

轨道填充宽度 = `(卷组辅助卷已用 + 已遍历字节) / 卷已用`，填充仍是动画条纹。

- 优点：与原版的观感和信息量都一致；偏差 `<=12` 点、单调，能支撑"还要等多久"；末尾跳变从 `12` 点降到
  `4` 点；分子分母都有实测出处；
- 代价：封顶 `95.9%`，靠终态补满；`catalog` 阶段条不动。

### 方案 B：维持不确定条（拒绝）

前提已不成立。继续不做等于把一个已有的真实信号丢掉。

### 方案 C：分母扣掉预估的隐藏空间，让条走满 100%（拒绝）

隐藏空间只有树总量确定后才算得出来。扫描期扣一个估计值就是编数字——正是 ADR-0027 要防的那件事。

### 方案 D：按节点数做分母（拒绝）

节点总数没有任何先验来源。

## 决策

### 1. 扫描中的进度条是确定进度

填充宽度 = `已统计字节 / 卷已用字节`，其中：

- **分母**：快照在 `CreateSnapshot` 时记录的卷已用字节（ADR-0052 §4）。该值不可用时（旧快照、非 APFS、
  权限不足）**退回不确定条**，不得用任何其他数猜。
- **分子**：`卷组辅助卷的 statfs 已用之和`（扫描开始前已知）`+ 已遍历字节`。辅助卷必须**前置计入**，
  否则末尾有 `12` 个点的跳变（R-054 §3.2/3.3）。
- 前置计数**不得重复计入最终总量**：辅助卷在枚举结束后挂上时，其字节已经在计数里。

### 2. 填充是条纹，宽度是进度

条纹动画表示"正在扫描"，宽度表示真实进度。两者同时存在，这是原版的形态（R-054 §3.5）。终态后条纹停止。

### 3. 封顶与补满

进度条封顶在 `已统计 / 已用`（本机实测 `95.9%`），缺口是 `hidden_space`，扫描期不可预知。
**只有进入终态才补满到 100%**，不得在扫描期用任何方式凑到 100%。

### 4. 口径必须可核对，不得伪造总量

- `aria-valuemin/valuemax/valuenow` 只在分母可用时设置；`aria-valuetext` 必须写明口径是
  "已统计占卷已用"，不是"完成度"；
- 分母不可用时不设 `aria-valuenow`，只给 `aria-valuetext`；
- 仍然禁止用容器容量、节点数或任何无实测出处的数推算百分比。ADR-0027 第 4 条的**原则**保留，
  措辞由"总量未知只能显示不确定进度"改为"必须有实测出处的真实比值"。

### 5. `catalog` 阶段的表现

该阶段没有遍历字节，进度条停在前置计数对应的位置（本机约 `8%`）。这是真实的：那部分空间确实已经统计。
不得为了"看起来在动"而让条自行爬升。

### 6. 不变边界

- ADR-0050 的其余各条不变：扫描中源页仍然只显示卷行、进度条、`扫描中…` 和 `取消`，**不显示计数、阶段、
  占用、已用时**；本 ADR 只把"不确定条"改成"确定条"；
- 进度事件仍限频 5 Hz，仍不触发用户可见的 Map 查询（ADR-0027 §4 的这部分不变）；
- 窗口骨架与高度不变（ADR-0050 §4）。

## 后果

正面后果：

- 扫描中能看出还要等多久，与原版信息量一致；
- 条纹 + 真实宽度同时复刻，R-051 的悬案闭环。

代价和风险：

- 偏差最大约 `12` 个百分点，且在 `t≈70%` 处**高估**进度（`0.798` 对 `0.70`），用户可能觉得最后一段变慢。
  这是真实数据的形状，不做平滑——平滑就是编数字；
- 封顶 `95.9%` 后有一次 `4` 点的补满跳变；
- 分母来自扫描开始那一刻。磁盘在扫描期间剧烈变化时，进度会带上这段漂移；
- 单机单次样本，其他机器的偏差范围未知（R-054 §5）。

## 验收门禁

1. 前端 `tsc`、`vite build`、全仓 Go 测试与 `go vet` 通过；
2. 分母不可用时退回不确定条，且不设 `aria-valuenow`；
3. 分子的前置计数不重复计入最终总量：扫描后的 `bytes` 汇总必须与 ADR-0052 的恒等式一致
   （`Σ根层子项 = 卷已用`），由既有测试覆盖；
4. 扫描中源页仍不出现计数/阶段/占用/已用时的可见文本（ADR-0050 §1 回归不破）；
5. 真实 `/` 复测一次曲线，记录偏差范围与封顶值；若偏差显著大于 R-054 的 `12` 点，必须如实记录。

## 修订（2026-09-01，R-067 §2.4）

§1 的分母升级为**上一次完成扫描的最终统计字节**，statfs 卷已用降为无历史时的一次性退路。

原分母（卷已用）与分子（lstat 分配字节)不同口径：卷已用含 purgeable、本地快照与容器开销，
分子看不见它们，两边天然差 ~6%。这个差先后以两种症状出现——分子虚高时条提前撞满 100%
干等数秒（预计数里混入了遍历永远到不了的嵌套挂载卷，见 R-067 §2.3 第三轮）；
虚高修掉后条只能爬到 ~94% 就跳进结果页。**任何保留口径差的修法都只能在这两种症状之间摇摆。**

与分子同口径的数只有一个：上一次遍历自己数出来的终值。同一块盘两次扫描之间总量变化通常
不足 1%，实测（R-067 §2.4）：第二次扫描 UI 分数单调爬升，走完前 0.43s 才过 99%，
终态恰为 1.000，由终止事件补满。

- 历史值存 `~/Library/Application Support/marmot/scan-totals.json`（明文 JSON，按根路径一条；
  非秘密，不进加密凭据文件）；损坏或缺失读作"无历史"，退回卷已用，不得报错；
- 只有 `completed` / `completed_with_issues` 记账——取消或失败的遍历数得比真相少，不许教学；
- 自上次扫描以来磁盘增长会让学习分母被超出：这是真实数据不是记账错误，由前端 99% 封顶吸收
  （§3 不变：只有终态可以补满），不定条兜底只对 statfs 退路生效；
- 方案 D 当年拒绝"节点数分母"的理由是"没有任何先验来源"——上一次运行如今就是先验来源，
  该理由对字节口径不再成立，对节点数仍成立（字节才是用户看的量纲）。

## 修订（2026-09-03，尾部停滞：字节与节点各半）

使用方反馈一次 25.9s 的扫描"快结束时一直在等待"。日志与历史值核对：上次终值 `192.0 GB`，本次终值
`198.0 GB`，分子到 `190.1 GB` 时条已到 99% 封顶，之后的 `7.9 GB`（本次字节的 4%）以及其后所有文件都在
封顶状态下走完。更根本的原因是**遍历是广度优先**：目录队列先进先出，大文件在中层就被计入，队尾是最深处
文件多、字节少的目录（`node_modules`、缓存、`.git` 对象）——按字节的进度在这一段几乎不动，而节点数仍在
快速上升。字节分母无论怎么修余量，都改不了"尾部字节稀疏"这个结构。

因此把上一条修订里"对节点数仍成立"的判断再往前推一步：**上一次运行同样是节点数的先验来源**。

1. `ScanTotals` 记录上次完成扫描的**字节与节点两个终值**（`scan-totals.json` 由裸数字改为
   `{"bytes","nodes"}` 对象；旧格式按"只有字节"读取，不算无历史）。
2. 两个终值都在时，进度 = `(min(1, 已统计字节/上次字节) + min(1, 已计节点/上次节点)) / 2`；先各自封 1
   再平均，任一口径超出都不能掩盖另一口径。只有字节历史时退回字节；无历史时退回 statfs，不变。
3. §4 "禁止用节点数推算百分比"改为"禁止用**没有实测出处**的节点数"：上一次遍历的终值有出处。
   `aria-valuetext` 必须写明"按上次扫描的字节与项数各半"，`aria-valuenow/max` 改为 0–100 的复合分数。
4. §3 不变：仍封顶 99%，只有终态补满。
5. 扫描运行中每 2s 写一行进度日志（用时、阶段、节点/文件/字节、两个口径的百分比），使"慢在哪一段"可以事后读出，
   而不是只有一行总结。

拒绝的替代：给分母加 3% 余量。使用方明确不要——它只是把封顶时刻往后挪，不改变尾部字节稀疏的结构。

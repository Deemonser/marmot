# ADR-0067：清理建议的事实与结论分层

- 状态：**Accepted**（2026-09-03 使用方对分析结论答复「很好，那就按照你的来」）
- 日期：2026-09-03
- 相关预研：[R-069](../research/R-069-清理判定的事实与结论分层预研.md)；
  依据 [R-063 §3.5](../research/R-063-AI建议稳定性与准确率基线预研.md) 的漂移数据（风险 `8/20`、恢复性 `1/20`）
  与 §4b 的干扰度公式。
- 关系：**扩展 [ADR-0061](0061-AI清理建议边界与证据装配.md) §7**（结果校验）——校验不再检查模型的 `risk`，
  因为模型不再输出它。不修改 ADR-0061 §1"建议不是授权"、[ADR-0063](0063-直接删除与不可恢复守卫的硬边界.md) 的删除链、
  [SDD §14.5d](../SDD.md) 的自动放入判据（`autoStageable` 一字不改，但 `safe` 的来源变了）。

## 背景

R-063 把判定主轴换了三次：风险 → 可恢复性 → 干扰度。每次换轴都对，但实现是叠加的：`Recommendation.Risk`
同时被规则声明、项目活跃度、三种护栏和模型主张写入，在三处代码里各写一部分，没有一处看得到全部事实。
用户看到一个 `需确认`，分不清是"泛规则拿不准"、"项目正在用"、"疑似登录态"还是"模型拿不准"。

同时，模型仍在输出 `risk`。R-063 已证明模型对"能不能回来"稳定（漂移 `1/20`）、对"危不危险"不稳定（`8/20`），
并且已经用"选择挪到程序侧"解决了覆盖稳定性。`risk` 是同一手法尚未用到的最后一个字段。

## 预研依据

R-069 §4.3 列出了 `Risk` 的三个写入点；§4.1 量了一个准备补的活跃度信号（属主应用）并否掉了它；
§4.2 论证了缓存自身年龄可作为应用缓存的活跃度信号，方向保守。

## 方案

### 方案 A：维持现状，在提示词里再强调风险标准

R-063 §3.1 已证明提示词措辞不改变漂移。被拒绝。

### 方案 B：合成单一"清理分数"

把恢复代价、活跃度、体积加权成一个数排序。分数把原因藏起来，而 R-063 三次换轴恰恰证明每个维度对用户意义不同。
被拒绝。

### 方案 C：事实与结论分层（采用）

见"决策"。

## 决策

### 1. 风险等级是推导出来的结论，不是输入

领域层新增 `Facts` 与 `Assess(Facts) Assessment`：

```text
Facts:
  Recovery      规则声明或模型主张，经护栏纠正后的值
  Declared      规则作者声明的基线风险；模型来源为空
  Source        rule | advisor
  Confidence    规则：Generic 报 0.7，其余 1；模型自报
  Activity      none | project_source | artifact_age | generation
  IdleDays      活跃度信号的天数
  Guards        命中的护栏码：user_content / repository / … / login_state / partial_install
  Generic       泛规则命中：规则声明自己只认识容器、认不出对象（Library/Caches/* 这类）

Assessment:
  Risk          safe | review | risky
  Reasons       机器码列表，UI 用它解释等级
  Note          前置到 what_breaks 的一句活跃度说明，可为空
```

推导顺序固定：

1. 不可恢复，理由 `irreplaceable`：护栏命中或模型主张 `irreplaceable` → `risky`；
   规则声明 `irreplaceable` → 取规则声明的等级、且不低于 `review`（目录作者知道它是永久的并据此选了等级：
   清空废纸篓是 `review`，删设备备份是 `risky`；这与 ADR-0067 之前的输出一致）。
2. 登录态护栏 → `risky`，理由 `login_state`。
3. 否则从基线出发：规则取 `Declared`；模型取 `redownloadable → review`、
   `regenerable 且 confidence ≥ 0.8 → safe`、其余 `review`。
4. 活跃度：`project_source` 且 ≤ 30 天：`safe → review`，理由 `project_active`；≥ 180 天：`review → safe`，
   理由 `project_dormant`——但模型置信度 < 0.8 时**不放宽**：停摆说明字节不会被想起，说明不了字节是什么。
   `artifact_age` ≥ 180 天：`review → safe`，理由 `cache_cold`；热缓存**不**抬高。
   `generation`：等级不变，理由 `generation_superseded`。
5. `partial_install` 护栏是**下限**，在活跃度之后施加：`safe → review`，且去掉活跃度那句说明——
   "下一次构建要重新下载"与"不会自动重新下载"不能并排出现。
6. 模型来源落在 `review` 时补理由 `redownload_cost` / `advisor_uncertain`；泛规则补 `generic_rule`；
   规则声明就是 `review`/`risky` 且没有别的理由时补 `catalog`。

证据包的折叠（ADR-0061 §2b，SDD §14.5c-1）按**推导后**的等级判"整块 safe"，不按规则声明：
活跃项目里的 `target/debug` 声明 safe、结论 review，正是使用者想从里面挑的地方，不能折起来。

规则建议**不**带位置护栏（`GuardsFor` 只用于模型主张）。位置护栏的作用是拦住模型认错对象——
它把 `~/Documents` 下的一切都视为用户内容；规则已经精确命名了对象，`~/Documents` 里项目的 `__pycache__`
仍然是字节码，套上护栏会让放在 Documents 里的每个项目的构建产物全部变成 `risky`。

规则来源与模型来源共用这一个函数。`irreplaceable` 绝不配 `safe` 由结构保证，不再靠校验。

### 2. 模型不再输出 `risk`

提示词的输出契约删掉 `risk` 字段与相关硬性规则。`Validate` 对仍带该字段的回复忽略而非拒绝。
模型只报事实：`recovery`、`category`、`confidence`、`evidence`、`what_breaks`、`how_to_restore`。
风险漂移由此结构性归零；剩下能漂的只有恢复性（`1/20`）与置信度。

### 3. 应用缓存拿到活跃度信号

`Rule.AgeSensitive` 标记应用缓存类规则（`用户缓存`、`沙盒应用缓存`、`应用组缓存`）。信号取缓存自身的
`NewestModified`：应用运行就会写缓存，180 天没写过就是没在用。只放宽不抬高，见 R-069 §4.2。
属主应用信号（是否已卸载、多久没打开）经 R-069 §4.1 实测不进本轮。

### 4. 泛规则如实报告置信度

规则 `Confidence` 不再恒为 1：标记 `Generic` 的容器规则（`用户缓存`、`沙盒应用缓存`、`应用组缓存`、`用户日志`
与两条根级 Manual 规则）报 0.7，并给出理由 `generic_rule`；其余规则命名了自己的对象，报 1。
`Generic` 由目录作者声明而不是按段数推断：`**/node_modules` 只有一段却精确命名了对象，按段数会算反。
数字进入 DTO；UI 对规则仍显示规则名，理由码以标签呈现。

### 5. 理由到达用户

`AdviceItem` 新增 `riskReasons`、`activity`、`idleDays`。待确认区每行的风险标签之后跟理由标签；
展开详情有"判定依据"一行。

## 后果

- 规则层输出在无活跃度信号时逐字不变（含三条声明 `irreplaceable / review` 的规则）；
  有信号时与旧 `AdjustForProjectActivity` 等价。这是回归测试的断言。
- 冷缓存（≥ 180 天）从 `review` 变 `safe`，会被 §14.5d 自动放入收集区。这是有意的：它满足 `safe` 的定义
  （应用自行重建、不含用户原创数据），此前停在 `review` 只因为规则作者不知道这个应用是否在用。
- 模型输出契约变化：既有 fixture 与探针里的 `risk` 字段被忽略。R-063 的风险漂移探针继续运行，
  但它测的东西变了：等级只随 `recovery` 与 `confidence` 跨过 0.8 阈值而变，所以读数的上界是恢复性漂移
  加上置信度在阈值两侧摆动的次数，不再是模型对"危不危险"的独立判断。
- 新增两条规则 `Downloads/*.dmg`、`Downloads/*.pkg`（≥ 30 天，`redownloadable / review`），只匹配文件节点
  （`Rule.FileOnly`，`MatchContext.Kind`）。年龄取文件 mtime，`curl -R` / `wget` 保留服务器时间戳时会把新下载
  当成旧的，代价是多一行 `review`，不是错的恢复性声明。
- 第二轮（深挖）的模型建议也拿到项目活跃度：展开包以区域为根，区域之上的项目根不在包里，
  区域内查不到项目的节点继承第一轮对该区域的答案。

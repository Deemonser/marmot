# ADR-0020 APFS 卷组与产品存储源映射

状态：Accepted

日期：2026-08-21

## 背景

ADR-0019 正确锁定了 APFS System/Data 的扫描边界和容量口径，但其“卷入口”被实现为技术卷一对一
展示，导致用户看到 `Macintosh HD` 和 `Macintosh HD - Data` 两个磁盘。技术事实与产品入口缺少
明确的映射层。

## 依据

- [R-018 APFS 卷组与产品存储源映射](../research/R-018-APFS卷组与产品存储源映射.md)
- [R-017 macOS APFS 卷组与全盘容量语义](../research/R-017-macOS_APFS卷组与全盘容量语义.md)
- [ADR-0019 macOS APFS 卷组与全盘容量语义](0019-macOS_APFS卷组与全盘容量语义.md)
- [ADR-0016 DaisyDisk 原生交互状态模型](0016-DaisyDisk原生交互状态模型.md)

## 决策

### 1. 分离技术事实与产品读模型

- Platform 的 `Volume` 表示 `APFSVolume`，必须保留挂载点、角色、卷自身容量、容器身份和卷组身份。
- Application 新增 `StorageSource` 投影，代表用户启动页的一个存储入口。
- Wails 和前端使用 StorageSource 查询，不直接把 Platform 技术卷列表渲染为磁盘入口。

### 2. 只按明确卷组身份分组

- 相同且非空的 `APFSVolumeGroupID` 生成一个 StorageSource。
- 主卷组的默认路径是 `/`；Data 作为成员明细。
- 没有卷组身份的外部卷保持独立；禁止按名称、路径或容量推断关系。
- `system_auxiliary` 不作为主 StorageSource，但保留在 Platform 事实层。

### 3. 保留扫描边界

StorageSource 的产品聚合不改变 `ScanScope`。默认扫描仍只扫描 `/` 的逻辑命名空间，扫描器继续跳过
嵌套 Data 挂载点；显式 Data 路径仍是独立高级范围。

### 4. 保留容量口径

- `StorageVolumeMember` 保留每个技术卷的 `volume_used` 等明细。
- APFS 卷组 StorageSource 使用 `container_total` 和 `container_used` 作为入口容量。
- 不把 System/Data 的两个 `volume_used` 相加，也不把 StorageSource 容量当作空间图
  `owned_allocated`。

## 被拒绝方案

- 仅在前端通过路径隐藏 Data：无法验证卷组身份，违反分层边界。
- 在 Platform 直接返回合并卷：丢失技术边界和独立 ScanScope 能力。
- 通过 `container_id` 合并所有同容器卷：同一容器可能包含多个独立用户卷，身份不足。

## 后果

- `ports.Volume` 增加 `container_id`、`volume_group_id` 和 `role` 技术字段。
- Platform 的 `diskutil` plist 解析增加 `APFSContainerReference` 和 `APFSVolumeGroupID`。
- Application 增加 StorageSource 分组和产品容量投影。
- Wails 绑定从 `GetVolumes` 切换为 `GetStorageSources`；前端启动页只显示产品入口。
- 现有扫描、快照、清理、权限和安全边界不变。

## 验收标准

1. 当前机器的 System/Data 只生成一个 `Macintosh HD` StorageSource。
2. 同一 StorageSource 的入口容量使用容器口径，成员明细保留卷自身口径。
3. 外部卷不因共享容器或相似名称被错误合并。
4. 根扫描和显式 Data 扫描边界测试继续通过。
5. Go、前端构建、Wails 绑定生成和 macOS 真实卷目录验证通过。

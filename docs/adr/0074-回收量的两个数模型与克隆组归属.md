  **代码审查后的两处修正（2026-09-10）**：

  1. **旧内核降级**（严重）。三个扩展属性是无条件请求的，而 `ATTR_CMNEXT_CLONE_REFCNT (0x1000)` 是最新的一位，
     应用最低支持 macOS 12——旧内核按自己的 `ATTR_CMNEXT_VALIDMASK` 校验 `forkattr`，超出即整调用失败，
     那样**每个目录都读不到、扫描结果是空树**。加了运行时降级：读到拒绝就永久放弃克隆属性并重试，
     每个在途读者各自重试一次（不是只让某一个线程重试，否则其余线程会丢掉自己的目录）。
     用一个当前内核也不认识的位（`0x2000`）模拟旧内核实测：**修之前 4,421 节点 → 1 节点（空树）；修之后 4,421 节点，与真实内核一致**。
     顺带测出内核返回的是 **ERANGE (34) 而不是 EINVAL**——原先只判 EINVAL 等于没有降级，两者现在都算拒绝。
     降级后克隆身份不可得，一对克隆各报 `Bytes 0 / SharedExcluded 全额`：**少报，不会多报**，方向符合决策 2。
     `scanner.CloneFactsAvailable()` 暴露这一状态，夹具测试据此断言降级后的保守答案而不是跳过。
  2. **建议总量的集合语义**。`Advice.TotalBytes` 原先是逐条相加，违反决策 2：两条建议各持克隆对的一半时，
     逐条各为 0、加起来还是 0，而收集区对同一批算出全额——同一份数据两个界面两个答案。改为对全部建议节点
     一次性问 `Reclaimable`；新增 `TotalUpperBound / TotalSharedExcluded / TotalUnknown`，未知不再被静默计入。
     `internal/application/advice_total_test.go` 覆盖三种情形（克隆对、含未知、store 不作答时退回 allocated）。

## 背景

收集区徽标显示"选中对象一共能释放多少"，算法是把每个条目的 `ownedAllocated` 直接求和（`App.tsx:1804`）。
这个数在 APFS 上会错，方向都是**高估**——R-076 §10.2 在本机实测：

| 场景 | 徽标承诺 | 删除后卷可用空间实际变化 |
| --- | --- | --- |
| 一对克隆（`cp -c`），两个都收集 | 16,384 KB | 第一个 `−32 KB`（无回收），第二个 `+8,192 KB`；**整整 2 倍** |
| 一对硬链接，只收集记账方 | 8,192 KB | **0 KB** |

原因有两层。扫描器对硬链接做"先到先得"折叠（`native_darwin.go:1098`）：同 `(device, inode)` 的第二条 `OwnedAllocated = 0`，
第一条记满额——所以只收第一条就承诺了一份别人还在用的空间。克隆完全没进这条逻辑：克隆的 `linkCount` 是 1，两份各自记满额。

这不是新发现。R-065 §2 已用 Preboot 里 342 MB 私有 0 的文件确认了双计"量级很大"；§2.1 试过把 `allocated` 换成
`ATTR_CMNEXT_PRIVATESIZE`，Preboot 从 45.7 GB 变成 3.77 GB 而 `df` 说 17 GB——**2.5 倍高估换成 4.5 倍低估**，已回退。
它给出的正确方向是"两个数分开"，并明说"这是一个设计决定，需要 ADR 与迁移，不是一次补丁"。本 ADR 就是那个 ADR。

有两件事让它现在能做而当时不能：

1. **属性已经在读了**。原生扫描的 bulk 请求带 `forkattr = ATTR_CMNEXT_PRIVATESIZE`，调用处传 `FSOPT_ATTR_CMN_EXTENDED`
   （`native_darwin.go:318, 479`），每条记录都拿到了私有大小，然后在 `:1041` 处 `_ = entry.has_private` 丢弃。
   代价为零——扫描已经在付这份钱。
2. **私有大小的语义量清楚了**。R-076 §10.2 实测：一对克隆的**两个成员私有大小都是 0**。这个值本身是对的
   （单独删任何一个确实回收 0），但它意味着"把私有大小当求和项"在整组都被收集时会**低估**成 0。
   正确的口径必须按**组**算：一组共享同一份数据的对象，共享区段只计一次，且只有整组都被收集时才计。

## 预研依据

- R-065 §2：克隆双计存在且量级大；§2.1：替换主口径失败的三条理由（两个问题混成一个；封印系统卷每个文件私有大小都是 0，
  整个 macOS 会显示成 0 GB；扩展属性在系统快照卷上不返回，同一棵树被两种方式量）；§2.2：无法归属的共享块应进"隐藏空间"平衡项。
- R-076 §10.2：收集区端到端复现（承诺 vs `df` 实际变化）；硬链接记账方一侧的高估；私有大小对克隆对两侧都为 0。
  探针 `internal/probe/hardlink_attribution_probe_test.go`、`clone_probe_test.go`。
- R-053 / ADR-0052：原版跟踪的也是 `allocated`，空间图口径不动。
- `sys/attr.h`：`ATTR_CMNEXT_PRIVATESIZE (0x08)`、`ATTR_CMNEXT_CLONEID (0x100)`、`ATTR_CMNEXT_EXT_FLAGS (0x200)`、
  `ATTR_CMNEXT_CLONE_REFCNT (0x1000)`，均属 `forkattr` 扩展组，随同一次 `getattrlistbulk` 返回；
  `VOL_CAP_FMT_CLONE_MAPPING` 标识卷是否支持完整克隆跟踪。

## 方案

### 方案 A：两个数，扫描期采集，按组归属（采用）

每个节点保留两个口径：

- `allocated`（现有 `OwnedAllocated`）：这东西占多少地方。空间图、列表、总量用它。**不变。**
- `reclaimable`：把它删了能拿回多少。**只**给收集区徽标、清理计划和建议层用。

`reclaimable` 的定义（对一个被收集的**集合** S，不是对单个对象）：

```
reclaimable(S) = Σ private(f)  对 S 内每个文件 f
              + Σ shared(g)   对每个共享组 g，当且仅当 g 的全部成员都在 S 内
```

共享组有两种，判据都来自扫描已有或同一调用可得的属性：

| 组 | 成员判据 | 组的大小 | 共享区段 |
| --- | --- | --- | --- |
| 硬链接组 | 同 `(device, inode)` | `ATTR_FILE_LINKCOUNT`（已有） | 该 inode 的 `allocated`，`private` 视为 0 |
| 克隆组 | 同 `ATTR_CMNEXT_CLONEID`（新增请求） | `ATTR_CMNEXT_CLONE_REFCNT`（新增请求） | `allocated − private`，取组内任一成员 |

"全部成员都在 S 内"用组大小判定，不靠扫描时是否见过所有成员：硬链接的另一条可能在扫描边界外，
克隆的另一半可能在别的卷或别的目录——只要收集的成员数小于组大小，共享区段就不计。这正是 ADR-0008 说的
"不依赖并发扫描顺序"，且比"先到先得"保守。

**采集**：扫描期把 `private_size` 从丢弃改为记录；新增请求 `CLONEID` 与 `CLONE_REFCNT`（同一 bulk 调用）。
存储用**旁表**而不是扩记录：记录表是 64 B 定长、`TestRecordStaysPacked` 钉死、ADR-0058 有稳态 `<= 280 MiB` 门禁；
私有大小 ≠ allocated 的文件与 refcount > 1 的克隆成员是少数，旁表按节点 ID 键只存这些例外。
目录上滚一个 `ownedReclaimable`（私有之和，不含共享），同样进旁表或复用现有目录尺寸结构——由实现切片按门禁选。

**未知的处理**：R-065 §2.1 第 3 条——封印系统快照卷上扩展属性不返回。属性缺失的文件 `reclaimable` 标 **未知**，
集合含未知成员时徽标显示 `≤ allocated`（上界）而不是一个假装精确的数。这些对象几乎都在 `/System` 下，
守卫本来就不让收集，实际影响很小，但口径必须诚实。

**归属展示**：树上不再需要为克隆选"唯一归属节点"——空间图按 `allocated` 画，两份克隆各画各的，这是 ADR-0052 的口径；
"共享了多少"由 `reclaimable` 回答。ADR-0008 那句"按稳定的卷内规范路径选择唯一归属节点"因此**只对硬链接的
`allocated` 折叠**有意义，本 ADR 不改那处的先到先得（R-076 §10.2 实测 12/12 稳定，未观察到漂移），
只让它不再影响回收量。

优点：属性零成本；收集区数字变准；硬链接与克隆用同一套组语义；不动空间图。
代价：旁表内存（待量）；`CLONEID` / `CLONE_REFCNT` 每条记录多 16 B 的 bulk 传输（同一调用，预期不可测）；
收集区求和从 `reduce` 变成按组去重。
风险：旁表在克隆密集的开发机上可能不小（`node_modules` 里包管理器大量用克隆）——所以有门禁。

### 方案 B：收集时按需读（备选）

不改扫描，收集区对已选对象及其子树用 `getattrlistbulk` 现场读 `PRIVATESIZE` / `CLONEID` / `CLONE_REFCNT`。

优点：扫描热路径和内存完全不动。
代价：一个 50 万文件的 `node_modules` 被拖进收集区要重读整棵子树（R-072：25k–207k 节点 0.5–1.4 s），
徽标要异步、要有"计算中"；跨条目的组完整性判断也要等所有条目读完。
用途：作为方案 A 门禁不通过时的退路，或作为"未知"成员的按需补读。

### 方案 C：维持现状，只改文案（拒绝）

DDD 37b 说文案不得暗示"删除即可释放这么多"，可徽标就是那个数。改文案不改数，是把错误藏进措辞。

## 决策

1. **两个数。** `allocated` 供空间图，不变；新增 `reclaimable` 供收集区、清理计划与建议层。两者不得互相替代
   （这是 R-065 §2.1 第 1 条，也是 ADR-0052 方案 B 被拒的原因）。
2. **按组归属。** `reclaimable` 对集合定义：私有之和，加上**整组都在集合内**的共享区段。硬链接组以 `(device, inode)` +
   `LINKCOUNT` 判定，克隆组以 `CLONEID` + `CLONE_REFCNT` 判定。组不完整就不计共享区段——宁可少报。
3. **扫描期采集，旁表存储。** `private_size` 不再丢弃；新增请求 `ATTR_CMNEXT_CLONEID | ATTR_CMNEXT_CLONE_REFCNT`。
   记录表 64 B 不动；例外进旁表。
4. **未知必须可见。** 属性缺失的对象 `reclaimable` 为未知；含未知成员的集合显示上界 `≤ N`，不显示精确数。
5. **收集区求和换算法。** `collectorBytes` 从逐条 `reduce` 改为：先按组归并，再套第 2 条公式。徽标、倒计时文案、
   删除后"已释放"汇总三处口径一致。
6. **建议层的"可回收字节"改用 `reclaimable`**（ADR-0061 §7 第 4 条），未知时退回 `owned_allocated` 并在事实里标注。
7. **硬链接的 `allocated` 折叠不动。** 先到先得保留，只影响画图，不再影响回收量。

### 门禁

| # | 门禁 | 通过标准 |
| --- | --- | --- |
| 1 | 稳态内存（ADR-0058 门禁 4） | 旁表计入后仍 `<= 280 MiB`；否则退方案 B |
| 2 | 纯扫描耗时 | 三次中位数不超过基线 `+ 2%`（新增两个属性走同一调用） |
| 3 | 克隆对复现（R-076 §10.2 夹具） | 收一个 → 徽标 0；收两个 → 徽标 8 MB；`df` 差值一致 |
| 4 | 硬链接对复现 | 只收记账方 → 徽标 0；两条都收 → 8 MB |
| 5 | 封印卷 / 旧内核 | 属性缺失的对象 `reclaimable` 为未知，不是 0 也不是满额；内核整体拒绝克隆属性时降级为"无克隆身份"，一对克隆少报而非多报 |
| 6 | 空间图不变 | 根层总量、`hidden_space`、任意目录的 `allocated` 与改动前逐字节相同 |

## 后果

- 收集区的数字从"高估"变成"准确或诚实的上界"。用户第一次会看到"收集了两个 8 MB 的克隆，徽标只显示 8 MB"，
  这需要一行说明（"其中 8 MB 与未收集的对象共享"）——R-065 §2.2 的"隐藏空间"文案更新一并做。
- 建议层拿到正确的可回收字节后，"删了能省多少"的排序会变——克隆密集的目录会掉下去，这是对的。
- 新增约束：任何显示"释放 / 回收 / 拿回"字样的数字必须来自 `reclaimable`；任何显示"占用 / 大小"的数字必须来自 `allocated`。
  两个词不许混用。
- ADR-0008 "唯一归属节点"的条款收窄为只针对硬链接的 `allocated` 折叠。

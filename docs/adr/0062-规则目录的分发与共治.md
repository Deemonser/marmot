# ADR-0062：规则目录的分发与共治

- 状态：**Proposed**——本 ADR 未经使用方确认，不能作为实施依据。
  §决策 5 与 §决策 8.1 各含一个需要使用方拍板的取舍，已单独标出。
- 日期：2026-08-28
- 相关预研：[R-062](../research/R-062-AI清理建议证据装配与规则覆盖率预研.md)、
  [R-063](../research/R-063-AI建议稳定性与准确率基线预研.md)
- 关系：**修改 [ADR-0061](0061-AI清理建议边界与证据装配.md) §4** ——该节写的是
  "除用户点击 AI 分析之外应用零出网：不做遥测、**不做检查更新**、不做模型探活"。
  本 ADR 新增第二条出网路径（拉取规则目录）和第三条可选出网路径（提交规则提案），
  §4 的"零出网"随之作废，必须以本 ADR 的 §决策 5 为准。
  **不修改** ADR-0061 §1（AI 产出建议不产出授权）、§7（模型输出一律不可信），
  本 ADR 把这两条从"约束模型"扩展到"约束目录"。
  **不修改** [ADR-0009](0009-清理计划与macOS废纸篓执行.md) 的清理计划生命周期——
  规则目录一个字节的删除路径都不新增。

## 背景

使用方提出：搭建一个中央服务器存放规则版本，后续持续更新规则；不同用户机器上装的软件
和资料各不相同，这部分交给 AI 判断，并让 AI 分析能否**归纳出新规则**，可以的话向中央
服务器提交，由人类审核决定是否收录或更新，达成"共治"。

这个提议对上了两个已经量出来的事实。

**第一，规则表现在是编译进二进制的 Go slice。** 截至 `a870c01`，
`recommendation.Rules` + `recommendation.Generations` 在真机 `$HOME` 上命中 **58 条
建议 / 73.8 GB，全程零出网**（`internal/probe` 证据探针不配 advisor，只调
`RuleFindings`）。规则层已经是这个功能的主体，而**改一条规则等于发一个应用版本**。
软件世界一直在变，这个节奏跟不上。

**第二，R-063 §6 留了一个我自己出不去的循环。** "晋升后的规则覆盖 73.8 GB"这个数字，
是在**规则出生的那台机器上**量的。规则是从这台机器的目录形状里归纳出来的，再拿这台机器
去验证覆盖率，取值由构造决定——和 R-060 批评过的那类假指标同一个毛病。单机永远走不出
这个循环，**一个用户群体是唯一的出路**：「这条规则在 12% 的机器上命中、中位回收 340 MB」
才是非循环的度量。

这是本 ADR 最强的理由，比"规则更新更快"强得多。

## 预研依据

| 证据 | 出处 | 对本决策的作用 |
| :-- | :-- | :-- |
| 固定规则清单够不到 `63.4%` 的字节，缺口集中在未知应用缓存、项目内工程产物、git 膨胀、冷数据四类 | R-062 §3.5 | 规则表必须能持续增长，否则缺口不会自己收敛 |
| 棘轮：AI 发现 → 核实 → 晋升为确定性规则 → 模型不再需要；候选选择排除已被规则覆盖的路径，每条新规则都把 AI 预算重定向 | R-063 §4a | 共治就是把这个棘轮从单机扩展到群体，架构上是同一个东西 |
| 我自己标注 `20` 条错了 `1` 条，`5%` 假"可恢复" | R-063 §3.7 | **判定安全性不能交给模型**，也不能只交给单个人 |
| Kotlin/Native 复核结论与预期相反（`klib/platform` 会自愈，Flutter 的 `bin/cache` 不会） | R-063 §3.7a、§3.7b | 同类目录的自愈行为无法从形状推断，只能查实或实测 |
| 晋升规则的覆盖率在规则来源机上度量是循环的 | R-063 §4a、§6 | 需要多机聚合才能打破 |
| 代际死活取决于用户还在用哪一代，路径形状一模一样 | R-063 §4c | 有些判断天生依赖本机状态，**永远不能靠目录下发解决** |
| `.rustup/toolchains/*/share/doc` 从内部把整代吃掉 | R-063 §4c.3 | 目录里每加一条规则都可能与既有规则重叠，收录流程必须跑重叠检查 |

## 方案

### 方案 A：维持现状，规则随应用版本发布

优点：零新增信任边界、零新增设施、离线性质不变。
代价：规则更新节奏 = 应用发布节奏；`63.4%` 的缺口只能靠一个人手写去填；
R-063 §6 的循环论证永远打不破。
风险：低，但**这个方案解决不了背景里的任何一个问题**。

### 方案 B：服务器直接下发规则（使用方提议的原始形态）

优点：更新即时；共治链路最短。
代价：需要运营一个服务器。
风险：**这是一个删除工具的供应链问题。** 控制服务器的人可以让 marmot 建议删除
`~/Documents`。这不能靠"我们不会这么干"来兜——它必须在架构上不可能。
方案 B 未加约束的形态不可接受。

### 方案 C：公开签名目录 + PR 审核 + 后置聚合端点（分阶段）

优点：把方案 B 的收益拿到，同时把风险夹死；**第一阶段不需要任何服务器**；
目录公开可审计，正面回答"凭什么让你的服务器告诉我的清理工具删什么"。
代价：审核流程是长期人力成本；聚合计数要等第三阶段。
风险：审核瓶颈（见 §决策 7.3 的诚实说明）。

**选择方案 C。**

## 决策

### 1. 权限单向：目录只能增加候选，永远不能降低守卫

这是本 ADR 的红线，其余各条都建立在它之上。

- `cleanup.DeleteBlock` 与 `recommendation.IrreplaceableReason` /
  `PartialInstallReason` / `LoginStateReason` **留在二进制里，不在目录的表达范围内，
  不可远程更新。**
- 目录能表达的，**只有 `Rule` 与 `GenerationRule` 已有的字段**：路径模式、
  年龄/项目空闲条件、`Recovery`、`Risk`、`Category`、`WhatBreaks`、`HowToRestore`。
  不含任意代码、不含守卫豁免、不含路径白名单。
- 一条目录规则若在守卫判为不可恢复的路径上声称 `safe`，**守卫赢**，并按 ADR-0061 §7
  既有的更正链路记一条更正。这里**复用**校验层，不新增机制：对模型输出不可信，
  对目录输出同样不可信。

这样一条恶意或错误规则的爆炸半径被夹死在：用户看到一个建议 → 显式确认 →
移进废纸篓（ADR-0009，不做永久删除）→ 可还原。**这是有界的**；
而"守卫也能远程更新"是无界的。**这条线现在不划，以后加不上去。**

### 2. AI 提模式，不提标签

R-063 §3.7 与 §3.7a 量出的能力差是不对称的，分工必须照着这个差来切：

| AI 产出 | 实测 | 归属 |
| :-- | :-- | :-- |
| 归纳模式（`40` 个目录同一形状 → `Library/Caches/*.ShipIt`） | 强 | 交给 AI |
| 判定安全（删了能不能回来、回来要多少代价） | 我自己标注 `5%` 假"可恢复"；Kotlin/Native 一条结论与预期相反 | **不交给 AI** |

因此：**提案里的 `Recovery` / `Risk` / `WhatBreaks` / `HowToRestore` 一律视为空**，
即便模型填了也不采信；这四个字段由审核依据 §决策 7 的证据分级填写。
AI 在共治链路里的产出只有一件事：**候选模式 + 它在本机观察到的形状证据**。

### 3. 提案的单位是模式，不是路径——脱敏由此成为构造性质

`~/Library/Caches/com.microsoft.VSCode.ShipIt/update.aWPJq21` 里有价值的部分是
`Library/Caches/*.ShipIt`。**泛化这个动作本身就把私有部分剥掉了**：有用的产物恰好是
匿名的那个。这不是"我们记得脱敏"，是提案格式里没有地方放绝对路径。

提案 schema（`docs/` 下另行冻结，本 ADR 只定边界）只允许：

- `pattern`：home 相对的段模式，**必须至少含一个通配段**，否则它就是一条私有路径；
- `shape`：形状证据——子目录名的**模式**、扩展名分布、字节量级（按 2 的幂分桶，
  不给精确值）、对象个数量级；
- `sibling_patterns`：同目录兄弟的模式（代际类提案需要）；
- `citation`：厂商文档 URL（可空，但空的最多进 `review`，见 §决策 7）；
- `catalog_version`：提案基于的目录版本。

**明令禁止**出现在提案里的：绝对路径、账户名、项目名与仓库名、精确字节数、
机器标识、时间戳到日以下、任何来自文件内容的字符串。
门禁 5 用真实证据包对这条做机器检查。

### 4. 提交逐条 opt-in，且原文展示

使用方此前就"上传完整路径给模型"说过"既然都要做到 ai 辅助了，那么就没什么隐私了"。
**那是使用方为自己的分析做的决定，不能继承到这里。** 向一个有人类审核的共享目录提交是
另一件事：它是**对外发布、面向其他人、且不可撤回**（提案一旦进公开仓库就留在 git 历史里）。

所以：

- 提交默认关闭；
- 逐条确认，不做"全部提交"；
- 确认框里展示**将要发送的完整原文**（沿用 ADR-0061 §3 已有的"查看发送内容"形态）；
- 提交后告知这条提案会进入公开仓库、且不可撤回。

### 5. 出网：拉取默认开、提交默认关

**这一条需要使用方拍板。** 它正面修改 ADR-0061 §4 的"不做检查更新"。

拉取规则目录是本产品第一次在用户没点任何按钮的情况下出网。取舍：

- **默认开**：新规则自动到达，用户什么都不用管；代价是应用不再是"完全离线"，
  且用户的 IP 会被 CDN 看到。
- **默认关**：离线性质不变；代价是绝大多数用户永远拿不到规则更新，
  §决策 7 的整个共治链路对他们等于不存在。

**我的建议：拉取默认开，但做成纯静态下载。** 具体形状：

- 对 CDN 上一个静态签名文件做 `GET`，**不带任何用户标识、不带机器指纹、
  不带版本以外的查询参数**；服务端不需要也不应该建立按用户的记录；
- 唯一泄露的是 IP 和"这台机器装了 marmot"这个事实，本 ADR 必须把这句话原样写进
  首次启动的说明里，不含糊；
- 频率上限一天一次，失败静默，**永不阻塞扫描或界面**（门禁 8）；
- 设置里可关。

提交（§决策 3、4）无论如何默认关闭。

### 6. 规则表外置为签名数据文件，带内嵌基线

- 目录是一个 **JSON 文件**，含单调递增的 `version`（整数）+ 发布日期 + 规则数组。
- **Ed25519 签名**，公钥编译进二进制。`crypto/ed25519` 与 `encoding/json` 都在标准库，
  **本决策不新增任何第三方依赖**（AGENTS.md 的依赖门禁因此不触发）。
- **内嵌一份基线目录**（`go:embed`），保证首次启动、离线、以及签名校验失败时应用照常工作。
- 校验失败、版本回退（拿到的 `version` 小于当前生效版本）、JSON 不合 schema：
  **一律丢弃，保留当前生效目录，绝不降级到未签名内容。**
- 生效目录版本**显示在界面里**（建议面板页脚，与已有的"实际生效下限"同一行区域）。
  这同时给出了撤回能力：发一个不含该规则的新版本即可。
  诚实的限制：**撤回只能到达会拉取的客户端**；关掉拉取的用户会一直留着旧规则。
- 收录时必须跑既有的重叠检查（R-063 §4c.3 那条 bug 的教训）：
  新规则与目录里所有既有规则、以及与代际判据的重叠关系必须显式通过。

### 7. 目录公开、开放许可、证据分级

#### 7.1 公开与许可

目录本体是一个**公开仓库 + 开放许可（建议 `CC0-1.0`）**。理由三条，缺一不可：

1. "共治"要成立，贡献者不能是在给一份私有资产做免费劳动；
2. 任何人可以审计目录内容——这才是"凭什么让你的服务器决定我的磁盘"的真答案；
3. 审核流程直接用 PR，第一阶段**不需要自建任何服务器**。

#### 7.2 证据分级决定一条规则最高能到什么档

| 级别 | 证据 | 上限 |
| :-- | :-- | :-- |
| T1 | 厂商/上游文档明确说明该目录可删除或会自动重建（`citation` 必填） | 可判 `safe` |
| T2 | 实测再生：移入废纸篓 → 跑一次该工具 → 确认重建（CI 固定机上可复现） | 可判 `safe` |
| T3 | 只有形状证据 + 多机命中 | **最多 `review`** |

**"没人投诉"不是安全的证据。** 用户不会把"下次构建慢了 8 分钟"归因到 marmot，
也不会把"扩展全没了"和三周前的一次清理联系起来。因此**禁止**用采纳量或投诉率把
`review` 自动提升为 `safe`——那条路是假的，它把"无人归因"误当成"无事发生"。
`review → safe` 只能由 T1 或 T2 达成。

#### 7.3 审核的瓶颈，诚实写明

1 万用户 × 5 条 = 5 万条提案，人审不过来。撑住它的唯一机制是**按模式去重**：
同一个 `Library/Caches/*.ShipIt` 从三千台机器来只是**一条**提案（计数 3000）。
审核界面按 `字节量级 × 机器数` 排序。

即便如此，**现阶段审核人只有一个（项目作者），这是本方案最硬的瓶颈**，本 ADR 不假装
它有解。规则只有一条：**审核人不得是提案人**——而在只有一个人的阶段，这意味着
作者自己机器产生的提案要么等第二个审核人，要么只能进 T1/T2（有外部证据，
不依赖审核人的判断）。

### 8. 分阶段，服务器最后才建

| 阶段 | 内容 | 需要服务器？ |
| :-- | :-- | :-- |
| 1 | 规则表外置为签名 JSON + 内嵌基线 + 版本显示（§决策 6） | **不需要** |
| 2 | 公开目录仓库 + 提案 schema + 本地生成提案文件（§决策 2、3、4、7） | **不需要**（PR） |
| 3 | 拉取通道（§决策 5） | 只需静态 CDN |
| 4 | 聚合 ingest：命中机器数、回收字节中位数 | 需要 |

阶段 4 才是"中央服务器"，而它恰好是打破 R-063 §6 循环论证需要的那个数字，所以它会来，
但**不在本 ADR 的实施范围内**——本 ADR 只覆盖阶段 1–3，阶段 4 需要单独一份预研
（隐私模型、聚合口径、是否需要按机器去重而不引入机器标识）。

#### 8.1 阶段 1 的一个取舍，需要使用方拍板

规则表从 Go 代码变成 JSON 数据，会**失去编译期检查**：现在写错一个枚举值编译不过，
之后变成运行期校验。缓解办法是 schema 校验 + 一份"内嵌基线必须通过全部既有单测"的门禁。
另一条路是保留 Go 代码作唯一事实源、由代码生成 JSON——但那样目录就无法被非贡献者
以数据形式更新，共治链路断掉。**建议选 JSON 为事实源 + schema 门禁**，请确认。

### 9. 门禁

| # | 门禁 | 判定方式 |
| :-- | :-- | :-- |
| 1 | `go test` / `-race` / `vet` / `tsc` / `vite build` / `npm test` / `wails3 build` 全过 | 现有门禁 |
| 2 | 被篡改的目录、未签名的目录、版本回退的目录**一律拒绝且保留当前目录** | 三条构造用例 |
| 3 | 断网时使用内嵌目录、界面不报错、功能不降级 | 断网跑证据探针 |
| 4 | 目录规则在守卫判为不可恢复的路径上声称 `safe` → 守卫赢并记更正 | 构造用例 |
| 5 | 提案载荷不含绝对路径、账户名、精确字节数、机器标识 | 对真实 `$HOME` 证据包生成提案后做机器检查 |
| 6 | 未经逐条确认不产生任何提交；确认框展示完整原文 | 用例 + 人工复核 |
| 7 | 生效目录版本在界面可见 | 人工复核 |
| 8 | 拉取不延迟扫描启动 | 与 ADR-0058 同法测启动延迟，差值须在噪声内 |
| 9 | 内嵌基线目录通过全部既有规则单测（防 8.1 的编译期检查丢失） | `go test` |
| 10 | 收录流程的重叠检查对新规则显式通过 | 目录仓库 CI |

门禁 4 与门禁 5 是本 ADR 的两条实质门禁：前者守住 §决策 1 的红线，后者守住 §决策 3 的
脱敏是构造性的而非记性上的。

## 后果

**得到**：规则表脱离应用发布节奏；`63.4%` 的缺口有了群体填补路径；R-063 §6 的循环论证
有了打破的可能（阶段 4）；AI 的产出从"给用户的建议"扩展出第二种"给目录的提案"，
且这两种产出的可信度要求被明确分开；目录公开可审计，把"信任服务器"换成了"审计数据"。

**付出**：新增一条默认开启的出网路径（应用不再完全离线）；新增签名与版本机制的维护面；
规则表失去编译期检查（8.1）；**长期人力成本：审核**；目录仓库、提案 schema、
签名发布流程三套设施。

**新约束**：守卫层从此不得进入任何可远程更新的表达范围——这条约束会限制未来所有
"让规则更强大"的提议，这是有意的。

**风险**：

- **审核是单点。** §7.3 已写明，没有解，只有"审核人不得是提案人"这一条纪律。
- **签名私钥泄露 = 供应链失守。** §决策 1 把爆炸半径夹到"可还原的废纸篓操作"，
  但不消除它。密钥管理不在本 ADR 范围，需单独决定。
- **T3 规则会长期停在 `review`。** 这是设计意图（§7.2），但会让用户看到大量需要自己判断的
  条目，体验上不如"全都告诉我可以删"。这是这个产品刻意付的代价。
- **有些判断永远不能靠目录下发。** R-063 §4c 的代际死活取决于本机还在用哪一代，
  形状完全相同——这类判据必须留在客户端计算。目录能长的只是"哪些目录是分代的",
  不是"哪一代死了"。
- 本 ADR 全部收益的前提是**有用户群体**。在只有一台机器的阶段，阶段 1–2 仍有价值
  （更新节奏、可审计），但阶段 3–4 的核心收益为零。**不应为了"以后有用户"提前建设施。**

## 修订记录（2026-09-08）

本文原版漏了一个后果：**护栏成为规则之后，它们也成为了建议。** `RuleFindings` 对每一条命中规则
生成一个 `AdviceItem`，唯一的过滤是 `cleanup.DeleteBlock`，而 `~/Documents` 能通过它。实测
（`TestIdentifyOnlyRulesNeverBecomeFindings` 的前身）：`~/Documents` 以 8 GB、`irreplaceable` /
`risky` 出现在建议列表**第一位**，`~/.ssh` 紧随其后。同时命中规则的路径会作为 `ruled` 覆盖其下
全部候选，于是 advisor 也看不到 Documents 下的任何东西。两者当时不可见，仅因建议面板已从前端拆除。

这正是本文 §5 之外、审核时点名过两次的风险：识别规则一旦进入建议通路，就是工具建议你删掉自己的东西。
合并时本应同时引入这个区分，原版没有。

**修订**：`Rule.IdentifyOnly`——命名对象但永不提议。零值提议，所有原有规则不变；41 条迁入的
位置护栏置为 `true`；合并前就带 `Guard` 的两条（iOS 设备备份、Docker 数据）本来就是建议，保持。
排除发生在 `buildEvidencePack` 进 `hits` **之前**而不是 `RuleFindings` 出口，因为 `hits` 还驱动折叠、
世代排除与候选覆盖——源头排除使 advisor 通路恢复到与合并前完全相同的行为。`DescribeNode` 不受影响：
识别照常显示，只是不提议。语料的答案行新增 `identify-only` 标记，护栏若变回建议会以一行 diff 出现。

`§1` 的表格因此补一列：「这是什么」的来源可以只识别不建议；「能不能删」仍然只有 `DeleteBlock`。

## 背景

面板新增「这是什么／能不能重建」区域后（ADR-0067 已把这些事实备好，此前只有 AI 那条路会消费），
`DescribeNode` 同时调用了 `Match()` 与 `IrreplaceableReason()` 并把两者并列显示，于是
`~/Documents/proj/node_modules` 在同一个块里同时是「可重新下载」和红色的「不可重建」。

**必须先说清：这不是原设计的缺陷。** ADR-0067 已明确决定「规则建议**不**带位置护栏
（`GuardsFor` 只用于模型主张）」，理由与本例完全一致。两条通路的分离是刻意的：`Match` 答
"这是什么"，`GuardsFor` 只用来更正**模型**认错对象。矛盾由新增的消费方引入，领域层此前是对的。

但这次事故暴露了一个真实的结构问题：**该不该合并两条通路，此前没有答案，只有一条约定。**
约定写在 ADR-0067 的正文里，不在类型里，所以第一个新消费方就违反了它。同时 R-070 §2 量出
11.5 GB / 31 项处于"仅守卫命中、无身份"——`~/Documents`、`~/.ssh`、`**/.git` 只有一个理由码，
说不出自己是什么，而面板要问的恰恰是这个。

## 预研依据

R-070 §1 记录矛盾与其自造性质；§2 给出按字节的覆盖率现状与"该写哪条规则"的工单；
§3 是合并的 28 行等价性 diff 与只看"守卫消失"方向的审计；§4 记录三个被度量推翻的结论，
其中 §4.2 是一个不依赖任何改动即已生效的缺陷；§5 列出仍算不出来的量。

## 方案

### 方案 A：维持两条通路，在 `DescribeNode` 里手写仲裁

即事故当天的第一版修法：给护栏加 `GuardScope`（`self` / `inherited`），并在消费方判定
"具体识别可以压制继承来的护栏"。它修好了症状，但把约定变成了**消费方的策略代码**——
每个新消费方仍要自己写一遍，且重复本身没有消掉（两套匹配、两套模式表、两种词汇）。
使用方读到这一版的反馈是「感觉这么乱？已经看不懂了」。被拒绝。

### 方案 B：合并为一张表，且仲裁按段数

把护栏并入目录，用"匹配段数多者胜"做仲裁。段数救不了目标场景：`~/Documents` 与
`**/node_modules` 都只钉住 1 段，平票，而平票两边是「不可替代」与「可重新下载」。被拒绝。

### 方案 C：合并为一张表，仲裁按"自身命中 / 段数 / 是否泛规则"（采用）

见"决策"。

## 决策

### 1. 一个问题一个答案来源

| 问题 | 唯一来源 | 可否被规则影响 |
| :-- | :-- | :-- |
| 能不能删 | `cleanup.DeleteBlock` | **不能**，编译进二进制 |
| 这是什么 | `Rule.Name` / `Category` | 能 |
| 能不能回来 | `Rule.Recovery` | 能 |
| 删了会怎样 | `Rule.WhatBreaks` / `HowToRestore` | 能 |

第一条是权限，与后三条不在同一维度，因此独立、不参与仲裁、不可外置。后三条**全部来自同一条规则**。

### 2. 位置护栏是目录里的规则

`homeRelativeIrreplaceable`、`anywhereIrreplaceable`、`suffixIrreplaceable`、`loginStatePaths`
共 4 张表并入 `Catalog`，每条成为携带 `Rule.Guard`（理由码）的普通规则，并被迫补上
`Name` / `Category` / `WhatBreaks` / `HowToRestore`——这正是 R-070 §2 那 11.5 GB 缺的东西。
`GuardsFor()` 改为对目录的一次查询；`IrreplaceableReason` / `LoginStateReason` /
`PartialInstallReason` 保留为按类别过滤的薄包装，调用方无需知道它们同源。

`IrreplaceableMessage` 这层"码 → 句子"的映射不再用于面板：句子写在规则的 `WhatBreaks` 上。
它保留给 advisor 更正链路（ADR-0061 §7）。

### 3. 仲裁只有一条，且范围是声明而非推断

`Match` 收集全部候选，按三元组字典序取最高：

```
(是否自身命中, Rule.Specificity(), 是否非 Generic)
```

1. **自身命中 > 祖先继承**——这一条使 ADR-0067「规则结论不带位置护栏」成为结构性质：
   `~/Documents/proj/__pycache__` 由 `__pycache__` 规则（自身）胜过 `Documents` 规则（继承）。
2. **钉住的段数多者胜**。
3. **认得对象者胜过认得容器者**（`Generic`）。

平票归表中靠前者，这保持了原先"先查 `AbsoluteCatalog`"的行为。

**范围与匹配域都是字段，不是从模式反推的：**

- `Rule.Covers`：`CoversSelfAndInside`（零值）/ `CoversSelfOnly`。`~/Documents` 要管里面的照片，
  `**/node_modules` 只管那个目录本身，只有规则自己知道是哪一种。
- `Rule.Anchor`：`AnchorHome`（零值，家目录相对）/ `AnchorPath`（完整路径）。两张表合并为一张，
  匹配域随之必须显式——两张表都含 `**/` 模式，所以"是否在家目录外生效"此前只取决于作者把规则
  放进了哪张表，而放错表正是 ADR-0063 §3 与 R-065 §3 记录的那个洞的机制。

`Rule.Risk` 改名为 `Rule.DeclaredRisk`。它是 `Assess` 的**输入**（`Facts.Declared` → `baseline()`
起点），与 `Assessment.Risk`（结论）同名是本区域可读性变差的主要原因之一。R-070 §4.3 记录了
"改为从 `Recovery` 派生"为何是错的。

### 4. "例外"不再是一种机制

`gitTransient` 是一张让护栏自我豁免的列表。合并后它是一条更具体的规则
（`**/.git/objects/pack/tmp_idx_*`，钉住 3 段且自身命中，压过 `**/.git` 的 1 段继承命中），
连同它缺失的 `tmp_idx_` 一并补齐。**目录里此后没有"例外"这个概念。**

### 5. ADR-0062 §1 的红线改为基线／覆盖层二分

ADR-0062 §1 原文把红线表述为"`DeleteBlock` 与三个护栏函数留在二进制里，不在目录的表达范围内"。
护栏成为目录规则后，这句话不再是对整张表的陈述。红线本身不变，改为：

- **`cleanup.DeleteBlock` 完全不在目录内**，一如既往，不可远程更新。这一条不动。
- **`Rule.Guard` 是基线专有字段。** 覆盖层规则若设置它，拒绝加载。
- **覆盖层规则永不得压过携带 `Guard` 的基线规则**，无论其具体度。
- **基线内部按 §3 仲裁**，包括具体识别压过继承来的护栏——这是 ADR-0067 要求的，也只在基线内成立。
- 覆盖层的爆炸半径与 ADR-0062 §1 一致：能增加候选、能把 `Recovery` 往 `irreplaceable` 方向调，
  不能移除或削弱任何护栏。

ADR-0062 §1 那条"目录规则在护栏判定的路径上声称 `safe` 则护栏赢"的复用式仲裁随之取消：
基线内由具体度决定，覆盖层则被上述约束挡在护栏之外。「`irreplaceable` 绝不配 `safe`」
由 ADR-0067 §1 的结构保证，不依赖此机制。

因 ADR-0062 §1 自称"这条线现在不划，以后加不上去"，`Rule.Origin` 与上述两条约束**现在**就落进
代码，尽管覆盖层尚未实现（ADR-0062 §8 排在最后）。

### 6. `Recovery` 增加第四个取值

护栏并入目录后，登录状态规则必须回答"能不能回来"，而三个既有取值都不对：它不是
`irreplaceable`（能重新登录，这样说是往保守方向撒谎），也不是 `regenerable`（没有工具自动重建）。
新增 `RecoveryReauthenticate`：**前三种花的是机器的时间，这一种花的是人的时间**——逐个网站重新
登录、两步验证重新登记。

**目录可以声明它，advisor 不许声称它**：`advisor.go` 的取值白名单仍是三个。它是关于"用户要重做
多少活"的本地判断，模型只能瞎猜。

### 7. 应用包内部由 `DeleteBlock` 拒绝

R-070 §4.2 度量到一个已在生效的缺陷：`~/Downloads/*.app/.../node_modules` 被标为「可重新下载」
且无人拒绝。具体度排序修不了它——需要"在 X 内部"压过"是 Y"，与 §3 第 1 条方向相反。

区别在于 `~/Documents` 是**位置**，`.app` 是**原子单元**：其内部不是可独立寻址的对象。
这是"能不能删"，因此落在 `DeleteBlock`，新增理由码 `ProtectionBundleInterior`。
一处修改封住三条路径：空间图授予 collect 能力时拒绝、建立计划时再拒绝一次、
建议通路本就过滤 `DeleteBlock` 拒绝的候选（ADR-0061 §7.2）。

**删除整个应用仍然允许**，只有内部不行。清单按扩展名（`.app`、`.framework`、`.bundle`、`.kext`
等 19 项），并在代码里注明：真正的判据是内部有 `Contents/Info.plist`，而 scanner 不读文件内容，
所以这是已知清单而非完备判据，漏掉一个是缺口不是决定。文档包（`.photoslibrary`）故意不在清单里
——它由"不可替代内容"规则负责，说的是损失代价而非结构。

### 8. 门禁：等价性 golden

`TestCorpusAnswers` 冻结 43 条路径的 `rule` / `recovery` / `risk` / `generic` / `guards`。
路径手写，不取自真实磁盘（真实语料会把项目名与雇主名带进仓库，且只能在采集它的机器上复现）。

**每次改动规则表，评审对象是这份 golden 的 diff，不是代码。** 重点看两件事：
有没有守卫消失（唯一会丢文件的方向），有没有意外命中别的路径。
`TestEveryRuleExplainsItself` 的检查范围从"仅 root 拥有的那张表"扩大到整张目录。

## 后果

- 回答"能不能重建"的表从 5 张变 0 张（全在目录里），判定入口从 4 个并行变 1 个，
  仲裁从"无"变"一处"，具体度概念从 2 份实现（新写的 `patternSegments` 与已有的
  `Rule.Specificity()`）收敛为 1 份，规则表从 2 张变 1 张，"例外"机制消失。
- 目录规则 72 → 113 条。增量全部是原护栏条目获得身份，`~/Documents` 现在能说出自己是「用户文档」。
- 前端同步塌掉一层：`guardLines`、`GuardLine`、`supersedes()`、`generic` 交互与
  `.describe-context` 样式全部删除。不可重建此后是规则自己的 `recovery` 标签加自己的散文，
  不再是第二套视觉概念；面板只保留一条独立红线「不可删除」，因为那是另一条轴。
- `NodeDescription` 的 5 个护栏字段收为 1 个 `Guard` 码。
- **`GuardsFor` 的语义变了**：此前无条件返回全部命中的护栏码，现在返回胜出规则携带的那一个。
  对 advisor 更正链路的影响是：目录已正确命名的对象不再额外套护栏——这正是 ADR-0067 要的；
  目录不认识的对象仍由护栏规则胜出并返回其码。
- 大小写：`suffixIrreplaceable` 原先比较小写化的完整路径，迁移为段匹配后区分大小写。
  语料记录了这一差异（R-070 §5），守卫码不变，仅身份精度下降。
- ADR-0062 §1 的实现约束提前落地，但覆盖层加载器尚不存在，所以 `Rule.Origin` 目前只有一个取值。

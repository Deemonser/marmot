# ADR-0054：遗留 SQLite 快照缓存清理

- 状态：Accepted
- 日期：2026-08-25
- 相关预研：[R-056](../research/R-056-快照缓存膨胀审计.md)

## 背景

[ADR-0028](0028-macOS原生扫描与追加式二进制快照.md) 用追加式二进制快照取代了 SQLite 快照存储。
生产链路里打开快照存储的位置只有一处，用的是 `binarysnapshot.OpenStore`（R-056 第 3.4 节）。

但旧实现留下的 `snapshots.db` / `-wal` / `-shm` **没有任何代码会删除**。本机实测 `4.57 GB` + `38 MB`，
修改时间停留在二进制存储接管之前，此后一直只是占着磁盘。

这不是"缓存该不该有上限"的问题——它已经完全不在任何读写路径上。一个磁盘清理工具在用户磁盘上留下
`4.6 GB` 永久垃圾，是自身产品价值的反面。

另一方面，**让应用删除用户磁盘上的文件需要明确边界**，这正是本 ADR 要定的东西。

## 预研依据

- [R-056 快照缓存膨胀审计](../research/R-056-快照缓存膨胀审计.md)
- [ADR-0028 macOS 原生扫描与追加式二进制快照](0028-macOS原生扫描与追加式二进制快照.md)：SQLite 被取代的出处。
- [ADR-0023 快照缓存生命周期与扫描中进度反馈](0023-快照缓存生命周期与扫描中进度反馈.md)：缓存维护的既有边界。
- [ADR-0009 清理计划与 macOS 废纸篓执行](0009-清理计划与macOS废纸篓执行.md)、DDD 不变量 9：
  用户数据的删除只能进废纸篓、不得永久删除——本 ADR 必须说明为什么应用自身的缓存是例外。

## 方案

### 方案 A：启动后在缓存维护阶段按精确文件名删除（采用）

在既有的缓存维护时机（`BeginRecovery` 之后的延迟维护，ADR-0023）删除三个**精确命名**的文件。

- 优点：用户不需要知道这件事就能拿回磁盘；不新增交互；边界可以写得非常死。
- 代价：应用会删除磁盘上的文件，必须有严格约束（见决策各条）。

### 方案 B：什么都不做，只在文档里写"手动删除"（拒绝）

把 `4.6 GB` 留给用户，且绝大多数用户永远不会知道。磁盘清理工具尤其不能这样。

### 方案 C：弹窗询问是否清理（拒绝）

为清理**应用自己的、已经不在任何读写路径上的缓存**去打断用户，是把实现历史包袱变成用户的决策负担。
用户删除的是**自己的**文件时才需要确认（DDD 不变量 9）；这里删的是我们自己的过期缓存。

### 方案 D：迁移旧数据到新格式（拒绝）

没有意义：SQLite 里是同一批扫描的旧格式副本，用户随时可以重扫，而重扫比迁移一个被取代的格式更便宜、
更不容易出错。

## 决策

### 1. 删除范围是三个精确文件名，不是模式匹配

只删除 `<缓存目录>/marmot/` 下的：

- `snapshots.db`
- `snapshots.db-wal`
- `snapshots.db-shm`

**禁止**使用通配符、正则或递归删除来实现这条。范围必须是一个写死的文件名列表：一个能匹配多个文件的
清理器，一旦路径拼接出错就会扩大成任意删除。

### 2. 只在应用自己的缓存目录内操作，且路径必须由平台 API 给出

目标目录由 `os.UserCacheDir()` 加固定子目录得到，与快照存储用的是同一个来源。不得接受来自配置、
命令行或前端的路径。若该目录无法确定，跳过清理。

### 3. 只清理"已被取代的存储"，不得推广为通用缓存清理器

本 ADR 授权的只有 ADR-0028 明确取代掉的 SQLite 快照存储。它**不是**一个"清理任何看起来没用的文件"的
机制。任何新增的清理目标都必须新增 ADR。

### 4. 与 DDD 不变量 9 的关系必须写明

不变量 9（只进废纸篓、不得永久删除）约束的是**用户数据**——用户在收集区里选中的文件。
本 ADR 删除的是**应用自身产生的、已经不在任何读写路径上的缓存产物**，直接删除而不进废纸篓：
把 `4.6 GB` 的过期缓存放进用户的废纸篓，只是把占用从一个地方搬到另一个地方，还要用户再去清空。
这个例外仅限第 1 条列出的文件。

### 5. 失败不得影响启动，且必须幂等

清理在后台维护阶段执行，任何错误只记录不上抛：缓存清理失败不是用户的问题，不能因此挡住窗口或让扫描
失败。文件不存在是正常情况（第二次启动、全新安装），不算错误。

### 6. 清理必须留下日志

删除了什么、释放了多少字节，必须记入关键日志。应用删除文件而不留痕迹是不可接受的。

### 7. SQLite 实现仍留在仓库，但不再是回退路径

`internal/infrastructure/snapshot` 仍被测试使用。本 ADR 确认它**不是**生产回退路径——否则清理会删掉
一个仍可能被打开的数据库。**若将来任何原因要把 SQLite 存储恢复为生产路径（含回退），必须在同一次改动里
移除本清理逻辑**，并在该 ADR 中说明。

### 8. 不变边界

- 快照格式、二进制存储的剪除策略、缓存字节预算与保留时长（ADR-0023）都不变；
- 不清理 `WebKit/`（WebView 自己的缓存，仍在使用中）；
- 不清理当前快照的任何文件；
- 不引入任何新的用户交互。

## 后果

正面后果：

- 从二进制存储之前升级上来的用户会拿回这部分磁盘（本机 `4.6 GB`）；
- 清理边界写死为三个文件名，误删风险接近于零。

代价和风险：

- 应用会在用户磁盘上删除文件。这是本 ADR 的核心风险，靠第 1、2、3、6 条约束：写死文件名、只在自己的
  缓存目录、不推广、留日志；
- 若第 7 条被违反（SQLite 被恢复为回退路径而清理未同步移除），会删掉一个仍在使用的数据库。这是本决策
  最危险的失效模式，必须在恢复 SQLite 的改动里同时处理；
- 已经手动删过这些文件的用户不受影响（幂等）。

一项未处理的相邻问题（R-056 第 3.6 节）：单个全盘快照实测 `843 MB`，而 `snapshotCacheBudget` 是
`512 MiB`，两者差一个量级。修复索引泄漏之后稳态是只保留一个快照，产品上可接受，但这个数字应当单独复核，
本 ADR 不改它。

## 验收门禁

1. 全仓 Go 测试、`-race`、`go vet` 通过；
2. 清理只删除第 1 条列出的三个文件名，由测试断言：在放了同名文件与若干**不同名**文件的临时目录上运行，
   只有那三个消失；
3. 幂等：在没有这些文件的目录上运行不报错、不产生副作用；
4. 清理失败不影响启动与扫描，由测试覆盖（注入不可删除的情形）；
5. 清理写出关键日志，包含释放的字节数；
6. 当前快照的 `data` / 索引 / manifest 在清理前后都存在，且清理后仍能打开结果页。

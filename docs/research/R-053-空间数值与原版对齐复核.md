# R-053 空间数值与原版对齐复核

状态：已复核（本机原版截图 + `diskutil apfs list` + `statfs` + 自建 `getattrlistbulk` 探针）；结论要求新增 ADR

日期：2026-08-25

## 1. 问题

同一台机器上，原版与 Marmot 的数值全面对不上：

| | 原版 | Marmot |
| :-- | --: | --: |
| 卷副标题 | `245.1 GB 加密的启动盘` | `228 GB 启动盘 · 2 个技术卷` |
| 扫描总量 | `231.9 GB` | `190 GB` |
| 用户 / Users | `133.7 GB` | `127 GB` |
| 系统 / System | `49.5 GB` | `25 GB` |
| 隐藏空间 | `9.3 GB` | **不存在** |
| 实际可用空间 | `13.2 GB` | 不显示 |

本记录把差距逐项拆开，直到账能闭合。

## 2. 环境与方法

- 原版截图：`~/Downloads/daisydisk截图/xw_20260825112640.png`（结果页）、`xw_20260825112942.png`（源页），
  上午 11:26 拍摄；
- Marmot 侧数据取自 `internal/probe/progress_probe_test.go` 与结果页实测，当日 17:50 前后。
  **两个时间点磁盘状态不同**（原版当时可用 `13.2 GB`，我们测时约 `10.1 GB`），约 3 GB 的总量差由此产生，
  下文所有比较都保留这一项；
- 容器真值用 `diskutil apfs list`；卷已用用 `df -k`；
- 逐文件口径用自建 C 探针 `getattrlistbulk`，同时取 `ATTR_FILE_ALLOCSIZE`、`ATTR_FILE_DATALENGTH` 和
  `ATTR_CMNEXT_PRIVATESIZE`（需 `forkattr` + `FSOPT_ATTR_CMN_EXTENDED`），跳过挂载点，与生产扫描器同规则。

## 3. 证据

### 3.1 容器分解：账是闭合的

`diskutil apfs list`（容器 `disk3`）：

| 卷 | 角色 | 已用 | 十进制 |
| :-- | :-- | --: | --: |
| `disk3s1` Macintosh HD | System | `11.71 GiB` | `12.6 GB` |
| `disk3s5` Macintosh HD - Data | Data | `186.48 GiB` | `200.2 GB` |
| `disk3s2` Preboot | Preboot | `8.36 GiB` | `9.0 GB` |
| `disk3s6` VM | VM | `11.00 GiB` | `11.8 GB` |
| `disk3s3` Recovery | Recovery | `1.20 GiB` | `1.3 GB` |
| **合计** | | **`218.75 GiB`** | **`234.9 GB`** |

与 `statfs` 口径 `total - available = 228.28 - 9.39 = 218.89 GiB` 一致。**Recovery 卷未挂载**，
任何按挂载点遍历的扫描器都看不到它。

### 3.2 缺陷一：显示单位用 1024 除却标 `GB`

`formatBytes` 以 `1024` 为除数，单位表写 `KB/MB/GB`，且 `>=10` 时 `toFixed(0)`。原版与 Apple 一致用
`1000`、保留一位小数。

`245.1 GB`（十进制）`= 228.3 GiB`（二进制）**就是我们显示的那个 `228`**。容量本身完全正确，
只是所有数字统一读低 `7.4%`，且丢掉小数位。这一项独立于其他缺陷。

### 3.3 缺陷二：卷组内的辅助卷被扫描边界无条件跳过

`newMountBoundaries` 把根目录下**每一个**挂载点都加入跳过集。因此漏掉同容器的：

- `/System/Volumes/VM` `11.00 GiB`
- `/System/Volumes/Preboot` `8.36 GiB`
- `Update` / `Hardware` / `iSCPreboot` / `xarts` 合计约 `0.02 GiB`

`/System/Volumes/Data` 必须继续跳过：其内容已经通过 `/Users`、`/Applications`、`/Library`、`/private`
等 **firmlink**（不是挂载点，`ATTR_DIR_MOUNTSTATUS` 不置位）被遍历，否则会重复计算。这也解释了为什么
我们能扫到 `Users 127 GiB` 却漏掉 VM/Preboot。

VM 与 Preboot 挂在 `/System/Volumes/` 之下，在以 `/` 为根的树里落在 `系统` 里面。原版
`系统 49.5 GB = 46.1 GiB` 对我们 `/System 25.57 GiB` 的差是 `20.5 GiB`，与 `VM + Preboot = 19.36 GiB`
在量级与方向上一致——**与"原版把这两个卷算进树里"的假设相符，但单凭截图无法证实其内部实现。**

### 3.4 缺陷三：`owned_allocated` 的"去重"语义从未实现

生产扫描器只请求 `ATTR_FILE_ALLOCSIZE` 与 `ATTR_FILE_DATALENGTH`，`OwnedAllocated` 直接等于
`AllocatedSize`。辅助卷探针输出 `owned_gib=27.59 allocated_gib=27.60`（Preboot）即为直接证据。

补取 `ATTR_CMNEXT_PRIVATESIZE`（"删掉此文件能释放多少字节"，10.15+）后的对照，单位 GiB：

| 目录 | `alloc`（现用） | `privatesize` | `datalength` | 原版（换算 GiB） |
| :-- | --: | --: | --: | --: |
| `/System` | `25.57` | `13.82` | `31.48` | `46.1` |
| `/Applications` | `21.37` | `17.55` | `26.41` | **`21.9`** |
| `/Library` | `6.96` | `5.27` | `9.96` | **`7.0`** |
| `/private` | `6.23` | `4.13` | `6.24` | `3.5` |
| `/opt` | `3.67` | `3.67` | `3.37` | `3.4` |
| `/usr` | `1.05` | `0.27` | `1.79` | **`1.02`** |
| `/Users` | `127.51` | `125.43` | `123.88` | `124.5` |
| `Preboot` | `27.60` | `1.78` | `48.73` | — |
| `VM` | `11.00` | `11.00` | `11.00` | — |

两个结论：

1. **原版跟踪的是 `allocated`，不是 `privatesize`。** `/Applications`（`21.37` 对 `21.9`）、
   `/Library`（`6.96` 对 `7.0`）、`/usr`（`1.05` 对 `1.02`）三项 `alloc` 几乎精确吻合，而 `privatesize`
   分别低 `4.3`、`1.7`、`0.75 GiB`，差得很远。
2. **克隆密集区按 `allocated` 会严重虚高。** Preboot 的 cryptexes 是系统卷内容的 APFS 克隆，块是共享的：
   `alloc 27.60` 对物理 `8.36`，虚高 `3.3` 倍；`privatesize` 只有 `1.78`，因为删掉它几乎释放不了空间。
   `data > alloc`（`48.73` 对 `27.60`）说明还叠了 APFS 透明压缩。

因此若把 Preboot 按 `allocated` 计入，树总量会变成 `190.4 + 11.00 + 27.60 = 229.0 GiB`，**超过磁盘已用
`218.89 GiB`**，平衡项会变负数。辅助卷必须按物理尺寸计。

### 3.5 缺陷四：没有隐藏空间平衡项

原版的两条恒等式：

```
总容量 245.1 = 扫描总量 231.9 + 实际可用 13.2
扫描总量 231.9 = 文件树 222.6 + 隐藏空间 9.3
```

即**按构造让树的总量等于 `statfs` 已用**，把残差放进「隐藏空间」。我们 Go 侧完全不产出这一项——
`hidden_space` / `purgeable_space` 只在前端存在标签（`grep` 全仓 Go 零命中）。所以我们的轮盘从来
就加不出磁盘容量，差额是静默丢失的。

### 3.6 修复后的算术

```
文件树（alloc，现状）              190.40 GiB
+ VM（statfs）                     11.00
+ Preboot（statfs）                 8.36
+ Update/Hardware/iSCPreboot/xarts  0.02
= 树总量                          209.78 GiB = 225.2 GB
已用（statfs 容器）               218.89 GiB = 235.0 GB
隐藏空间 = 已用 - 树总量            9.11 GiB =   9.8 GB
```

原版隐藏空间 `9.3 GB`，我们 `9.8 GB`，**差 0.5 GB**。总量 `235.0` 对原版 `231.9`，差 `3.1 GB`，
与第 2 节记录的磁盘状态变化（可用 `13.2` → `10.1 GB`）一致。**账闭合。**

隐藏空间里包含哪些东西，已能逐项说明：未挂载的 Recovery 卷 `1.20 GiB`、权限读不到的区域
（全盘扫描 440 个 issue）、APFS 元数据，以及 `alloc` 与物理占用的差额。这也解释了为什么我们能扫的两个卷
（`11.71 + 186.48 = 198.19 GiB`）比我们实际扫出的 `190.40` 多 `7.8 GiB`。

## 4. 结论

1. 单位口径错误，独立可修，解释统一的 `7.4%` 偏低；
2. 扫描边界漏掉同容器辅助卷 `19.4 GiB`，且必须继续跳过 `/System/Volumes/Data`（firmlink 已覆盖）；
3. `owned_allocated` 的"去重后实际占用"是一条**从未实现的承诺**，实测等于 `allocated`；原版跟踪的也是
   `allocated`，因此主口径保持 `allocated`（产品决策），但文档必须停止声称去重；
4. 克隆密集的辅助卷不能按 `allocated` 计，否则树总量超过磁盘已用；按 `statfs` 物理尺寸计入；
5. 必须产出隐藏空间平衡项，使 `树总量 + 隐藏空间 = 已用`、`已用 + 可用 = 容量`，与原版同构。

进入 [ADR-0052](../adr/0052-空间数值口径与卷组覆盖对齐.md)。

## 5. 限制

- 原版的内部实现只能由数值反推，第 3.3/3.4 节的两条结论是"与实测一致"，不是证实；
- `ATTR_CMNEXT_PRIVATESIZE` 只在探针里验证过，**未测量把它加进生产扫描器的耗时**；本轮不引入；
- 原版逐目录数值与我们相隔约 6 小时，`/private`（`3.5` 对 `6.23`）这类高频变动目录不具备精确可比性；
- 未复核外接卷与非启动容器（`disk5`/`disk7` 的 iOS Simulator 容器是独立容器，不属于 Macintosh HD）。

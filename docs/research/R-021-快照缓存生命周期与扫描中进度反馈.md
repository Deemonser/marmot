# R-021 快照缓存生命周期与扫描中进度反馈

状态：已完成，结论由 ADR-0023 接受

日期：2026-08-21

## 1. 问题

用户点击全盘分析时，界面容易表现为“卡死”，而原版产品会持续显示扫描阶段和计数。需要区分：

1. 扫描器本身的目录枚举耗时；
2. SQLite 快照写入、旧缓存和空间图查询的争用；
3. 前端是否持续给出可信的进度反馈。

## 2. 环境与方法

- macOS arm64，Go 1.25.13，SQLite WAL；
- 只读 `/` 扫描 smoke：约 270 万节点，当前 Darwin 扫描器约 20.45 秒；
- `ListVolumes()` 卷容量探测约 0.8 秒，不是主要瓶颈；
- CPU profile 显示约 93% 的累计样本位于 `getattrlistbulk(2)` 目录枚举调用；
- 本机 Marmot 缓存曾达到约 3.4 GB，包含 13 个快照和约 1100 万节点，其中多个旧的中断快照仍保留；
- 检查 React 事件处理和 `GetMap` 调用：扫描期间可能按进度事件重复请求深度 3 的空间图投影，并与单连接 SQLite 写入竞争。

## 3. 证据

| 观察 | 结论 |
| --- | --- |
| 纯扫描仍约 20 秒 | `<15s` 不是 UI 假象，仍需独立的原生递归枚举/缓存预研 |
| 卷目录探测低于 1 秒 | 不需要通过延迟卷模型解决全盘耗时 |
| 旧快照超过 3 个且数据库达到 GB 级 | 既定缓存 TTL/数量边界没有落到 `SnapshotStore` 实现 |
| 扫描中重复深层 `GetMap` | UI 查询会与批量写入争用，可能放大“卡住”感受 |
| 全盘节点总数在遍历前未知 | 不能把已扫描节点伪装成精确百分比 |

## 4. 结论

### 4.1 快照缓存

- `SnapshotStore` 在应用恢复时先将运行中快照标为 `interrupted`；启动不自动淘汰历史库，超过 24 小时或超出最近 3 个保留位的非运行快照在扫描后的空闲维护窗口清理；
- 扫描完成后安排逻辑清理，但扫描终态事件必须先发出，避免缓存维护阻塞结果展示；
- 新数据库启用 SQLite incremental vacuum；历史数据库只在没有运行任务的空闲维护窗口执行维护；
- 缓存只保存 Marmot 生成的扫描观察结果，不影响用户文件和清理计划；
- 512 MB 是缓存维护门槛。单个当前扫描快照超过该门槛时，必须保留当前结果，后续空闲维护再压缩或淘汰旧快照，不能在扫描中途删除当前快照。

补充复测发现旧数据库约 3.4 GB 时，只读统计本身约需 22.5 秒；因此启动恢复不能把淘汰、WAL
checkpoint 或历史库压缩放在扫描请求的同步路径上。节点批次提交时同步累计快照摘要，启动只快速标记
中断并释放 barrier；缓存维护延后到没有活动扫描的空闲窗口，扫描完成事件先于维护发出。
若用户在维护已开始后发起扫描，扫描请求先取消维护并等待 SQLite 连接释放；维护 SQL 使用 context
取消，避免延后维护形成新的卡顿窗口。

### 4.2 扫描期间的查询

- 扫描中当前层空间图刷新最多每秒一次；
- 扫描中使用深度 1 的有界投影，扫描完成后再请求完整的首屏深度 3 投影；
- 进度事件仍只传摘要，不传节点；
- 源页面始终显示阶段、节点数、文件数、文件树占用、已用时和取消入口；
- 进度条保持不确定态，直到后端拥有可信的总量，不伪造百分比。

## 5. 限制

- 这次修复解决缓存失控和查询争用，但没有把 Darwin 全盘扫描从约 20 秒直接宣称为 `<15s`；
- `getattrlistbulk(2)` 仍是纯扫描主耗时，后续必须单独验证原生递归枚举、缓存命中和真实 DaisyDisk 扫描范围；
- 当前没有在锁屏状态下完成原生窗口点击 smoke，UI 仍需解锁 macOS 后验证。

## 6. 对 DDD/SDD 的影响

- DDD 领域对象和清理安全不变量不变；缓存仍是快照基础设施，不是新的领域事实；
- SDD 明确 `SnapshotStore` 的清理/维护端口、扫描中空间图查询预算和不确定进度语义；
- 该结论由 [ADR-0023](../adr/0023-快照缓存生命周期与扫描中进度反馈.md) 固化。

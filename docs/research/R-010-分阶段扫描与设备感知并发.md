# R-010 分阶段扫描与设备感知并发

状态：已完成，结论由 ADR-0014 接受

日期：2026-08-20

## 1. 问题

当前 Marmot 在真实目录上扫描偏慢，无法达到 DaisyDisk 的“先看到概览、再逐步得到结果”的体验。需要确定扫描阶段、并发模型、缓存边界和事件发布策略，避免实现阶段再次推倒扫描器。

## 2. 假设

- SQLite 批量写入和分页查询不是当前首要瓶颈；主要瓶颈可能在串行目录遍历、每节点回调和目录汇总。
- 先发布卷概览和顶层目录，再进行深层扫描，能显著缩短用户等待首个可用结果的时间。
- SSD、机械盘、网络/虚拟卷需要不同的并发上限；无限制并行会增加 I/O 争用和资源风险。
- 扫描事件必须是摘要和最新状态，而不是每个文件的消息流。

## 3. 环境与方法

- macOS 26.5.2，arm64，Go 1.25.13，SQLite 3.51.0。
- 阅读 Marmot 的 `internal/infrastructure/scanner`、`internal/application`、`SnapshotStore` 和 R-004 基准。
- 核对 DaisyDisk 的扫描、并行扫描和权限用户指南。
- 核对本机 Mole `V1.40.0` 固定提交 `c3ef1f50ea7a2490957dd8cbffadfcc350dd1182` 的扫描策略记录。
- 用本机 `mo analyze --json /Users/deemo/CodeProjects/marmot` 做行为对照：约 1.39 秒返回 60 个文件的直接分析结果，但 JSON 只有 15 个直接条目，不是完整递归树。

## 4. 证据与发现

### 4.1 Marmot 当前瓶颈

当前扫描器使用串行 `filepath.WalkDir`：

- 每个条目调用 `entry.Info()` 获取元数据；
- 每个节点同步经过 Application 的 emitter；
- 每个文件沿父链更新目录汇总，目录深度增加时单节点工作增加；
- 直到 10,000 个节点才提交一批，根节点和首层结果不能保证立即可查询；
- 没有 SSD/机械盘/网络卷的设备调度；
- 没有可复用的目录/文件元数据缓存；
- 进度虽然按 100 ms 发送，但缺少最新值合并和事件队列边界。

R-004 的合成基线显示 SQLite 树形写入 100 万节点约 3.1 秒、分页查询约 13 ms，说明存储层已有足够起点。优化重点应放在扫描生产端和首批结果发布，不应先重写 SQLite。

### 4.2 成熟产品和开源策略

- DaisyDisk 在 SSD 上允许并行扫描，在机械硬盘上按同一磁盘排队；它把 SSD 通常数秒、机械盘可能约两分钟作为用户预期，并明确网络共享、虚拟磁盘和 Time Machine 可能更慢。
- Mole `V1.40.0` 采用受限 worker、排队任务、取消边界、硬链接去重、分批发布和带 TTL/容量上限的缓存；其 JSON 只适合作为摘要，不适合作为 Marmot 的完整树协议。
- GrandPerspective 和 R-001 共同显示：扫描、绘制、刷新应后台化；UI 只按需加载当前层级。

### 4.3 约束

- 不能跟随符号链接；不同卷必须隔离；硬链接和 APFS 克隆语义不能被并发改写。
- 取消后已经提交的批次保留，取消观察点之后不能再提交新批次。
- 缓存结果不能直接冒充当前事实；必须带版本、权限指纹和文件身份校验。
- 扫描事件不得阻塞文件遍历，也不得向 WebView 推送每个节点。

## 5. 结论

Marmot 采用“卷概览 -> 顶层快速发布 -> 深层受限并发 -> 分批快照 -> 目录汇总 -> 事件摘要”的扫描流水线。首层结果和完整结果是两个不同的用户可用性指标，必须分别测量。

### 5.1 阶段

```text
Catalog
  -> VolumeOverview
  -> TopLevelPublish
  -> DeepScan
  -> Finalize
```

- `Catalog`：列出挂载卷、容量、类型、权限和可扫描状态，不遍历文件树。
- `VolumeOverview`：读取卷根和直接子项的元数据，尽快提交首层快照。
- `TopLevelPublish`：首层数据可查询后，UI 可以进入空间图和目录列表；深层扫描继续运行。
- `DeepScan`：按目录任务遍历，受设备和全局并发上限控制。
- `Finalize`：完成目录汇总、问题汇总和快照终态。

### 5.2 并发和队列初始预算

由 `VolumeCatalog` 给每个 scope 提供 `DeviceProfile`：`ssd`、`rotational`、`network_or_virtual` 或 `unknown`。

- 全局目录 worker 上限：8；
- 单个 SSD 卷上限：4；
- 单个机械盘上限：1，同一物理设备的 scope 共享队列；
- 网络/虚拟卷上限：2；
- 未知设备上限：2；
- 目录任务队列容量：4096；
- 待提交批次数量：2；
- 队列满时生产端阻塞在受控边界，不创建无限 goroutine。

这些是第一版可测量的默认值，不暴露为用户配置。实际样本若连续违反性能门槛，只能通过新的预研和 ADR 调整。

### 5.3 缓存

- 快照仍由 SQLite 承载，不引入第二套内存树缓存；
- 可复用单元为目录条目元数据和已完成快照；
- 缓存键至少包括 `volume_id`、路径、`device`、`inode`、`size`、`mtime`、模式、扫描器版本、空间口径版本和权限指纹；
- 结果复用默认 TTL 24 小时，最多保留 3 个完整快照或 512 MB，先达到的限制生效；
- 命中缓存只能显示为“上次结果/正在复核”，完成身份复核后才标记为当前；
- 目录结构变化、权限指纹变化、扫描器/口径版本变化或条目身份不匹配时，失效该目录及其后代缓存；
- 缓存不读取文件内容，不作为清理授权，不改变快照的部分结果语义。

### 5.4 事件

- `scan-progress` 每个任务最多 5 次/秒；
- 事件只携带阶段、计数、汇总、问题数量、当前快照版本和被更新的父节点 ID；
- 同一任务使用容量为 1 的最新值槽位，旧进度被合并，不允许事件堆积阻塞扫描；
- 批次提交或阶段变化后可以发送 `snapshot-updated`，前端重新查询当前目录；
- 不发送单文件事件，不把事件当作节点传输协议；
- 客户端重连后先查询状态，再按快照 ID 拉取当前层。

## 6. 性能验收

- 本地 SSD、节点数不超过 100,000 的代表性目录，首层可浏览结果 p95 不超过 2 秒；
- 100 万节点合成快照写入继续满足 R-004 的 20 秒门槛；
- 事件频率不超过 5 Hz，事件队列不会随节点数增长；
- 取消请求到扫描停止并完成最后一个允许提交边界，p95 不超过 1 秒（真实权限/网络错误单独记录）；
- 真实扫描完整耗时按设备、节点数、冷/热缓存分别记录，不把 DaisyDisk 宣传数字当作保证。

## 7. 限制

本预研没有把真实全盘、机械硬盘、网络盘、FileProvider 和 APFS 克隆全部跑完；并发预算必须在 P0 实现后以只读样本压测。缓存的最终 SQLite schema 需要实现切片补充 migration 测试，但缓存语义已由 ADR-0014 锁定。

## 8. 对 DDD/SDD 的影响

- `ScanJob` 增加阶段和发布边界，但不改变终态语义。
- `ScanSnapshot` 必须记录阶段、缓存状态、设备 profile 和指标版本。
- `SnapshotStore` 继续是唯一快照存储端口；扫描器只产出批次，不直接依赖 SQLite。
- SDD 增加卷概览、首层发布、设备并发、缓存和事件预算。

# R-076 开源磁盘优化工具功能盘点

## 1. 问题

Marmot 现在只做一件事：把空间画出来，让人自己挑对象删。"磁盘优化"这个方向要往下走，先要知道
这一类产品**普遍**提供哪些能力、哪些能力是共识、哪些是各家自选，以及这些能力各自需要什么事实、
什么权限、什么守卫。本记录盘点 GitHub 上有代表性的开源实现，产出能力清单和许可证边界，
不产出实现方案。

## 2. 假设

- H1：这一类产品的能力可以归纳成有限几类，且大多数类目只需要"路径规则 + 元数据"，不需要新的扫描内核。
- H2：Marmot 已有的扫描事实源（全盘节点树 + 逻辑大小/实际占用）足以支撑其中相当一部分类目。
- H3：星数高的项目里，能直接复用代码的很少，多数只能作为规则线索和交互基线。

## 3. 环境与方法

- 日期：2026-09-10。
- 方法：GitHub Search API 按星数取候选（关键词 `mac cleaner`、`macos cleaner`、`disk usage analyzer`、
  `duplicate file finder`、`app uninstaller macos`），逐个读 README、命令表、模块表与规则源码目录；
  许可证与星数取自 `api.github.com/repos/<repo>` 当日返回。
- 限制：第 4-9 节只读了公开文档和规则资源，没有编译、没有逐条验证各家规则的安全边界，
  下面所有"功能"都是**它们声称的**功能。
- 第 10 节（2026-09-10 追加）读的是实现源码，并逐条对照本仓库代码；其中 §10.2 做过本机实测，
  数字标注了来源。审核中撤回的两条说法保留在 §10.2 里，不删——错在哪里比结论更值得留档。

## 5. 证据：能力分类总览

把上面所有项目的功能合并去重，落到 12 个类目。"普遍"= 多数综合型产品都有。

### A. 空间分析（普遍，Marmot 已有）
Sunburst 或 treemap + 当前目录列表 + 面包屑；边扫边显示；隐藏/受限空间单列。
各家在此之上普遍还有：**大文件**（阈值 50–100 MB）、**旧文件**（按 mtime/atime，> 1 年）、
**全树即时搜索**、**purgeable 分解**、**APFS 卷组与 firmlink 归一**、**增量重扫**、
**外接卷自动出现**。gdu 把筛选维度铺得最全：`--min-age/--max-age/--since/--until`、
`--type/--exclude-type`、`--top N`、`--no-cross`（不跨文件系统）、`--show-item-count`、
`--show-apparent-size`（逻辑 vs 占用）、JSON 导出与 `--db` 落库后 `-r` 复用。

### B. 规则型垃圾清理（普遍）
按具名类目扫已知路径。合并各家类目：系统缓存/临时/诊断日志、用户缓存、崩溃报告、
语言包、损坏的偏好设置与登录项、文档版本历史（`.DocumentRevisions`）、
邮件附件缓存（Mail/Outlook/Spark）、iOS 备份与模拟器运行时、
浏览器缓存（Safari/Chrome/Chromium/Edge/Firefox/Brave/Arc/Opera/Vivaldi）、
开发者工具缓存（Homebrew/npm/yarn/pnpm/bun/pip/poetry/uv/cargo/go/gradle/maven/CocoaPods/
JetBrains/VS Code/mise/conan/nuget/composer/gem）、AI 工具缓存（Ollama/LM Studio/HuggingFace/
Claude/Codex/ChatGPT）、容器（Docker 镜像/构建缓存）、所有卷的废纸篓。
mac-cleanup-py 的模块名单和 MangoDisk 的规则库可以直接当索引用。

### C. 项目构建产物（普遍，且被单独切出来）
CleanMyMac CLI 明确把 `clean`（共享缓存）和 `purge`（项目内可重建物）分成两个命令，理由是
后者在**用户的源码目录里**，风险性质不同。识别方式是"项目标识文件 → 相对目录"：
`package.json → node_modules/.next/.turbo`、`Cargo.toml → target`、`*.xcodeproj → DerivedData/Pods`，
再加 `.venv`、`__pycache__`、`vendor`、`build`、`cmake-build-*`。
两个通行做法：**按项目分组展示**、**只预选 7 天以上的产物**，新产物可见但不勾。

### D. 安装包残留（常见）
扫 `.dmg/.pkg/.iso/.xip` 并批量删（Mole `installer`）。MangoDisk 还有一条
`system.stale-partial-downloads`：只在 Downloads、只匹配 `.crdownload/.download/.partial/.part`、
只 7 天以上、深度 ≤ 3。

### E. 应用卸载与残留（普遍）
- **匹配引擎**：PureMac 与 MacSai 都自称"10 级匹配"——bundle ID、team identifier、entitlements、
  Spotlight 元数据、容器发现、公司名启发式、路径部分匹配，覆盖 `~/Library` 下 17+ 个子目录；
  PureMac 声称路径库有 120+ 条。
- **灵敏度分档**：Strict / Enhanced / Deep 三档，让用户选激进程度。
- **孤儿文件**：反向做——遍历 `~/Library`，和已安装应用的 bundle ID / 归一化名比对，剩下的是残留。
- **Sentinel**：常驻监听"应用被拖进废纸篓"，自动接上残留清理（Pearcleaner，约 2 MB 内存）。
- **附带**：未使用应用检测、应用重置（保留应用删数据）、Sparkle appcast 批量查更新、
  Apple 自带应用强制排除。

### F. 重复与相似（普遍）
fclones 的流水线是这一类的标准答案，逐级淘汰、每级都是并行、上一级全部完成才进下一级：
1. 遍历取 size → 2. 按 size 分组，丢弃小于下界的组 → 3. 同组内按 inode 去重（硬链接是同一份数据）→
4. 文件头小块 hash → 5. 文件尾小块 hash → 6. 全文 hash → 7. 出组。
全程不做逐字节比较，理由是 128 位以上 hash 的碰撞概率可忽略；hash 可持久化缓存，
**缓存键是 inode + mtime + 长度**，所以移动和改名不失效。
MacSai 的四级（size → 前 4 KB SHA-256 → 全量 → inode 校验）是同一思路的简化。
删除侧不只是删：可以换成硬链接/软链接，或用文件系统的 copy-on-write（reflink/APFS 克隆）**只去重数据不删文件**。
链接语义必须显式：默认不把互为链接的文件算重复，`--isolate`（跨树算重复、同树算一份）和
`--match-links`（全算重复）是两个不同选项，混用软链接选项很容易只剩一堆孤儿链接。
相似类（czkawka / lemon-cleaner / dupeguru）另有一套：感知 hash 比相似图片、抽帧比相似视频、
按 tag 或内容比同一首歌。

### G. 应用瘦身（少数）
Universal binary 里非本机架构的 slice 用 `lipo` 剥掉（Pearcleaner 自带实现，不依赖 Xcode 工具链；
MacSai 在"系统垃圾"里做同样的事），以及删语言包（Monolingual 的老本行）。
这是**改写别人的应用**，不是删垃圾，风险类别单独一档：会破坏签名，也会被应用自更新还原。

### H. 隐私清理（常见）
浏览器历史/cookie/缓存、系统最近项目、剪贴板残留，通常带时间范围过滤。

### I. 系统维护与优化（常见，边界最模糊）
释放非活跃内存（`purge`）、请求系统释放 purgeable、`tmutil thinlocalsnapshots` 精简本地快照、
重建 Launch Services、重建 Spotlight 索引、刷 DNS、重启 Dock/Finder、修复权限、
登录项与 LaunchAgents 开关管理。
两个值得注意的自律做法：MacSai 给每个任务标 severity（safe / disruptive）且 "Run All" 要额外确认；
MangoDisk 明确"系统优化只用内置且验证过的设置，绝不接受任意注册表路径、终端命令或脚本",
改完还要回读确认。

### J. 监控与历史（少数，属于另一条产品线）
CPU/内存压力/GPU/磁盘 IO/网络/电池 + 健康分 + 进程表 + 菜单栏 HUD；
burrow 在 CLI 之上加了本地 SQLite 长期指标历史和 MCP server，让 AI agent 能查这台机器。

### K. 安全与可解释性（这一类产品真正的分水岭）
- **dry-run / 只读扫描**默认：MangoDisk "默认只读扫描"，Mole/CleanMyMac CLI/kondo 都有 `--dry-run`。
- **删除前逐项复核 + 显式确认**；`--force` 存在但被明确警告。
- **保护路径与忽略清单**：`cleanmymac ignore add <path>`，永久排除在 clean/purge/analyze 之外。
- **风险分级**：MangoDisk 的 `risk = safe | recoverable | highImpact`，且只有 `safe` 允许默认勾选；
  `recoverable` 想进推荐集，必须每个 root 都 `verified_rebuildable = true`。
- **废纸篓优先**：几乎所有产品的默认路径是移到废纸篓，永久删除是单独的、需要额外同意的动作。
- **操作历史**：清理了什么、回收多少、有没有失败，落成可查的日志（`~/Library/Logs/mole/operations.log`）。
- **特权分离**：需要 root 的部分走 XPC privileged helper 或系统自带的管理员对话框，不自己存密码。
- **FDA 引导**：说清没有完整磁盘访问会漏多少（PureMac 说约 70%），提供一键跳转、轮询权限状态、
  拿到权限后自动重试失败批次；burrow 另给一条"用管理员身份扫描"绕开 TCC 弹窗风暴。
- **不吹牛**：PureMac 显式拒绝把 purgeable 算成可删垃圾，理由是第三方应用无法可靠回收它，
  连 Finder 的 purgeable 数字本身都不准；也拒绝"提速""释放内存"这类说法。Clean-Me 的 README
  甚至劝用户别删缓存。
- **AI 只解释不执行**：MangoDisk 的 AI 解释基于条目描述和当前扫描结果，给用途和注意事项，动作仍由人选。

### L. 集成与分发（常见）
CLI + JSON 输出（`--format json`、`mo status --json`）、GUI 与 CLI 共用同一清理引擎、
定时清理（含"只有值得清才真跑"的阈值）、MCP server、Homebrew cask 分发、
Developer ID 签名 + 公证、Sparkle 签名更新源。

## 6. 证据：值得单独记下来的实现细节

### 6.1 MangoDisk 的声明式规则 schema（对 ADR-0062/0068 最有参考价值）
规则是 TOML 资源，构建期校验并嵌入，运行期用同一 schema 再解析一次。目录强制为
`filesystem/<platform>/<category>/<rule-id>.toml`，类目固定 `system | browser | application |
development | ai | container`；当日 macOS 侧共 119 条（system 10、browser 12、application 56、
development 39、ai 1、container 1），另有 31 个生态的 `project-artifacts/*.toml`。
一条规则的字段分四组：

- **身份与选择**：`id`（文件名必须等于 id）、`rule_version`（语义变更就递增）、`platform`、`category`、
  `risk`、`default_selected`、`recommended_selected`、`required_stopped_processes`。
- **适用性探针** `[[applicability]]`：`anyRootExists`、`pathExists`、`applicationInstalled`、
  `applicationVersion`、`executableAvailable`、`systemVersion`、`fileSystemIn`、`capabilityAvailable`、
  `processRunning`，可用 `anyOf/allOf/not` 组合。作用只是**避免无谓遍历**，永不放松安全约束；
  探针输入不接受任意绝对路径、环境变量或命令执行。
- **根与匹配**：`roots.template` 必须以受控变量开头（`${home}` `${temp}` `${system_root}`
  `${user_library}` `${application_support}` `${darwin_user_cache}`），只能用 `/`；
  matcher 只有 `all/nameEquals/nameGlob/extensionIn/pathSegmentIn/olderThan/largerThan/smallerThan/
  maxDepth` 加布尔组合，名字匹配只匹名字不匹路径。校验器拒绝上跳、非受控变量、重复根、受保护位置，
  以及"缓存或已验证可重建边界之外的宽匹配"。
- **验证** `[verification]`：`lifecycle`（生产只收 `verified/stable/deprecated`）、
  `evidence`（必须说明为什么这份数据可丢、以及边界外保住了什么）、`verified_at`、
  `verified_platform`、权威 `references`。

执行策略两种：`deleteMatchingContents`，和可选的 `deleteWholeRoot`——把整个已验证的 root
**原子移动到同卷私有暂存目录**再删掉那棵树，省下逐文件一次受保护删除事务；但它只接受静态 root +
`verified_rebuildable` + 精确 `all` matcher + 非默认勾选，且运行期一旦发现规则不独占该 root、
原生遍历不支持、或有任何条目被跳过（链接、权限），在改动前自动退回逐项删除。
另有一条硬规矩：home 根、下载、文档、桌面、项目目录、仓库、凭据、云同步目录**不是普通缓存根**，
不允许和 `all` 或宽名字模式组合；AI 模型属于高价值可下载数据，普通规则不许碰，交由专门的清理器
在执行前逐个校验官方存储布局、共享 blob 和链接。

### 6.2 OpenDisk 的扫描与增量（与 Marmot 撞在同一条路上）
`getattrlistbulk(2)` 批量读元数据、`searchfs(2)` 做目录编目扫描；子树 4–5 个并发读者、
整卷约 8 个，理由是 APFS 串行化目录读、再高吞吐反降（与 R-022/R-024 的结论一致）；
阻塞读跑在固定线程池上从共享工作栈取活；用 per-child mount 标志在挂载点和快照卷处停下，
避免扫 `/` 时把盘算两遍。**增量重扫复用上次扫描结果并回放文件系统事件，声称比冷扫快 20–28 倍**；
自报 1 TB 冷扫 17 s（同机 DaisyDisk 37 s）。产品侧同样有收集区（拖入、看累计回收量、一次删除）
和 purgeable 分解页。

### 6.3 CleanMyMac CLI 的命令切分
`clean`（共享缓存与工具垃圾）/ `purge`（项目内可重建物）/ `analyze`（交互式空间浏览）/
`optimize ram|purgeable` / `ignore add|list|remove`。`analyze` 只读，任何删除都要显式选择加确认。
这套切分的价值在于**按"这份数据属于谁"分命令**，而不是按"能省多少"分。

## 7. 结论

1. H1 成立。12 个类目里只有 A（空间分析）和 F（重复检测）需要扫描内核级别的能力，
   B/C/D/E/G/H 本质都是"路径规则 + 元数据判定 + 守卫"，I/J/K/L 与扫描无关。
2. H2 成立且比预期更强。Marmot 的全盘节点树已经带 size / mtime / 类型 / device+inode
   （R-073 已确认 inode 单调不复用），所以**大文件、旧文件、项目构建产物、安装包残留、
   重复候选按 size 分组、孤儿文件比对**这几项都不需要新扫一遍盘，是对现有事实源的查询。
   重复检测只有 hash 阶段需要额外读盘，且只读候选组。
3. H3 成立。可直接读代码的只有 MIT/BSD 那几个（PureMac、OpenDisk、fclones、gdu、MacSai、
   kondo、Sloth、uninstally）；Mole 当前 `main`、MangoDisk、lemon-cleaner、dupeguru、rmlint、
   XcodeCleaner、DevCleaner、Monolingual 都是 GPL，Pearcleaner 是 Apache-2.0 + Commons Clause（非 OSI）。
   GPL 项目只能当**研究线索**——MangoDisk 自己也把第三方项目定位成 research leads，规则要独立验证后才收。
   这与 ADR-0004/0005 已有的 Mole 隔离策略同构，不需要新策略，只需要把它套用到规则线索上。
4. 规则该长什么样，业界已有可抄的形状：MangoDisk 的 schema 把"身份 / 适用性 / 根与匹配 / 验证"
   四组分开，且**风险等级决定是否允许默认勾选**。Marmot 的规则目录（ADR-0062/0068）目前是
   识别与守卫合一，缺的是 `rule_version`、`applicability` 探针、受控根变量白名单、
   以及 `verified_at` + `evidence` + `references` 这套可审计字段。
5. 一个必须正视的差异：**Marmot 的直接删除比盘点到的每一个产品都激进**。所有产品的默认路径
   都是废纸篓，永久删除是单独的、需要额外同意的动作；PureMac 甚至在 README 里逐项列出
   "哪些流程会永久删除"。ADR-0063 已经把这条定成硬边界，但对照之后，缓解手段就该学它们：
   风险分级决定默认勾选、忽略清单、操作历史、以及"回收多少"的事后汇总。
6. 有三件事业界普遍做而 Marmot 已明确不做，不需要改主意，但应该在文案上学 PureMac 的说法：
   宣称回收 purgeable（不可靠）、释放内存/提速（无法验证）、安全擦除（已在不做清单里）。
   本地 APFS 快照占用是唯一值得单独对待的：它确实是"看得见删不掉"的主要来源，
   系统自带 `tmutil thinlocalsnapshots` / `deletelocalsnapshots` 是唯一正路，
   把它作为**可解释的事实**展示（而不是当垃圾去删）是诚实的做法。

## 8. 限制

- 全部结论来自公开文档与规则资源，没有编译或实测任何一个项目；各家声称的性能数字（OpenDisk 17 s、
  增量 20–28 倍）未在本机复现。
- 星数、许可证、规则条数是 2026-09-10 当日快照，会漂移。
- 没有评估任何一条第三方清理规则的安全性——按 MangoDisk 自己的标准，规则必须逐条独立验证，
  本记录不构成规则来源。
- 相似图片/视频的算法只看了功能描述，没有看实现，感知 hash 的具体口径未确认。

## 9. 对 DDD 与 SDD 的影响

### DDD
- 需要一个比"清理建议"更宽的概念层：现在的规则目录既管识别也管守卫，但盘点显示业界的规则
  还带**适用性**（这台机器上有没有这个应用/命令）和**可重建性**（这份数据丢了能不能自动长回来）
  两个独立维度，后者才是风险分级的依据。
- "重复"和"相似"不是同一个领域概念：前者是内容相等（可用 inode/hash 判定，可判真假），
  后者是感知相近（只能给候选，必须人看）。合成一个概念会污染守卫。

### SDD
- A 类的补位项（大文件、旧文件视图）属于对现有内存事实源的查询，走 `MapQuery` 同一条路，
  不新增扫描阶段。
- F 类需要在 SDD 里新增一个阶段化的重复检测契约：size 分组（复用现有节点表）→ inode 折叠 →
  头/尾块 hash → 全文 hash，每级可取消、可给进度；hash 缓存键必须是 inode + mtime + 长度。
- C 类需要"项目标识文件 → 相对产物目录"的规则形状，与现有的"绝对路径根 + matcher"不同形，
  应作为规则目录里的第二种规则类型，而不是硬塞进第一种。
- K 类里 Marmot 缺的是忽略清单与操作历史两个契约。

### 建议的后续 ADR
1. **规则目录 schema 升级**：引入 `rule_version`、适用性探针、受控根变量白名单、
   `verified_rebuildable` 与可审计的验证字段；确定"只有 safe 允许默认勾选"是否作为硬约束。
   （在 ADR-0062/0068 之上做增补，不推翻。）
2. **重复文件检测的阶段契约与守卫**：分级流水线、链接语义（默认不把硬链接算重复）、
   每组至少保留一份的强制约束、以及 APFS 克隆已经不占额外空间时的口径
   （与 ADR-0008 的"去重后占用"字段对齐）。
3. **项目构建产物作为第二种规则类型**：识别锚点、按项目分组、7 天预选的默认值。
4. **忽略清单与操作历史**：作为直接删除（ADR-0063）的配套缓解，定清单的作用域
   （扫描/建议/删除三处是否一致）和历史的保留边界。
5. **本地 APFS 快照与 purgeable 的展示口径**：只展示与解释，不纳入可删对象；
   与 ADR-0019/0052 的容量语义对齐。

## 10. 代码级复核：对 Marmot 明显有增量的机制

第 4-9 节只读了文档。这一节读的是实现，并逐条对照 Marmot 现有代码，只留下"我们缺、且拿得到"的部分。
按（增量 × 可行性）排序。

### 10.1 冷启动秒开：持久化扫描缓存 + FSEvents 历史回放（最大的一项）

**机制**（`OpenDisk/Services/Scanning/ScanCache.swift`、`SystemInterop/FSEventsChangeJournal.swift`、
`IncrementalUpdater.swift`，MIT）：

1. 扫描**开始前**取 `FSEventsGetCurrentEventId()`，和扫完的树一起落盘。
2. 下次扫同一个根，用这个 eventID 作 `FSEventStreamCreate` 的 `sinceWhen`，
   macOS 的**按卷持久化事件日志（跨重启保留）**会把这段时间的目录级变更重播出来，
   等 `kFSEventStreamEventFlagHistoryDone` 表示重播结束。
3. 只重读变了的目录：普通事件 → 浅重读该目录；带 `MustScanSubDirs` → 整棵子树重扫。
4. 任何一条不成立就整份丢弃、退回全扫：`EventIdsWrapped | UserDropped | KernelDropped | RootChanged`、
   变更目录数超过 `40_000`、重播超过给定 timeout（timeout 按被替代的全扫成本定，
   "增量路径不能花掉全扫的可观比例"）、任务取消。原始事件数超过 `40_000 × 4` 就提前放弃，
   因为结论（全扫）已经定了，再流完日志只是拖延。
5. 缓存头部除了 eventID 还存**根路径 + device id**，两者都必须对上——同一挂载点换了一块盘
   或重新格式化过，不能复活旧树。
6. `peek()` 只解析头部不解树，于是日志重播可以和树的反序列化**并行**开始；文件字节数当作
   "上次扫了多大"的廉价代理，用来定重播的时间预算。
7. 变更目录去重后**按路径深度排序，父在子前**：新建目录还没有节点，它由最近的、也收到事件的
   祖先在浅重读时收养。
8. 缓存树落盘时**目录尺寸不做上卷**，拼接完再统一 roll-up 一次。
9. 缓存淘汰：最多 8 个文件 / 4 GB，按 mtime 新的优先保留，刚写的那个永远保留；
   顺带清掉 1 小时以上的 `.tmp`（崩在 create 和 replace 之间的残留）。

**证据**：README 自报重复扫描比冷扫快 20-28 倍。

**Marmot 现状**：拼图缺一块。已有的是——
`internal/platform/fileevents_darwin.c` 的 FSEvents 监听、
`internal/application/liveupdate.go` 已经处理 `MustScanSubDirs` 与 `Dropped`（`pending[path] || MustScanSubDirs`）、
目录浅重读与子树重读（ADR-0070/0072，R-072 实测 25k-207k 节点目录重读 0.5-1.4 s）、
`group()` 约 70 ms、R-074 已量过全盘事件量（空闲机器每秒 1-1.5 个事件）。
缺的恰好是持久化和回放这一环：`FSEventStreamCreate` 现在传的是 `kFSEventStreamEventIdSinceNow`
（`fileevents_darwin.c:29`），从不取当前 eventID，也没有 `EventIdsWrapped`/`RootChanged` 的标志位；
快照持久化在 ADR-0055 被取消，`internal/infrastructure/snapshot/binary/{format,reader,writer}.go`
在提交 `3d9546e` 一并删除。

**落地代价**：比看起来小。序列化器在仓库历史里存在过，可以从 `3d9546e^` 取回来改；
回放产出的变更目录清单可以直接喂给现有的实时更新拼接路径；新代码主要是
"取 eventID + 头部校验 + 回放与放弃条件 + 缓存淘汰"。

**与 ADR-0055 的关系**：需要一个新 ADR，但不必推翻它。ADR-0055 的主张是**内存是唯一事实源**，
而这份缓存不是第二个事实源，是内存树的**种子**：要么被回放完整校验后升级为内存树，要么整份丢弃重扫，
永远不存在"半可信的旧事实"。这条边界必须写进 ADR，否则它就退化成 ADR-0055 要消灭的东西。

**已实测（R-078，2026-09-10）**：树落盘 227.5 MiB，读回并重建分组 **0.25 – 0.30 s**；
FSEvents 回放 1 h 0.6 s、6 h 1.5 s、24 h 7 – 11 s、7 天 178 s 且 `UserDropped`（不可用）。
所以"秒开"只在闲置 6 小时以内成立，24 小时是"快一倍"，一周必须全扫；放弃条件可以在回放前由 ID 跨度判定。
OpenDisk 的"20 – 28 倍"对应的是短闲置。数字与预算见 R-078 §4 – §5。

### 10.2 回收量口径：克隆双计、硬链接高估（已实测，且是 ADR-0008 未落地）

**这条在 2026-09-10 做过审核和本机实测，下面的数字都是量出来的，不是推断。**

**先纠正一处引用错误**：生产扫描路径是 `native_darwin.go`（`scanner.Scanner` 在 MountResolver
非空时走 `scanConfiguredTree`，darwin 版在 `native_darwin.go:819`），不是 `scanner.go`。
两处的硬链接折叠逻辑相同，但本节此前引的 `scanner.go:153` 是非生产的 Go 回退路径，
实际生效的是 `native_darwin.go:1098-1107`。

**现状**：
- 硬链接"先到先得"折叠：`native_darwin.go:1098`，`linkCount > 1` 且已见过 `(device, inode)` 的
  后续节点 `OwnedAllocated = 0`，并向父目录追加一条 `-AllocatedSize` 的修正增量。
- 克隆**读到了但没用**：原生扫描的 bulk 请求带了 `forkattr = ATTR_CMNEXT_PRIVATESIZE`，
  调用处传 `FSOPT_ATTR_CMN_EXTENDED`（`native_darwin.go:318, 479`），每条记录都拿到了私有大小，
  然后在 `:1041` 处 `_ = entry.has_private` 丢弃——那段注释引 R-065 说明了为什么不能拿它替换 allocated。
  没有请求 clone ID / `ATTR_CMNEXT_EXT_FLAGS` / `CLONE_REFCNT`。克隆的 `linkCount` 是 1，走不进上面那条折叠。
  （本节上一版写"原生扫描没有请求 private size"，错在只看了 `:315` 没看 `:318`。）
- 收集区徽标是**直接求和**：`entrySize` 取 `entry.ownedAllocated`（`App.tsx:399`），
  `collectorBytes = selected.reduce(...)`（`App.tsx:1804`），显示在 `App.tsx:3650`。
- `cleanup.HasOverlappingPaths` 只挡嵌套路径，挡不住"两条路径指同一份数据"。

**实测**（本机 APFS，8 MB 文件，`ln` 造硬链接、`cp -c` 造克隆，
`internal/probe/hardlink_attribution_probe_test.go`）：

| 场景 | 扫描器记账 | 删除后卷可用空间实际变化 |
| --- | --- | --- |
| 克隆对，删其中一个 | 两个各报 8192 KB（合计 16384 KB） | `-32 KB`（即没回收，噪声） |
| 克隆对，再删另一个 | — | `+8192 KB` |
| 硬链接对，删记账方 | 记账方 8192 KB、另一条 0 KB | `0 KB` |

也就是：**克隆对整整高估 2 倍；硬链接对若只收集记账方，承诺 8 MB、实际回收 0。**
方向都是高估——危险的那一侧。反过来收集非记账方那条会显示 0 字节，困惑但安全。

**撤回一条上一版的说法**："记账方随扫描顺序漂移"。9,604 个文件、硬链接对分放在同深度的
两个目录里，连扫 12 次，记账方 12/12 稳定不变。结构上（并发批次 + 先到先得 + 无规范路径裁决）
它是可能的，但**没有观察到**，不作为动手的理由。

**再撤回一条**："我们已经有解，用 `PRIVATESIZE` 就行"。太轻率了。实测
`ATTR_CMNEXT_PRIVATESIZE` 对克隆对的**两个成员都返回 0**（私有 0、共享 67.1 MB），
这个值本身是对的——单独删任何一个确实回收 0——但把它当收集区的求和项，
整组都被收集时又会**低估**成 0。正确语义必须是分组的：一组完整克隆的可回收量 =
各自私有部分之和 + 共享区段计一次，且只有整组都被收集时才计。
另外 `platform.ReadFileSizes` 目前在生产代码里**没有任何调用方**，只有
`internal/probe/clone_probe_test.go` 这个探针用它，属于预研遗留，不是可直接接线的能力。

**这不是新发现，仓库里已经有 R-065《APFS 克隆双计与规则表的可达范围》**。它 §2 用 Preboot 里
342 MB 私有 0 的文件确认了克隆双计"量级很大"；§2.1 试过用私有大小替换 allocated，Preboot 从 45.7 GB
变成 3.77 GB 而 `df` 说 17 GB——**2.5 倍高估换成 4.5 倍低估**，已回退，理由有三：画图问"占多少"要 allocated、
建议问"删了拿回多少"要 private，是两个问题；封印系统卷上每个文件私有大小都是 0，整个 macOS 会显示成 0 GB；
该属性在系统快照卷上根本不返回，同一棵树会被两种方式量。§2.2 说无法归属的共享块该进"隐藏空间"平衡项；
§4 明说两个数模型**没有实现**。ADR-0008 原文也早写了"完整克隆按 clone group 归属一次、
按稳定的卷内规范路径选择唯一归属节点"。

所以本节真正新增的只有三点：收集区一侧的端到端复现（承诺 vs `df` 实际变化）、硬链接记账方那一侧的高估、
以及"私有大小对克隆对两个成员都是 0，收集区的口径必须按 clone group 分组"这个语义约束。

**上一版说"唯一未知数是代价"，现在这个问题已经答了**：属性本来就在同一次 bulk 调用里，扫描已经在付这份钱。
剩下的未知只有两个小的：再加 `ATTR_CMNEXT_CLONEID / CLONE_REFCNT / EXT_FLAGS` 每条记录多几个字节的代价
（同一调用，预期可忽略，未量）；以及 R-065 §2.1 第 3 条——扩展属性在封印系统快照卷上不返回，
克隆身份恰恰在共享最多的地方拿不到。这两条不阻塞 ADR，可以在实现切片里量。
性质是**补齐 ADR-0008 / R-065 §2.1 的"两个数模型"**，可以直接起草 ADR。

### 10.3 删除的感知性能：同卷 rename 到暂存目录

**机制**（MangoDisk 的 `deleteWholeRoot`）：把已验证的整个根 `rename(2)` 到**同卷**的私有暂存目录，
再删那棵树。它的说法是省下"每个文件一次受保护删除事务"；对我们更重要的是 `rename` 是 O(1)：
对象在用户眼里**立刻消失**。
它的接受条件很紧：静态根、`verified_rebuildable`、精确 `all` 匹配、非默认勾选；
运行期一旦发现规则不独占该根、原生遍历不支持、或有任何条目被跳过（链接、权限），
**在改动任何东西之前**退回逐项删除。

**Marmot 现状**：4 worker 直接删，实测约 62k inode/s（见记忆里的 APFS 吞吐测量），
一个 50 万文件的 `node_modules` 树就是 8 秒；进度环在 1.5 s 后才出现（ADR 的删除进度设计）。
身份校验（ADR-0071：只核对 device + inode + 类型）发生在删除前，正好是 rename 之前该做的事。

**增量**：把"用户等待"从 8 秒压到一次 rename。删除仍然真实发生，只是移到后台；
崩溃后暂存目录要能被下次启动清理（OpenDisk 的 `.tmp` 清扫是同一类问题的同一类解法）。
风险点必须写清：跨卷时 rename 失败要退回逐项删除；暂存目录必须在同卷且是私有的；
"已删除"的对外口径要和"字节已回收"分开——前者 rename 完成即成立，后者要等后台删完。

### 10.4 工作队列纪律：**撤回**，见 R-077

前提读错了。worker 派发子目录走 `marmot_native_queue_try_push`，队列满时返回 `-1`，随后**在当前 worker 上
就地处理**（`native_darwin.go` 的 `marmot_native_schedule_children`）；阻塞版 `push` 只用于根任务。
所以生产者从不阻塞。R-077 加计数器实测真实 `/` 三次：队列全程 4096/4096 满，
`try_push` 撞满约 48 万次（60.6 万目录的 79%），**82 – 84% 的节点走就地路径**，就地递归最深 22 – 26 层，
worker 饥饿等待合计 < 0.5 s。实际遍历已经是 DFS 主导，队列纪律不是瓶颈，"换 LIFO"没有意义。

R-077 顺带发现的是另一件事：就地处理复用了父目录的 256 KB 页缓冲和 batch，而 `flush_batch` 在
**页读取中途**（累计条目跨过 8192）也会被调用，此时若走就地处理，父目录剩余记录会被子目录数据覆写。
本机有 10 个目录超过 8,192 项（最宽 67,614），三次扫描均未触发（`midpage_inline = 0`），但结构上成立。
这才是该处值得立 ADR 的东西。

### 10.5 重复文件：分级流水线，加上我们独有的克隆感知

**机制**（fclones）：size 分组 → 同 inode 折叠 → 头部小块 hash → 尾部小块 hash → 全文 hash，
每级并行、上一级全部完成才进下一级、每级都剪掉小于下界的组；全程不做逐字节比较
（128 位以上 hash，碰撞概率可忽略）。hash 持久化缓存的键是 **inode + mtime + 长度**，
所以移动和改名不失效。链接语义必须显式：默认不把互为链接的文件算重复。
删除侧不止删——可以换成硬链接，或用 reflink/APFS 克隆**只去重数据不删文件**。

**Marmot 现状**：没有任何重复检测。但前四级几乎是免费的：
`memtree` 的 record 里已经有 `logicalSize`、`device`、`inode`、`modifiedUnix`
（`table.go` 的 56 字节布局），所以 size 分组和 inode 折叠是**对现有内存表的一次遍历**，
不读盘；只有 hash 阶段要读盘，且只读候选组。

**我们的差异点**：`ATTR_CMNEXT_PRIVATESIZE` 让我们能对一组"内容相同"的对象再回答一句
盘点到的产品都答不出的话——"这几份是 APFS 克隆，删掉任意一份回收 0 字节"。
去重的正确终点在 APFS 上未必是删除，可能是克隆（fclones 的 `dedupe` 子命令就是这个意思）。

### 10.6 大文件与旧文件的平面视图（几乎免费）

**机制**：所有产品都有（阈值普遍 50-100 MB / 1 年以上），且普遍**默认不勾选**。
gdu 的参数面是这一类查询的完整维度表：`--min-age/--max-age/--since/--until`、`--type/--exclude-type`、
`--top N`、`--no-cross`、`--show-item-count`、`--show-apparent-size`。

**Marmot 现状**：空间图只能按层下钻，没有跨层的平面榜单。
但 `memtree/evidence.go` 的证据装配已经在做一次全表后序遍历，并且已经在算
"子树文件数、最大单文件、扩展名画像、项目源活跃度"——比一个 top-N 榜单要的东西多得多。
所以这是对现有事实源的一次查询，不是新扫描，也不需要新权限。

### 10.7 忽略清单（直接删除的唯一现实缓解）

`cleanmymac ignore add/list/remove` 把路径永久排除在 `clean`、`purge`、`analyze` 之外——
注意它连**分析**都排除。对 Marmot 的意义在第 7 节第 5 条已经说了：
我们的直接删除比盘点到的每个产品都激进，而忽略清单、风险分级决定默认勾选、操作历史
这三件事是它们用来平衡激进度的东西，我们一件都没有。
需要定的边界是：清单作用于扫描、建议、删除三处是否一致（CleanMyMac 选择了一致）。

### 10.8 两条负面结论（省下要做的事）

- **searchfs 不用再考虑**。OpenDisk 实现了它（`CatalogScanner.swift` + `SystemInterop/SearchFS.swift`），
  然后在自己的注释里写明：只对 HFS+ 值得，"在 APFS 上比并行 `getattrlistbulk` 遍历慢约 2 倍
  （400 万条目的卷上约 15 万条/秒 vs 约 32 万条/秒），且任何并发的卷修改都会以 EBUSY 中止它"，
  所以 `ScanEngine` 在 APFS 上优先遍历。这**独立验证了 ADR-0021** 的选择，
  也意味着这条路不必再花时间。
- **应用清单 / 最近使用时间不用再试**。业界（PureMac、MacSai 的"10 级匹配"，Pearcleaner 的孤儿查找）
  把它当核心能力，但 R-069 已经在本机量过：属主应用信号在 Caches 里只触及 4% 的字节，
  "孤儿"几乎全是 `com.apple.*` 守护进程，最近使用时间没量到。结论不变，不进下一轮。

### 10.9 一个小缺口：Xcode 分项口径

DevCleaner（`vashpan/xcode-dev-cleaner`）把 Xcode 拆成六项：Device Support（每个系统版本 2-5 GB，
最占地方，默认勾选但**保留每个系统的最新一版**）、Archives、DerivedData、Documentation Cache、
旧的模拟器与设备日志、旧的离线文档下载。
我们的目录（`rules.go`）有 DerivedData、Archives、iOS DeviceSupport、CoreSimulator 四项，
缺 Documentation Cache 和旧日志两类。
另有一个执行细节：**已下载的模拟器运行时是磁盘映像，得用 `simctl runtime delete` 删，不能 `rm`**
（PureMac 就是这么做的）——这类"删除方式不是 unlink"的对象，在我们的模型里应该走
类似 `Manual` 的分支，而不是当普通目录交给删除器。

## 11. 修订后的优先级建议（2026-09-10 审核与预研后）

1. **10.2 回收量口径**——已实测的缺陷（克隆整整 2 倍高估，硬链接承诺 8 MB 回收 0），
   且 R-065 §2 早已记录、§2.1 已试错、ADR-0008 已定方向，属性也早已随 bulk 调用取回。
   **不需要再预研，直接起草"两个数模型 + clone group 归属"的 ADR**；clone ID 属性的代价和
   封印卷上属性缺失的处理放进实现切片里量。
2. **10.1 冷启动**——R-078 实测：加载 0.3 s；回放 ≤ 6 h 为 0.6 – 1.5 s、24 h 为 7 – 11 s、7 天不可行且不可靠；
   放弃条件可由 ID 跨度提前判定。收益真实但比借来的数字窄：**是"闲置半天内秒开"，不是"永远秒开"**。
   起草 ADR，且第一个实现切片必须补量拼接成本（R-078 §6）。
3. **10.6 大文件/旧文件** + **10.7 忽略清单**——不变：对现有事实源的查询或一张清单。
4. **10.3 删除感知性能**——不变：先写清同卷、崩溃残留、"已删除"与"已回收"分开三条边界。
5. **10.5 重复文件**——不变：前四级免费，hash 阶段可控。
6. **10.4 队列纪律**——**撤回**。替换为 R-077 §5.3 的就地处理页缓冲别名隐患：给就地处理独立缓冲，
   或页中途禁止就地；`midpage_inline` 计数器可作为永久守卫。
7. **10.9 Xcode 缺口**——不变。

# R-070：识别与守卫合并的等价性度量

- 日期：2026-09-05 ~ 2026-09-07
- 机器：8 核 / 16 GB / 内置 NVMe / APFS 未加密 / FileVault 关闭
- 目的：为 [ADR-0068](../adr/0068-识别与守卫合并为单一规则目录.md) 提供数据；本文只记度量与其推翻的结论，不记决策。

## 1. 起因：一次自造的矛盾

面板新增「这是什么／能不能重建」区域时，`DescribeNode` 同时调用了 `Match()` 与
`IrreplaceableReason()`，把两者的结果并列显示。实测：

```
~/Documents/proj/node_modules   Match=node_modules  recovery=redownloadable  Irreplaceable="user_content"
~/Documents/proj/build          Match=—             recovery=—               Irreplaceable="user_content"
~/Desktop/app/target            Match=—             recovery=—               Irreplaceable="user_content"
```

第一行在面板上同时出现「可重新下载」与红色「不可重建」，且红的那句是错的。

**这不是原设计的缺陷。** [ADR-0067](../adr/0067-清理建议的事实与结论分层.md) 已明确决定
「规则建议**不**带位置护栏（`GuardsFor` 只用于模型主张）」，理由与上表第二、三行完全一致：
位置护栏把 `~/Documents` 下的一切视为用户内容，套在规则结论上会让 Documents 里每个项目的
构建产物变成 `risky`。矛盾由新增的消费方引入，领域层此前是对的。

同时暴露第二个缺陷：`DescribeNode` 把 `IrreplaceableReason` 的**返回码**直接传给了面板，
所以那行红字实际渲染为「不可重建：user_content」——`IrreplaceableMessage()` 就在旁边没有被调用。

### 2.1 按项数排优先级会排错

先前用项数估过一次：`~/Library/Caches` 一级 40/40 命中、`~/Library` 一级 2/39。据此把

**2.6%**——缓存目录数量多但都很小。项数与字节在此处结论相反，字节是对的口径。

### 2.2.1 更正：`Residue` 不等于"没有规则覆盖"

上表按 `Residue` 排序，而 `Residue` 的定义是"未被**保留的子节点**覆盖的部分"，与"未被**规则**
覆盖"是两件事。据此写规则时踩了三次：

- `~/.gradle/caches/8.13` 排在表上 0.56 GB，据此以为 `~/.gradle` 那 18 GB 无人认领。实际目录里
  **已有 8 条版本无关的 Gradle 规则**（`caches/build-cache-*`、`caches/modules-*`、`caches/jars-*`、
  `caches/*/transforms` 等），18 GB 的绝大部分早已被覆盖，0.56 GB 是版本目录里那些规则之外的残余。
- `~/AndroidStudioProjects/*` 排 2.6 GB，而单个模块 4.4 GB 的 `build` 里有 3.7 GB 是
  `build/intermediates`，**那条规则也已存在**。项目侧不需要新规则。
- `Telegram postbox/db_sqlite` 排 0.62 GB，但它是聊天记录本身，是**守卫**而非清理项。

**用法更正**：这份工单是"哪里的字节没被解释"，不是"哪里缺规则"。写规则前必须先
`grep Pattern` 查现有目录，并核对 `du` 的真实分布——两次都由现有测试兜住（
`TestGradleCacheIsSplitByWhatItCostsToGetBack` 拦下撞名与更窄的模式，
`TestNoRuleClaimsTheWholeGradleCacheDirectory` 拦下一条会触发折叠的通用规则）。

按此更正后真正缺规则的是：Android SDK（0 条，约 9.5 GB）、`.lldb/module_cache`、
`Library/Application Support/Code/CachedExtensionVSIXs`、`.gradle/wrapper`、`.gradle/daemon`。

## 3. 合并的等价性度量

### 3.1 方法

`TestCorpusAnswers` 冻结 43 条路径的答案（`rule` / `recovery` / `risk` / `generic` / `guards`），
路径手写而非取自真实磁盘：真实语料会把项目名、雇主名带进仓库，且只能在采集它的那台机上复现。
每一步重构的评审对象是这份 golden 的 diff，而不是代码。

### 3.2 结果

合并 5 张守卫表（`homeRelativeIrreplaceable`、`anywhereIrreplaceable`、`suffixIrreplaceable`、
`loginStatePaths`、`gitTransient`）进目录后，全部差异 **28 行**：

- **27 行**：`rule=—` → 获得身份（`~/Documents` → 用户文档、`~/.ssh` → SSH 密钥、
  `**/.git` → 版本库历史……），**守卫码逐条不变**。这是第 2 节「仅守卫命中、无身份」那 11.5 GB 的直接收益。
- **1 行**：`~/Documents/proj/node_modules` 的 `guards=[user_content]` → `[]`，即第 1 节那个矛盾。

专门做过一次只看「守卫消失」方向的审计（唯一会丢文件的方向），结果只有上述那一行。

### 3.3 两张表合一后零差异

`Catalog` 与 `AbsoluteCatalog` 合并为一张、匹配域改为 `Rule.Anchor` 字段后，golden **零差异**。
第四个 `Recovery` 取值（`reauthenticate`）引入时差异 4 行，全部是登录状态规则获得该值，
`risk` 与守卫码不变。

## 4. 被度量推翻的三个结论

### 4.1 「把 18 条 `**/` 规则改为按完整路径匹配」——错

`Catalog` 中 18 条 `**/` 模式（`**/node_modules`、`**/target/debug`、`**/__pycache__`、
`**/GPUCache` 等）语义上位置无关，却锚定在家目录，与 ADR-0063 §3 记录的 `**/` 守卫洞同源。
拟改为 `AnchorPath`。全盘扫描（2,620,670 节点）度量其收益：

| 分组 | 家目录外命中 | 字节 |
| :-- | --: | --: |
| 浏览器缓存 6 条 | **0** | 0 |
| 项目/SDK 12 条 | 50 | 0.66 GB |

浏览器 6 条收益为零。项目 12 条命中的 50 处**全部**是应用包内部或 Homebrew 全局前缀：

```
/Applications/Visual Studio Code.app/.../extensions/copilot/node_modules/...
/Applications/ChatGPT.app/Contents/Resources/cua_node/lib/node_modules
/Applications/RustRover.app/.../python3.12/test/__pycache__
/opt/homebrew/lib/node_modules/...
```

这些是应用自带负载，不是项目依赖；标为 `redownloadable` 是 npm 不会兑现的谎。
`cleanup.DeleteBlock` 拒绝了其中 **0 处**。18 条全部保持 `AnchorHome`。

### 4.2 应用包内部是一个已在生效的缺陷

上一条的度量顺带证明该问题**不依赖任何改动即已存在**。家目录内、下限 8 MB：

```
~/Downloads/Realm Studio.app/Contents/Resources/app.asar.unpacked/node_modules   （及其 4 个子节点）
```

被 `**/node_modules` 命中、标为「可重新下载」、`DeleteBlock` 不拒绝，可拖入收集区并删除。
体积仅 0.01 GB，但标签为假且动作不可恢复，而 `~/Downloads`、`~/Applications` 正是放应用的位置。

具体度排序无法修正它：`**/node_modules` 是**自身命中**，任何 `**/*.app` 规则只能是**继承命中**，
自身胜。此处需要「在 X 内部」压过「是 Y」，与 `~/Documents` 那个案例方向相反——因为
`~/Documents` 是位置，`.app` 是原子单元，其内部不是可独立寻址的对象。

### 4.3 「`Risk` 应改为从 `Recovery` 派生」——错

`Rule.Risk` 不是与 `Assess` 竞争的第二个答案，而是它的输入：
`Rule.Risk` → `Facts.Declared` → `baseline()` 的起点 → `Assess` 可上调但不重算。
ADR-0067 §1 与代码注释均已说明理由：`Recovery` 推不出 `Risk`，两个 `regenerable` 的对象
重建 40 GB 与重建 3 MB 的干扰完全不同，只有规则作者知道是哪一种。

真实问题仅是命名：`Rule.Risk` 与 `Assessment.Risk` 同名而分别表示声明与结论。

## 5. 未解决的度量缺口

- **可操作性算不出来**：`scan.Node` 无属主字段，scanner 未取 `ATTR_CMN_OWNERID`，
  所以「这条路径删得动吗」只能靠 `Rule.Manual` 逐条硬写。要为 `/Library` 一类共享位置写规则时会撞上。
- **`protectedTrees` 不含 `/Library`**：`/Library/Application Support/...` 可通过 `DeleteBlock`
  并变成可暂存的建议，但删除时 EACCES。第 4.1 节的浏览器规则若曾扩大，会直接落进这个洞。
- **`~/Downloads`（1.70 GB）无法用现有机制表达。** 它需要被**识别**（"下载目录"）而不该成为
  **建议**：里面混着可重新下载的安装包与只此一份的东西，整块给任何一个 `Recovery` 都是过度声称。
  `Match` 的结果会进建议通路，所以加一条识别规则等于加一条建议。缺的是"仅识别、不建议"的区分
  （`Rule.Suggest` 一类）。`Downloads/*.dmg`、`Downloads/*.pkg` 两条按年龄条件的规则不受影响。
- **`~/.codex`（sessions 757 MB + logs_2.sqlite 746 MB）需要一个判断，不是一条规则。**
  本机的 AI 会话记录算不算用户数据？若算，它是守卫（irreplaceable）；若不算，它是可清理的日志。
  这个判断影响所有同类工具（Codex、Claude Code、各 IDE 的助手），不该在写规则时顺手定。
- 大小写：`suffixIrreplaceable` 原先比较小写化的完整路径，迁移为 `**/*.ext` 段匹配后区分大小写。
  语料中 `~/Pictures/Trip.PhotosLibrary` 一行记录了这个差异：守卫码仍为 `user_content`（由
  `Pictures` 规则给出），仅身份从「照片图库」降为「图片」。

# R-073：删除前校验的内容复核

- 日期：2026-09-08
- 机器：8 核 / 16 GB / 内置 NVMe / APFS / macOS 26 (Darwin 25.5.0)
- 目的：为 [ADR-0071](../adr/0071-删除前只核对身份不核对元数据.md) 提供依据。本文只记事实与推理，不记决策。

## 1. 起因

R-072 之后使用方问：删除时"目录变化了导致删除失败"是否也解决了。没有——删除前的校验
（`validateCleanupItem`）拿磁盘当前状态与快照记录比三层：设备号 + inode；类型；大小 + mode + 修改时间。
第三层一不等就拒绝，提示"扫描之后内容有变化（多半是仍在被写入的缓存），重新扫描后再试"。

随后使用方问了更根本的问题：**为什么删除前要做这个比对？**

## 2. 这个比对在回答什么问题

把三层拆开看，它们回答的不是同一个问题：

| 层 | 回答的问题 | 出错的后果 | 误报的频率 |
| :-- | :-- | :-- | :-- |
| 设备号 + inode | 路径现在指的还是用户在图上点的那个对象吗 | 删掉一个用户从未看过的对象 | 几乎没有（见 §3） |
| 类型 | 同上的另一面（文件 / 目录 / 符号链接） | 同上 | 几乎没有 |
| 大小 / mode / mtime | 这个对象和用户看它的时候一模一样吗 | 用户看到的数字与实际删掉的不同 | **对活缓存几乎必发**（见 §4） |

前两层守的是"删的是不是那个东西"，删除不可撤销（ADR-0063），这一点不能错。第三层守的是"那个东西
有没有变"，而用户的意图是删掉这个对象，不是删掉扫描那一刻的字节快照。

## 3. APFS 的 inode 号不复用

身份检查的可靠性取决于 inode 号会不会被新对象接手。HFS+ 会复用。APFS 实测（`/System/Volumes/Data`，
`disk3s5`）：

```
file 142963506 -> recreated 142963507 (dir 142963508)
file 142963507 -> recreated 142963509 (dir 142963510)
file 142963509 -> recreated 142963512 (dir 142963513)
```

删掉再建，号码单调递增，从不回到旧值。所以"同一路径、同一设备号、同一 inode"在 APFS 上就是同一个对象，
身份层不需要第三层来加固。firmlink 曾让这一层误报，R-071 / SDD §13f 已修。

## 4. 第三层为什么几乎必发

目录的 mtime 在其**直接子项**增删时变化。一个仍在被写入的缓存目录（浏览器缓存、构建输出、包管理器缓存）
从扫描到用户点删除的这几十秒里，几乎一定有子项增删。这正是用户最常想删的那一类对象——检查在它最该放行
的地方拦下，在它想防的场景（用户看的时候是旧产物、几秒后有人往里放了重要东西）几乎不会发生。

第三层唯一有用的副作用是保证用户看到的大小是准的。这个需求现在有更直接的解法：ADR-0070 的目录就地重读
0.5-1.4 s 就能把该目录换成当前状态，收集区显示当前大小。

## 5. 硬约束怎么说

AGENTS 与 SDD §10 的硬约束是"清理计划必须独立、可审查，并在执行前重新校验"。**它要求重新校验，没有规定
校验的是什么。** ADR-0009 写的是"每项执行前再次校验 `lstat` 身份"——身份，不是元数据。元数据比对是 SDD §10
在实现时加上的一条，当时删除还走废纸篓，代价是可逆的；ADR-0063 之后删除不可逆，但同时也把"保护用户不删自己
的东西"明确交给了倒计时与三次确认，而不是交给工具的猜测。

## 6. 结论

1. 身份层（设备号 + inode + 类型）保留，它是"删的是不是那个东西"的唯一保证，且在 APFS 上无误报。
2. 元数据层（大小 / mode / mtime）应当去掉：它拦的几乎都是正常删除，防的几乎不会发生。
3. "看到的大小要准"由创建计划前重读所涉目录承担（ADR-0070 机制），而不是由拒绝承担。

## 7. 限制

- 没有统计元数据层的实际拦截率；"几乎必发"是对目录 mtime 语义的推理加日常观察，不是度量。
- 未在 HFS+ 卷上验证身份层；Marmot 当前只扫 APFS 卷组，HFS+ 外置盘若进入范围需另行复核。

## 8. 对 DDD/SDD 的影响与建议 ADR

- SDD §10：两条关于"预期元数据"和"大小和修改时间"的校验条目改为只核对身份与类型；补一条"创建计划前重读所涉目录"。
- DDD：无变化；`CleanupPlan` 仍在执行前重新校验。
- 建议 ADR-0071。

# R-057 内存唯一事实源可行性预研

状态：已实测（结论：取消持久化后内存反而下降，`340–385 MiB` + `843 MB` 盘 → `~237 MiB` + `0`）

日期：2026-08-25

## 1. 问题

R-056 测出一次全盘扫描在磁盘上留下 `843 MB`。产品是磁盘清理工具，用户的盘本来就快满了，应用自己长期占着
将近 1 GB 属于自身价值的反面。

产品决策提出：**不再缓存扫描结果，结果只存在于内存；刚启动时没有结果就只能重新扫描。**

这条推翻了 ADR-0003 的持久化条款与 DDD 不变量 37。本预研只回答一个技术问题：
**内存能不能自持有一棵完整的树，代价是多少？** ADR-0049 的投影是**故意只存偏移、名字从数据文件重读**的，
所以取消文件不是纯减法——名字与清理校验字段都必须进内存。

## 2. 环境与方法

真实 `/`，`2,782,449` 节点。直接消费 scanner 的批次流统计：节点/目录/文件/符号链接计数、**全部文件名的字节
总和**、以及 `kind` / `volumeID` / `sizeBasis` / `confidence` 四个字段的**去重后基数**。批次 emitter 由多个
native worker 并发调用（ADR-0045），统计加锁。

复现：`PROBE_ROOT=/ go test ./internal/probe/ -run TestMemoryOnlyFootprint -count=1 -v`

## 3. 证据

### 3.1 规模

| 指标 | 值 |
| :-- | --: |
| 节点 | `2,782,449` |
| 目录 | `589,216` |
| 文件 | `2,097,157` |
| 符号链接 | `96,076` |
| 读不到的路径 | `440` |
| **文件名字节总和** | **`55.7 MiB`**（均长 `21.0`，最长 `178`） |

### 3.2 四个"字符串"字段的真实基数是个位数

| 字段 | 不同取值 | 盘上按节点写全文的代价 |
| :-- | --: | --: |
| `kind` | **3** | `~11 MiB` |
| `volumeID` | **1**（`"mount:/dev/disk3s1s1"`） | **`53.1 MiB`** |
| `sizeBasis` | **2**（几乎全是 `"darwin_getattrlistbulk_native_v1"`） | **`84.9 MiB`** |
| `confidence` | **1** | `~14 MiB` |

合计 `~163 MiB`，全部可以用 1 字节码表示。这解释了 R-056 第 3.2 节里"每节点 195 字节"中的 30%。

### 3.3 自持有内存布局的推算

按节点 `56` 字节的定长部分：

```
parentID int64(8) + ownedAllocated int64(8) + logicalSize int64(8)
+ device int64(8) + inode int64(8) + modtime int64(8)
+ nameOffset uint32(4) + nameLen uint16(2) + kind uint8(1) + flags uint8(1)
```

**nodeID 不占空间**——它就是数组下标。`device`/`inode`/`modtime` 必须在内存里：清理计划要靠 device+inode
复核对象没被换掉（DDD 不变量 17 与 ADR-0009 的复核链）。

| 组成 | 大小 |
| :-- | --: |
| 定长部分 `56 B × 2.78M` | `148.6 MiB` |
| 名字 arena | `55.7 MiB` |
| 子项索引（每子一个 `uint32`） | `10.6 MiB` |
| 目录 roll-up 表（`40 B × 589k`） | `22.5 MiB` |
| **合计** | **`237.4 MiB`** |

### 3.4 与现状对比：取消持久化后内存**下降**

| | 内存（稳态） | 磁盘 |
| :-- | --: | --: |
| 现状（ADR-0049 投影 + durable 快照） | `340–385 MiB` | `843 MB` |
| 内存唯一事实源（本节推算） | **`~237 MiB`** | **`0`** |

这个方向和直觉相反，原因是现在这套结构**为了"能从盘上重读"付了双份代价**：

- `projectionEntry` 的 `dataOffset` + `stringBase` 两个 `int64` 专门用来定位盘上记录，
  `16 B × 2.78M = 42 MiB`，自持有布局里名字引用只要 `6` 字节；
- `projectionEntry` 还带 `allocatedSize`（与 `ownedAllocated` 恒等，R-053）与 `logicalSize`，
  而 nodeID 又单独存了一份（`8 B × 2.78M = 21 MiB`），自持有布局里 nodeID 是下标；
- `projectionDirectory` 每个目录带 `confidence` / `sizeBasis` 两个 Go string（`32 B`）和三个切片头（`72 B`），
  自持有布局里前者是 1 字节码、后者只需 `childStart/childCount`。

**"为了省内存所以从盘上重读"这个前提不成立**：维持这个能力本身的开销比它省下的更多。

## 4. 结论

1. 内存自持有一棵完整树的推算成本是 `~237 MiB`，**低于**现状的 `340–385 MiB`，且磁盘从 `843 MB` 降到 `0`；
2. 四个"字符串"字段的真实基数是 `3/1/2/1`，全部应为 1 字节码——这既是盘上 30% 浪费的来源，也是内存里
   `projectionDirectory` 膨胀的来源；
3. 名字总量只有 `55.7 MiB`，把名字搬进内存不是问题；
4. `device`/`inode`/`modtime` 必须进内存，已计入。

## 4b. 实施后实测（2026-08-26）

按 ADR-0055 → ADR-0056 实施后，真实 `/`（`2,783,0xx` 节点）：

| 指标 | 推算 | 实测 |
| :-- | --: | --: |
| 留存堆 | `237.4 MiB` | **`276.0 MiB`** |
| 磁盘 | `0` | **`0`**（扫描后缓存目录不新增文件） |
| 可见终态 | — | `15.2s`（基线 `16.5s`） |
| 目录覆盖率 | — | `589191/589191` |
| 装配 p95 | — | `4.34ms` |
| **峰值 RSS** | 未推算 | **`1113 MiB`** |

推算与实测差 `38.6 MiB`，来源清楚：节点记录实际是 **64 字节而非 56**（第 3.3 节只算了 `kind`+`flags` 两个
字节，实际还要 `volume`/`basis`/`confidence` 三个码），即 `+21.5 MiB`；另有 `childStart`/`childCount`
两个按节点 ID 索引的 `uint32` 数组 `+21 MiB`，以及切片余量与码表。

**峰值 RSS 未达门禁,原因已定位且量化**：留存堆达标，但扫描管线仍然为每个节点 materialise 一个
`scan.Node`——`184` 字节结构体加**均长 `122` 字节的完整路径（全盘 `325 MiB`）**——再交给存储，存储随即丢弃
路径（本记录第 3.3 节的布局就是不存路径的）。这些是瞬时垃圾，但 RSS 记住高水位。修它要改扫描器的输出契约，
需另立 ADR。

第 3.4 节"取消持久化后内存反而下降"的结论成立：留存堆 `276 MiB` 低于原先的 `340–385 MiB`，且磁盘从
`843 MB` 归零。

一条测量纪律的补充：本轮有一次采样报出可见终态 `247.756s`，我最初归因为机器换页——**错的**。真实原因是
那次运行卡在权限弹窗上等待用户点击同意。复测 `15.2s`。R-047 第 3.11 节的"wall 必须在静默环境测量"要再加一条：
**阻塞在权限对话框上的样本是无效样本，不是性能数据**。

## 4c. "1.19 GB"归因：报数口径、churn、以及 Darwin 不回收 footprint（2026-08-26）

使用方报告应用占用 `1.19 GB`。拆开后**只有 `258 MiB` 是扫描结果**，其余是已释放但系统仍在计数的堆页。

### 4c.1 两个数不是一回事

`ps rss` 与**活动监视器"内存"列（`phys_footprint`）** 在 Darwin 上会分叉，分叉点恰好就是 Go 持有的空闲
span。探针（`internal/probe/rss_probe_test.go`）现在两个都采。真实 `/`，扫描结束并 `FreeOSMemory` 后静置
`10s`：

| 口径 | 值 |
| :-- | --: |
| RSS 峰值 | `1058.9 MiB` |
| footprint 峰值 | `1126.4 MiB` |
| footprint（`runtime.GC()` 后） | `1024.0 MiB` |
| footprint（`FreeOSMemory()` 后） | `813.9 MiB` |
| **footprint（静置 10s 后）** | **`814.0 MiB`** |
| 扫描期总分配量 | `2478.1 MiB` |

同一时刻 Go 运行时自己的账：

| `runtime/metrics` | 值 |
| :-- | --: |
| **活跃堆（真正留存）** | **`258.0 MiB`** |
| 空闲、仍映射 | `2.5 MiB` |
| **已归还给系统** | **`875.8 MiB`** |
| goroutine 栈 | `1.1 MiB` |
| 运行时元数据 | `8.2 MiB` |

**两本账对不上 `~544 MiB`**：Go 认为已归还 `875.8 MiB`，系统仍记着 `814 MiB`。

### 4c.2 对不上的原因：`MADV_FREE_REUSABLE` 在 macOS 26.5 上是空操作

`vmmap --summary` 显示 Go 堆所在的 `VM_ALLOCATE` 区 `RESIDENT 980.3M`，其中 **`DIRTY 826.9M`**——页仍是
脏的，脏页全额计入 footprint。

Go 1.25 `runtime/mem_darwin.go` 的 `sysUnusedOS` 调用 `madvise(MADV_FREE_REUSABLE)` 并**丢弃返回值**。
用一个 512 MiB 的独立最小样本直接验证（`mmap` → 逐页触碰 → `madvise` → 读 footprint 与 `VM_ALLOCATE`
dirty）：

| 操作 | 返回 | footprint | `VM_ALLOCATE` dirty |
| :-- | :-- | --: | --: |
| 触碰 512 MiB | — | `515.1M` | `513.3M` |
| `MADV_FREE_REUSABLE` | **ok** | `515.3M` | `513.5M` |
| 　同上，3s 后 | — | `515.4M` | `513.6M` |
| `MADV_FREE` | ok | `515.5M` | `513.7M` |
| 　同上，3s 后 | — | `515.5M` | **`319.5M`** |
| `munmap` | ok | **`3696K`** | **`2184K`** |

三条结论：

1. **`MADV_FREE_REUSABLE` 返回成功但什么也没做**——dirty 不降，footprint 不降。Go 丢弃返回值，所以失败也
   是静默的（这里连失败都不算，是"成功地无效"）；
2. `MADV_FREE` 会让内核**真的**回收（dirty `513.7M → 319.5M`，且是在完全没有内存压力下自发发生的），
   但 **footprint 仍然不降**；
3. **只有 `munmap` 能让 footprint 掉下来**（`515.7M → 3.7M`，立即）。而 Go 从不 `munmap` 堆 arena——它保留
   地址空间以便复用。

因此 footprint 是**单调高水位**：一旦扫描把它顶到 `1.1 GB`，进程活着就一直显示那么高，与是否还需要这些
内存无关。`debug.FreeOSMemory()` 能拿回 `~300 MiB`（`1126 → 814`），但拿不回大头。

> 更正：本记录此前记述"`debug.FreeOSMemory()` 对 RSS 完全无效"。不准确——它能降 footprint 约 `300 MiB`，
> 只是降不到留存量。以本节实测为准。

### 4c.3 因此唯一的杠杆是 churn

既然高水位不可回收，唯一能降低使用方看到的数字的办法是**一开始就不要分配它**。分配剖析（`2478 MiB` 总量）：

| 分配点 | 量 | 归属 |
| :-- | --: | :-- |
| `scanner.addNodes` | `968 MB` | 扫描器 |
| `memtree.(*tree).insert` | `911 MB` → 已修 | 本次实施 |
| `scanner.joinNativePathAndName` | `356 MB` | 扫描器 |
| `memtree.(*arena).put` | `298 MB` → 已修 | 本次实施 |

`insert`/`put` 两处是**本次实施引入的缺陷**：靠 `append` 的 `~1.25×` 增长把一个最终 `178 MiB` 的数组长起来，
累计复制约五倍于终态。改为翻倍增长，但翻倍会长期持有最多 2 倍容量（留存堆 `276 → 368 MiB`，违反 ADR-0056
门禁），所以在 `finish()` 里加 `trim()` 裁到精确大小。净效果：

| | 修前 | 修后 |
| :-- | --: | --: |
| 留存堆 | `276.0 MiB` | **`257.8 MiB`** |
| 扫描期分配量 | `2794 MiB` | `2478 MiB` |

剩余 `1324 MB`（`addNodes` + `joinNativePathAndName`，占 churn 的 `53%`）全在扫描器，原因见第 4b 节：
逐节点 materialise `scan.Node` 加完整路径，而存储立即丢弃路径。这是 ADR-0056 门禁 2（峰值 `≤400 MiB`）
未达标的**唯一剩余原因**，修它要改扫描器输出契约，需另立 ADR。

### 4c.4 `GOMEMLIMIT` 不是解法

| `GOMEMLIMIT` | RSS 峰值 | 扫描耗时 | 留存堆 |
| :-- | --: | --: | --: |
| 无 | `1022.9 MiB` | `17.10s` | `257.8 MiB` |
| `700MiB` | `956.8 MiB` | `16.93s` | `257.8 MiB` |
| `500MiB` | `797.1 MiB` | `22.20s` | `257.8 MiB` |
| `400MiB` | `889.7 MiB` | `22.09s` | `257.8 MiB` |

`400MiB` 在 RSS 和耗时上**都不如** `500MiB`：上限压到工作集之下后 GC 空转，时间白花而峰值反弹。这是个有
拐点的旋钮，且拐点位置取决于被扫卷的规模——写死一个值会在更大的盘上踩空。**不建议**在 churn 修复前设置软
上限：它掩盖症状并引入一个规模相关的失效点。

### 4c.5 测量纪律补充

- **报"内存占用"时必须写明口径**。`ps rss`、`phys_footprint`、`runtime/metrics` 活跃堆在本场景下分别是
  `912.9 / 814.0 / 258.0 MiB`——相差 `3.5×`。不写口径的内存数字没有意义；
- **不要相信运行时的"已归还"计数**。Go 报 `875.8 MiB` 已归还，系统侧一个字节都没减。跨越 runtime/kernel
  边界的结论必须在两边各测一次；
- **系统调用返回成功不等于生效**。`MADV_FREE_REUSABLE` 返回 `ok` 且完全无效，只有对比 footprint/dirty
  才能发现。

## 5. 限制与风险

- 第 3.3 节是**按布局推算**，不是实测：真实占用还要加 Go 的分配器碎片与切片扩容余量。R-047 第 3.9/3.10 节
  的经验是 compact arena 方案的实测值接近推算（`+62 MiB` 对朴素 `+295 MiB`），但本方案未实现、未实测；
- **崩溃或取消后不留任何可用结果**。当前实现里扫到一半崩掉仍有一个可查询的部分快照，取消持久化后没有；
- 单机单卷样本。`volumeID` 基数为 1 是因为只扫一个卷组；多卷 scope 下会变，但仍是个位数；
- 本预研不评估"取消持久化"对产品的影响（重启即需重扫 `~17s`），那是产品决策，不是技术结论。

## 6. 建议

分两个 ADR：

1. **取消快照持久化，内存成为唯一事实源**——推翻 ADR-0003 的持久化条款与 DDD 不变量 37，作废整条 durable
   管线（`FinishSnapshot`、索引构建、manifest、剪除、缓存预算）及 ADR-0031/0033/0035/0036/0038/0042/0043/
   0044/0046 一系列 FinishSnapshot 优化。这是产品决策，必须由决策者接受。
2. **内存事实源的结构与发布峰值**——`56` 字节定长布局、四个字段改 1 字节码、nodeID 用下标、名字 arena、
   发布阶段就地排序以消除 2× 峰值（现状峰值 `500 MiB` 对稳态 `340 MiB`）。

# R-069 清理判定的事实与结论分层预研

- 日期：2026-09-03
- 触发：使用方「当前我对于分析可清理项的功能还是感觉需要再提升，我们当前从多个维度来评判是否需要清理，
  你觉得是否是正确的？是否可以优化？」
- 结论：多维评判方向正确，问题在维度之间的关系。`risk` 已经变成一个把四种不同事实压成一个标签的混合字段，
  而且仍由最不稳定的一方（模型）直接产出。修法是把**事实**与**结论**分开：事实由规则、护栏和活跃度信号提供，
  风险等级由一个纯函数从事实推导，规则来源与 AI 来源共用同一个函数，模型不再输出 `risk`。
  顺带量了一个准备补的活跃度信号（属主应用是否还在、多久没打开），结果**弱于预期**，记为限制，不进本轮实现。

## 1. 问题

R-063 把判定主轴换了三次：风险 → 可恢复性（§0）→ 干扰度（§4b）。每次换轴都有实测支撑，但代码里三次换轴是
**叠加**上去的，不是重新组织的。复核 `internal/domain/recommendation` 与 `internal/application/advice.go`，
当前参与判定的维度与它们落到哪个字段：

| 维度 | 来源 | 落到哪 |
| :-- | :-- | :-- |
| 可恢复性 recovery | 规则声明 / 模型主张，护栏纠正 | `Recovery` |
| 风险 risk | 规则声明 / 模型主张 | `Risk` |
| 项目源码活跃度 | `projectIdleDays`，确定性 | 改写 `Risk`，前置一句到 `WhatBreaks` |
| 产物年龄 | `MinAgeDays`，确定性 | 决定规则是否命中 |
| 代际间隔 | `Generations`，确定性 | 独立 finding，`Risk` 取规则声明 |
| 护栏（不可恢复 / 登录态 / 部分删除） | `IrreplaceableReason` 等 | 改写 `Recovery` 与 `Risk`，前置一句到 `WhatBreaks` |
| 置信度 | 规则恒为 1，模型自报 | `Confidence` |

四个具体问题：

1. **`risk` 是混合字段。** 一个 `review` 可能来自"规则作者拿不准这个泛路径"、"项目正在用"、"疑似登录态"、
   "模型拿不准"四种完全不同的事实，用户看到的是同一个标签。R-063 §4b 写下了公式
   `干扰成本 = 恢复代价 × 即将需要的概率`，实现却是 `AdjustForProjectActivity` 里的 switch。
2. **模型仍输出 `risk`，而这正是它最不稳定的字段。** R-063 §3.5 实测风险漂移 `8/20`，恢复性漂移 `1/20`。
   R-063 已经把"选什么"从模型挪到程序侧来解决覆盖稳定性；同一手法没有用到 `risk` 上。
3. **活跃度信号只覆盖项目内对象。** `~/Library/Caches/*` 这类最大的一块没有任何"还会不会用"的信号，
   全部落到「用户缓存 / review / 个别应用会丢失登录态」这句最不可行动的话上（R-063 §6 已列为限制）。
4. **规则置信度恒为 1 不诚实。** `Library/Caches/*` 与 `Library/Caches/Google/Chrome/*` 给用户的确定性完全不同，
   `Rule.Specificity()` 已经算出了差别，只用于重叠裁决，没有到达用户。

## 2. 假设

- H1：把 `risk` 改为从事实推导，规则层的现有输出不变（行为保持），AI 层的风险漂移结构性归零。
- H2：属主应用的存活与最近使用时间（LaunchServices 注册 + Spotlight `kMDItemLastUsedDate`）可以给
  `Library/Caches/<bundle id>`、`Library/Containers/<bundle id>` 补上活跃度信号，覆盖 §1 第 3 条的空洞。
- H3：对应用缓存而言，缓存自身的最新 mtime 就是"应用最近何时运行过"的近似，可作为 H2 的低成本替代。

## 3. 环境与方法

参考机（R-062/R-063 同一台，重度开发者画像）。对三个根目录逐个一级子目录：`du -sk` 取体积；
名字含两个以上 `.` 视为 bundle id；`mdfind "kMDItemCFBundleIdentifier == '<id>'"` 查是否有注册的 `.app`；
对查到的应用 `mdls -name kMDItemLastUsedDate`。脚本见本次会话 scratchpad，未入库。

## 4. 证据

### 4.1 属主应用信号（H2）

| 根目录 | 有对应 .app | 无对应 .app（"孤儿"） | 非 bundle id 命名 |
| :-- | --: | --: | --: |
| `~/Library/Caches` | 22 个 / 27 MB | 60 个 / 134 MB | 24 个 / **3,904 MB** |
| `~/Library/Containers` | 62 个 / 1,172 MB | 632 个 / 347 MB | 0 |
| `~/Library/Application Support` | 9 个 / 208 MB | 30 个 / 818 MB | 58 个 / **6,087 MB** |

三个发现，都不利于 H2：

1. **字节不在 bundle id 目录里。** Caches 里 96% 的字节在 `Google`、`go-build`、`zymix-desktop-updater`
   这类厂商命名目录，它们已被现有规则命中（Chrome 网页缓存、Go 构建缓存）。属主应用信号能触及的只有 4%。
2. **"孤儿"绝大多数是假阳性。** 632 个 Containers 孤儿几乎全是 `com.apple.*` 的守护进程、XPC 服务和小组件
   （最大的是 `com.apple.mediaanalysisd` 278 MB，它当然没有 .app）。第三方假阳性也有三类：
   已装应用的 helper（`com.netease.uuremote.server`、`com.nektony.App-Cleaner-SIII-UIHelper`）、
   库而非应用（`com.hackemist.SDImageCache`）、应用目录名与 bundle id 拼法不同（`Luffa` 与 `com.luffa.tauri.pc`）。
   排除 `com.apple.*` 并做"已装 bundle id 是其前缀"的 helper 归并之后，本机真孤儿约
   `com.netease.uuremote.updater` 215 MB + `io.weshare.weShare` 132 MB，合计不到 400 MB。
3. **最近使用时间没有量到。** 本次运行环境下 `mdls` 对 `/Applications/*.app` 一律报 `could not find`，
   `kMDItemLastUsedDate` 是否可靠**未验证**。

### 4.2 缓存自身年龄作为活跃度（H3）

证据包里每个节点已有 `NewestModified`。应用运行时会写自己的缓存目录，所以"缓存 180 天没有任何文件变化"
在实践上等于"这个应用 180 天没跑过"。它与 R-063 §4b.1 否掉的"产物 mtime"不是一回事：
产物冷但源码热是要重建的信号，而缓存冷就是没在用。方向是保守的：只在冷时把 `review` 放宽到 `safe`，
从不把热缓存判 `safe`。不需要新的平台调用。

### 4.3 结论字段的现状

`Recommendation.Risk` 现有写入点：`RuleFindings`（规则声明 → 活跃度改写）、`generationFinding`（规则声明）、
`Validate`（模型主张 → 三种护栏改写）。三处各自实现"从事实到结论"的一部分，没有一处能看到全部事实。

## 5. 结论

1. **H1 成立，作为本轮实现。** 引入 `Facts`（recovery、规则声明的基线风险、活跃度种类与天数、护栏命中、置信度）
   与 `Assess(Facts) → (Risk, Reasons)`。`Reasons` 是机器码，UI 用它解释"为什么是需确认"。
   模型输出契约删掉 `risk`；`Validate` 对仍带 `risk` 的回复忽略而非拒绝。
2. **H2 不进本轮。** 信号能触及的字节太少（Caches 4%）、假阳性太多、最近使用时间未验证。
   记为后续工作，前提是先解决 §4.1 的三个问题。
3. **H3 采用。** 应用缓存类规则标记 `AgeSensitive`，缓存冷（≥180 天）时 `review → safe` 并说明；
   阈值沿用 §14.5a 的 30/180，同样未经验证。
4. 泛规则如实报告置信度：由目录作者声明 `Generic`（容器规则），报 0.7 并给出理由码 `generic_rule`；
   不按 `Specificity()` 推断——`**/node_modules` 只有一段却精确命名了对象，按段数会算反。
5. 补两条零判断力的规则：`Downloads/*.dmg`、`Downloads/*.pkg`（≥30 天）。安装包是典型的可重下载、
   零干扰对象，目前既不在规则里也不在不可恢复清单里，全靠模型。

## 6. 限制

- 属主应用调查只有一台机器，`kMDItemLastUsedDate` 在本环境读不到，H2 的否定结论是"本轮做不了"，
  不是"永远做不了"。
- H3 的"缓存冷 = 应用没跑"没有做逐应用验证；已知例外是只读缓存（安装后不再写）。保守方向使例外的代价是
  少放宽一条，不是错放宽一条。
- 30/180 天阈值继续沿用，未做敏感性分析。

## 7. 对 DDD / SDD 的影响与建议 ADR

- DDD：新增不变量 10a——风险等级是从事实推导的结论，不是任一来源的输入。
- SDD：新增 §14.5h（事实与结论分层），修订 §14.5（模型输出契约）与 §14.6（校验不再检查 `risk` 枚举）。
- 建议 ADR-0067：清理建议的事实与结论分层。

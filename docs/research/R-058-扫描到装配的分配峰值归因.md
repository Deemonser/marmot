# R-058 扫描到装配的分配峰值归因

- 日期：2026-08-26
- 触发：使用方报告应用占用 `1.19 GB`。[R-057 第 4c 节](R-057-内存唯一事实源可行性预研.md)已证实其中只有
  `258 MiB` 是扫描结果，其余是**已释放但在 Darwin 上不可回收**的高水位，且高水位由扫描期的分配量决定。
  本记录归因那个分配量。
- 关联门禁：[ADR-0055](../adr/0055-取消快照持久化与内存唯一事实源.md) 门禁 4、
  [ADR-0056](../adr/0056-内存事实源的结构与发布峰值.md) 门禁 2 的峰值部分至今未达成。

## 1. 问题

一次全盘扫描分配 `2530 MB`，而终态只留存 `258 MiB`——churn 比是 `9.8×`。R-057 第 4c 节已经证明这个高水位
**事后无法回收**（Go 的 `MADV_FREE_REUSABLE` 在 macOS 26.5 上返回成功却不降 `phys_footprint`，只有 `munmap`
能降而 Go 从不 `munmap` 堆 arena）。因此唯一的杠杆是**不要分配**。

问题是：这 `2530 MB` 具体分配在哪些语句上，各自的最小可能成本是多少，差额能不能拿回来。

## 2. 假设

- H1：主要成本是扫描器为每个节点 materialise 一个 `scan.Node` 加完整路径（R-057 第 4b 节的判断）。
- H2：路径对**文件**是纯浪费——存储的内存布局不存路径，靠父链重建。
- H3：ADR-0056 实施时引入的翻倍增长与 `trim()` 是净收益。

三条假设**只有 H2 完全成立**，H1 严重不完整，H3 是错的（见第 4 节）。

## 3. 环境与方法

- 机器：本机，macOS 26.5.2 (25F84)，arm64，Go 1.25.0。
- 被测：真实 `/`，`2,782,493` 节点。
- 方法：
  1. `internal/probe/scanner_contract_probe_test.go`——用 `ScanBatched` 直接接管批次，统计节点分布、
     按 kind 分开的路径字节、名字字节、**批次数量与大小分布**；
  2. `go tool pprof -sample_index=alloc_space -lines`——把分配量落到**具体行号**，分别对"裸扫描"（不接存储）
     和"完整管线"各取一次；
  3. `internal/probe/contract_alternatives_probe_test.go`——把每条改法在**实测批次分布**下隔离测量，
     与生产剖析交叉校验。

**一条方法学纠正**：本记录第一版探针用普通计数器统计，跑出 `concurrent map writes` 才发现
**扫描器的 emit 回调是并发调用的**（实测峰值并发 `2`）。加锁重测后结论未变，但那一版数字本身不可信。
凡是挂在 emit 回调上的测量都必须先假定并发。

## 4. 证据

### 4.1 节点与批次形态

| 指标 | 值 |
| :-- | --: |
| 节点 | `2,782,493` |
| 　目录 | `588,786`（`21.2%`） |
| 　文件与符号链接 | `2,193,707`（`78.8%`） |
| `unsafe.Sizeof(scan.Node)` | `184` 字节 |
| **批次数** | **`421,701`** |
| 　平均批大小 | **`6.6` 节点** |
| 　最大批 | `2,773` |

批大小分布是本记录最重要的一个发现：

| 批大小 | 批次数 | 占比 |
| :-- | --: | --: |
| **`1`** | **`192,771`** | **`45.7%`** |
| `2–8` | `186,853` | `44.3%` |
| `9–64` | `38,087` | `9.0%` |
| `65–512` | `3,572` | `0.8%` |
| `513+` | `418` | `0.1%` |

**九成的批次不超过 8 个节点，近一半只有 1 个节点。** 因此所有"每批次一次"的固定分配要付 `42` 万次，
其权重远高于按节点数的直觉估算。H1 之所以不完整，就是因为它只算了按节点的成本。

### 4.2 契约本身的成本与下界

| | MiB |
| :-- | --: |
| `scan.Node` 结构体 | `488.3` |
| 路径字节，目录 | `61.3` |
| **路径字节，文件与符号链接（随即丢弃）** | **`263.4`** |
| 　其中父前缀（每个子项重建一次） | `269.1` |
| **名字字节（存储唯一保留的文本）** | **`55.7`** |
| **契约总成本** | **`813.0`** |
| **存储实际需要的下界** | **`55.7`** |

父前缀 `269.1 MiB` 大于目录路径总量 `61.3 MiB`——因为同一个父前缀被复制给它的每一个子项。这是一份
**已经存在于父记录里**的信息，被复制了 278 万次。

### 4.3 分配落到行号

裸扫描（不接存储），总 `1329.90 MB`：

| 行 | 语句 | MB |
| :-- | :-- | --: |
| `native_darwin.go:843` | `nodes: make([]Node, 0, len(raw))` | `502.47` |
| `native_darwin.go:796` | `joinNativePathAndName` 的路径分配 | `341.05` |
| `native_darwin.go:892` | `prepared.directoryDeltas[node.ParentID] = delta` | `192.11` |
| `native_darwin.go:903` | `native.dirSizes[node.ID] = ...` | `139.35` |
| `native_darwin.go:902` | `native.directories[node.ID] = ...` | `78.99` |
| `native_darwin.go:824` | `parentPaths := make([]string, len(raw))` | `40.37` |
| `native_darwin.go:884` | `make(map[int64]scan.DirectorySize)`（每批次一个） | `18.50` |
| `native_darwin.go:844` | `linkCount: make([]uint32, 0, len(raw))` | `8.02` |

**三个 map 合计 `428.95 MB`**，这是 H1 完全没有覆盖的一头。其中 `directoryDeltas` 一项就是 `210.61 MB`：
一个**每批次新建、平均只装几个条目**的 map，建了 `42` 万次，光 map 头与首次插入的桶就是这个量级。

完整管线（接存储），总 `2530.50 MB`：

| 分配点 | MB | 归属 |
| :-- | --: | :-- |
| `scanner.addNodes`（flat） | `1022.25` | 扫描器 |
| **`memtree.growRecords`** | **`511.99`** | ADR-0056 结构 |
| `scanner.joinNativePathAndName` | `341.55` | 扫描器 |
| **`memtree.(*tree).trim`** | **`225.55`** | ADR-0056 结构 |
| `memtree.(*arena).put` | `160.43` | ADR-0056 结构 |
| `application.runScan`（func7 + 本体） | `176.29` | 应用层 |
| `memtree.(*tree).group` | `48.47` | ADR-0056 结构 |

扫描器 `1363.80 MB`（`53.9%`），memtree `946.44 MB`（`37.4%`），应用层 `176.29 MB`（`7.0%`）。

### 4.4 H3 是错的：翻倍增长加裁剪是一笔昂贵的交换

ADR-0056 实施时，我把节点表与名字 arena 从 `append` 的 `~1.25×` 增长改成翻倍，再在 `finish()` 里 `trim()`
裁到精确长度，报告的净效果是留存堆 `276.0 → 257.8 MiB`。那个结论只看了**留存**，没看**分配**：

- `growRecords` `511.99 MB`——翻倍的累计副本量约为终态容量的 2 倍，而容量最多是长度的 2 倍；
- `trim` `225.55 MB`——把 `178 MiB` 的记录数组和 `56 MiB` 的 arena 各**再完整复制一遍**。

即：**用 `737.54 MB` 的分配量，换来 `110 MiB` 的留存下降。** 在"高水位不可回收"这个前提下（R-057 第 4c 节），
这笔交换的方向是反的。

正确的解法是两者都不做：节点 ID 由单一计数器分配、**稠密**，所以记录表可以做成**分页数组**
（固定大小的页，扩容只追加一页，永不复制），既没有翻倍浪费也不需要裁剪，留存端的余量上限是一个半空页。

### 4.5 每条改法的隔离测量

在实测批次分布（`421,701` 批，第 4.1 节的直方图）下：

| 改法 | 现状 | 改后 | 省 |
| :-- | --: | --: | --: |
| 每批次分配（`[]Node`＋`[]string`＋`[]uint32`＋delta map）→ 按 worker 复用缓冲 | `831.1 MiB` | `0.6 MiB` | `830.5` |
| 两个持久 map（`directories`/`dirSizes`）→ 稠密数组＋序号索引 | `224.2 MiB` | `55.5 MiB` | `168.7` |
| 　（若只做"预分配容量"这一步） | `224.2 MiB` | `112.1 MiB` | `112.1` |
| 文件建完整路径 → 只建名字 | `267.8 MiB` | `50.2 MiB` | `217.6` |

与生产剖析交叉校验：持久 map 合成 `224.2` 对实测 `218.34`（`902`＋`903`），每批次合成 `831.1` 对实测
`761.47`（`824`＋`843`＋`844`＋`884`＋`892`），文件路径合成 `267.8` 对实测约 `276.6`（`341.55` 按
`263.4/324.7` 的字节占比折算）。三项都在 `±10%` 内，模型可用。

## 5. 结论

1. **H1 不完整。** 扫描器确实是最大的一头（`1363.80 MB`，`53.9%`），但其中 `428.95 MB` 是 map 扩容，
   与"materialise `scan.Node` 加路径"无关。真正的结构性原因是**批次极小**（近半数只有 1 个节点），
   而契约要求每批次交付一个独立拥有的 `[]scan.Node`。
2. **H2 成立。** 文件路径 `263.4 MiB` 建完即弃，存储只保留名字 `55.7 MiB`。父前缀被复制 278 万次共
   `269.1 MiB`，这份信息已经在父记录里。
3. **H3 是错的。** 翻倍＋裁剪花 `737.54 MB` 分配换 `110 MiB` 留存，方向与"高水位不可回收"相反。
   分页数组能同时拿到两头。
4. **契约成本 `813.0 MiB`，信息下界 `55.7 MiB`，倍率 `14.6×`。**
5. 三条改法叠加的推算落点：扫描器 `1363.8 → ~170 MB`，memtree `946.4 → ~280 MB`，应用层不变 `~176 MB`，
   **合计 `~626 MB`，较现状 `2530 MB` 降 `75%`**。

**但推算不支持"门禁 2 因此达成"。** 留存堆 `258 MiB` 不变，而 `GOGC=100` 的定义就是堆涨到活跃量的
`2×` 才回收，即峰值堆约 `516 MiB`。ADR-0056 门禁 2 写的是"稳态 `<=280 MiB`、峰值 `<=400 MiB`，
且峰值/稳态 `<=1.2`"——**`<=1.2` 这个比值在 `GOGC=100` 下由构造决定就达不到**，与 churn 多少无关。
这是门禁本身的规格问题，必须由决策者裁决，不得由实施方擅自放宽。

## 5b. 实施后实测（2026-08-26）

按 [ADR-0057](../adr/0057-扫描到装配的分配契约.md) 实施后，真实 `/`：

| 指标 | 改前 | 推算 | 实测 |
| :-- | --: | --: | --: |
| 扫描期总分配量 | `2530 MB` | `~626 MB` | **`650.1 MiB`** |
| churn 比 | `9.8×` | — | **`1.4×`** |
| 峰值 `phys_footprint` | `1126.4 MiB` | 未推算 | **`569.0 MiB`** |
| 峰值 `ps rss` | `1058.9 MiB` | 未推算 | `581.2 MiB` |
| 留存堆 | `257.8 MiB` | 不变 | `256.7 MiB` |
| 可见终态 | `15.2s` | 中性偏好 | **`14.259s`** |

推算 `~626` 对实测 `650.1`，差 `3.9%`——第 4.5 节的隔离测量模型成立。第 6 条"三条叠加后的真实峰值只有
实施后才能测"的保留意见也成立：峰值降到 `569.0 MiB`，是留存堆的 `2.2×`，与 `GOGC=100` 的构造一致。

第 5 条最后一段的判断得到证实：**门禁 2 的"峰值/稳态 `<=1.2`"仍然达不到**，但原因已经不是 churn。
churn 降了 `74%` 之后峰值/稳态是 `2.2`，正是 `GOGC=100` 的定义值。这条门禁需要决策者裁决。

一条实施教训，值得单独记：中途有一版把分配量做到了 `19934 MiB`，比改之前差 20 倍。原因是消费侧缓冲
耗尽时"按下限容量新建一个"，而自由链表基本总是空的。**在一条以回收为目的的路径上写"分配一个新的"作为
兜底，等于没有回收**，而且比不回收更糟——兜底容量比原本按需分配的还大。它是被下一次测量抓到的，
不是被推理抓到的：每一步都要重测，不能只测最后一步。

## 6. 限制与风险

- **第 5 条第 5 点是推算，不是实测。** 隔离测量证明了每条改法在合成负载下的省量，但三条叠加后的真实
  峰值受 GC 时机影响，只有实施后才能测；
- **emit 契约当前明确转移所有权**（`scan.BatchEmitter` 的文档），消费侧把批次送进带缓冲 channel
  （`scanPersistQueueCapacity = 2`）交给写入 goroutine。复用缓冲**必须**同时改契约与消费侧，否则是数据竞争。
  且回调并发度实测为 `2`，缓冲必须按 worker 分配，不能用单一全局缓冲；
- 即使不建文件路径，`Node.Name` 仍需一次分配（当前名字是路径的尾切片，与路径共享同一次分配）。
  第 4.5 节的 `50.2 MiB` 已计入这笔；
- **单机单卷样本。** 批次大小分布取决于目录扇出，`45.7%` 单节点批这个比例在别的树形上会变；
- 本记录不评估改动对扫描**耗时**的影响。分页数组与缓冲复用应当中性偏好，但未测。

## 7. 对 DDD / SDD 的影响

- **DDD**：不变量 17（路径本身不是授权）**因本改动而更强**——文件节点在扫描流里将不再携带路径，
  想对一个文件做操作必须按 ID 回查。这与 `ProjectedEntry` 已有的设计一致，建议在不变量 17 下补一条
  结构性说明；
- **SDD**：`scan.BatchEmitter` 的所有权语义要重写（从"转移所有权"改为"仅在回调期间有效"），
  扫描器→应用层→存储的数据流一节需同步；
- **ADR-0056 §1** 定义的"`records []record`，nodeID 即数组下标"要改为分页，属于对已接受 ADR 的实质修改，
  必须由新 ADR 替代该条，不能就地改。

## 8. 建议 ADR

一个 ADR，覆盖同一个门禁下的三条改法（拆开会让门禁无法归属）：

1. **扫描器输出契约改为"仅回调期内有效"**，缓冲按 worker 复用；
2. **文件节点不再携带完整路径**，目录仍需要（walk 要 `opendir`）；
3. **按节点 ID 索引的 map 一律改为稠密数组**，含扫描器的两个持久 map 与 memtree 的记录表分页化
   （后者替代 ADR-0056 §1 与本次实施的 `trim()`）。

同时请决策者裁决 ADR-0056 门禁 2 的"峰值/稳态 `<=1.2`"是否可实现——若保留，需要一并决定
`GOGC`/`GOMEMLIMIT` 策略，而 R-057 第 4c.4 节已证明在当前 churn 下 `GOMEMLIMIT` 有拐点、不是安全旋钮。

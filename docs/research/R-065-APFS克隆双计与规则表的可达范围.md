# R-065：APFS 克隆双计，与规则表够不到的地方

- 日期：2026-08-31
- 触发：使用方问「`/System` 下面的 `Volumes` 和 `Library` 里面是什么，就没有能清理的吗」
- 结论：**克隆双计确认存在，但按私有大小替换体积是错的，已回退**；规则表的可达范围
  是真缺口，已修（见 §3）。

## 1. `/System` 下面确实没有可清理项

| 位置 | `du` | `df`（真实） | 是什么 |
| :-- | --: | --: | :-- |
| `/System/Volumes/Data` | — | 134 GB | `/Users` 的 firmlink，**不是额外占用** |
| `/System/Volumes/Preboot` | 43.6 GB | **17 GB** | 开机路径（`cryptex1`、`restore`/`restore-staged`） |
| `/System/Volumes/VM` | 8 GB | 8 GB | 交换文件，内核管理，删了立刻长回来 |
| `/System/Volumes/Update` | 731 MB | 731 MB | 系统更新暂存 |
| `/System/Library` | 18.0 GB | `/` 16 GiB ≈ 17.2 GB | **封印只读**：`apfs, sealed, read-only`，`touch` 即 `Operation not permitted` |

`/System/Library` 那 18.0 GB **是准确的**——我一度以为它高估了 3 倍，那是我拿十进制 GB
去比 `df` 的 GiB。**单位换算错误也能伪装成一个 bug。**

## 2. 克隆双计：确认存在，量级很大

`ATTR_CMNEXT_PRIVATESIZE`（不与任何其他文件共享的字节数）实测：

| 文件 | allocated | 私有 |
| :-- | --: | --: |
| `Preboot/Cryptexes/OS/.../aot_shared_cache.0` | 342.2 MB | **0.0 MB** |
| `Preboot/.../Incoming/OS/.../dyld_shared_cache…` | 143.2 MB | **0.0 MB** |
| `~/.gradle/.tmp/gradle_download…bin` | 188.3 MB | 188.3 MB |

**克隆文件删掉释放 0 字节，而 `du` 和 `lstat` 都给它记满额。** 比 inode 也看不出来
（inode 不同、`links=1`、大小相同）——只有卷自己的 `df`，或这个扩展属性，能看见。

### 2.1 按私有大小替换 allocated：试过，是错的，已回退

改动很小（`getattrlistbulk` 的 `forkattr` 加一个属性，无额外系统调用），效果立刻可见：
Preboot 从 **45.7 GB → 3.77 GB**。但 `df` 说 17 GB——**把 2.5 倍高估换成了 4.5 倍低估。**

三个理由使它不能发：

1. **两个问题被我混成了一个。**
   「这东西占多少地方」（画图用）的答案是 allocated；
   「删了能拿回多少」（建议用）的答案是 private。
   `/System/Library` 删不掉，问第二个问题没有意义，显示它占 17 GB 才是有用的。
2. **封印系统卷上每个文件的私有大小都是 0**（与快照底下的卷共享）。抽样 `CoreImage`
   的 metallib：`alloc=15.1MB / 私有=0.0MB`。这个属性一旦在那里生效，
   **整个 macOS 会显示成 0 GB**。
3. **它现在没在那里生效，纯属偶然**：`getattrlistbulk` 在普通卷（Preboot）返回该属性，
   在系统快照卷不返回。**同一棵树被两种方式量，取决于卷类型。**

正确的做法是**两个数分开**：allocated 供空间图，private 供"可回收"。这是一个设计决定，
需要 ADR 与迁移，不是一次补丁。属性请求保留（不花系统调用），替换回退，
`SizeBasis` 仍为 `v1`。

### 2.2 无法归属的共享块该进"隐藏空间"

即便做了两个数，仍有一类值无法归属：**一对克隆的两侧都在被扫的子树里**时，
各报私有 0，而删掉整个子树确实会释放那份共享块。这类字节属于
`map_assembly.go` 已有的 `隐藏空间` 平衡项——它的注释里本来就写着
"allocated 与物理大小的差"。文案需要相应更新（当前只说"有目录未能完整读取"）。

## 3. 规则表够不到家目录之外（真缺口，已修）

实测，修复前：

```
/Library/Developer/CoreSimulator/Caches/dyld  -> <nil>
/Library/Updates/140-17812                    -> <nil>
/Library/Caches                               -> <nil>
```

`Match` 先走 `homeRelative()`，**只认 `/Users/<账户>/`**。扫描根是整盘，
而工具只在家目录里认得东西。**与 ADR-0063 §3 那个 `**/` 守卫的洞是同一个根因**，
上次只修了守卫那一半。

新增 `AbsoluteCatalog`（对完整路径匹配，先于家目录判断）四条，全部标 `Manual`：

| 规则 | 实测 | 恢复代价 |
| :-- | --: | :-- |
| 模拟器 dyld 缓存 | **3.5 GB** | 模拟器下次启动重建，不联网 |
| 系统更新包残留 | **899 MB** | 需要时重新下载 |
| 根级用户缓存 | — | 多数自动重建 |
| 根级日志（>30 天） | — | 不可恢复，但不影响功能 |

### 3.1 为什么是"报告但不执行"

这些路径是 `root:wheel` / `root:admin`，当前用户不可写。三种选择：

- 不报告 → 用户永远不知道有 4.4 GB 可清（**最差**：没被告知的东西无法行动）
- 报告并提权 → 一个清理工具拿到 root，爆炸半径和现在完全不是一个量级，收益 4.4 GB
- **报告 + 给出确切命令，工具不碰** ← 选这个

`Rule.Manual` 的项**不能加入收集区**（自动放入与批量放入都排除），
详情里给出可选中的命令原文。**一个必然以权限错误失败的收集项，比不提供更糟**——
用户已经为一次删除下了决心，才拿到一个错误。

## 4. 未验证 / 已知限制

- §2.1 的两个数模型**没有实现**，因此空间图目前仍会把克隆数两遍
  （`/System/Volumes` 那 27.3 GB 里有相当一部分是这个）。
- §2.2 的"隐藏空间"文案没改。
- `AbsoluteCatalog` 的四条只在本机一台验证过；`根级用户缓存`、`根级日志`
  在本机体积不足以进入证据下限，**未在真实数据上看到过**。
- 私有大小属性在非 APFS 卷上的行为未测。

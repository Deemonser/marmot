# R-004 百万级节点性能与快照存储

状态：已完成（本机合成基准；真实全盘仍需发布前 smoke test）

## 问题

在 macOS 全盘规模下，如何保存和查询百万级扫描节点，同时保持首屏、目录展开和取消操作可用？

## 假设

- 后台受限并发扫描可以持续输出顶层和目录汇总。
- SQLite 通过批量写入、合适索引和分页查询可以承载第一阶段快照。
- WebView 只需要当前层级和摘要，不需要完整树常驻内存。

## 验证环境

- macOS 26.5.2，arm64，8 CPU，约 16 GiB 内存；
- Go 1.25.13，SQLite 3.51.0，`github.com/mattn/go-sqlite3`；
- 10 万、50 万、100 万节点的合成快照；
- 树形目录和 100 万节点挂在同一父节点的高扇出目录；
- 页面返回 1000 个节点的 JSON 载荷。

## 测量指标

- 首次显示顶层结果的耗时；
- 完整扫描耗时；
- 峰值内存和 goroutine 数量；
- SQLite 批量写入吞吐和数据库大小；
- 子节点分页查询延迟；
- 取消请求到扫描停止的延迟；
- Wails 绑定返回大小和响应时间；
- 重启后打开快照的耗时。

## 本机结果

使用 `snapshot_id + parent_id + owned_allocated DESC + id` 索引、WAL、
`synchronous=NORMAL` 和 10,000 节点一批提交时，热身后的结果如下：

| 场景 | 写入 100 万节点 | 1000 次子节点查询 | 汇总查询 | 数据库 | 运行时 RSS |
| --- | ---: | ---: | ---: | ---: | ---: |
| 树形目录 | 约 3.1 秒 | 约 13 ms | 约 35 ms | 约 159 MB | 约 101 MB |
| 单父节点高扇出 | 约 10.2 秒 | 约 171 ms | 约 34 ms | 约 152 MB | 约 101 MB |

1000 个节点的分页 JSON 约 150 KB。首次 `go run` 的编译内存不计入运行时
RSS；结果仅代表快照层合成基线，不代表真实全盘扫描耗时。

## 锁定方案

- 使用 `SnapshotStore` 端口，第一实现使用 SQLite；
- 采用增量写入、WAL、批量事务和分页查询；
- 默认批次为 10,000 节点，取消只在批次提交边界发布新的持久化结果；
- 页面最多返回 1000 个节点，事件只发送摘要和进度；
- 使用 `snapshot_id, parent_id, owned_allocated DESC, id` 支持稳定分页；
- 快照数据库属于缓存/观察结果，不作为文件操作授权。

## 验收门槛

- 合成 100 万节点写入不超过 20 秒；
- 1000 个节点分页查询 p95 不超过 50 ms；
- 单快照存储层运行时 RSS 不超过 256 MB；
- 单次绑定返回不超过 256 KB，不能一次向 WebView 发送百万节点；
- worker、队列、事件批次和缓存必须有上限；
- 取消后不得提交新的扫描批次。

门槛是本机基线和回归预算，不是对所有真实磁盘的硬性耗时承诺。

## 限制与后续

真实全盘文件名长度、权限错误、FileProvider 占位文件、APFS 克隆和扫描器内存
尚未纳入此合成基准；Wails 运行时绑定耗时也尚未实测，只锁定了 256 KB JSON 预算。
需要在垂直切片和发布前继续跑真实只读目录样本。

产出已用于更新 ADR-0003，并新增具体的 SQLite 与工具链决策。

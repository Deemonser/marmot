# R-063 AI 建议的稳定性与准确率基线预研

- 日期：2026-08-28
- 触发：[ADR-0061](../adr/0061-AI清理建议边界与证据装配.md) 门禁 9 刻意留空——"幻觉率、准确率、
  两段式增益"在没有真实调用之前无法设数。首次真实调用已完成（`deepseek-v4-flash`），
  本记录建立可复现的基线。
- 关系：证据装配与规则覆盖率基础见
  [R-062](R-062-AI清理建议证据装配与规则覆盖率预研.md)。

## 0. 主轴的修正：不是风险，是可恢复性

本记录第一版把 `risk`（safe/review/risky）当作核心轴，并把"假 safe 率"定为发布门槛。
使用方在看过标注清单后指出这是错的：

> 很多东西，只要不是完全无法恢复的情况下，确实没有很大问题，甚至有些工具例如 flutter、rust
> 直接全部删了重新安装，也能清理里面很多无用文件，这些也是能接受的。
> **不能接受的是那些删了就没办法恢复的部分。**

这句话改掉了三件事：

1. **判断依据是 `recovery` 而不是 `risk`。** 重装一整套工具链是可接受的恢复方式；
   删掉照片库不是。前者最坏是等一次下载。
2. **`recovery` 基本是事实问题，不是偏好问题。** "删了能不能装回来"可回答且可核验；
   "该不该删"要求使用者预测自己未来的需求，多数情况无法回答——
   这正是第一版标注清单填不下去的原因。
3. **因此发布门槛变成：模型有没有把"删了就没了"的东西说成可恢复。**
   其余判断错了最多多等一次下载，只有这一类不可挽回。

实测印证了这个选择：**恢复性漂移 `1/20`，而风险漂移 `8/20`**——
模型对"能不能回来"的判断远比对"危不危险"的判断稳定，而前者恰好是使用者决策所依赖的那个。
唯一漂移的那条在 `redownloadable` 与 `regenerable` 之间摆动，两者都是"能回来"。

## 1. 问题：清理建议没有客观真值

"该不该删 `~/.rustup/toolchains/1.89.0`" 取决于使用者还用不用 Rust 1.89。没有算法能回答，
所以用单一标签算 accuracy 是错的框架。

可度量的部分必须先和不可度量的部分分开：

| 类别 | 指标 | 是否需要人 |
| :-- | :-- | :-- |
| 事实性 | 引用属实率——建议引用的每个数字都出自证据包，可逐一回查 | 否 |
| 一致性 | Jaccard、**恢复性漂移**、风险漂移 | 否 |
| 合规性 | 覆盖率、护栏丢弃、**守卫纠正次数** | 否 |
| **安全** | **误判可恢复率：模型说能回来，实际删了就没了** | **是**（清单外的部分） |

只有最后一类需要人，而且它是**事实判断**——所以标注一次即可固化为 fixture 长期复用，
不会因为使用者改了主意而失效。这是把主轴从 `risk` 换到 `recovery` 的额外收益。

### 1.1 `IrreplaceableReason`：与删除护栏同构的第二道守卫

`cleanup.DeleteBlock` 回答"能不能删"；`recommendation.IrreplaceableReason` 回答"删了能不能回来"。
覆盖用户原创内容（含沙盒应用的 `Data/Documents`——它与缓存只隔一个路径段）、
应用为用户保存的数据、版本库历史、设备备份、虚拟机磁盘、密钥。

模型声称可恢复而守卫判定不可恢复时，**纠正而不丢弃**：覆盖为 `irreplaceable` + `risky`，
把真相拼到 `what_breaks` 之前，并计数。丢弃会把对象和错误一起藏起来。

`.git` 在清单内，理由记录在代码里：远端也许有副本，但本工具无法确认，
"应该推过了"不是恢复方案。**已知的一处误判并已修正**：`tmp_pack_*` / `tmp_idx_*`
是 git repack 中断后遗留的临时文件（实测有一个 `438.5 MB` 长期滞留），不是历史。
例外按字面前缀开，不开成 pattern——宽泛的例外正是安全守卫长出漏洞的方式。

## 2. 环境与方法

- 机器：本机，`PROBE_ROOT=$HOME`（**不是全盘**）。证据包 `643`–`669` 节点 / 约 `43 KB`，下限 `122 MB`。
- 模型：`deepseek-v4-flash`，`reasoning_effort=low`，`json_object`，SSE 流式。
- 每轮：**一次扫描、一份证据包、连问三遍**——三次之间的差异全部来自模型，不来自输入。
- 探针：`internal/probe/baseline_probe_test.go`（opt-in）。

### 3.1 三个被否掉的假设

**假设一：temperature 是主因。错。** `0.35 → 0.37`，基本没动。

但 `temperature=0` 仍然保留：它把引用属实率推到 `100%`、风险漂移从 4 个降到 1 个。
**收益是真的，只是不是预期的那一项。**

**假设二：提示词要求穷尽能解决。错，而且更糟。** `0.37 → 0.28`，覆盖率只有 `21–26%`，
产出量崩到 14/7/8。

成因是指令不可执行：证据包按**树结构**渲染，而我要求"按占用从大到小处理最大的 40 行"——
模型得在脑内把 666 行重排一遍。它不是在偷懒，是这件事在这个格式下做不可靠。
**要求一个没有提供条件去完成的动作，得到的是崩溃而不是拒绝。**

**假设三（成立）：让模型不做它做不好的那件事。**

前两轮的数据一直在指同一个方向：**模型对"某个对象是什么、危不危险"的判断是稳定的**
（引用 `100%`、风险漂移 1/50），**飘的只有"这次愿意提哪些"**。那不是采样问题也不是指令问题，
是任务形态问题。

于是选择权收回到确定性代码：`EvidencePack.Candidates(40)` 剔除受保护路径与规则已覆盖的子树，
排序取前 N；输出契约从"自由列建议"改为"逐候选给判定"（`cleanable` / `keep` / `unknown`）。
**覆盖率从此是请求的属性，不是回复的运气。**

### 3.2 第四轮的实现 bug 与 residue 的正确用法

第四轮按 `OwnedAllocated` 排序，产出量崩到 3/2/2。

成因：`~/Library` 有 `28 GB` 且规则不匹配它（规则匹配的是 `Library/Caches`），
于是占据候选第一名，随后"祖先排除子孙"把它下面的一切都剔掉了——
上一轮真正找到的 `Code/CachedExtensionVSIXs`、`Application Support/Caches` 全部消失。
模型对 `~/Library` 正确地回答了 `keep`，而一轮只剩两条建议。

**正确的排序键是 `residue`。** 这个字段的存在意义正是区分二者：

- `residue ≈ 占用` → 内容在这个节点身上，它是可行动的单位；
- `residue` 很小 → 它只是路过的中间节点，内容在已列出的子节点里。

`residue` 还是一个**分区**，所以取前 N 的字节覆盖天然不重叠，祖先去重那一步根本不需要。
第五轮改用 residue 后产出量回到 18/19/24，稳定性与覆盖率保持。

**这是一次用错自己设计的字段的错误**，不是模型的问题。

### 3.3 第五轮的残留问题

- **风险漂移升到 7 个对象，全部是 `review` ↔ `safe`。** 这恰好是最危险的方向，
  而假 safe 率是发布门槛。7 个对象列表见 fixture 的 `risk_runs` 列。
- 引用属实率回落到 `97.0%`（165 个数字中 5 个对不上）。未逐一核查是加总还是编造。
- **收窄候选的代价是真实的**：第二轮找到的 `CachedExtensionVSIXs`、`codex-runtimes/native`
  在第五轮不在候选前 40（按 residue）或被判 `keep`。稳定性与召回之间存在取舍，未量化。

## 3.6 两个把度量本身搞错的错误（已修）

1. **换了主轴却没换尺子。** 把 `recovery` 提升为主轴之后，探针继续只报告风险漂移——
   量的是被降级的那个轴。现在按**路径**统计恢复性漂移。
2. **刚加的核心指标自己没输出。** 守卫纠正次数在第七轮实际触发了 1 次，
   但探针没有打印，只能从标注表的 `what_breaks` 文本里反推出来。现在逐条打印。

## 3.7 标注：由谁标，以及测出来的数

使用方指出标注者不该是使用方：

> 这个能不能恢复应该是你能回答的，毕竟很多东西用户自己都不清楚，但你能查文档，了解真实情况。

这是对的，而且是把 `recovery` 选作主轴的必然结果——**事实问题应该由能查证的一方回答**。
20 条建议由本次会话标注，依据逐条记录在 `fixtures/R-063-label-notes.tsv`，可复核。

```
ok 19   bad 1        误判可恢复率 = 1/20 = 5%
```

**唯一一条 `bad`：`~/dev/flutter/bin/cache/dart-sdk/bin/snapshots`（`349.6 MB`）。**
模型判 `redownloadable`，恢复方式写"运行 flutter doctor 或重新安装 Flutter SDK"。

从磁盘上的 `flutter_tools/lib/src/cache.dart` 查实（非推测）：

```dart
Future<bool> isUpToDate(FileSystem fileSystem) async {
  if (!location.existsSync()) return false;                    // 只看根目录存在性
  if (version != cache.getStampFor(stampName)) return false;   // 只比 stamp
  return isUpToDateInner(fileSystem);                          // 也只查目录存在性
}
```

**只校验 artifact 根目录是否存在与 stamp 是否匹配，从不校验内部文件完整性。** 由此：

- 删掉**整个**根目录 → `existsSync()` 为 false → 会重新下载（清单第 2 条
  `artifacts/engine` 因此判定正确）；
- 删掉根目录**内部**的子目录 → 根还在、stamp 还在 → **永远不会自愈**，工具链一直是坏的。
  `flutter doctor` 恢复不了任何东西；真实代价是删除整个 `bin/cache` 重新拉取约 GB 级数据。

### 3.7a Kotlin/Native 的复核：结论与预期相反

`.konan/.../klib/platform` 初标 `unsure`。查 `kotlin-gradle-plugin 2.2.21` 源码
（版本与本机安装的发行版一致）后改为 `ok`：

```kotlin
// PlatformLibrariesGenerator.checkLibrariesInDistribution()
val presentPlatformLibs = platformLibsDirectory
    .listFiles { file -> file.isDirectory }.orEmpty()
    .map { it.name }.toSet()
return presentDefs.toPlatformLibNames().all { it in presentPlatformLibs }
```

**逐个校验每个 platform lib 目录是否存在**，缺任何一个即调 `runGenerationTool()`
从 `.def` 文件本地重新生成。删掉 `klib/platform` 会自愈。
模型判 `redownloadable` 在机制上略有偏差（实际是 `regenerable`：本地生成而非下载），
但**可恢复性判断正确**。

（下载决策本身也确认了不是它触发的：`NEED_TO_DOWNLOAD_FLAG =
parameters.classPath.files.none { it.exists() }`，只在编译器 classpath 全部缺失时才下载。）

### 3.7b 这个对比修正了 3.8 的提示词规则

| 工具链 | 完整性校验方式 | 删内部子目录 |
| :-- | :-- | :-- |
| Flutter | 只查 artifact 根目录存在性 + stamp | **不自愈** |
| Kotlin/Native | **逐个校验每个 platform lib** | **自愈**（本地重新生成） |
| rustup | 按 component 跟踪 | 自愈（`component add`） |

**两种模式在真实世界里都存在**，所以 3.8 最初写的"拿不准时按内部子目录处理、把恢复代价说重"
是**一条过粗的规则**：用在 Kotlin/Native 上会夸大恢复成本。方向保守，但仍然不准。
提示词已改为讲清这个对比，并要求"知道就照实说，不知道就判 `unknown` 让程序展开，
不要拿一个方向的猜测代替事实"。

**这同时反向验证了守卫的窄口径是对的**：若当初把"工具链内部不自愈"写成通用规则进代码，
Kotlin/Native 这一条就会被错误纠正。查实的事实进守卫、一般性推理进提示词，这个分工成立。

### 3.8 修法：查实的事实进守卫，一般性原理进提示词

- **守卫**：`PartialInstallReason` 只覆盖已从源码查实的一处（Flutter `bin/cache/dart-sdk` 内部）。
  纠正为 `redownloadable` + 风险抬出 `safe`，并把真实代价拼在 `what_breaks` 之前。
  **窄口径是有意的**：某个安装器是按组件跟踪（rustup 是）还是只查存在性（Flutter 是），
  属于工具特定知识，守卫靠猜会比提示词规则更糟。
- **提示词**：新增一节讲清"整个根目录 vs 根内部子目录"的区别，并要求拿不准时
  **把恢复代价说重而不是说轻**。

复跑验证：守卫在 `dart-sdk/bin/snapshots` 上准确触发，该条从 `safe` 降为 `review`
并带上真实恢复路径。Jaccard `0.95`（仅 2 次运行，不可与 3 次的数比较）。

**顺带修掉一处自造的错误陈述**：纠正提示原本对两类纠正共用一句"已改标为不可恢复"——
而 partial_install 那类其实**仍然可恢复，只是代价高一个量级**。工具在自己的纠正说明里说了假话。

## 4. 两个把基线自己搞坏的 bug（已修）

1. **标注表按 `node_id` 对齐。** node id 是每次扫描重新编号的，重扫一次同一路径即是另一个 id，
   **按它对齐的标注跨扫描全部失效**。改为按 `path` 对齐。
   这个缺陷会静默地让整份 fixture 失去意义。
2. **产出为空时仍无条件写入标注表。** 一次 `HTTP 402 Insufficient Balance` 的失败运行
   把 26 行的清单覆盖成 0 行，且无副本。现在为空则不写，并在覆盖前留 `.prev` 备份。

## 4a. 架构结论：AI 负责发现，规则负责稳定

使用方问的是"规则 + AI 是否更稳定"。当前实现**已经是**规则 + AI（见 SDD §14），
所以真正的问题是这条线画在哪、以及它会不会移动。

数据说它应该移动，而且是单向的：

**AI 是发现机制，规则是稳定机制。** AI 找到一个东西 → 人核实其可恢复性 → 写成规则 →
从此不再需要模型。候选选择本来就排除规则已覆盖的路径，所以**规则每增加一条，
AI 的预算就自动流向更未知的地方**——这个机制早已在代码里，只是规则表太小。

本轮把 R-063 §3.7 标注确认过的发现整理成 15 条新规则（目录 `28 → 43`），实测同一台机器：

| | promotion 之前 | promotion 之后 |
| :-- | --: | --: |
| 规则层（完全确定性） | 24 条 / `53.9 GB` | **48 条 / `71.6 GB`** |
| AI 层 | 18–20 条 | **7 条** |
| 引用属实率 | `97%` | `100%` |
| 恢复性漂移 | `1/20` | `0/7` |

**这个测量是循环的，必须明说**：这 15 条规则正是从这台机器的发现里提炼的，
在同一台机器上量它们的覆盖率等于自证。`71.6 GB` 不能作为规则层能力的证据，
它只证明"棘轮的机制通了"。真正的检验是另一台机器——那时新规则命中多少、
AI 又找到多少规则表里没有的东西，才是有意义的数字。

### 4a.1 规则表能表达的比 R-062 说的多

R-062 §3.4 断言"规则没有时间概念，冷数据这一类结构上判断不了"。**这个断言是错的**：
它实际测的是那份手写目录没有年龄条件，不是目录不能有。

`Rule.MinAgeDays` 已加入，`**/build/intermediates` 因此有了两条规则——
`180` 天以上判"冷构建产物 / safe"，其余判"编译产物 / review"，
first-match 保证冷的那条先命中。同时补了两个模式能力：
段内 `*` 单段通配（`**/target/*/debug` 覆盖交叉编译目标）和段尾 `*` 前缀匹配
（`tmp_pack_*` 这类随机后缀产物）。

### 4a.2 AI 交不出去的部分

- **未知应用的识别**：`LunaCacheV2` 是缓存还是用户的离线歌曲，规则表没有这个 app 就永远不知道。
  这类**刻意不写成规则**——按 app 名硬编码既脆弱又无法穷尽，正是模型该做的事。
- **清单外对象的说明文字**：规则的"删了会怎样"是静态文案（写一次、审一次），
  比模型每次生成更可靠；但规则覆盖不到的对象只能由模型现写。

## 4b. 第三次换轴：可恢复性也不是标准

使用方在 §0 之后又指出一层：

> 删除后能否恢复并不是一个标准。我们的标准应该是对于用户的使用没有太大影响才对。
> 例如我最近在做一个项目，里面的缓存越来越大，虽然删掉都能恢复，但恢复就需要重新下载，
> 这明显不好。

这是对的，而且 §0 的 `recovery` 轴把两件事压成了一件：**拿回来的代价** 与
**你多久之后会需要它**。第二项在实际使用中占主导。

```
干扰成本 = 恢复代价 × 你即将需要它的概率
```

第二个因子是可以由代码估的：项目**源码**的活跃度。实测三个真实项目：

```
zymix-im-android-cloud   源码 0 天前改动     ← 在用
FirstApplication         源码 618 天前       ← 停摆
StarChat                 源码 0 天前         ← 在用
```

`ProjectSensitive` 规则的风险据此调整：在用（≤30 天）不得为 `safe` 并说明原因，
停摆（≥180 天）可放宽。真机效果：`FirstApplication` 的 `547 MB` 产物从 `review` 变 `safe`，
而 `zymix-im-android-cloud` 的 `3 GB`、`StarChat` 的 `846 MB` 全部从 `safe` 降为 `review`
并附上"这个项目 0 天前还改过源码，正在使用中"。

### 4b.1 两个把这个信号量错的 bug

**一、我上一轮刚提交的 `MinAgeDays` 冷规则用的是产物自己的 mtime。**
设想 200 天前构建过、昨天改了源码准备重新构建——产物还是 200 天前的，冷规则命中，
**正好在使用方描述的那个场景下把在用项目的缓存判成 safe**。年龄条件必须挂在项目源码活跃度上。

**二、目录 mtime 不是源码活动。** 排除 `.DS_Store` 文件之后，`FirstApplication` 仍报 148 天。
原因是 **Finder 写 `.DS_Store` 会同时更新该目录自己的 mtime**，而目录 mtime 照样向上传播。
链条完整是：浏览目录 → 写 `.DS_Store` → 目录 mtime 更新 → 一个 641 天没编辑的项目
看起来"148 天前还在用" → `547 MB` 停在 `review`。

修法不是再加一层排除，而是改模型：**源码活跃度只能取自源码文件，目录只从子节点继承**，
自己的 mtime 一概不算。`.git` 也归入"工具写的"（`fetch`/`gc` 都会改它），
但它作为项目标记的角色不变——两个角色互相独立。

### 4b.2 浏览器：明确说做不到什么

可以做到目录级区分（`Cache`/`Code Cache`/`GPUCache` 可清理，
`Cookies`/`Login Data`/`Local Storage`/`IndexedDB` 必须保留），
因此"清缓存但保住登录态"可达成；长期未用的整个 profile 可作为一个对象提出。

**按站点删除登录信息不做。** 那是 SQLite 数据库里的行，按站点清理等于写入应用的数据库——
超出"移入废纸篓"的边界，且浏览器持有文件时写入有损坏风险。
"很久没访问的站点的登录信息也可以删"这个诉求，本产品只能以"整个 profile"的粒度部分满足。

## 4c. 代际清理：不能只按"最新"

规则表能命名一个目录，但命名不了"这个目录里哪一代已经死了"——`.rustup/toolchains`
下面每一代的路径长得一样，死掉的是哪一代取决于用户还在用哪一个。这一类只能靠
**兄弟之间比较**：同一个父目录下的各代，保留仍在用的，其余提供出来。

本机实测的四处代际结构：

| 位置 | 各代（体积 / 最近写入距今） |
| --- | --- |
| `.rustup/toolchains` | stable 1454MB / 4 天 · 1.91.0 1225MB / 57 天 · 1.89.0 1207MB / 59 天 |
| `.nvm/versions/node` | v24.19.0 896MB / 17 天 · v22.15.1 1022MB / 25 天 |
| `.gradle/wrapper/dists` | gradle-8.13-bin 290MB / 4 天 · gradle-9.6.1-bin 151MB / 38 天 |
| `.konan` | kotlin-native-prebuilt-2.2.21 900MB / 0 天（只有一代） |

### 4c.1 nvm 是"保留最新、其余提供"的反例

最自然的写法是"按最近写入排序，留第一个，其余都提供"。这个写法在
`.nvm/versions/node` 上是错的：v24.19.0 距今 17 天、v22.15.1 距今 25 天，两代都活着
——**同时保留多个 Node 版本本来就是 nvm 存在的理由**。只因为用户第二个碰到的是
v22，就提议删掉一个 1 GB 的在用工具链，这个建议一旦被采纳，代价是用户下次切到那个
项目时构建直接失败。

所以判据里加了 `MinGapDays`：一代要被提供，必须比**保留下来的那一代**老得足够多，
而不只是"比它老"。同一份阈值在两处的结果：

- rustup：最新 4 天，候选 57 / 59 天 → 间隔 53 / 55 天 ≥ 30，提供（2.2 GB）
- nvm（阈值 90 天）：最新 17 天，候选 25 天 → 间隔 8 天，**不提供**
- Gradle 发行版：最新 4 天，候选 38 天 → 间隔 34 天 ≥ 30，提供（151 MB）

`.konan` 只有一代，`KeepNewest` 直接把它挡住了。这是代际清理和"按年龄清理"的分界：
**一台一年没构建过的机器上，唯一的那条 Rust 工具链再老也不能提供**，而年龄规则会把它
删掉。

阈值取值（rustup / Gradle / Xcode 30–60 天，nvm 90 天）是根据本机这四处的实测间隔
选的，不是验证过的普适值；nvm 取更大的间隔，理由是版本轮换在 nvm 上是常态而不是例外。

### 4c.2 mtime 只是"何时被写过"，不是"何时被用过"

读文件不改 mtime。对 Gradle 缓存、Xcode DeviceSupport 这类工具会往里写的目录，
最新 mtime 约等于"最近一次使用"；对一份只读发行版，它说的是"何时装的"。
`MinGapDays` 正好把这份不精确挡在门外：要跨过几十天的间隔，得是真的换代了。

### 4c.3 一个规则内部命中把整代吃掉的 bug（已修）

`.rustup/toolchains/*/share/doc` 是一条真规则（rustup 本地文档，safe）。按 4a.1 定的
"特异性高的先占"，它的字面段数（4）高于整代（3），于是它先占掉了 718 MB，然后整代作为
它的**祖先**被重叠折叠丢掉。结果：用户看到的是一份**已经不用的工具链的文档**，而不是
那条 1.1 GB 的工具链本身。

修法不是调数字，而是把不变量写清楚：**在一代内部命中的规则，是对同一批字节更弱的
陈述，整代优先**；反过来，**祖先上的规则提供的是超集，祖先优先**。后者本机上靠折叠
恰好也成立（`.gradle/caches` 在证据包里是一个 33.9 GB 的叶子，下面没有版本目录了），
但那是两套条件不同的机制碰巧一致，不能当保证——所以显式判了一次祖先。两个方向各有
一条回归测试。

修完本机结果：代际合计 **2.5 GB**，规则层 58 条 / 73.8 GB。

## 4d. 依赖缓存里的"旧版本"：测了，不做，以及一个差点写下的错结论

使用方问：`~/.gradle/caches/modules-2` 里的旧版本依赖是不是可以删。方向对——
`files-2.1` 的结构就是 `<group>/<artifact>/<version>/`，天然是代际。实测：

| 指标 | 数值 |
| :-- | --: |
| `files-2.1` 合计 | 2.90 GB |
| 构件数（group:artifact） | 1053，其中多版本 394 |
| 版本目录 | 1969 |
| **非最新版本** | 916 个 / **0.95 GB（32.8%）** |

上限只有 0.95 GB，占规则层已找到的 73.5 GB 的 **1.3%**。而且信号本身不成立：

| 比保留的那一版旧多少 | 字节 |
| :-- | --: |
| 0–29 天 | **733.2 MB** |
| 30–59 天 | 216.9 MB |

**77% 的"旧版本"是和保留版本在 29 天内一起写下来的。** mtime 记的是下载时间，
不是使用时间；同一次构建会一次拉下多个版本。而多版本共存恰恰是因为它们都活着：
`kotlin-stdlib` 在这台机器上有 **18 个版本**，不同项目各自 pin 不同的 Kotlin。
**这是 §4c.1 那个 nvm 反例的 1000 倍放大版**，按"保留最新"删，正好命中使用方最初的担心：
删了下次构建立刻下回来。

`atime` 也不可用：1053 个构件里只有 104 个的 atime 明显晚于 mtime。

### 4d.1 一个差点写下的错结论

按年龄分桶时，`files-2.1` 里 **90 天以上的内容是 0 MB**，95% 在 30 天内。
我据此准备写下"Gradle 自己的清理已经在做这件事了"——`journal-1/file-access.bin`
两天前刚写过，看起来是完整的证据链。

**这个结论是错的。** 查 birthtime：

| 目录 | 创建于 |
| :-- | --: |
| `~/.gradle` | 597 天前 |
| `~/.gradle/caches` | **48 天前** |
| `files-2.1` 里最老的文件 | 48 天 |

`caches` 目录在 48 天前被整个重建过。**没有冷数据不是因为有人在清理，是因为这个缓存
只有 48 天大**——样本里根本不存在长尾。同一批数字，两个完全不同的解释，而我先选中的是
错的那个：因为它更像一个漂亮的结论。

判据：**"某个年龄以上什么都没有"永远要先查容器自己多大**，否则那只是在测量样本的年龄。

### 4d.2 结论：不做，且现在做不了

- 上限 1.3%，风险是删掉正在用的依赖，收益风险比不成立；
- 唯一能区分死活的信号是"最后一次被使用"，Gradle 有（`file-access.bin`），本工具没有。
  那是 Gradle 内部的二进制格式，解析它会随 Gradle 版本静默失效——一个会悄悄给出错误
  答案的信号，比没有信号更糟；
- 就算要定阈值，这台机器上**没有 48 天以上的样本可用来定**。在 48 天大的缓存上调一个
  "多久算旧"的阈值，是 §6 那个循环论证的又一个变体。

真正该给使用方的是**能用的杠杆**：Gradle 8+ 可以按"未使用天数"自行回收，
因为它有访问时间记录。这条写进了 `modules-*` 规则的 `HowToRestore`。

重新评估的条件：拿到一份**长期未清理**的依赖缓存——这正是 ADR-0062 阶段 4 聚合数据
要解决的那类问题（单机看不到长尾），也是 §6 换机器跑基线的又一个理由。

## 5. 结论

0. **架构上应当是"AI 发现、规则固化"的单向棘轮**，不是静态二分（§4a）。
   规则层每扩一条，AI 预算自动流向更未知的地方；本轮 promotion 使确定性部分
   从 `24 条 / 53.9 GB` 升到 `48 条 / 71.6 GB`，AI 侧收窄到 `7` 条——
   但该测量在同一台机器上是循环的。
1. **稳定性问题的根因是任务形态，不是采样参数或提示词措辞。** 让模型自由选择要点评什么，
   它每次给出不同的三分之二；给它固定清单逐项判定，`0.35 → 0.75`、覆盖率 `100%`。
2. `temperature=0` 对事实性和风险一致性有效，对覆盖一致性无效。
3. 排序键必须是 `residue` 而非子树占用。
4. 可自动化的三类指标（引用属实、稳定性、护栏）已作为探针固化，可回归。
5. **准确率仍未建立。** 需要人对 fixture 标注一次。

## 6. 本次未验证 / 已知限制

- **误判可恢复率已测得 `1/20 = 5%`，但样本极小**：20 条、一台机器、一个模型、家目录。
  5% 这个数字不应被当作产品指标，它只说明"在这 20 条里有 1 条错，且错因已定位并修复"。
- Kotlin/Native 那条已查实为 `ok`（见 §3.7a）。但只查证了 Flutter、Kotlin/Native、rustup 三例，
  其余工具链（Android SDK、Xcode、konan 之外的 JetBrains 运行时等）的完整性校验方式未查。
- 提示词新增的"整个根目录 vs 内部子目录"规则**只验证了一次复跑**，是否泛化到其他工具链未测。
- 干扰度阈值 `30` / `180` 天是**未经验证的整数**，没有做敏感性分析，也没有问过使用者
  "多久不碰算停摆"。项目根标记与"非源码文件"清单同样是手写的，遗漏会让信号失真。
- 项目活跃度只覆盖**有标记文件的项目**。家目录里大量对象不在任何项目内，
  对它们这个轴完全没有信号，风险仍按规则声明。
- 风险漂移仍有 `8/20`（全部 `review` ↔ `safe`）。在新主轴下它不再是发布门槛，
  但"摆到 safe 那次会让用户少看一眼"这个后果没有消失，未处理。
- 只有 `$HOME`，不是全盘；只有一台机器、一种（重度开发者）使用画像。
- 只有一个模型（`deepseek-v4-flash`）。换模型的结论不可推断。
- 每轮只有 3 次运行，Jaccard 的置信区间未估计。`0.75` 与 `0.78` 之间的差异不应被解读为差异。
- 恢复性声明（`regenerable` 是否真的可再生）未做任何验证。
- 稳定性与召回的取舍（§3.3）未量化：候选数 `40` 是按输出预算拍的，未做敏感性分析。
- 引用属实率里"对不上的数字"未逐一区分加总与编造。

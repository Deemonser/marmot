# R-023 SQLite 目录汇总写入优化预研

状态：已完成，结论由 ADR-0025 接受

日期：2026-08-21

## 1. 问题

应用层全盘 smoke 已经可以持续发布进度，但完整快照落盘仍约 61 秒。CPU profile 显示，最终阶段
将约 53 万个目录汇总逐行更新回 `scan_nodes` 约占 11 秒；该更新还会维护按父节点和占用排序的索引。
这会把用户看到的扫描完成时间拖到纯目录枚举之后很久。

## 2. 证据

- 纯扫描器：约 270 万节点，8 worker，两次为 15.22s 和 14.64s；
- 应用层 SQLite smoke：约 55s 到 61s；
- CPU profile：`getattrlistbulk` 约 20.5s，节点写入约 8.2s，`UpdateDirectorySizes` 约 11.2s；
- 将目录更新改为临时表集合更新的实验升到约 1m41s，将 CTE 分块更新仍约 61s，不能继续采用；
- 直接把目录汇总写回节点事实表会触发目录节点的父排序索引维护。

## 3. 方案

接受在 SQLite 中增加 `directory_sizes` 汇总表：

1. `scan_nodes` 只保存路径、身份、类型和扫描时的节点事实；
2. `directory_sizes` 以 `(snapshot_id, node_id)` 保存渐进和最终目录汇总；
3. `SnapshotStore` 通过分块 upsert 写入汇总，不更新 `scan_nodes` 的父排序索引；
4. `NodeByID`、`NodeByPath`、当前层查询和聚合查询读取目录节点时叠加汇总表；
5. 没有汇总行的旧快照回退到 `scan_nodes` 中已有的目录大小，保证迁移期间可读。

## 4. 拒绝方案

- 继续逐行更新 `scan_nodes`：语义正确但已证明是端到端主要落盘瓶颈；
- 临时表或 CTE 集合更新：本机实验没有改善，且临时表版本明显回归；
- 在 Application 保留百万级完整内存树：违反 SQLite 唯一快照存储和内存边界；
- 查询时每次递归计算全部目录汇总：会把写入成本转移到交互查询，不能保证当前层响应。

## 5. 验收门槛

- 旧 schema 和新 schema 的节点查询、Map 排序、三种大小、可信度和目录分页结果一致；
- 取消、重启恢复和快照删除不会留下可见的孤立汇总；
- 应用层大样本 smoke 的目录汇总写入明显低于逐行更新版本，并记录节点数、问题数和耗时；
- 不改变 Wails、Domain、清理校验、挂载边界和进度事件契约。

## 6. 限制

该优化只解决快照落盘路径，不承诺把包含 SQLite 和前端的完整 App 运行时间直接降到 15 秒；
如果大样本验证未改善，必须回退该方案并重新预研，不用文档掩盖实际耗时。

# R-028 应用持久化队列上限与终态内存预研

状态：已完成，结论由 ADR-0030 接受；代码切片已实施，完整终态总门槛仍未完成

日期：2026-08-24

## 1. 目标

修正 Application 扫描事件队列的容量边界，降低真实 `/` 扫描期间的峰值内存，并保持扫描吞吐、
部分结果、首层发布 barrier、取消和快照完整性语义不变。

本轮不改变原生 worker 数量、SnapshotStore 文件格式、提交校验和、目录索引或 Wails 契约。

## 2. 问题与证据

SDD 已将待提交批次固定为 `2`，但当前 `runScan` 使用：

```go
const scanBatchSize = 50000
events := make(chan persistEvent, scanBatchSize*2)
```

这把 SnapshotStore 的节点聚合批次误用成了 Application 事件队列容量，实际容量为 `100000` 个事件。
原生 `BatchScanner` 每次最多交给 Application 一个受限节点批次；队列满之前，扫描线程可以继续保留大量
节点切片，形成与节点规模同阶的内存增长。此前真实 `/` 采样出现约 `590 MB` 峰值，而原生 worker
固定缓冲本身约占几十 MB；这不能证明全部峰值都来自事件队列，但足以构成明确的内存上界违约风险。

`scanBatchSize` 的职责应与队列容量分离：前者是 writer 在 Application 内聚合节点后调用
`SnapshotStore.InsertNodes` 的提交阈值，后者是等待 writer 消费的事件批次数。两者单位和生命周期不同。

## 3. 方案比较

### 方案 A：Application 持久化事件队列固定为 2

采用。增加独立常量 `scanPersistQueueCapacity = 2`，事件 channel 只允许保留两个待消费批次。
队列满时，生产端在可取消的发送路径上等待 writer 消费，形成受控背压。

### 方案 B：继续使用 `scanBatchSize*2`

拒绝。把提交批次大小映射成事件数量，无法给内存建立稳定上界；节点批次大小、切片生命周期或后续
批量策略变化都会放大峰值。

### 方案 C：改为无缓冲 channel

暂不采用。无缓冲会让扫描和持久化过度同步，可能放大 writer 抖动对原生扫描的影响；当前 SDD 已锁定
待提交批次为 `2`，没有证据证明容量 `0` 能带来可接受的完整终态收益。

## 4. 决策与语义

- `scanPersistQueueCapacity` 固定为 `2`，不作为用户配置；
- `scanBatchSize=50000` 只表示 SnapshotStore writer 的内存聚合阈值，不能用于计算事件 channel 容量；
- 队列满时发送端受 context 控制地阻塞，不能丢弃节点、跳过问题记录或绕过 writer；
- writer 出错或退出时，发送端必须得到错误并结束扫描，不能继续向已停止的 writer 投递；
- barrier 事件仍按 FIFO 顺序等待 writer 刷完此前节点，`TopLevelPublish` 的可见性边界不变；
- 取消只阻止尚未提交的新批次，已经进入 writer 的批次按既有取消和部分快照语义收尾；
- 不关闭 `Sync`、footer、数据/索引校验和 manifest 原子发布，不改变查询或清理前身份校验。

队列容量 `2` 只限制 Application 等待中的事件数量；原生 worker 固定缓冲、writer 当前聚合批次和
SnapshotStore 内部必要缓冲仍分别受各自 ADR 约束，不能用本常量替代它们的预算。

## 5. 验收与测量

1. Application 事件队列使用独立容量常量，代码中不存在由 `scanBatchSize` 推导 channel 容量的路径；
2. scanner、snapshot、application 窄测试和相关 race 测试通过，取消、writer 错误、首层 barrier、
   批量 emitter 和快照尾部恢复语义无回归；
3. `go vet ./...`、前端构建和 `git diff --check` 通过；
4. 真实 `/` 串行运行三次，分别记录纯扫描、完整终态、`FinishSnapshot`、节点/问题数量和峰值 RSS；
5. 不能用单次低于 15 秒或单次 RSS 下降宣称完整终态目标达成；仍以同条件三次中位数 `<=15s` 为总门槛。

本轮同一工作区串行复测结果如下。节点数较历史基线更高，文件系统内容和缓存状态也会变化，因此只用于
验证本切片的当前证据，不与不同节点规模的历史秒数直接做性能结论：

| 轮次 | 完整终态 | FinishSnapshot | 节点 | 问题 | 最大 RSS |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | `20.504s` | `4.054s` | 2,846,083 | 441 | `611,942,400` |
| 2 | `25.731s` | `4.127s` | 2,846,083 | 443 | `619,282,432` |
| 3 | `20.895s` | `4.112s` | 2,846,083 | 441 | `611,860,480` |

三次完整终态中位数为 `20.895s`，最大 RSS 约 `584–591 MiB`；队列容量修正没有让总终态达到 15 秒，
也没有证明峰值 RSS 的主要来源就是事件 channel。下一步应对 `FinishSnapshot` 和索引阶段做分段 profile，
不能继续扩大或收紧事件队列替代证据。

## 6. 限制与后续

- 当前峰值 RSS 还包含原生缓冲、Go allocator、快照索引排序和系统文件缓存，队列收紧后的收益必须用
  `/usr/bin/time -l` 和同条件运行验证；
- 若完整终态仍未达到 15 秒，下一步必须基于新的分段耗时和 RSS 证据选择 `FinishSnapshot`、路径构建或
  索引阶段切片，不能在本轮隐式改变快照协议；
- 目录增量缓存、mmap、索引格式重写和 worker 数量调整仍需独立预研与 ADR。

## 7. 对 DDD、SDD 和实现的影响

该决定只约束 Application/Infrastructure 的运行时背压和内存预算，不增加领域对象、领域事件或领域不变量。
DDD 不变；SDD 增加 Application 持久化事件队列的明确容量和 `scanBatchSize` 的职责边界；实现已将
`runScan` 的 channel 容量固定为 `2` 并保留现有发送、barrier、取消和错误路径。

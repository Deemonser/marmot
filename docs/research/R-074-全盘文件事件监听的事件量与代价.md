# R-074：全盘文件事件监听的事件量与代价

- 日期：2026-09-08
- 机器：8 核 / 16 GB / 内置 NVMe / APFS / macOS 26 (Darwin 25.5.0)
- 目的：为 [ADR-0072](../adr/0072-结果跟随磁盘的实时更新.md) 提供数据。本文只记测量，不记决策。

## 1. 起因

ADR-0064 §4 在没有预研的情况下拒绝了 FSEvents 全盘监听，理由是"图会永远在抖"和"分析建立在同一时刻上"。
使用方指出原版会隔一段时间刷新一次，且对象变化本来就正常，问为什么不做监听。R-072 之后重读一个目录已经
是毫秒到秒级的事，缺的是"知道哪个目录变了"。本文量三件事：全盘监听的事件量、浅刷新一个目录的代价、
firmlink 下事件路径的形态。

## 2. 事件量：监听 `/`，合并窗口 2 s，300 s

自制 cgo 程序（`FSEventStreamCreate`，目录级事件，`NoDefer`，latency 2.0）。前 30 s 跑了仓库的 Go 测试套件
与前端构建作为"开发机负载"，其余时间机器空闲（浏览器、IDE 常驻）。

| 时段 | 回调数 | 事件数 | 备注 |
| :-- | --: | --: | :-- |
| 0-30 s（负载） | 2,694 | 78,993 | 测试套件在 `/private/var/folders/.../T` 下建删数万文件 |
| 30-60 s | +15 | +39 | 空闲 |
| 60-90 s | +15 | +41 | 空闲 |
| 90-120 s | +15 | +44 | 空闲 |
| 120-150 s | +15 | +82 | 空闲 |
| 150-180 s | +53 | +1,348 | 一次本文自己的 Go 编译 |
| 300 s 合计 | 2,906 | 81,924 | 1,460 个不同目录 |

按前缀：`/private/var` 79,942（几乎全是测试临时目录）、`/Users/deemo` 1,936、`/private/tmp` 37、其他 < 10。

三个对实现有约束力的观察：

1. **每次回调最多 32 个事件**（min 1 / 中位 32 / max 32），与 latency 无关。系统只按 latency 合并**时间**，
   不合并**数量**：突发时回调仍然密集。所以应用层必须自己再攒一批（ADR-0072 取 2 s），否则一次 `npm install`
   会触发上千次树更新。
2. **每次回调的不同目录数中位数为 1，p90 为 3。** 事件绝大多数是同一个目录被反复写。攒批后按目录去重，
   一批要处理的目录数量级是几十，不是几千。
3. **5 分钟、8 万事件，没有出现任何标志位**：`MustScanSubDirs`、`KernelDropped`、`UserDropped` 均为 0。
   它们会出现在更极端的情况下（系统日志里常见于 Time Machine 或大规模 rsync），实现必须处理，但不是常态。

空闲机器约 **1-1.5 事件/秒**，落在十来个目录上（日志、浏览器、系统守护进程）。

## 3. 浅刷新一个目录的代价

`readDirectoryBulk`（现有 getattrlistbulk 单目录读取），5 次取最好：

| 目录 | 条目数 | 用时 | 每条 |
| :-- | --: | --: | --: |
| `/usr/bin` | 924 | 2.22 ms | 2.4 µs |
| `~/Library/Preferences` | 403 | 0.71 ms | 1.8 µs |
| `~/Library/Caches` | 116 | 0.16 ms | 1.4 µs |
| `~/Downloads` | 89 | 0.07 ms | 0.8 µs |
| `/Applications` | 35 | 0.03 ms | 0.9 µs |
| 合成 10,000 文件目录 | 10,000 | 12.9 ms | 1.3 µs |

**1-2.5 µs/条。** 一批几十个目录的浅刷新是个位数毫秒；随后一次 `group()` 重建约 70 ms（R-072 §2）。
所以一批的总成本由 `group()` 主导，这正是要攒批的第二个理由。

## 4. 路径形态

监听 `/` 时，在 firmlink 目录下创建探针目录，报回的路径为：

```
/Users/deemo/Downloads/fsevents-probe-…/
/private/tmp/fsevents-probe-…/
/Users/deemo/Library/Caches/fsevents-probe-…/
```

- Data 卷上的变化以 **firmlink 形态**（`/Users/...`）报回，不是 `/System/Volumes/Data/Users/...`，与扫描器
  存树的路径一致，无需转换；
- `/tmp` 是符号链接，报回的是真实路径 `/private/tmp`，与树一致（扫描器不跟随符号链接，`/private/tmp` 是
  它实际走到的目录）；
- 路径带**结尾斜杠**，接入前要去掉。

## 5. 顺带修正的一个假设

浅刷新用 `readDirectoryBulk` 一次读到父目录的全部直接子项，包括子目录自身的身份与 mtime；**子目录的子树
总量不需要也不能从这次读取得到**，它保持树里已有的值。只有新出现的目录需要深读一次（ADR-0070 的机制），
新目录一般很小。已存在目录内部的变化会以它自己的事件到来。

## 6. 结论

1. 全盘监听在正常使用的机器上是每秒个位数事件、十来个目录；开发负载下会突发到每秒数千事件，但集中在极少
   目录，攒批去重后每批几十个目录。
2. 一批的成本：浅刷新个位数毫秒 + `group()` 约 70 ms。2 s 一批完全可承受。
3. 事件路径与树路径同形，只需去掉结尾斜杠。
4. 丢事件与"请重扫子目录"在本次测量中未出现，但 API 定义了它们，实现必须有出路（深读、或标记并提示重扫）。

## 7. 限制

- 5 分钟、一台机器；未测 Time Machine 备份、大规模 `rsync`、外置盘插拔期间的行为。
- 未测 `kFSEventStreamCreateFlagFileEvents`（文件级事件）——设计上用不到，目录级足够。
- 没有量在真实 UI 上"抖"的主观感受；ADR-0072 用批量与阻塞条件处理，效果待真实窗口验证。

## 8. 对 DDD/SDD 的影响与建议 ADR

- SDD：推翻 14.5d 中"实时更新不做"的段落；§13h 记录机制；§8 用例表加状态查询；事件表加 `snapshot-updated`。
- DDD：无新聚合；`DirectoryRefresh` 与 `SubtreeReplacement` 同类。
- 建议 ADR-0072，取代 ADR-0064 §4，并收窄 ADR-0071 §2（创建计划前重读仅在未跟随时进行）。

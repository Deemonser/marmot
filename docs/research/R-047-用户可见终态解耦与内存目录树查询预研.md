# R-047 用户可见终态解耦与内存目录树查询预研

状态：已实施并端到端实测（ADR-0047 已接受；`16s` 门禁差 `1.1s` 未达成）

日期：2026-08-24

## 1. 问题与目标

R-038 到 R-046 连续九个切片在 `FinishSnapshot` 和 Darwin 原生扫描内部做 CPU、分配和 I/O 优化，
产品完整终态目标一次都没有达成。当前稳定 profile 的构成是：

| 项目 | 耗时 | 占比 |
| --- | ---: | ---: |
| 纯 macOS 原生扫描 | `14.952s` | `70.3%` |
| Application 批次持久化、排空和收尾（差额估算） | 约 `2.07s` | 约 `9.7%` |
| `FinishSnapshot` | `4.227s` | `19.9%` |
| 终态查询与 close | 约 `5.5ms` | `0.03%` |
| 完整终态 | `21.254s` | `100%` |

预研过程中先纠正了两个被沿用多轮的错误前提：

1. `15s` 门槛没有实测出处。同机同卷原版三次实测为 `18s` / `16s` / `15s`，中位数 `16s`，真实差距约
   `5.25s` / `33%`（第 3.4 节）。注意 `15s` 这个数值本身并不离谱——它接近原版的最好一次；真正的错误
   是**口径**：它被当成 durable 完整终态的目标，而原版的数字是可见终态。
2. 原版**不是**「先出首屏再补齐」。它扫描完成时整张空间图可见、可下钻五层，说明终态时全盘结构已经
   全部记录在内存中（第 3.5 节）。因此任何「只发布首层、深层等待」的方案都不构成追平，只是把等待
   从进页面前挪到下钻时。

修正后的问题与假设：

- 问题：可见终态如何在不牺牲快照耐久性的前提下追平实测原版中位数 `16s`，且终态时的可下钻深度不低于
  原版；
- 假设：继续缩短 `FinishSnapshot` 不是可靠路径。应解耦「用户可见的可查询终态」和「durable 二进制快照
  发布完成」，并用扫描结束时**已经在内存中的全盘目录聚合树**应答空间图查询，而不是只应答首层。

本轮不改变快照格式、checksum、manifest 原子发布、恢复语义、清理授权和扫描并发预算。

## 2. 环境与测量口径

测量口径必须先冻结，本预研的任何结论都以冻结后的口径为准。

历史三次串行数据的方差已经超过 `100%`，且 R-039 明确记录「真实 `/` 样本在复测中发生变化」：

| 切片 | 完整终态三次 | 中位数 |
| --- | --- | ---: |
| R-038 | `47.780s` / `29.727s` / `24.315s` | `29.727s` |
| R-039 | `39.163s` / `38.355s` / `32.105s` | `38.355s` |
| R-043 | `77.250s` / `55.663s` / `47.996s` | `55.663s` |
| R-044 | `22.70s` / `34.15s` / `35.28s` | `34.15s` |
| R-045 | `26.691s` / `28.961s` / `23.266s` | `26.691s` |

在样本会变化的真实 `/` 上做 `3%` 级子目标判定是不成立的。因此 R-047 要求：

1. 使用固定只读样本作为性能判定口径，节点规模与真实 `/` 同量级（约 `285` 万节点、`440` 级问题数）；
2. 真实 `/` 继续测量，但只作为量级参考和正确性 smoke，不作为子目标达成/未达成的判定依据；
3. 每次记录必须同时包含：纯扫描、用户可见终态、投影目录覆盖率、投影外首次下钻可用、durable 发布
   完成、`FinishSnapshot`、节点数、问题数、首屏查询、checksum、恢复和最大 RSS；
   注意最大 RSS 目前也没有稳定基线：ADR-0030 记录的三次最大 RSS 约为 `584 MiB`
   （`611,942,400` / `619,282,432` / `611,860,480` 字节），R-045 记录的单次 smoke 约为 `420 MiB`
   （`440,795,136` 字节）。冻结样本必须重建 RSS 基线，不能沿用任一历史值；
4. 单次 smoke 不构成达标证据，判定一律使用同口径串行三次中位数。

## 3. 当前证据

### 3.1 枚举侧已接近硬件边界

`14.952s / 2,845,962` 节点约为 `190k nodes/s`。当前实现已经包含 `getattrlistbulk(2)` 批量读取、
`256KB` 缓冲、8 worker pthread 池、`openat` 目录 fd 复用与 `2048` 槽位上限、共享 name/path backing
buffer、目录状态 map 合并和回调临界区削减（ADR-0021/0022/0024/0037/0040/0041/0045），入口在
`internal/infrastructure/scanner/native_darwin.go`。

R-040 到 R-045 的收益全部落在累计分配量（`1150.04MB` → `1102.12MB`），wall time 子目标无一达成。
该方向的剩余期望值是个位数百分比。

### 3.2 缺口来自扫描结束后的全量后置 pass

R-042 的终态阶段 profile：

| 阶段 | 耗时 |
| --- | ---: |
| `buildIssueSection` | `0.8815s` |
| `sort-inputs` | `1.3914s` |
| `normalize-relations` | `1.6937s` |
| `sync-index-sections` | `0.1274s` |
| `write-index-atomic` | `1.5176s` |

这些阶段全部在扫描结束之后才开始，且都是对全量节点/关系的完整遍历。R-043、R-044、R-046 三轮在这个
外排结构内部替换排序方式、归并方式和 run 容量，终态中位数分别为 `55.663s`、`34.15s` 和待验证，
没有一次达成子目标。证据支持「结构问题」而不是「参数问题」。

### 3.3 可见终态当前被 durable 发布阻塞

`PhaseTopLevelPublish` 已经有落盘 barrier，见 `internal/application/service.go:590`。但
[ADR-0027](../adr/0027-DaisyDisk扫描中窗口状态边界.md) 把前台切页绑定在任务终态且最终 Map 查询成功
之上，而终态当前隐含要求 `store.FinishSnapshot(...)` 已完成、reader 索引可用。用户因此要为已经在内存
中的结构额外等待约 `6.3s`。

### 3.4 「原版 `<15s`」是推定值；实测三次中位数为 `16s`

仓库内此前找不到任何一次 DaisyDisk 实机计时。`<15s` 最早出现在
`docs/research/R-020-macOS目录fd与openat扫描路径优化预研.md:52` 和
`docs/research/R-024-SQLite扫描写入并发与端到端性能复测.md:22`，两处都是推定表述；R-014 的本机复核
只记录窗口尺寸、菜单项和「扫描中卷行内显示进度条」，没有耗时。

本轮已补测。同机同卷原版「开始 → 扫描完成进入结果页」三次串行：

| 次序 | 结果 |
| --- | ---: |
| 第 1 次 | `18s` |
| 第 2 次 | `16s` |
| 第 3 次 | `15s` |
| **中位数** | **`16s`** |

对照：

| 口径 | 结果 |
| --- | ---: |
| 原版可见终态（三次中位数） | `16s` |
| Marmot 完整可查询终态 | `21.254s` |
| 差距 | 约 `5.25s` / 约 `33%` |

两个修正：

1. **`15s` 的数值不离谱，错的是口径。** 它接近原版的最好一次（`15s`），并不比原版严 `3s`（这是本预研
   上一版基于单次 `18s` 得出的错误结论）。真正的错误是把一个「可见终态」的数字当成「durable 完整终态」
   的目标，于是 R-038 到 R-046 九轮都在用错误的口径判定达成与否。
2. **差距比单次测量显示的大一倍。** 从 `3.2s` / `15%` 修正为 `5.25s` / `33%`。这直接改变了风险预算，
   见第 3.8 节。

限制：三次结果单调下降（`18s` → `16s` → `15s`），高度疑似 APFS cache 逐次预热，因此中位数 `16s` 里
混入了缓存温度差异。Marmot 的对照测量必须使用相同的冷热次序纪律（同样连续三次、同样不清缓存），否则
拿 Marmot 的冷启动去对原版的预热运行是反向不公平。原版节点口径仍未知（排除策略、共享块与硬链接计数
方式都可能与 Marmot 的 `2,856,437` 节点不同）。

### 3.5 原版终态是「全盘结构已在内存」，不是「首屏 + 后台补齐」

实机观察：原版扫描完成进入结果页时，整张空间图可见，可连续下钻五层，不存在扫一部分展示一部分的
渐进补齐。这说明它在 `18s` 这个时刻已经把全盘结构保留在进程内存中，而不是把「可浏览」压缩成一屏。

该观察否掉了「只在内存中保留根 + 首层、其余等待 durable」的方案：那不是追平，只是把等待从进页面前
挪到首次下钻时，用加载态掩盖成本。

对照的正确口径是：

| 产品 | `16s` / `21.254s` 这一时刻拥有什么 |
| --- | --- |
| 原版 | 全盘结构在内存，可任意下钻；无 durable 快照 |
| Marmot 当前 | durable 二进制快照已原子发布，可任意下钻、可分页、可重启恢复 |

即 Marmot 慢 `33%`，但做的是严格更多的工作。

### 3.6 扫描结束时内存里已经有完整目录树

关键事实：两条扫描路径在扫描结束时都已经为**每一个目录**持有 path、parentID 和聚合尺寸。

Go 路径 `internal/infrastructure/scanner/scanner.go`：

- `directoryParents`（第 136 行）、`directoryPaths`（第 137 行）、`directorySizes`（第 138 行）逐目录写入；
- 文件节点在 `emitNodes` 中被累加进父目录的 `directorySizes`（第 172-174 行）；
- 第 337-345 行按 id 逆序把子目录聚合并入父目录，得到全深度 roll-up，写入 `result.DirectorySizes`。

Darwin 原生路径 `internal/infrastructure/scanner/native_darwin.go`：

- 第 902 行 `native.directories[node.ID] = nativeDirectoryState{path: node.Path, parentID: node.ParentID}`；
- 第 923-926 行按批次累加 `native.dirSizes`；
- 第 949-964 行 `finishDirectorySizes()` 完成全深度 roll-up，第 764 行写入 `result.DirectorySizes`。

也就是说，**全盘目录聚合树（任意深度）在扫描结束那一刻已经是已付成本**，它已经计入当前的峰值 RSS
（历史记录为 ADR-0030 的三次约 `584 MiB` 和 R-045 的单次约 `420 MiB`，两者不一致，见第 2 节）。
缺的只有两样：

1. 子项的排序列表（按 `owned_allocated DESC, node_id`）；
2. 单个**文件**条目——文件只被累加进父目录totals，个体没有保留。而 `MapEntry` 是包含文件条目的
   （`internal/domain/scan/model.go:79`），所以纯目录树无法完整应答一层的 Map。

因此可行的内存投影是「全深度目录树 + 每目录 top-K 子项」，而不是「首层」，也不是「全量节点」。
top-K 的具体成本见第 3.7 节实测。

### 3.7 top-K 保留成本实测

本机 `/` 只读探测（`os.ReadDir`，不跟随符号链接，跳过 `/System/Volumes`、`/Volumes`、`/dev`、
`/private/var/vm`、`/.vol`）：目录 `771,265`，文件 `2,737,195`，`439` 个目录无权限。

该探测没有 Marmot 的挂载边界、硬链接去重和 APFS 归属规则，总数 `3,507,596` 与 Marmot 的
`2,856,437` 不同，只作同量级和分布参考。

**深度分布**（否掉了「按深度收口」的思路）：

| 深度上限 | 累计目录数 | 占全部目录 |
| --- | ---: | ---: |
| `<=4` | `6,914` | `0.9%` |
| `<=5` | `19,805` | `2.6%` |
| `<=6` | `37,303` | `4.8%` |
| `<=8` | `254,529` | `33.0%` |

树很深：`50%` 的目录在深度 `>=10`，最深到 30 层。因此「只保留深度 `<= D` 的 top-N」几乎无法覆盖
真实下钻，必须按目录而不是按深度收口。

**子项数分布**（决定了成本）：`p50=1`、`p90=5`、`p99=53`、`p99.9=252`、`max=67,614`。分布极度偏斜，
绝大多数目录只有个别子项，所以全深度 top-K 远比按深度保留更划算。

**保留成本**（精确按保留条目累加名称字节，条目按 `8B` node id + `8B` owned_allocated +
`16B` string header + 名称字节估算）：

| 方案 | 保留条目 | 子项被完整覆盖的目录 | 估算内存 |
| --- | ---: | ---: | ---: |
| 全深度 top-8 | `1,529,545` | `93.26%` | `72.8 MiB` |
| 深度 `<=4` top-256，其余 top-8 | `1,552,980` | `93.31%` | `74.0 MiB` |
| 深度 `<=6` top-256，其余 top-8 | `1,649,359` | `93.72%` | `79.6 MiB` |
| 深度 `<=4` top-256，其余 top-16 | `1,878,049` | `95.90%` | `89.8 MiB` |

两个结论：

1. **分层几乎免费。** 纯 top-8 会把根目录的 18 个子项折掉 10 个，首屏比原版残缺；给深度 `<=4` 的
   `6,914` 个目录放到 top-256（与 `MapQuery` entries 上限一致）只多 `1.2 MiB`，浅层不再截断。
2. **top-8 是成本拐点。** 升到 top-16 多花 `15.8 MiB` 只换 `2.6` 个百分点覆盖率，性价比明显下降。

因此本轮固定：**深度 `<=4` 保留 top-256，其余深度保留 top-8**，估算约 `74 MiB`。第 3.9 节的原型实测
把这个估算替换为真实堆占用，并推翻了其中一种实现表示。

### 3.8 中位数 `16s` 使「只做 R-046」不再能追平

本预研上一版基于单次 `18s` 写过一条风险预算：若方案 A 代价偏高，可以只实施 R-046 并接受与原版持平。
三次中位数 `16s` 让这条结论失效：

| 路径 | 预期 | 相对原版 `16s` |
| --- | ---: | ---: |
| 当前完整终态 | `21.254s` | 慢 `5.25s` |
| 仅实施 R-046（其自身目标） | `<=20.50s` | 慢 `4.5s` |
| 方案 A 可见终态 | `15s` 量级 | 持平或略快 |

因此方案 A 从「把 `15%` 变成领先」的可选项，变成追平的**必要条件**。回退到只做 R-046 仍然是一个合法的
工程结果，但必须如实记录为「未追平原版」，不能再写成「与原版持平」。

同时要注意方案 A 的余量很薄：预期 `15s` 量级对原版中位数 `16s`，只有约 `1s`；而投影的 `74 MiB` 是估算，
真实 Go 堆开销更高。所以第 6 节的内存和构建耗时必须实测，不能按估算收尾。

### 3.9 投影原型实测：估算被推翻，表示方式决定成败

已用真实扫描器（`scanner.Scanner{MountResolver: platform.Adapter{}.ListMounts}`，即 Darwin 原生路径）
跑了一个只测量的原型：在批次 emitter 中按 `parent_id` 累加 top-K，扫描结束后 finalize，再分别测量两种
内存表示的真实堆占用（`runtime.ReadMemStats` 的 `HeapAlloc`，两次 `GC` 之后）。

真实规模（与第 3.7 节的文件系统探测不同，这里带挂载边界与去重规则）：

| 项目 | 数量 |
| --- | ---: |
| 节点 | `2,860,136` |
| 目录 | `589,497` |
| 文件 | `2,270,639` |
| 问题 | `439` |
| 非空目录（有子项） | `422,577` |
| 保留条目 | `1,159,430` |

注意目录数是 `589,497`，不是第 3.7 节文件系统探测的 `771,265`；扫描器的边界和去重规则让真实规模更小，
因此第 3.7 节的成本表偏保守。

**耗时（好消息）：**

| 阶段 | 耗时 |
| --- | ---: |
| 扫描 wall（含累加） | `14.390s` |
| 其中累加在 callback 内（跨 worker 累计） | `651.6ms` |
| finalize（逐目录排序） | **`62.3ms`** |
| compact arena 构建 | `145.2ms` |

可见终态 ≈ 扫描结束 `+ 62ms` ≈ **`14.45s`**，不但低于原版中位数 `16s`，也低于 stretch `15s`。
「构建耗时吃掉 `1s` 余量」的风险不成立。

**堆占用（坏消息，也是本节的核心）：**

| 状态 | `HeapAlloc` | 相对扫描结果的增量 |
| --- | ---: | ---: |
| 仅扫描结果（已付成本） | `72.4 MiB` | — |
| `+` 朴素表示：`map[int64]*dirProjection`，`Name string` | `367.5 MiB` | **`+295.1 MiB`** |
| `+` compact arena：扁平条目切片 `+` 名称字节 arena `+` span 索引 | `134.3 MiB` | **`+62.0 MiB`** |

三条结论，其中两条改变决策：

1. **`74 MiB` 的估算对朴素表示错了 4 倍。** 真实开销是 `295.1 MiB`，超预算 `3` 倍。原因是每对象开销：
   `422,577` 个 map 项、同样多的结构体指针分配和切片 backing、`1,159,430` 个 string header 加同样多的
   独立字符串分配。**朴素的 map-of-slices 表示必须明确拒绝。**
2. **compact arena 是 `62.0 MiB`，低于 `96 MiB` 预算。** 方案 A 在这个表示下成立。因此 ADR 必须把
   「compact arena」写成实现约束，而不是留给实现者选择。
3. **累加器必须分片。** 原型第一版用单个 map 直接 `fatal error: concurrent map writes`——R-045 已把
   emitter 移到全局锁外，批次 emitter 由 8 个 native worker 并发调用（`native_darwin.go:936` 的
   `emit`）。原型改为按 `parent_id` 取模的 `64` 个分片各自加锁后通过；一个目录的全部子项落在同一分片，
   不需要跨分片合并。用单锁会把 R-045 刚消除的争用加回去。

**仍未解决的风险：扫描期的瞬时峰值。** compact arena 的 `62.0 MiB` 是稳态；但扫描期必须有一个可增长的
per-dir 结构，本原型用的就是那个 `295.1 MiB` 的朴素表示，compact 是扫描结束后从它构建的。也就是说峰值
仍会触及 `295 MiB`，超出预算。本次 `/usr/bin/time -l` 的最大 RSS 为 `727,482,368` 字节（约 `694 MiB`），
但该值包含两种表示同时存活，不代表生产峰值。

可行的缓解方向（需要在实现切片中验证，不能按推断收尾）：一个目录的子项由单个 worker 在一次目录枚举中
产生（`marmot_native_flush_batch` 按 task 刷批），因此目录枚举结束时其子项即已完整，可以**逐目录立即
compact**，把扫描期结构压到接近稳态。这是实现切片必须实测的第一项。

### 3.10 逐目录 compact 原型实测：尖峰消除，但扫描期仍有 2x 瞬时余量

已按第 3.9 节末的方向做了原型 v2：**逐批 compact**。native 每次 flush 的批次都是单父目录的
（`marmot_native_flush_batch` 中 `batch[index].parent_id = task->parent_id`），原型实测
`multi_parent_batches=0`、`batches=422,881` ≈ 非空目录数 `422,743`，即一个批次基本对应一个目录的
完整子项集。因此每收到一个批次就可以直接合并进 arena 并裁到 top-K，不需要保留可增长的 per-dir 结构。

正确性自检：`sum(Total)=2,861,479`，恰好等于 `nodes-1`；`garbage entries=8,040`（跨批次目录重排留下的
孤立条目），占 `1,167,856` 活跃条目的 `0.7%`。

**修掉的一个实现陷阱：** v2 第一版把每个子项的名称先写入 arena 再排序裁剪，被裁掉的子项名称成为垃圾，
名称字节达 `62,028,760`（约全部 `286` 万子项）。改为**先排序裁剪、只为存活条目复制名称**后降到
`19,179,851`（`18.3 MiB`）。

**内存（内存测量在多次运行中完全稳定，`72.4 MiB` 的扫描结果基线每次复现）：**

| 状态 | `HeapAlloc` | 增量 |
| --- | ---: | ---: |
| 仅扫描结果 | `72.4 MiB` | — |
| `+` 逐批 compact 投影（稳态，已 clip 余量） | `131.3 MiB` | **`+58.9 MiB`** |
| 对照：v1 朴素 map-of-slices | `367.5 MiB` | `+295.1 MiB` |

稳态 `58.9 MiB`，**在 `96 MiB` 预算内**，也低于 v1 的 compact arena（`62.0 MiB`）。

**扫描期峰值（`runtime/metrics` 的 `/memory/classes/heap/objects:bytes`，`50ms` 采样，控制组与投影组
同样采样因此可比）：**

| 运行 | 扫描期峰值活跃堆 |
| --- | ---: |
| 控制组（完全不建投影） | `272.6 MiB` |
| 逐批 compact 投影 | `389.7 MiB` |
| **投影对峰值的贡献** | **`+117.1 MiB`** |

因此：

1. **v1 的 `295 MiB` 尖峰确实被消除了**，投影峰值贡献从 `295.1 MiB` 降到 `117.1 MiB`，稳态降到
   `58.9 MiB`。第 3.9 节末的方向成立。
2. **但峰值仍是稳态的约 2 倍，且 `117.1 MiB` 超 `96 MiB` 预算 22%。** 原因是 arena 用 `append` 按倍数
   扩容，扩容瞬间新旧数组共存；分片 map 增长同理。
3. 缓解方向明确且可实现：**arena 改为固定块链式扩容**（chunked arena）而不是倍增复制，就能把峰值压到
   接近稳态；也可按 `nodes` 预估预分配。这需要在实现切片中实测，不能按推断收尾。

**分片 map 的预分配是可观成本：** 控制组测出 `64` 个各预留 `1<<13` 槽位的空 map 就占 `26.7 MiB`；
降到 `1<<10` 后只占 `3.3 MiB`。预分配容量必须按实测定，不能随手写。

**扫描 wall 成本：本机实时 `/` 上测不出来。** 关掉采样后同配置各三次：

| 运行 | 三次 | 中位数 |
| --- | --- | ---: |
| 控制组 | `21.356s` / `13.285s` / `13.336s` | `13.336s` |
| 逐批 compact | `14.057s` / `20.301s` / `17.282s` | `17.282s` |

两个分布完全重叠——控制组的最大值（`21.356s`）比投影组的最小值（`14.057s`）还大。噪声压过信号，
因此**不能声称投影的 wall 成本是 `+4s`，也不能声称是 `+455ms`**（后者来自单次配对，同样不可信）。
这正是 R-039 记录的真实 `/` 样本方差问题，也是第 2 节要求冻结样本的直接证据：投影的 wall 成本判定
**阻塞在固定样本上**。

**一条测量纪律：** `50ms` 的 `runtime/metrics` 采样在大堆下把扫描 wall 从 `14.410s` 抬到 `22.869s`
（用 `runtime.ReadMemStats` 更糟）。**峰值和 wall 必须分两次运行测量，不能同一次。**

### 3.11 峰值不是 arena 问题，wall 必须换指标；两个假设被自己的测量推翻

本节记录第 3.10 节两个待验证项的结果。两项都推翻了原先的假设。

**（1）冻结样本在本机不可行。** `sudo tmutil localsnapshot` 能建快照
（`com.apple.TimeMachine.2026-08-24-195910.local`），但 `mount_apfs -o ro -s` 先报
`Operation not permitted`（SIP 下需要调用进程有 Full Disk Access），授予 FDA 后改报
`No such file or directory`——两个快照都已被 `deleted(8)` 回收。Data 卷 `184 GiB` 已用、仅剩 `11 GiB`
（`95%`），本地快照是 purgeable 的，在这个占用率下活不到一轮测量结束，且中途被回收会静默污染样本。
同样的空间约束也排除了「复制一份只读语料」。**ADR-0047 第 4 条要求的固定只读样本必须改写。**

**（2）chunked arena 无效——我的假设错了。** 第 3.10 节推断峰值超标源于 arena 的 `append` 倍增扩容，
于是实现了固定块链式 arena。实测（`50ms` 采样，各组同样采样因此可比）：

| 运行 | 扫描期峰值活跃堆 | 投影峰值贡献 |
| --- | ---: | ---: |
| 控制组（不建投影） | `297.7` / `278.6 MiB` | — |
| `append` arena | `385.1` / `396.5 MiB` | 约 `+103 MiB` |
| chunked arena | `419.4` / `415.4` / `389.7 MiB` | 约 `+127 MiB` |

chunked 不但没降低峰值，反而略高。稳态两者相同（`+63.6 MiB`）。因此峰值超标与 arena 表示无关。

**真实原因是 GC 锯齿余量随活跃堆等比放大。** 采样的 `/memory/classes/heap/objects:bytes` 包含尚未回收的
垃圾；`GOGC=100` 下目标堆约为活跃堆的两倍，投影把活跃堆从约 `72 MiB` 抬到约 `136 MiB`，锯齿峰值随之
抬高。验证：

| 配置 | 控制组峰值 | 投影组峰值 | 投影峰值贡献 |
| --- | ---: | ---: | ---: |
| `GOGC=100`（默认） | `278.6`–`297.7 MiB` | `389.7`–`419.4 MiB` | 约 `+103`–`127 MiB` |
| `GOGC=50` | `244.0 MiB` | `335.2 MiB` | **`+91.2 MiB`** |
| `GOMEMLIMIT=400MiB` | — | `340.5 MiB` | — |

即峰值是**GC 策略**决定的，不是数据结构决定的；`GOGC=50` 下投影峰值贡献 `91.2 MiB` 已进 `96 MiB` 预算。
ADR 里「必须使用 chunked arena」这条约束应删除，替换为「扫描阶段必须有显式 GC 策略，峰值在该策略下测量」。

顺带两条实测量化（若将来仍要用 chunked）：分片 arena 的块大小会被分片数放大 `64` 倍，`1 MiB` 名称块导致
`64 MiB` 地板，降到 `64 KiB` 后 arena 分配 `50.2 MiB` 才贴近活跃的约 `45 MiB`；每分片的排序 scratch 必须
释放或设上限，一个批次可携带 `8192` 个子项，`64` 个未释放的 scratch 会占数十 MiB。

**（3）配对交替也救不了 wall——噪声不是漂移。** 六对交替（控制组 / 投影组，关采样）的配对差为
`-0.534` / `-7.435` / `-6.247` / `-4.443` / `-1.868` / `+10.942` 秒：六对里五对显示投影组**更快**，
而增加工作量不可能加快扫描。两组 wall 都在 `14`–`25s` 间随机跳。测量时机器上 `WindowServer` 占 `33%`、
`Terminal` `11%`、`Chrome` `10%`、另一个后台应用 `9.6%`——I/O 与 CPU 争用是噪声来源。

**（4）改用 CPU 时间后信号立刻干净。** 同样三对交替，`/usr/bin/time -l`：

| 配对 | 控制组 user | 投影组 user | 控制组 sys | 投影组 sys |
| --- | ---: | ---: | ---: | ---: |
| 1 | `3.12s` | `3.38s` | `43.06s` | `40.93s` |
| 2 | `3.10s` | `3.35s` | `39.90s` | `40.31s` |
| 3 | `3.08s` | `3.45s` | `41.50s` | `42.86s` |

- `user` CPU 三次都稳（控制组约 `3.10s`，投影组约 `3.39s`），**投影成本为 `+0.29s` user CPU，约 `+9.4%`**；
- `sys` CPU 无差异（约 `41.5s`），符合预期——投影不产生系统调用；
- `real` 仍然噪声（`15.08` / `18.53` / `14.90` 对 `14.60` / `14.43` / `15.12`）。

扫描是 I/O bound（`sys` 约 `41.5s` 对 `user` 约 `3.1s`），因此 `+0.29s` user CPU 摊到 8 个 worker 上对
wall 的影响远小于 `0.3s`，与回调内累计 `577`–`647ms`（跨并发 worker 累加）一致。

**结论：投影的时间成本已可信地量化为 `+0.29s` user CPU，对 `16s` 门槛可忽略。** 但这也暴露一个更大的
问题——**本机实时 `/` 上任何 wall 门槛都无法验证**，扫描 wall 自身就在 `14`–`25s` 间跳，连对原版
`16s` 的绝对比较都不可靠。ADR 的 `16s` 门槛需要静默环境，或改用「CPU 时间 + 单独的延迟检查」表述。

原型源码不进仓库（基准提交只含文档），保存在会话 scratchpad 的 `projection_probe_test.go.keep`，
可按需重跑；开关为 `PROBE_MODE=off`（控制组）、`PROBE_ARENA=append|chunked`、`PROBE_SAMPLE=1`（采样峰值）、
`PROBE_ENTRY_CHUNK` / `PROBE_NAME_CHUNK`。

### 3.13 实施后端到端实测（2026-08-25）

方案 A 已在生产代码中实现（见 ADR-0047 实施状态）。用同一个 harness 做 A/B：控制臂隐藏
`PublishProjection`，让服务走 ADR-0047 之前的路径（durable 发布完成后才进终态）。

真实 `/`：节点 `2,869,6xx`、目录 `591,55x`、文件 `2,278,0xx`、问题 `438`–`439`。

| 指标 | 控制臂（旧行为） | 投影臂 |
| --- | ---: | ---: |
| 用户可见终态（中位数） | `20.651s` | **`17.110s`** |
| durable 完成（中位数） | `20.716s` | 约 `21.8s` |
| durable 窗口 | `0.06s` | `3.8`–`8.7s` |
| 最大 RSS（中位数） | `1013 MiB` | 约 `893 MiB` |

控制臂三次：`20.651` / `21.053` / `20.121`。投影臂七次：`16.489` / `16.788` / `16.813` / `17.110` /
`17.281` / `17.669` / `24.087`（末次撞上 `pkd` `35%` 与 `CacheDelete`）。

**扫描速度**：可见终态口径约 **`167,000 nodes/s`**（区间 `162k`–`174k`）。

结果对照门禁：

| 门禁 | 结果 |
| --- | --- |
| 目录覆盖率 `>=90%` | **`92.86%`**（`549,300` / `591,540`）达成 |
| 投影与 durable 逐字段一致 | 真实 `/` 每次运行 `map_consistent=true`，达成 |
| 首屏零等待 | 投影首屏 Map `29.6`–`90.8ms`，durable 侧 `51ms`，无退化，达成 |
| 可见终态中位数 `<=16s` | `17.110s`，**差 `1.1s` 未达成** |
| 峰值内存 | 见下，预算本身需重定 |

三条结论：

1. **解耦生效，差距从 `5.25s` / `33%` 缩到 `1.1s` / `7%`。** 用户可见终态 `20.651s` → `17.110s`，
   提前约 `3.5s`（`-17%`）；durable 在其后 `3.8`–`8.7s` 静默完成。
2. **投影不抬高峰值内存，反而略降**（`~893 MiB` 对 `~1013 MiB`）。控制臂在 `FinishSnapshot` 期间扫描器
   的结果 map 仍全量存活，投影臂的时序不同。
3. **`700 MiB` 预算是错的，必须重定。** Marmot 在引入投影**之前**就已经峰值 `~1013 MiB`。该预算是拿原版
   观察到的 `700M+` 定的，从未与 Marmot 自己的同口径基线对照；第 3.12 节因此是一次「用别人的标尺量自己」
   的错误。同口径基线现在有了：**控制臂 `~1013 MiB`**。

限制与失败记录：

- 测量环境始终不安静（DaisyDisk 自身、`CacheDelete` `33%`、`pkd` `35%`、Android Studio `206%`、
  TimeMachine `backupd`）。按第 2 节口径，绝对 wall 门禁在非安静环境下应记为「未验证」；但七次中六次
  紧密聚在 `16.5`–`17.7s`，因此本节把 `17.110s` 记为可信中位数，同时保留环境说明。
- 探针本身出过两个错误，都不在实现里：`plainStore` 嵌入端口接口时把可选的 `InsertIssues` 一并隐藏，
  导致 `issue summary mismatch`（这反而验证了 durable 失败会如实传播为 `task_state=failed`，DDD 不变量
  36）；随后改为嵌入具体类型，又通过方法提升重新暴露了 `PublishProjection`，使「控制臂」并非控制臂。
  第二批数据已按投影臂计入。
- 可见终态口径包含扫描与投影发布，不含 Wails 序列化与前端渲染。

## 4. 方案比较

### 方案 A：可见终态由内存目录树投影应答，durable 发布转后台，采用

- **投影内容**：
  - 全盘目录聚合树（任意深度）——直接复用扫描结束时已在内存的 `directories` / `dirSizes`，不新增结构；
  - 每个目录的 top-K 子项（含文件条目），按 `owned_allocated DESC, node_id` 排序，分层取值：
    深度 `<=4` 用 `K=256`（与 `MapQuery` entries 上限一致），其余深度用 `K=8`；
  - 超出 top-K 的部分折叠进已有的 `MapResult.Remaining` 与 `ProjectionTruncated` 语义，不新增契约字段。
- **表示方式（实现约束，不是选项）**：必须使用 compact arena——扁平条目切片、名称字节 arena、
  `parent -> (offset, count, total)` span 索引。朴素的 `map[int64][]childEntry` 已被第 3.9 节实测否决
  （`295.1 MiB`，超预算 3 倍）。
- **累加器必须按 `parent_id` 分片**：批次 emitter 由 native worker 并发调用（R-045 之后 emitter 在全局
  锁外），单 map 会 `concurrent map writes`，单锁会把 R-045 消除的争用加回来。
- **成本**：稳态 `+63.6 MiB`（预算内）；扫描期峰值贡献 `+91.2 MiB`（`GOGC=50`，预算内）；
  `+0.29s` user CPU；finalize `3.8ms`。见第 3.10、3.11 节。
- **应答范围**：目录级信息在任意深度无等待可用；top-K 覆盖范围内的下钻（含文件条目）无等待；
  需要 top-K 之外的子项或分页超出 top-K 时等待 durable 就绪并显示加载态；不得返回空结果、
  截断结果或与 durable 不一致的结果。
- **权威切换**：`store.FinishSnapshot(...)` 在后台完成，durable 就绪后 `SnapshotStore` 恢复为唯一查询
  权威，投影释放。当前在 `FinishSnapshot` 之前串行执行的 `UpdateDirectorySizes` 和 `InsertIssues`
  一并移入后台，它们属于 durable 侧工作。
- **预期**：第 3.9 节实测可见终态 ≈ `14.45s`（扫描 `14.390s` + finalize `62.3ms`），低于原版中位数
  `16s` 也低于 stretch `15s`；`90.04%` 的非空目录（计入空目录为 `92.9%`）在可见终态即可无等待下钻。
- **代价**：查询权威在一次生命周期内切换一次，必须保证切换前后同一层结果逐字段一致；新增 `62.0 MiB`
  常驻内存，突破原定的 `5%` RSS 门禁，必须显式给出新的内存预算（第 6 节）。
- **内存已收敛**：逐批 compact 稳态 `+63.6 MiB`（预算内）；峰值贡献在 `GOGC=50` 下为 `+91.2 MiB`
  （预算内），在默认 `GOGC=100` 下为 `+103`–`127 MiB`（超预算）。峰值由 GC 策略决定，与 arena 表示无关
  （第 3.11 节）。
- **时间成本已量化**：`+0.29s` user CPU（`+9.4%`），`sys` CPU 无变化；对 `16s` 门槛可忽略。
- **剩余阻塞项不在方案上，而在测量环境上**：本机实时 `/` 的扫描 wall 在 `14`–`25s` 间跳，任何 wall
  门槛都无法验证；冻结样本因磁盘 `95%` 占用被 `deleted(8)` 回收而不可行。

### 方案 B：全量事实常驻内存，取消二进制快照，拒绝

`285` 万节点的完整对象、路径、子项和索引会把 RSS 推到远高于当前峰值，并失去取消后的部分结果、
重启恢复和快照缓存复用，同时仍要为分页、Map 和子项排序重建内存索引。与 ADR-0028/0030 的内存边界冲突。
注意：这与方案 A 不同——方案 A 复用的是**目录级**聚合，规模比全量节点小一到两个数量级。

### 方案 C：只在内存保留根与首层，或只保留深度 `<= D` 的 top-N，拒绝

前者被第 3.5 节的实机观察否掉：原版终态可下钻五层，首层投影不构成追平，只是把等待挪到首次下钻。
后者被第 3.7 节的深度分布否掉：深度 `<=4` 只覆盖 `0.9%` 的目录，深度 `<=5` 只覆盖 `2.6%`，按深度
收口几乎无法覆盖真实下钻。收口必须按目录做，不能按深度做。

### 方案 D：扫描期间提前切换到结果页，拒绝

违反 ADR-0027 第 1 条，也与 R-014/R-025 复核的原版行为不一致。方案 A 保持窗口只在扫描结束后切换一次。

### 方案 E：继续在 `FinishSnapshot` 内部做微优化以达标，拒绝作为达标路径

九轮证据表明该路径 wall time 收益不可预测。R-046 的正确性和 CPU 收益保留并继续实施，但不再作为门槛
达成路径。

### 方案 F：扫描期按 `parent_id` 分桶增量构建索引，本轮不采用

`node_id` 由 native 层单调分配（`marmot_native_reserve_ids`），`parent_id` 在 emit 时已知
（`marmot_native_flush_batch`），child/directory section 原则上可在扫描期间分桶追加，`FinishSnapshot`
退化为封口、checksum 和 manifest 发布。它改动 durable 发布路径和临时索引布局，风险显著高于方案 A，
且缩短的是后台窗口而非可见终态。留作方案 A 落地并冻结测量口径之后的独立预研（R-048 候选）。
若方案 A 实测显示深度 `> D` 的下钻等待成为主要抱怨来源，应优先做方案 F，而不是扩大 `D`。

## 5. 实施边界

- 投影的 top-K 部分容量必须由 `K` 与目录数共同决定并设硬上限；超过预算时按 `owned_allocated` 降序
  裁剪并置 `ProjectionTruncated`，不得无界增长；全盘目录树复用已有结构，不新建第二份副本；
- 不改变 `formatVersion`、快照 section 布局、数据帧与 index checksum、manifest 同步与原子 rename、
  尾部恢复语义和 `SnapshotStore` 公开方法的返回契约；
- 不改变 `MapQuery` / `MapResult` 契约；超出 top-K 的部分使用已有的 `Remaining` 和
  `ProjectionTruncated` 语义；
- 不改变 scanner worker 预算、`scanPersistQueueCapacity = 2` 的背压语义和 `scanBatchSize` 提交阈值；
- durable 发布失败必须传播为任务级失败并对用户可见，不得因为可见终态已展示而被静默吞掉；
- durable 完成前崩溃的语义不变：无可复用快照；不得因内存终态宣称快照已发布；
- 投影只做展示层聚合，不改变 APFS 共享块归属、硬链接计数和空间语义；
- 不引入新的扫描并发模型、缓存格式或外部命令编排。

## 6. 验收

1. 冻结固定只读样本与测量口径（第 2 节），并补足原版另外两次同条件实测形成 `18s` 的中位数基线；
2. scanner、binary snapshot、application 的窄测试、race、全仓 Go 测试和 `go vet` 通过；
3. 一致性回归：同一层的投影 Map 与 durable Map 逐字段一致，覆盖 `owned_allocated DESC, node_id`
   排序、分页、`Remaining`、`ProjectionTruncated`、空目录、部分结果和问题状态；
4. 边界回归：top-K 外下钻与分页的等待态、durable 就绪后的权威切换、扫描中不切页（ADR-0027）、
   取消、durable 失败传播、崩溃恢复；
5. 性能目标（固定样本同口径串行三次中位数）：
   - **用户可见终态 `<=16s`**（追平实测原版中位数），stretch `<=15s`（原版最好一次）；
     测量必须与原版同样的冷热次序纪律：连续三次、不清缓存、记录每次而非只记中位数；
   - **首屏五环图在可见终态零等待，且投影完整覆盖 `>=90%` 目录的全部子项**——这是防止用加载态
     掩盖成本的硬性指标，不满足则本方案不算达成；
   - 开始 → top-K 外首次下钻可用 `<=21.254s`（当前完整终态），即任何路径都不得变慢；
   - durable 发布完成相对 R-046 实施后的同口径完整终态不回退超过 `3%`；
   - 内存：总峰值 RSS `<=700 MiB`（实测原版量级，第 3.12 节），投影新增部分 `<=160 MiB`；扫描期瞬时
     峰值与稳态同受该预算约束——原型的 `295.1 MiB` 朴素表示仍不可接受。原定的 `5%` 门禁和 `96 MiB`
     预算均作废（后者是在没有产品标尺时凭空设的）；
   - 纯扫描不回退超过 `3%`；
6. 若一致性或 RSS 代价超出第 5 条，可回退到仅实施 R-046，但必须如实记录为「未追平原版」（第 3.8 节）；
   若可见终态达成但 top-K 外的等待成为抱怨来源，优先转方案 F（R-048）缩短 durable 窗口，
   而不是升到 top-16（第 3.7 节实测其性价比明显更低）。

## 7. 限制

- 本预研不声称缩短了 durable 完整终态；它改变的是用户可见终态的定义和达成路径；
- 原版中位数 `16s` 来自三次单调下降的测量（`18s` / `16s` / `15s`），混入 APFS cache 预热；节点口径
  未知；它是当前最好的可用基线，但不是无偏基线；
- 「原版终态可下钻五层」是实机观察，不是对其内部实现的证明；本预研只用它否定首层方案，不据此推断
  原版的内存结构细节；
- 第 3.7 节的探测缺少挂载边界、硬链接和 APFS 归属规则，其目录数 `771,265` 高于扫描器真实的
  `589,497`，只能作分布参考；其 `74 MiB` 估算已由第 3.9 节实测替换（朴素 `295.1 MiB`、
  compact arena `62.0 MiB`）；
- 固定样本与真实 `/` 的绝对值不可互相替代，历史三次数据不能与冻结口径后的数据直接比较；
- 单次 smoke、单项 RSS 下降或单次 `<16s` 都不构成达标证据；
- 时间余量的担忧已由第 3.9 节实测解除（可见终态 `14.45s` 对原版 `16s`），但该数字来自单次原型运行，
  且原型不包含权威切换、Wails 序列化和前端渲染；实现切片必须按第 2 节口径重测；
- 扫描期瞬时峰值仍未解决，是方案 A 目前唯一可能致其失败的因素。

## 8. 对 DDD、SDD 的影响

DDD：`ScanJob` 需要显式区分「用户可见可查询终态」和「durable 快照发布完成」两个状态事实，并保留
不变量——durable 未发布时不得宣称快照可复用或可恢复。该区分属于领域状态，不能只存在于 Presentation。

SDD：需要写明一次扫描生命周期内查询权威可以切换（有界内存目录树投影 → `SnapshotStore`）、切换点、
切换期间的一致性要求、投影的深度与容量上限。若前端需要区分某次下钻是否需要等待，Wails DTO 需增加
durable 就绪标志，属 ADR 决策项。

ADR-0027 的「扫描中保持源页」「终态只触发一次最终首屏查询」「失败不用空 Map 伪装成功」全部保留；
需要由新 ADR 更新的只是「终态」隐含要求 durable 快照发布完成这一前提。ADR-0013 的 `MapQuery` /
`MapResult` 契约和 ADR-0017 的有界投影语义不变，方案 A 复用它们而不是扩展它们。ADR-0028/0029/0030
的快照格式、资源复用和内存边界不变。

此外，实测 `18s` 使 `15s` 门槛失效，替换产品对标口径本身也是 ADR 决策项，不能由预研文档单方面改写
`docs/BASELINE.md` 和 `docs/SDD.md` 中已有的 `15s` 表述。

[ADR-0030](../adr/0030-应用持久化队列上限与终态内存.md) 没有给出数值内存上限，它约束的是事件队列容量
与背压语义，这些不变。但 `74 MiB` 的常驻投影需要一个此前不存在的显式终态内存预算，这属 ADR 决策项。

建议 ADR：[ADR-0047 用户可见终态解耦与内存目录树查询权威](../adr/0047-用户可见终态解耦与内存目录树查询权威.md)。

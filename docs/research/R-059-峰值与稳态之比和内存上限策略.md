# R-059 峰值与稳态之比和内存上限策略

- 日期：2026-08-26
- 触发：[ADR-0057](../adr/0057-扫描到装配的分配契约.md) 把扫描期分配量从 `2530 MB` 降到 `650 MiB` 之后，
  [ADR-0055](../adr/0055-取消快照持久化与内存唯一事实源.md) 门禁 4 与
  [ADR-0056](../adr/0056-内存事实源的结构与发布峰值.md) 门禁 2 的峰值部分**仍然**未达成。
  ADR-0057 的实施状态里已经指出原因换了：不再是 churn，而是门禁本身的规格。本记录验证这个判断，
  并重测 [R-057 第 4c.4 节](R-057-内存唯一事实源可行性预研.md)在高 churn 下观察到的 `GOMEMLIMIT` 拐点。

## 1. 问题

留存堆 `255.3 MiB`，峰值 `phys_footprint` `568.5 MiB`，比值 `2.2`。门禁 2 要求"稳态 `<=280 MiB`、
峰值 `<=400 MiB`，且峰值/稳态 `<=1.2`"。三条里前一条通过，后两条不通过。

要回答两件事：

1. `<=1.2` 这个比值是不是**在任何 churn 水平下都达不到**？如果是，门禁写错了，必须换。
2. `GOMEMLIMIT` 在 churn 修复后还有没有 R-057 观察到的拐点？如果没有，它就从"掩盖症状的危险旋钮"
   变成一个可用的工具。

## 2. 假设

- H1：`GOGC=100` 的定义是堆涨到活跃量的 `2×` 才回收，所以峰值/稳态 `≈2` 是**构造性**的，与 churn 无关。
- H2：R-057 观察到的 `GOMEMLIMIT` 拐点（`400MiB` 的峰值与耗时都劣于 `500MiB`）是高 churn 的产物，
  churn 降低后会消失。
- H3：**固定**上限不是安全的产品策略，因为它只在高于活跃集时有意义，而活跃集是节点数的函数。

三条都成立（第 4 节）。

## 3. 环境与方法

- 机器：本机，macOS 26.5.2，arm64，Go 1.25.0，系统空闲内存 `74%`，被测应用已退出。
- 被测：真实 `/`，`2.78M` 节点，ADR-0057 实施后的代码。
- 方法：
  - 峰值用 `internal/probe/rss_probe_test.go`（`ps rss` ＋ `vmmap` 的 `phys_footprint`）；
  - 耗时**单独跑**用 `TestSingleSourceEndToEnd`（不采样 RSS），每档 3 次取中位数——
    R-047 §3.11 的纪律：峰值与耗时不在同一次运行里测；
  - 上限策略对比用新增的 `internal/probe/memory_limit_probe_test.go`，
    三种配置**在同一个探针里**测，每档 3 次。

**一条方法学纠正，它先让我得出了错误结论。** 自适应上限的第一版实验读
`/memory/classes/heap/objects:bytes` 当作活跃集。**这个指标包含尚未被清扫器处理的死对象**，
所以扫描刚结束时它读出 `515.6 MiB` 而不是真实的 `255.3 MiB`。用它推出的上限永远落在堆的当前位置之上，
**等于没设上限**——四档 headroom 全部"无效果"，我差点据此判定自适应方案不可行。
正确的指标是 `/gc/heap/live:bytes`（上一轮 GC 标记出的活跃对象）。

同一个错误也解释了一个此前没有追查的异常：`TestRSSBreakdown` 在扫描刚结束时报"留存堆 `434.9 MiB`"，
静置后却是 `256.7 MiB`。不是真的多留了内存，是指标选错。两处探针都已改用 `/gc/heap/live:bytes`，
改后两个读数一致（`255.3`）。

## 4. 证据

### 4.1 比值是构造性的

| | 值 |
| :-- | --: |
| 留存堆（`/gc/heap/live:bytes`） | `255.3 MiB` |
| 峰值 `phys_footprint` | `568.5 MiB` |
| 峰值 `ps rss` | `580.8 MiB` |
| **峰值 / 稳态** | **`2.2`** |

`GOGC=100` 的定义就是"堆增长到上一轮存活量的 100% 之上时触发回收"，即目标堆约为活跃量的 `2×`。
实测 `2.2` 正是这个值加上运行时元数据与栈。**churn 已经从 `2530 MB` 降到 `650 MiB`，比值没有跟着降**——
因为它根本不由 churn 决定。门禁 2 的 `<=1.2` 要求峰值只比稳态高 `20%`，在 `GOGC=100` 下**不可能**，
除非改 `GOGC` 或设内存上限。H1 成立。

### 4.2 `GOMEMLIMIT` 的拐点消失了

`TestRSSBreakdown`，每档一次；耗时是 `TestSingleSourceEndToEnd` 单独跑 3 次的中位数：

| `GOMEMLIMIT` | 峰值 footprint | 峰值 RSS | 分配量 | 可见终态（中位） | 耗时样本 |
| :-- | --: | --: | --: | --: | :-- |
| 无 | `577.2 MiB` | `589.3` | `650.7 MiB` | `14.35s` | `16.10 / 14.35 / 13.99` |
| `700MiB` | `570.8` | `582.9` | `658.6` | `14.27s` | `14.27` |
| `500MiB` | `520.4` | `554.5` | `669.9` | `14.44s` | `14.44 / 14.10 / 14.88` |
| `400MiB` | `486.2` | `526.0` | `666.9` | `14.72s` | `16.21 / 14.63 / 14.72` |
| `300MiB` | `473.2` | `505.0` | `795.0` | **`17.00s`** | `21.17 / 16.61 / 17.00` |

对比 R-057 第 4c.4 节（churn `2478 MB` 时）：那时 `400MiB` 的峰值 `889.7 MiB` **反而高于** `500MiB` 的
`797.1 MiB`，耗时也更差。现在峰值 `577.2 → 570.8 → 520.4 → 486.2 → 473.2` **单调下降，没有反弹**。
H2 成立：拐点是高 churn 的产物。

代价出现在 `300MiB`：耗时 `+18%`，分配量也涨到 `795.0 MiB`（GC 空转做的额外工作）。
`400MiB` 及以上的耗时差异落在噪声带内（无上限自身的三次采样跨度就有 `2.1s`）。

### 4.3 自适应上限比固定上限更好，也更安全

同一探针、每档 3 次、取中位数：

| 策略 | 峰值 footprint | 峰值 RSS | 耗时 | 三次样本（峰值） |
| :-- | --: | --: | --: | :-- |
| 无上限 | `549.0 MiB` | `561.2` | `17.27s` | `549.0 / 547.0 / 551.3` |
| 固定 `400 MiB` | `521.9` | `534.2` | `17.11s` | `521.9 / 522.1 / 513.8` |
| **`live + 100 MiB`** | **`499.5`** | `533.0` | `16.33s` | `459.0 / 499.5 / 516.3` |

> 本表的耗时在采样循环下测得，绝对值高于第 4.2 节的干净测量；三行同法，横向可比，不可与 4.2 节对比。

自适应上限（每 `100ms` 读一次 `/gc/heap/live:bytes`，调用 `debug.SetMemoryLimit(live + headroom)`）
headroom 扫描结果：

| headroom | 峰值 footprint |
| :-- | --: |
| `100 MiB` | `459.0` |
| `150 MiB` | `472.2` |
| `200 MiB` | `550.9`（无效果） |
| `300 MiB` | `564.7`（无效果） |

`200 MiB` 以上无效果，因为那时上限已经高于 `GOGC=100` 自己会到达的位置。

**H3 成立，而且这才是自适应方案的主要理由。** 固定 `400MiB` 在本机有效，是因为活跃集是 `255 MiB`；
活跃集约为 `92` 字节/节点（`255.3 MiB / 2.78M`），所以节点数超过约 `4.3M` 的卷，活跃集就会顶穿
`400MiB`，上限落到活跃集之下。Go 把 GC 的 CPU 占用封在 `50%`，所以那是**退化而不是死锁**——
第 4.2 节 `300MiB` 那一行就是退化的样子（`+18%` 耗时）——但那意味着**一个在本机调好的固定值，
会在更大的盘上变成纯粹的性能损失**。

自适应上限把峰值与稳态的关系从**比例**（`GOGC` 给的 `2×`）变成**加法常数**（`live + 100 MiB`）。
这正是让门禁在不同卷规模上都有意义的性质。

## 5. 结论

1. **门禁 2 的"峰值/稳态 `<=1.2`"必须改，它不可实现。** 该比值在 `GOGC=100` 下由构造决定约为 `2`，
   与 churn 无关——churn 降了 `74%` 而比值纹丝不动，这就是证明。
2. **峰值 `<=400 MiB` 也必须改。** 留存堆 `255.3 MiB` 是数据下界（`92` 字节/节点 × `2.78M`），
   `400 MiB` 只留 `57%` 余量给 GC，而 `GOGC=100` 要 `100%`。
3. **`GOMEMLIMIT` 现在可用了**，拐点随 churn 一起消失。但**不应设固定值**：本机最优的 `400MiB`
   会在超过约 `4.3M` 节点的卷上落到活跃集之下。
4. **推荐自适应上限 `live + 100 MiB`**：本机峰值中位数 `549.0 → 499.5 MiB`（`-9%`），耗时无可测代价，
   且在任何卷规模上都不会落到活跃集之下。

## 5b. 实施后实测（2026-08-26）

按 [ADR-0058](../adr/0058-扫描内存上限与峰值门禁.md) 实施后，真实 `/`，各三次：

| 指标 | 实施前 | 实施后（中位） |
| :-- | --: | --: |
| 峰值 `phys_footprint` | `568.5 MiB` | **`487.8 MiB`** |
| 峰值 `ps rss` | `580.8 MiB` | `532.4 MiB` |
| 稳态（`/gc/heap/live:bytes`） | `255.3 MiB` | `254.7 MiB` |
| 峰值 `-` 稳态 | `313.2 MiB` | **`233.1 MiB`** |
| 扫描期分配量 | `658.0 MiB` | `665.2 MiB` |

第 4.3 节推算峰值 `499.5 MiB`，实测 `487.8`——生产实现比探针略好，因为上限在 `hold()` 里立即应用一次
而不是等第一个 tick（探针只在 tick 里设）。这同时使第 6 节"比轮询间隔更短的扫描拿不到任何调整"
这条限制失效。

**一个 A/B，比本记录第 4.3 节的证据强**：可见终态在**不采样**的运行里各测六次——

| | 样本 | 中位数 | 慢模式 |
| :-- | :-- | --: | :-- |
| 限流器开 | `13.528 / 13.627 / 13.687 / 13.766 / 19.555 / 20.217` | `13.727s` | `2/6` |
| 限流器关 | `13.528 / 13.635 / 13.733 / 14.408 / 20.240 / 20.370` | `13.983s` | `2/6` |

两件事同时被证实:自适应上限**没有可测的耗时代价**（第 4.3 节的耗时是在采样循环下测的，只能横向比较，
这里是干净测量且同环境对照）；以及**测量环境存在一个约 `20s` 的慢模式，与本改动无关**——
六次里两次，开关限流器都一样。成因未查明。

由此得到一条测量纪律：**这台机器上的耗时判定必须给出多次采样**。单次数字有三分之一的概率落在慢模式上，
结论会取决于运气——本记录第 4.2 节"无上限"那一档的三次采样跨度有 `2.1s`，当时我把它当成噪声，
现在看那是双峰的边缘。

## 6. 限制与风险

- **只测了一个卷。** 第 4.3 节"自适应在更大的盘上更安全"是**推理，不是实测**：`4.3M` 节点这个阈值
  由 `92` 字节/节点外推得到，没有在真实的大盘上验证过；
- **`-9%` 是中等收益，且有方差**（三次 `459.0 / 499.5 / 516.3`）。主要理由是规模安全性，不是这 `50 MiB`；
- 第 4.3 节的耗时在采样循环下测得，只可横向比较。自适应策略的干净耗时要等它进入生产代码后才能用
  `TestSingleSourceEndToEnd` 测；
- ~~自适应实现每 `100ms` 轮询一次。比这更短的扫描拿不到任何调整~~——实施时改为在持有的瞬间
  立即应用一次，本条不再成立（第 5b 节）；
- `debug.SetMemoryLimit` 是**进程全局**的。扫描结束必须还原，否则会影响应用其余部分的 GC 行为。

## 7. 对 DDD / SDD 的影响

- **DDD**：无。这是运行时策略，不涉及领域规则；
- **SDD**：内存布局一节要补"扫描期内存上限策略"，并把三口径报数与门禁数值更新；
- **BASELINE**：更新门禁数值与实测峰值。

## 8. 建议 ADR

一个 ADR，两条决定：

1. **替代 ADR-0055 门禁 4 与 ADR-0056 门禁 2 的峰值条款**，给出可实现的数值，并说明"峰值/稳态"
   必须是加法余量而不是比例；
2. **扫描期采用自适应内存上限 `live + 100 MiB`**，扫描结束还原。不采用固定 `GOMEMLIMIT`。

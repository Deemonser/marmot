# R-055 空间图配色与角度基准取样

状态：已取样并实施（颜色、起始角、最小弧宽三项已对齐；色相分配方式的差异未解决，见第 5 节）

日期：2026-08-25

## 1. 问题

三条反馈：扇区颜色不如原版亮；起始角不对；小扇形堆积成"毛刺"。前两条和第三条都需要原版的真实数值，
不能靠肉眼比对。

## 2. 环境与方法

原版结果页截图 `~/Downloads/daisydisk截图/xw_20260825112640.png`（`2586x1760` 物理，轮盘中心
`(801, 905)`）。自建 Swift 取样器 `NSBitmapImageRep.colorAt` 按极坐标读像素，角度以 12 点为 `0°`、
顺时针为正，输出 sRGB 与 HSB。取样器保留在 `scratchpad/sample.swift`（不进仓库，`AppKit` 一次性工具）。

## 3. 证据

### 3.1 亮度与饱和度：原版几乎顶满亮度

| 环 | 样本 | HSB | 换算 HSL |
| --: | :-- | :-- | :-- |
| 1 | `#9EF860`（用户） | `(96, 61%, 97%)` | `hsl(96, 91%, 67%)` |
| 1 | `#4252FB`（系统） | `(235, 74%, 98%)` | `hsl(235, 96%, 62%)` |
| 1 | `#EB67FA`（应用程序） | `(294, 59%, 98%)` | `hsl(294, 94%, 69%)` |
| 2 | `#ACF977` | `(95, 52%, 98%)` | `hsl(95, 92%, 72%)` |
| 3 | `#DDFB85` | `(75, 47%, 98%)` | `hsl(75, 92%, 76%)` |
| 3 | `#99F996` | `(119, 39%, 98%)` | `hsl(119, 91%, 78%)` |
| 4 | `#E48EFB` | `(287, 44%, 99%)` | `hsl(287, 94%, 79%)` |

规律：**HSB 亮度恒定在 `97%`–`99%`**，饱和度随深度从 `61%`–`74%` 降到 `39%`–`47%`。换算成 HSL 就是
**饱和度基本恒定在 `91%`–`96%`，亮度随深度从 `67%` 升到 `79%`**。

我们此前是 `hsl(72% - 4×depth, 58% + 4×depth)`——**饱和度低了约 20 个点、亮度低了 9 个点**，这就是
"没有原版那么亮"。已按上表改为饱和度 `[91,93,92,95,96]`、亮度 `[67,72,76,78,79]`。

### 3.2 起始角：已用部分在 3 点钟收尾，圆盘代表总容量

在 `r=150` 上以 `2°` 步长扫描边界：

| 角度 | 内容 |
| --: | :-- |
| `76°`–`86°` | 隐藏空间（`#874A96`，被压暗） |
| **`88°`–`106°`** | **背景 `#31343B`（空缺口）** |
| `108°`–`306°` | 用户（`#9EF860`） |
| `308°`–`24°` | 系统（`#4252FB`） |

缺口宽 **`20°`**。而 `实际可用 13.2 GB / 总容量 245.1 GB × 360° = 19.4°`。因此：

- **圆盘代表卷的总容量，可用空间是那道空缺口**，不画出来；
- **已用部分正好在 `90°`（3 点钟）收尾**——最后一项"隐藏空间"结束于 `86°`–`88°`；
- 用户 `133.7/245.1×360 = 196.4°`，实测 `108°`–`306°` = `198°`，在取样误差内。

我们此前从 12 点起始并填满 `360°`。已改为：根层扫过
`已用/(已用+可用) × 2π`，终点固定在 `+π/2`；非根层仍然满圈，同样在 3 点钟收尾。

### 3.3 小项：折叠成灰块，更小的直接留背景

原版的灰块实测 `#888787` = `HSB(0, 1%, 53%)`——饱和度 `1%`，是刻意的中性灰，不是某个色相压暗。

更关键的是 `r=320` 与 `r=400` 的扫描：绿色楔形内部有大量角度读到的是**背景 `#31343B`**
（`r=320` 的 `24°`/`36°`/`48°`/`72°`–`108°`，`r=400` 的 `24°`–`96°`）。也就是说原版并不把每个小项都画出来——
**太小的直接不画，留背景透出来**，介于中间的折叠成一个灰块。

我们此前无条件绘制每个投影后代，于是外圈出现大量 1px 发丝——就是"毛刺"。已改为：按环半径把最小可读宽度
`2.5px` 换算成角度（`minArcPixels / r_mid`），低于它的兄弟折叠成**一个**灰块；若连灰块都不够宽，整组不画，
背景透出。被折叠/不画的项其子树也不再递归。

## 4. 结论

1. 亮度/饱和度差异有确切数值来源，已按实测表改；
2. 圆盘代表总容量、可用空间留空缺口、已用在 3 点钟收尾——三者是同一个版式规则的三个侧面；
3. 毛刺的成因是"无条件绘制"，原版有明确的最小可读宽度与两级降级（折叠成灰块 → 不画）。

## 5. 未解决：色相是按子项序号分配的，不是按角度

实测原版根层各项的色相：用户 `95`、系统 `235`、应用程序 `294`、资源库 `323`、private `340`。
按顺时针位置看，色相步进是 `140 / 59 / 29 / 17`——**每一项大约是前一项的一半**，与角度位置不成比例。
同一楔形内部色相恒定（绿色从 `130°` 到 `280°` 全是 `hsb(96,61%,97%)`），到下一环才由其子项各自取新色相
（`r=320` 上绿色楔形内部依次是 `30 / 75 / 119 / 156 / 170 / 189`）。

即：**原版按子项序号从色相环上取色，一个节点的整棵子树保持该色相直到下一层重新分配**。

我们的模型是**色相由角度位置决定**。可观察后果：最大的楔形吃掉色相环的一大段，相邻的小楔形因此颜色相近、
不易区分；原版则给每个子项一个跳跃明显的独立色相。

本轮未改这一条：现有的"跨层级色相稳定"机制（`entryColors` / `entryRanges` / `hueRange` 继承）整个建立在
角度区间上，改成按序号分配需要一并重做，且会影响形变动画里颜色的连续性。作为已知差异记录在此。

## 6. 限制

- 单张截图、单一磁盘状态；色相步进"每项减半"只有 5 个样本，不足以确定原版的实际算法；
- 最小弧宽 `2.5px` 是按原版外圈齿宽目测选定的量级，未从截图精确回归；
- 取样器读的是已经抗锯齿的截图，边界角度有 `±2°` 误差，色值在边界处会混合。

# R-054 扫描进度条真实分母预研

状态：已复核并实施（ADR-0053 已接受）；实施后复测见第 3.6 节：偏差 `-0.116`–`+0.032`，封顶 `0.959`，前置计数无重复

日期：2026-08-25

## 1. 问题

原版扫描时显示的是**有进度的**条（R-051 的截图里条纹段占轨道约 `36%`），我们显示的是不确定条。

此前不做进度是因为没有可信分母：[ADR-0027](../adr/0027-DaisyDisk扫描中窗口状态边界.md) 第 4 条与
[ADR-0050](../adr/0050-扫描中源页反馈与原版一致.md) 第 3 条都写着"全盘总量未知时只能显示不确定进度…
不能用容器容量伪造百分比"。

[ADR-0052](../adr/0052-空间数值口径与卷组覆盖对齐.md) 之后前提变了：快照在创建时就记录了卷的
容量/已用/可用，**分母现在是一个有实测出处、随快照存下来的真实值**。本预研测量以它为分母的进度曲线
到底准不准，再决定是否推翻那两条。

## 2. 环境与方法

真实 `/`（`2,778,7xx` 节点），经 `application.Service` 端到端扫描，采样其 `ScanProgress` 事件流
（即 UI 实际收到的数据），记录 `(elapsed, nodes, files, bytes, phase)`，共 `76` 个样本。

- 分母取 `GetStorageSources` 报告的卷已用字节 `217.6 GiB`（与快照记录的是同一个值）；
- 分子有两种口径，都测：**仅已遍历字节**，以及 **已遍历字节 + 卷组辅助卷的 statfs 已用**（后者在扫描
  开始前就已知，见第 3.3 节）；
- 判定标准是与**挂钟线性**的偏差：进度条的用处是让用户估计还要等多久，所以按十分位对照
  `bar - t`（正值＝高估进度，负值＝低估）；
- 复现：`PROBE_ROOT=/ go test ./internal/probe/ -run TestScanProgressCurve -count=1 -v`。

## 3. 证据

### 3.1 曲线单调，分母可用

`bytes_monotonic=true`。最终 `bytes = 208.7 GiB`，`final_bytes/used = 0.9591`。

### 3.2 不做前置计数时，最后一个十分位会跳 `26.7 GiB`

仅用已遍历字节做分子：

| 挂钟 | 阶段 | 已遍历 | 占已用 |
| --: | :-- | --: | --: |
| 80% | deep_scan | `167.6 GiB` | `0.770` |
| 90% | deep_scan | `182.1` | `0.837` |
| 100% | finalize | `208.7` | `0.959` |

最后一格从 `0.837` 直接跳到 `0.959`（`+26.7 GiB`）。原因明确：ADR-0052 的卷组辅助卷（`VM`、`Preboot`）
是在枚举结束后**一次性挂上**的，不是逐步遍历出来的。进度条照抄这个曲线，末尾必然有一次可见跳变。

### 3.3 前置计数消除末尾跳变

这些辅助卷的大小在扫描开始前就已经从 `statfs` 拿到了（本轮实测 `17.37 GiB`），它们必然进入最终树，
因此可以在 `t=0` 就计入分子。实测曲线：

| 挂钟 | 阶段 | 进度条 | 与挂钟偏差 |
| --: | :-- | --: | --: |
| 10% | catalog | `0.080` | `-0.020` |
| 20% | catalog | `0.080` | `-0.120` |
| 30% | deep_scan | `0.182` | `-0.118` |
| 40% | deep_scan | `0.307` | `-0.093` |
| 50% | deep_scan | `0.490` | `-0.010` |
| 60% | deep_scan | `0.658` | `+0.058` |
| 70% | deep_scan | `0.798` | `+0.098` |
| 80% | deep_scan | `0.850` | `+0.050` |
| 90% | deep_scan | `0.917` | `+0.017` |
| 100% | finalize | `0.959` | `-0.041` |

最后一格只剩 `0.917 → 0.959`（`+4.2` 点），跳变从 `12.2` 点降到 `4.2` 点。

偏差范围 `-0.120` 到 `+0.098`，**最大约 12 个百分点**。前 `20%` 的挂钟时间里进度条停在 `0.080`
不动——那是 `catalog` 阶段，还没有任何遍历字节。

> 注意：探针早期版本在 `t=100%` 行打出 `bar=1.039`，那是重复计算——终态样本的 `bytes` 已经含了末尾挂上的
> 辅助卷，又加了一次前置计数。真实上限是 `0.959`（该行的 `of_used`）。探针算术已修正。

### 3.4 进度条封顶在 `95.9%`，缺的 `4.1%` 是隐藏空间

`4.1%` 对应 ADR-0052 的 `hidden_space`（未挂载的 Recovery 卷、权限读不到的区域、APFS 元数据、
表观与物理之差）。它只有在树总量确定后才算得出来，扫描期无法预知，因此进度条**必然**在 `~96%` 处
停住，靠终态补满。

### 3.5 原版的条纹段与真实进度不矛盾

R-051 第 5 节记录过一个未解的观测：原版扫描中的条纹段只占轨道约 `36%`，"单帧无法判断是真实进度还是
动画的一帧"。结合本轮数据，两者其实是同一件事的两半：**条纹是"正在扫描"的质感，宽度是真实进度**。
`36%` 落在本轮曲线的 `t≈40%` 附近，完全自洽。因此复刻原版既要条纹也要真实宽度，不是二选一。

### 3.6 实施后复测（ADR-0053 门禁 5）

按 ADR-0053 实施后，直接采样 UI 收到的 `CountedBytes` / `VolumeUsedBytes` 复测（`85` 个样本，
`visible_s=21.295`，前置计数 `18.37 GiB`，卷已用 `219.0 GiB`）：

| 挂钟 | 阶段 | `counted` | 进度条 | 与挂钟偏差 |
| --: | :-- | --: | --: | --: |
| 20% | catalog | `18.4 GiB` | `0.084` | `-0.116` |
| 30% | deep_scan | `42.7` | `0.195` | `-0.105` |
| 40% | deep_scan | `68.6` | `0.313` | `-0.087` |
| 50% | deep_scan | `98.1` | `0.448` | `-0.052` |
| 60% | deep_scan | `121.0` | `0.552` | `-0.048` |
| 70% | deep_scan | `160.2` | `0.732` | `+0.032` |
| 80% | deep_scan | `181.0` | `0.826` | `+0.026` |
| 90% | deep_scan | `199.2` | `0.910` | `+0.010` |
| 100% | finalize | `210.1` | `0.959` | `-0.041` |

三点确认：

1. **偏差 `-0.116` 到 `+0.032`**，与第 3.3 节预估的 `12` 点同量级，且 `deep_scan` 期间全程在 `±0.105`
   之内。高估只出现在 `t>=70%`，最大 `+0.032`——比预估的 `+0.098` 更好；
2. **终态 `counted == bytes`（`210.1 == 210.1`）**：前置计数在终态正确退出，没有重复计入；
3. 封顶 `0.959`，与第 3.4 节一致。

条纹的形态经过一次纠错。原版实测（`xw_20260825113207.png`、`xw_20260825203416.png`）是**蓝白相间的斜条纹
持续行进**，整体进度不前进时纹样也在走——第 3.5 节的结论成立。实施中先撞到一个陷阱：斜向
`repeating-linear-gradient` 若不指定 `background-size`，渐变按元素盒铺开，相位随盒宽变化，宽度每变一次
（5 Hz）纹样就整体横向平移，条纹蠕动。当时错误地把倾斜和动画都去掉（改成 `90deg` 静态竖虚线）来消除蠕动，
这背离了原版。正确的修法是**固定 `background-size` 为纹样的水平周期**（`105deg` 下 `6px / sin(105°) =
6.21px`）：纹样以左边缘为原点按固定尺寸平铺，与盒宽无关，宽度增长只是露出更多格；行进由
`background-position` 动画单独提供。实测连续两帧纹样相位不同（在行进），且宽度增长时无横向跳变。

教训：诊断"纹样在动"时必须分清两种运动——**行进**（要的）和**因盒宽变化导致的相位平移**（不要的）。
去掉动画会同时消掉前者。

第一轮实施漏掉了 `countedBytesLocked` 的接线，探针直接暴露出 `counted_gib=0.0`（分母 `219.0` 正常）——
UI 上表现为进度条恒为空。这条只有端到端采样 UI 实际收到的字段才能发现，用挂钟或日志都看不出来。

## 4. 结论

1. 分母已经存在且有实测出处（快照记录的卷已用字节），"总量未知"这个前提不再成立；
2. 以它为分母的进度与挂钟的偏差 `<=12` 个百分点，且单调——足以支撑"还要等多久"的判断；
3. 分子必须包含卷组辅助卷的前置计数，否则末尾有 `12` 个点的可见跳变；
4. 进度条封顶 `95.9%`，缺口是隐藏空间，只能由终态补满，不得预估；
5. `catalog` 阶段（约前两成挂钟时间）没有遍历字节，进度条在此期间不动；
6. 原版的条纹与真实进度并存，复刻要两者都要。

进入 [ADR-0053](../adr/0053-扫描进度条真实分母.md)。

## 5. 限制

- 单机单次样本，`76` 个进度事件。偏差范围未在其他机器或其他卷上复核；
- `catalog` 阶段时长取决于 `diskutil` 与权限探测，未单独测量其分布；
- 未测量把进度计算加进前端后的渲染开销（进度事件已限频 5 Hz，预期可忽略）。

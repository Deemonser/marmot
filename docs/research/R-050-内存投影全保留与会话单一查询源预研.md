# R-050 内存投影全保留与会话单一查询源预研

状态：已实施并实测（ADR-0049 已接受；100% 目录覆盖率达成，跨 durable 发布的空间图逐字段一致已实测）

日期：2026-08-25

## 1. 问题

[ADR-0047](../adr/0047-用户可见终态解耦与内存目录树查询权威.md) 把"用户可见终态"与"durable 发布完成"
拆成两个独立事实后，会话里出现了**两个查询源**：

- durable 发布落地前：内存投影回答 `Map` / `Children`；
- durable 发布落地后：`finishing` 记录被删除，同样的查询改由 `Reader` 从磁盘索引回答。

两个源带来两个可观测后果：

1. **扇区跳动**。前端 `scheduleMapRefresh` 在每个非 `running` 的进度事件上重新查询，而
   `publishDurable` 会再发一个终态事件。用户先看到投影的结果，几秒后看到 reader 的结果，
   中间那一次重绘就是"补充跳动"。
2. **覆盖率缺口**。投影按 ADR-0047 的分层 top-K 保留（浅层 `256`、深层 `8`），真实 `/` 上目录覆盖率
   只有 `92.86%`。未保留的页要么标记截断，要么回落等 durable——两条路都让"投影是权威"变成有条件的。

原版 DaisyDisk 的行为（R-047 第 3.5 节）是：扫描结束即可全深度操作，没有二次填充。它把整棵树留在内存里，
RSS 稳定在 `300M`–`700M+`。

本预研测量"投影保留全部子项"的真实内存代价，判断它是否能成为会话唯一查询源。不在预研完成前改上限。

## 2. 环境与方法

真实 `/` 卷（`2,862,7xx`–`2,863,1xx` 节点、`591,344`–`591,850` 目录，快照写入临时目录），
经 `application.Service` 端到端跑完整扫描，与 R-047 第 3.13 节同一条链路。

- 保留量通过临时注入的 `SetProjectionKeep(shallow, deep)` 切换，`deep < 0` 表示"保留全部子项"；
  测量完成后该钩子已删除；
- 堆用 `runtime/metrics` 的 `/memory/classes/heap/objects:bytes` 采样，不用 `ReadMemStats`
  （R-047 第 3.11 节记录：`ReadMemStats` 的 STW 会把扫描 wall 从 `14.41s` 抬到 `22.87s`）；
- 最大 RSS 用 `/usr/bin/time -l`，与 wall **同轮**测量——本轮不涉及 STW 采样，不受该纪律限制；
- 覆盖率取 `Store.ProjectionCoverage`，即"完整保留了子项页的目录数 / 目录总数"。

## 3. 证据

### 3.1 三档保留量的实测代价

| 保留量 | 目录覆盖率 | 堆 @ 可见终态 | 最大 RSS | 可见终态 | 首屏 Map |
| :-- | --: | --: | --: | --: | --: |
| `256/8`（ADR-0047 现状） | `92.86%` | `245.4 MiB` | `895 MiB` | `17.693s` | `104.01ms` |
| `256/64` | `99.33%` | `277.2 MiB` | `966 MiB` | `20.851s` | `444.68ms` |
| **全保留** | **`100.00%`** | **`315.5 MiB`** | **`1098 MiB`** | **`16.870s`** | **`192.71ms`** |

三档都在同一台机器上连续跑，`map_consistent=true`（投影与 durable 的空间图逐字段一致）在三档都成立。

### 3.2 中间档 `256/64` 严格更差，不构成折中方案

`256/64` 的意图是"用较小的内存换接近全覆盖"，实测反而三项都输给全保留：

- 覆盖率仍不满（`99.33%`，还剩 `3,978` 个目录有缺口）；
- 首屏 Map `444.68ms`，是全保留的 `2.3` 倍、现状的 `4.3` 倍；
- 可见终态 `20.851s`，比全保留慢 `4s`。

只省 `130 MiB` RSS。所以"提高 K"不是一条有意义的中间路线：**要么维持 top-K，要么全保留**，
中间取值同时付两边的代价。首屏变慢的原因是 top-K 的 `2*keep` 修剪排序会在扫描期反复触发，
而全保留完全不排序、只在 publish 时排一次。

### 3.3 全保留的可见终态没有回退

`16.870s` vs 现状 `17.693s`，差值在 R-047 第 3.13 节记录的本机 wall 噪声内（同一配置多轮
`16.5s`–`17.7s`）。全保留去掉了扫描期的修剪排序，理论上应当略快；但本轮样本不足以声称它更快，
只能声称**没有回退**。

### 3.4 会话单一查询源的端到端验证

投影改为服务整个会话（不再在 durable 发布后交还给 `Reader`）后，实测：

| 指标 | 实测 |
| :-- | --: |
| 目录覆盖率 | `591344/591344`（`100%`） |
| **跨 durable 发布空间图逐字段一致** | **`true`** |
| 首屏 Map | `114.73ms` |
| 稳态 Map 中位 / p95 | `2.06ms` / `2.29ms` |
| 载荷 | `141.8 KiB` |
| 弧数 | `1619` |
| 可见终态 / durable 完成 | `16.554s` / `24.412s` |
| 堆 @ 可见终态 / durable 之后 | `499.5 MiB` / `410.8 MiB` |
| 最大 RSS | `1064 MiB` |

`map_identical_across_durable=true` 是这轮的关键结论：durable 发布落地时空间图**一个字段都没变**，
所以"补充跳动"在数据层面已经不可能发生。前端那次多余的重新查询也已经去掉（每个快照只加载一次空间图）。

稳态 p95 `2.29ms` 远低于 ADR-0048 的 `150ms` 门槛——投影常驻后既不重新打开 reader 也不读索引文件。
首屏 `114.73ms` 是唯一一次冷查询（要从数据帧解码 `1619` 个名称）。

### 3.5 常驻内存是真实代价，不是零成本

`heap_after_durable` 从原来的 `~0.4 MiB`（投影随 writer 一起释放）变成 `410.8 MiB`：
**扫描结束后这棵树会在会话里一直占着**。这是单一查询源的定价，不是实现瑕疵。

对照口径：R-047 第 3.12 节实测原版 DaisyDisk 的 RSS 是 `300M` → `700M+`。我们的 `1064 MiB` 峰值
高于它，但同属一个数量级，且我们的峰值包含扫描期的临时结构。

这条超出了 ADR-0047 第 2.1 节写的"总峰值 `<=700 MiB`"。该预算在 ADR-0047 写下时的依据是当时误判的
`96 MiB` 投影预算（第 3.12 节已记录该依据被推翻），而现状 `256/8` 的实测峰值本来就已经是 `895 MiB`——
**这条上限在本轮之前就已经不成立**，不是全保留引入的回退。ADR-0049 重新定价。

### 3.6 `ProjectionTruncated` 这个名字在全保留后是错的

全保留之后，`Map` 结果里的截断标记不可能再表示"投影没保留这一页"。实测 `density_truncated=true`
仍然出现——因为 `2000` 个弧覆盖不了 `2.86M` 个节点，这是**绘制预算**的边界，不是**存储知识**的边界。

这解释了一个之前没解释清的观测：ADR-0048 的按比例分配上线后，差分测量里的 `495 truncated /
800 deferred` 没有变。当时的假设是"按比例分配会消除投影截断"，该假设被数据否证；真实原因是这两个数
从一开始统计的就是密度耗尽，跟保留量无关。字段已按 ADR-0049 改名为 `DensityTruncated`。

## 4. 结论

1. 全保留达到 `100%` 目录覆盖率，代价是堆 `+70 MiB`、最大 RSS `+203 MiB`；
2. 可见终态无回退，稳态查询延迟反而下降一个数量级（p95 `2.29ms`）；
3. `256/64` 中间档严格更差，不作为候选；
4. 单一查询源使"跨 durable 发布逐字段一致"从测试约束变成结构事实，扇区跳动在数据层面被消除；
5. ADR-0047 第 2.1 节的 `700 MiB` 总峰值预算在本轮之前已不成立，需要重新定价。

进入 [ADR-0049](../adr/0049-内存投影全保留与会话单一查询源.md)。

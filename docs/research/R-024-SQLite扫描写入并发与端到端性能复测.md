# R-024 SQLite 扫描写入并发与端到端性能复测

状态：已完成，结论由 ADR-0026 接受

日期：2026-08-21

## 1. 问题

R-023 的目录汇总旁路表解决了约 53 万目录逐行回写的问题，但 Application 仍在扫描器回调中同步等待 SQLite。扫描器和单连接 SQLite 互相阻塞，界面容易把“正在落盘”表现成扫描卡住。

## 2. 环境与方法

- macOS arm64，Go 1.25.13，SQLite WAL，`synchronous=NORMAL`；
- 扫描根为 `/`，只读，使用当前 `getattrlistbulk`、挂载边界、fd/openat 和 SSD 8 worker 路径；
- 记录节点、文件、目录、问题和完整 Application + SQLite smoke 耗时；
- 对照组为纯扫描器 smoke，不含 SQLite；所有样本都没有前端渲染耗时。

## 3. 证据

| 方案 | 节点 | 问题 | 耗时 | 结论 |
| --- | ---: | ---: | ---: | --- |
| 纯扫描器，8 worker | 约 270.6 万 | 441 | 14.58s | 已进入原版 `<15s` 纯枚举目标 |
| 同步 SQLite，目录旁路表 | 约 270.6 万 | 441 | 约 30.6s | 扫描回调被写入阻塞 |
| 有界异步写入、2 批、10,000 提交批次 | 约 270.6 万 | 441 | 约 24.5s | 扫描与写入可以重叠 |
| 2,000 行 prepared SQL、父节点索引、50,000 提交批次、64 MB cache | 约 270.6 万 | 441 | 20.06s | 当前接受方案 |
| 同上但 `synchronous=OFF` | 约 270.6 万 | 441 | 18.65s | 拒绝，耐久性不满足快照契约 |

节点数会随扫描期间文件变化而轻微波动；问题数在样本中保持 441。当前 smoke 证明了明显改善，但没有把包含 SQLite 落盘的完整任务宣称为 `<15s`。

## 4. 结论

1. Application 使用容量为两个提交批次的有界事件队列；扫描器回调只负责入队，队列满时受控背压。
2. 持久化 worker 每 50,000 个节点提交一次事务；事务内部使用 2,000 行 prepared multi-row statement，尾批单独准备。
3. `TopLevelPublish` 使用顺序 barrier，只有根和首层已经落盘后才发布首层可查询状态；深层写入继续后台进行。
4. 取消停止继续接收扫描输出，写入 worker 只收尾已经进入有界队列的批次，保留可查询的部分快照。
5. 目录汇总通过 `directory_sizes` 旁路表读取；当前层使用 `(snapshot_id, parent_id)` 定位，再按叠加后的 `owned_allocated` 稳定排序。旧的占用复合索引不能有效支持 `CASE + LEFT JOIN` 的新口径。
6. SQLite 使用 64 MB 页缓存和内存临时排序；耐久性仍固定为 `synchronous=NORMAL`。

## 5. 拒绝方案

- 无限增大内存队列：会把百万级节点转成不可控内存峰值，拒绝；
- `synchronous=OFF`：虽然样本约快 1.4 秒，但进程或系统异常可能损坏缓存，拒绝；
- 在 Application 保留完整内存树：违反快照唯一存储和百万级节点边界，拒绝；
- 用进度条把已处理节点伪装成精确百分比：总量未知，拒绝。

## 6. 限制与后续门禁

- 20.06s 是本机、当前缓存状态和 `/` 样本的 Application + SQLite 结果，不是所有机器的产品保证；
- 首层结果和扫描进度可以在完整快照收尾前展示，真实 Wails 窗口仍需原生 smoke 验证；
- 真实签名/TCC、冷缓存/热缓存、外部卷和发布包性能仍需单独验证；
- 如果产品必须把“完整可查询快照终态”也压到 `<15s`，下一项必须新增技术预研，研究可恢复的 append-only 扫描 spool 或专用持久化格式，不能继续在当前 SQLite 写入路径上无证据调参。

## 7. 对 DDD/SDD 的影响

DDD 领域事实、清理安全不变量和存储/执行分离不变。SDD 新增 Application 写入队列、首层 barrier、50,000 提交批次、2,000 行 SQL 批次、索引口径和完整 smoke 的诚实门槛；结论由 ADR-0026 固化。

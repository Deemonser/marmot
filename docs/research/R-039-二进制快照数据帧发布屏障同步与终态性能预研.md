# R-039 二进制快照数据帧发布屏障同步与终态性能预研

状态：已完成（代码切片和真实 `/` 三次复测完成；正确性通过，性能子目标未达成），结论由 ADR-0039 接受

日期：2026-08-24

## 1. 目标

在不削弱追加式快照的 footer、checksum、索引校验、manifest 原子发布和部分结果语义的前提下，
降低真实 `/` 扫描期间数据帧频繁 `Sync` 造成的 I/O 等待，推进完整可查询终态向 `15s` 目标靠近。

本轮只调整已写入数据帧的持久化时机，不改变快照格式、SnapshotStore 端口、Wails DTO、节点事实、
挂载边界、取消或清理校验。

## 2. 问题与证据

R-038 后对当前 Darwin 原生扫描和二进制快照链路做了分阶段 trace。一次真实 `/` 运行记录：

| 指标 | 结果 |
| --- | ---: |
| 节点 | `2,845,907` |
| 问题 | `442` |
| 完整终态 | `22.071s` |
| FinishSnapshot | `4.056s` |
| 数据帧 Sync 次数 | `173` |
| 数据帧 Sync 累计耗时 | `2.437s` |

输入临时文件的同步只有毫秒级；最终索引 section 的同步和复制存在波动，但不是本次最稳定的新增成本。
`AppendBatch` 当前每写完一个带 commit footer 的数据帧就调用一次 `w.data.Sync()`。真实样本约 285 万
节点形成 173 次数据帧同步，累计耗时已达到完整终态的可见比例。

应用只在以下时刻把数据变成可查询版本：

1. `TopLevelPublish` 等待首层节点后构建索引并更新 manifest；
2. 终态 `Finish` 构建最终索引并更新 manifest。

`manifest.IndexFile`、`DataEnd` 和 snapshot version 是查询入口。两次发布之间追加的数据即使已经写入
文件，也不会被旧 manifest 指向的索引查询。因此逐帧 `Sync` 不是每个数据帧的必要查询边界。

## 3. 方案比较

### 方案 A：在发布屏障批量同步数据帧

采用。Writer 记录数据文件存在未同步追加内容；`Publish` 或终态 `Finish` 在构建索引前同步一次，
确保索引只读取已经进入 durable 边界的数据。未完成 writer 的 `Close` 也同步一次，保持显式关闭
后的文件耐久性行为。

### 方案 B：继续每个数据帧同步

拒绝。当前 trace 证明每帧同步累计成本达到秒级，而帧 footer、checksum 和 manifest 仍可保持不变。
继续逐帧同步无法改善真实终态。

### 方案 C：只在最终 Finish 同步

拒绝。`TopLevelPublish` 是后端首层部分结果和中断查询的发布屏障；跳过该屏障会让首层索引可能读取
未耐久的数据，破坏现有部分结果和恢复边界。

### 方案 D：关闭 footer、checksum 或 manifest 同步

拒绝。它们是已提交快照的结构完整性、崩溃恢复和原子可见性边界，不能作为性能交换项。

## 4. 决策与恢复语义

- `AppendBatch` 仍按现有格式写 header、节点/字符串/问题 payload 和 commit footer；写入成功后只标记
  数据文件为 dirty，不在每个批次调用 `Sync`。
- `Publish` 和 `Finish` 在 `buildIndex` 前调用一次数据文件 `Sync`。同步失败必须让 writer 失败，不能
  继续构建或发布索引。
- `Close` 对仍 dirty 的 writer 补一次 `Sync`，再执行现有临时 writer flush 和文件关闭；正常完成的 writer
  已在最终发布屏障清除 dirty 状态，不会重复同步。
- 数据帧的 footer、帧内 checksum、`scanData` 校验、最终 index section 的 `Sync`、最终 index 临时文件的
  `Sync`、manifest 的 `Sync` 和原子 rename 全部保留。
- 进程在下一次发布前退出时，旧 manifest/index 仍是唯一可查询版本；未同步或已写入但未被 manifest 指向的
  尾部都不可查询，启动恢复继续标记 running snapshot 为 interrupted。
- 取消、扫描错误和正常完成都经过终态 `Finish`，因此已经接收的部分批次在最终部分快照发布前会被同步。
- 不修改 format version、数据帧宽度、索引布局、SnapshotStore/Wails 公共接口或 DDD 领域语义。

## 5. 验收与性能目标

1. Writer 单元和 binary snapshot 回归覆盖 dirty 状态、首层发布、终态发布、关闭和失败传播；已有 footer、
   checksum、尾部恢复、分页、Map、问题索引和目录汇总测试继续通过。
2. 正常完整扫描的 `AppendBatch` 不再逐帧同步；真实 `/` 的数据帧同步次数应降为首层和最终发布屏障的
   有界次数，不能随节点数量线性增长。
3. 真实 `/` 串行三次记录纯扫描、完整终态、`FinishSnapshot`、节点/问题数量、查询、checksum、恢复和
   最大 RSS。R-039 子目标为完整终态中位数 `<=18.50s`，且 `FinishSnapshot`、纯扫描和其他指标相对本轮
   基线不回退超过 `3%`。
4. 完整终态总 `15s` 仍是独立产品门槛；即使 R-039 子目标达成，也不能宣称总目标完成。
5. 运行 `go test ./...`、相关 race、`go vet ./...`、前端构建和 `git diff --check`。

## 6. 对 DDD、SDD 和后续实现的影响

DDD 不变：扫描事实、ScanSnapshot、部分结果和 CleanupPlan 语义不变。SDD 只把数据帧的 durability
边界从逐帧同步明确为发布屏障同步；最终索引、manifest、checksum、取消恢复和查询契约不变。

目录增量缓存、mmap、调整原生 worker 数量、放宽数据格式限制和跨快照索引仍不属于本轮范围，必须分别
预研并新增 ADR。

## 7. 实施结果

代码切片已完成：数据帧追加不再逐批次调用 `Sync`，首层/终态发布前同步 dirty 数据，未完成 writer
关闭时补同步；新增 dirty 状态、发布、关闭和同步失败回归，footer、checksum、分页、Map、问题索引、
目录汇总和尾部恢复测试通过。发布屏障同步次数由代码路径固定为有界次数，不再随数据帧数量线性增长。

在同一工作树、串行执行真实 `/` smoke，应用结果如下：

| 轮次 | 完整应用耗时 | FinishSnapshot | 节点 | 问题 | 查询/关闭 |
| --- | ---: | ---: | ---: | ---: | --- |
| 1 | `39.163s` | `5.588s` | `2,833,216` | `442` | 通过 |
| 2 | `38.355s` | `5.961s` | `2,833,218` | `442` | 通过 |
| 3 | `32.105s` | `6.852s` | `2,838,344` | `446` | 通过 |
| 中位数 | `38.355s` | `5.961s` | - | - | - |

纯扫描 smoke 三次为 `25.019s`、`29.507s`、`25.938s`，中位数 `25.938s`，节点约 `284.4` 万、问题
`445-448`。本轮未采集最大 RSS，也未在生产代码中保留同步计时；同步边界由代码审查和 dirty 状态测试
验证。真实 `/` 文件在三轮之间发生变化，节点/问题数量不完全一致，因此不能把墙钟差异归因于单一因素。

R-039 的完整终态 `<=18.50s` 子目标未达成，且当前 `FinishSnapshot` 相对预研单次基线 `4.056s` 有波动；
不能宣称产品总 `15s` 门槛达成。下一轮必须基于稳定的真实 `/` profile 重新定位热点，再提出新的预研和
ADR；不能继续扩大本轮代码范围。

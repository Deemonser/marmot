# R-067 扫描进度提前贴满，与真正的瓶颈

- 日期：2026-08-31
- 触发：使用方「那个扫描进度都满了，但是等了好一会儿才进入结果页面」
- 结论：进度条**在整段扫描约 60% 处就贴死在 100%**，因为分子超过分母 19%；
  而扫描本身的瓶颈**不是文件系统，是内存树插入**。

## 1. 先排除的两个猜测

日志在 `scan ... finished` 之后什么都没有，所以先量了那段空白里的候选：

| 调用 | 实测 |
| :-- | --: |
| 首次 `GetMap`（2,221,753 节点） | **0ms** |
| `GetStorageSources` | 418–451ms |

**都不是。** 顺带说明日志的缺口：应用侧有了日志，但**前端等待 map 的那段没有任何记录**，
所以"扫描完到出结果"这段目前只能靠探针量，不能靠日志读。

## 2. 进度曲线：12.8 秒贴满，25.0 秒才结束

按 `countedBytes / 源已用字节` 采样（这正是界面用的分数）：

| t (s) | 百分比 | 阶段 |
| --: | --: | :-- |
| 8.7 | 80% | deep_scan |
| 11.7 | 90% | deep_scan |
| 12.8 | **100%** | deep_scan |
| 14.0 | **104%** | deep_scan |
| 24.9 | **119%** | finalize |
| 25.0 | 94%（收尾校正） | finalize |

**进度条从 12.8 秒起就是满的，扫描到 25.0 秒才结束——满格之后等了 12 秒。**

### 2.1 分子里有一份从 t=0 就恒定存在的预计数（真正的原因）

**我第一次把它归因给 APFS 克隆，那是错的**，下面是分解到数字的实测：

| t | 进度 | `Bytes` | `Counted` | **预计数** | 阶段 |
| --: | --: | --: | --: | --: | :-- |
| 0.0s | 0% | 0.0 | 0.0 | 0.0 | catalog |
| 2.0s | **30%** | 11.2 | 57.9 | **46.7** | deep_scan |
| 6.9s | 70% | 88.9 | 135.6 | **46.7** | deep_scan |
| 13.7s | **100%** | 146.5 | 193.2 | **46.7** | deep_scan |
| 14.5s | 118% | 182.6 | 229.3 | **46.7** | finalize |
| 终态 | — | 182.6 | **182.6** | **0.0** | — |

`countedBytesLocked()`：

```go
if t.state == scan.JobRunning {
    return t.bytes + t.preCounted   // 运行中
}
return t.bytes                      // 终态：预计数撤出
```

`preCounted` 是卷组辅助卷的 statfs 已用之和，**46.7 GB，从 t=0 恒定**，
占分母 192.9 GB 的 **24.2%**。后果有两条：

1. **进度条在一个字节都没走查之前就已经是 24%**；
2. 走查过程中这些辅助卷的内容**也会进 `t.bytes`**，于是同一批字节被数两遍，
   条子在 `Bytes=146.5GB`（最终 182.6GB 的 80%）时就贴到 100%；
3. 终态那一刻预计数撤出，分子**凭空掉 46.7 GB / 24 个百分点**
   （实测 118% → 94.7%）。

`countedBytesLocked` 的注释写着"终态时辅助卷已经在 bytes 里了，预计数必须撤出，
否则会数两遍"——**它们不是终态才进 bytes 的，走查过程中就在进。**
注释描述的双计，在整段扫描里一直存在。

设计意图（ADR-0053 §1 / R-054 §3.2）是"避免在最后十分之一出现 12 点的跳变"。
实际得到的是**一个 24 点的起跑线，外加终态一次 24 点的倒扣**。

### 2.2 与 APFS 克隆无关（更正）

克隆那次改动**已经回退，从未发布**：`SizeBasis` 仍是 `v1`，替换那一行是 `_ = entry.has_private`。
字节计数那几行最后一次被修改是 `3d9546e`（内存事实源那次），不是今天。
**克隆调查一个字节的计数都没有改。**

真正把进度条弄坏过的是另一次改动——跳过辅助卷的 `diskutil`（§12a 已回退）：
辅助卷因此报出容器级用量，`preCounted` 与附加节点同时膨胀，
日志里 16:32–16:34 那三次 `bytes=729680154624`（729 GB）就是它。

### 2.3 已做的缓解，与没做的修复

**已做**：分子超过分母时切不定式，并显示阶段名。这不让进度更准，只让它不再说谎。

**已做（第二轮）**：预计数在**那些字节落进 `task.bytes` 的那一刻**让位，
而不是等到终态。`attachGroupVolumes` 加 36.1 GB 进 `task.bytes` 时状态仍是 `running`，
那个窗口里两边同时计入——这就是 118% 的来源。改为 `task.preCounted -= attachedBytes`
（下限 0）。实测：

| | 修复前 | 修复后 |
| :-- | --: | --: |
| 峰值 | 118% | **104.7%** |
| 贴满后还要等 | **12.2s** | **1.0s** |

同时把不定式的门槛从 `>= 1` 提到 `> 1.05`：**贴满读作"快好了"，扫动读作"不知道要多久"**，
第一轮那个改法把一个谎言换成了读起来更糟的东西。不定式作为兜底保留——
真出现大幅超出就说明账又算错了，那时"在忙，不知道还剩多少"才是唯一为真的显示。

**仍没做**：残余 4.7% 超出来自 `preCounted`（46.7 GB，所有卷组辅助卷）
与 `attachGroupVolumes` 实际附加（36.1 GB）的差。父目录未被走查到的卷会被整个跳过
（`parentID == 0` 就 `continue`），而预计数无条件全加。差的 10.6 GB 需要先查清是哪几个卷、
为什么它们的父目录没进 `watched`。

**已做（可观测性）**：`GetMap` 现在记录耗时，且**每个快照的第一次根图一定记一行**——
"扫描完成"与"结果出现"之间此前在日志里是空白，两次都只能靠探针倒推。
现在 `scan ... finished` 与紧随其后的 `map snapshot=... 用时` 两行相减，就是用户等的那段。

## 3. 真正的瓶颈：插入，不是走查

单独跑扫描器（空 emitter）扫 `/`：**13.8 秒，2,221,728 节点，没有任何 >250ms 的慢批次**。
同一次走查在应用里：日志 `walk=29.37s tail=128ms`。

`enqueueBatch` 是有界通道，写入协程落后时它阻塞，**扫描器就被拖到写入者的速度**。
所以：

- 日志里的 `walk` 是**走查 + 插入**，不是走查；
- `tail` 很短（128ms）只是因为退出时队列已经被拉平；
- **扫描器比应用快 2.1 倍**，慢的那一半在 `InsertNodes`。

这也顺带解释了 §2 的现象：扫描器 13.8 秒就交完货、`countedBytes` 定格，
而应用还要再插入十几秒——**进度条自然一动不动**。

## 4. 未验证 / 已知限制

- **没有量 `InsertNodes` 自身的吞吐**，也没有定位那 15 秒里的具体开销
  （arena 追加？`recordTable` 扩容？锁竞争？）。ADR-0056/0057 对内存布局有严格约束，
  动它需要先有测量，本记录只确立了"瓶颈在这里"。
- 修法没有让进度变得更准，只是让它**不再说谎**。要让它准，得让分子与分母同口径
  ——即 R-065 §2.1 那个两个数的模型。
- 日志仍看不到"扫描完成 → 结果页"这段，前端时序无记录。

# R-066 页面切换动画帧序列复核

- 日期：2026-08-31
- 触发：使用方三次指出页面切换没有过渡、或看不出过渡，最后要求「你看看原版的动画，
  它的页面跳转衔接很丝滑，你直接参考过来」。
- 结论：**原版的页面切换就是窗口尺寸动画，它完全不动内容。** 我此前两版都在动内容，
  方向从一开始就错了。

## 1. 我前两版为什么白做

第一版给进入的页面加淡入 + 轻微缩放；使用方说看不到。第二版补上交叉淡入让两页重叠；
使用方仍说「没看到类似原版的过渡动画」。

**两版都不可能看得出来**，因为我们的窗口在切页时是**一次瞬时 `SetSize`**
（源页 `968 × (151 + 行数×54)`，结果页 `968 × 715`）。那一下跳变就是整个事件，
在它下面做任何内容动画都被盖过去。

## 2. 方法

复用 R-061 的做法（原版在本机运行，直接抓原生帧），工具重建于
`docs/research/tools/R-066/`：`winlist.swift` / `grab.swift` / `click.swift`，
外加本次新增的 `height.swift`——**因为发现动画对象是窗口之后，要量的曲线根本不需要像素**：
以 6ms 间隔轮询 `CGWindowListCopyWindowInfo` 的 `Height`，只在变化时输出。

R-061 记的三个坑仍然全部有效（`CGWindowListCreateImage` 已移除、CLI 进程需先触碰
`NSApplication.shared`、位图必须按 `bytesPerRow` 取样）。

**本次新踩的一个坑**：为了让窗口获得焦点，我先在窗口内"随便点一下"——那一下点在轮盘上，
把原版钻进了 `用户 > deemo > AndroidStudioProjects > android`，**我自己污染了要观测的状态**。
改用 `osascript activate`，不点。

### 3.3 三个直接可抄的结论

1. **动画对象是窗口高度，不是内容。** 原版切页时内容没有任何淡入淡出或缩放。
2. **曲线是线性的。** 步长均匀在 `49–50pt`，**不是缓动**——如果是 ease，首尾步长会差几倍。
   `49.4pt/帧 @ 60fps` ⇒ 593pt 需要 12 帧 ⇒ 200ms，与实测吻合。
3. **窗口 Y 全程不变**（两个方向都是 `141.0`），窗口从固定的上边缘向下生长/收缩。

### 3.4 内容是水平推移，不是淡入淡出，更不是缩放（补测）

使用方指出「除了窗口大小变化，里面的内容是一个所有平移的动画」。重抓返回过程，
中段一帧（`fixtures/R-066-daisydisk-push-mid.png`）不需要任何测量就能读出来：

- **出去的结果页整体向右平移**——轮盘偏右，右侧列表的数字已经被推出窗口边缘；
- **进来的源页从左侧滑入**——左上角是源行的碎片（容量条、`7.3 GB`、`查看` 按钮），
  左下角是「扫描云存储」。

两页像转盘一样一起走。返回时新页从左来，正向是镜像。

### 3.5 推移的缓动没测出来，两种方法都失效

- **互相关**（`tools/R-066/shift.swift`）：**退化**。第一版没有按重叠像素数归一化，
  于是"重叠最少的位移"总是得分最低，每一帧都报极值 `-1656`，包括参考帧与自身比。
  归一化之后不再退化，但结果在 `0` 与 `-1640` 之间跳——因为**过渡中每一帧同时含有两页内容**，
  单一全局位移本来就描述不了它。
- **亮像素重心**（`tools/R-066/centroid.swift`）：也失效。窗口在同时收缩，
  取样带区（y=1000–1600）逐渐落到窗口之外，质量从 `363k` 掉到 `0`。

所以**推移的时长与缓动没有观测值**。精确测到的只有窗口斜坡（200ms、线性、49.4pt/帧）。
落地时让推移与它共用同一个时钟和同一条曲线——**这是与证据一致的选择，不是对推移本身的观测**。

## 4. 落地

- 窗口高度改为帧循环线性推进，**步长照抄 `49.4pt/帧`**。
  步数由距离除以步长得出，而不是固定帧数——**固定帧数会让更高的窗口resize得更快**，
  速度就不再和原版一致。
- **内容改为水平推移**（§3.4）：出去的页移出一整个窗口宽，进来的页从对面移入，
  与窗口斜坡同一个 200ms 线性时钟。**不做缩放、不做交叉淡入**——窗口正在改高度，
  再叠一个缩放或溶解就是第二个与它竞争的运动，这正是前两版看不出效果的原因。
- （已作废的第一版）**内容上的缩放删掉。** 窗口在改高度，同时缩放内容是两个互相打架的运动，
  这正是第一版看不出效果的原因之一。只留 140ms 的纯不透明度淡入，
  让被长出来的窗口露出的内容不至于突然出现，且**比 resize 先结束**。
- `prefers-reduced-motion` 在代码里判：resize 由帧循环驱动，不判的话
  "不要动效"仍会收到 12 次窗口尺寸变更。

## 5. 顺带验证到的一件事

原版源页的容量条是**琥珀色**，实测占用 `192.2 / 245.1 = 78%`。
这落在 §12a 刚定的 `70–85% 琥珀` 档内，**与原版一致**——那一档不是凭感觉选的。

## 6. 未验证 / 已知限制

- 只测了一个尺寸差（593pt）。**无法区分"固定 200ms 时长"与"固定 49.4pt/帧 步长"**，
  两者在这个 Δ 上给出同一条曲线。取了后者，理由见 §4，但这是选择而非观测。
- 原版在窗口被手动改过大小、或屏幕高度不足时的行为未测。
- 只测了「查看」与面包屑两条路径；扫描结束自动进入结果页的那一次未单独测
  （原版扫描耗时长，未安排）。

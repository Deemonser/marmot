# R-062 AI 清理建议的证据装配与规则覆盖率预研

- 日期：2026-08-27
- 触发：使用方提出新增"AI 分析"功能——在结果页右下角放一个按钮，点击后把扫描结果交给大模型判断
  哪些可以清理，要求"比市面上那些规则类的清理软件更好"。
- 关系：`Recommendation` 领域此前只在 [DDD](../DDD.md) 和 [BASELINE](../BASELINE.md) 冻结了边界，
  没有进入任何切片，SDD 也没有对应条目。本记录是该领域的第一份证据基础。
  安全边界继续受 [ADR-0015](../adr/0015-macOS预览Finder定位与收集区平台边界.md)（Collector 只映射
  清理候选）和 [ADR-0048](../adr/0048-空间图投影条目精简与密度上限.md)（投影条目不携带路径、不能授权
  文件操作）约束。

## 1. 问题

"把整个扫描结果发给 AI"这句话里有三个未经验证的假设，任何一个不成立，功能形态就要变：

1. 扫描结果**发得出去**吗；
2. 如果发不出去、必须剪枝，剪枝之后剩下的东西**还够不够判断**；
3. 让模型来做这件事，相对一个固定规则清单**到底多出多少东西**——这是使用方给的验收标准，
   不量出来就只是个说法。

## 2. 环境与方法

- 机器：本机 macOS（Darwin 25.5.0），APFS。
- 样本：`$HOME`（`/Users/deemo`）、`/Applications`、`/Library` 三棵树。
  **`/System` 与 `/private/var` 未走**：前者 SIP 只读且已被 `cleanup.DeleteBlock` 无条件拒绝，
  后者需要 FDA 且大部分对清理无意义。因此下文"全盘"是**部分全盘**，不是产品意义上的全盘。
- 工具：一次性 Go 探针（`filepath.WalkDir` + `syscall.Stat_t`），走盘结果 gob 落盘缓存，
  指标在缓存上反复计算。占用一律取 `st_blocks * 512`，不跟随符号链接。
- **走盘耗时不是产品指标。** 探针用的是 stdlib 递归，同一棵 `$HOME` 冷态 `183.00s`、
  热态 `68.79s`。产品的 Darwin 原生扫描器在 `/` 上的纯扫描中位数约 `13.99s`（SDD §9）。
  两者不可比，这里记录只是为了说明**证据装配绝不能自己再走一次盘**，必须读现成快照。

### 2.1 第一版指标是错的，纠正在这里

我最初量的是"剪枝后保留的节点覆盖了多少字节"，八档阈值全部输出 `100%`。

原因是**根节点在任何阈值下都存活**，它一个人的子树就是全部字节，覆盖率于是恒等于 1。
这个指标问了一个由构造决定答案的问题，没有任何信息量。

改为**残余分区（residue partition）**：对每个保留节点 A，

```
residue(A) = subtree(A) - Σ subtree(c)，c 取遍 A 的**保留**子节点
```

即 A 身上"模型看不进去"的那部分。每个字节属于且只属于一个保留节点的残余，
所以 `Σ residue = total` 是个可校验的恒等式，探针每档都断言了它，无一档报错。

**教训与 R-060 那次同类：当一个量由构造决定其取值时，它不是度量。**

## 3. 测量结果

### 3.1 整棵树发不出去，不是"有点大"，是差三个数量级

按最紧凑的行格式（`id parent name kind bytes age`，制表符分隔）序列化整棵树：

| 树 | 节点数 | 占用 | 整树载荷 | 估算 token |
| :-- | --: | --: | --: | --: |
| `$HOME` | `1,731,862` | `119.89 GB` | `82.31 MB` | `21,578,173` |
| `/Applications` | `196,091` | `21.38 GB` | — | `2,129,367` |
| `/Library` | `97,493` | `6.97 GB` | — | `1,000,954` |
| **合计** | **`2,025,446`** | **`148.24 GB`** | — | **`24,708,494`** |

token 数按 `字节 / 4` 估算，是估算不是测量。即便如此，`2470 万 token` 对 `20 万` 上下文是
**123 倍**，对 `100 万` 上下文仍是 **25 倍**。这不是调参能解决的差距。

### 3.2 剪枝极其便宜，比预期便宜一个数量级

`$HOME` 上的剪枝档位（保留子树占用 ≥ 阈值的节点）：

| 规则 | 保留节点 | 残余块数 | 最大残余块 | 最深层数 | 载荷 | 估算 token |
| :-- | --: | --: | --: | --: | --: | --: |
| ≥ `2.40 GB`（总量 2%） | `51` | `46` | `19.18 GB` | `9` | `2.7 KB` | `683` |
| ≥ `1.20 GB`（1%） | `87` | `77` | `18.75 GB` | `10` | `4.5 KB` | `1,161` |
| ≥ `613.83 MB`（0.5%） | `241` | `206` | `14.00 GB` | `11` | `12.8 KB` | `3,271` |
| ≥ `245.53 MB`（0.2%） | `491` | `388` | `12.63 GB` | `15` | `25.4 KB` | `6,511` |
| **≥ `128 MB`（绝对下限）** | **`830`** | **`654`** | **`12.48 GB`** | **`15`** | **`43.4 KB`** | **`11,110`** |
| ≥ `64 MB` | `1,486` | `1,142` | `10.14 GB` | `16` | `77.1 KB` | `19,729`  |

三棵树合起来取 `≥128 MB` 档：**`1,084` 个节点、`55.4 KB`、约 `14,200 token`**。
相对整树的 `2470 万`，压缩比约 **`1740:1`**。

**这一档推翻了我在设计讨论里给出的"50–150k token"估计，低了一个数量级。**
后果是正面的：省下来的预算应当花在**每个节点带更多证据**（子树文件数、目录数、扩展名画像、
最新/最旧 mtime、最大单文件）上，而不是留着不用——判断力来自这些字段，不来自节点条数。

绝对下限（B 族）与相对占比（A 族）在本机几乎等价（`830` 对 `882` 节点）。
选**绝对下限**，因为它可解释：低于 `128 MB` 的东西不值得占用一条建议。

深度上限（C 族）是更差的省法：`depth<=4` 把载荷从 `43.4 KB` 压到 `14.3 KB`，
但最大残余块从 `12.48 GB` 涨回 `18.75 GB`，且丢掉了 `~/AndroidStudioProjects/*/build/intermediates`
这类**恰好在第 5–7 层**的工程产物。**不采用深度上限。**

### 3.3 最大的不透明块是什么——这一条改了设计

`≥128 MB` 档下最大的残余块，以及它们的画像：

| 残余 | 文件数 | 最大单文件 | 最新 mtime | 主扩展名 | 路径 |
| --: | --: | --: | --: | :-- | :-- |
| `12.48 GB` | `139,969` | `124.20 MB` | 今天 | `.jar` | `~/.gradle/caches/8.13/transforms` |
| `10.14 GB` | `10,730` | `48.21 MB` | 今天 | — | `~/.gradle/caches/build-cache-1` |
| `3.31 GB` | `1,071` | `9.68 MB` | 2 天 | `.bin` | `~/Library/Containers/com.soda.music/…/LunaCacheV2` |
| `3.28 GB` | `1` | `3.28 GB` | 77 天 | `.pack` | `~/AndroidStudioProjects/android/.git/objects/pack/pack-….pack` |
| `1.02 GB` | `1` | `1.02 GB` | 33 天 | `.db` | `~/AndroidStudioProjects/luffa2/.codegraph/codegraph.db` |
| `778.17 MB` | `1` | `778.17 MB` | **`618` 天** | `.mov` | `~/Library/Application Support/com.apple.wallpaper/aerials/videos/….mov` |

最大的那块不是一个大文件，是 **`139,969` 个中等文件**。任何阈值剪枝在结构上都切不开它——
把下限降到 `64 MB`，最大残余块也只从 `12.48 GB` 降到 `10.14 GB`。

**但它不需要被切开。** `~/.gradle/caches/8.13/transforms` 整块就是一条建议；
真把 `139,969` 个 `.jar` 摊开给模型看，结果只会更差。

所以"残余占比"这个指标本身也没有在问对的问题。真正决定成败的不是**模型能不能看进去**，
而是**这块东西能不能被认成一个可以承载一条建议的单位**。两段式深挖的触发条件因此不是
"大且不透明"，而是"**大且模型认不出来**"——由模型在第一段自己声明，而不是由后端按大小判定。

### 3.4 规则清单够不到 63.4%

手写一份规则目录（26 条，覆盖 `Library/Caches`、`Logs`、`.Trash`、沙盒容器缓存、
Xcode `DerivedData`/`Archives`/`iOS DeviceSupport`/`CoreSimulator`、iOS 备份、Mail、Homebrew、
npm/yarn/pnpm、Gradle、Maven、Cargo、Go mod/build、pip、`node_modules`、`__pycache__`、
Docker、CocoaPods），在 `≥128 MB` 的残余块上匹配：

```
规则命中    43.84 GB    36.6% of total
规则未命中  76.04 GB    63.4% of total
```

命中明细里 `32.46 GB` 全部来自 Gradle 缓存一条规则；去掉它，其余 25 条规则合计只命中 `11.38 GB`。

**规则够不到的部分，恰好落在四类上：**

1. **未知应用的私有缓存**——`com.soda.music/…/LunaCacheV2` `3.31 GB`、
   `QQMusicMac/iMusic` `753.74 MB`、`GoogleUpdater/crx_cache` `705.72 MB`、
   Telegram `postbox/db` `636.30 MB`。规则清单里一条都没有，因为清单只能写它认识的 app。
2. **项目目录内的工程产物**——`zymix-model/build/.transforms` `820.97 MB`、
   `StarChat/target/debug/deps` `796.12 MB`、`nook/app/build/intermediates` `675.38 MB`、
   `.venv/lib/python3.13/site-packages` `499.84 MB`。它们在用户自己的项目路径下，
   位置不固定，固定清单写不出来。
3. **git 仓库膨胀**——多个 `.git/objects/pack`，单个最大 `3.28 GB`，合计超过 `7 GB`。
4. **冷数据**——壁纸 `.mov` `618` 天、`FirstApplication/app/build` `617` 天、
   `Library/Java/JavaVirtualMachines/corretto-17.0.13` `619` 天、flutter engine artifacts `126` 天。
   规则**没有"上次活动时间"这个概念**，这一类它结构上就判断不了。

第 2 类和第 4 类合起来最能说明差别：同样是 `build/intermediates`，
`nook` 的 `13` 天没动、`FirstApplication` 的 `617` 天没动。前者该留，后者该删。
这个区分只需要一个字段（子树最新 mtime），而规则清单里没有它。

**这个 36.6% 必须谨慎解读。** 规则目录是我手写的、且写得偏宽（`node_modules` 按任意深度匹配），
所以 `36.6%` 是规则覆盖率的**上界**，`63.4%` 是剩余空间的**下界**；但它也不是对任何一款具体
商业软件的测量，只是同类方法的估计。

### 3.5 单机单画像，不可外推

本机是重度 Android/Rust/Flutter 开发机：`~/AndroidStudioProjects`、`~/.gradle`、`~/.cargo`、
`~/dev/flutter`、`~/.konan` 主导了整个分布。一台以照片、视频和 iOS 备份为主的机器，
剖面会完全不同，规则覆盖率大概率显著更高。

**因此 `63.4%` 是一台机器上的一次观察，不是产品结论。**
在拿到至少一台非开发者机器的剖面之前，不得把它写进任何对外表述。

### 3.6 证据本身有脏数据

`~/` 自身的残余块报出 `AGE_D = -534`：存在 mtime 位于**未来** `534` 天的文件。
若原样送进证据包，模型会把它读成"刚刚用过"。

装配时必须把 `age_days` 夹到 `[0, +∞)`，并且**未来 mtime 要单独标记**而不是静默夹掉——
它本身就是"这个文件不正常"的线索。

### 3.7 判断力来自公共词汇，私有段基本是纯身份

问题：证据包里的名字，哪些承载**分类信息**，哪些只承载**身份**。

方法：对 `≥128 MB` 骨架的每个节点，把路径切段，用一份手写的公共词汇表
（macOS 目录结构、开发工具产物名、反向 DNS bundle id、版本号、架构名）判定每段是否"公共"。

```
骨架节点              830
  路径含公共词汇信号  746  (89.9%)
  全程只有私有段       83  (10.0%)

私有段出现 2500 次，其中带结构标记（old/backup/copy/v2/日期/副本编号）18 次 (0.7%)
```

结论有两条，第二条推翻了我自己先前的论据：

1. **约九成节点的分类信息来自公共词汇。**
   `~/AndroidStudioProjects/zymix-im-android-cloud/zymix-model/build/.transforms` 里，
   模型需要的是 `build/.transforms` + `820.97 MB` + `.dex` + `0` 天；
   `zymix-im-android-cloud` 对判断的贡献是零。
   选择性假名化（只替换非公共段、保留结构标记）因此在技术上成立，判断力损失 `≤10%`。

2. **"名字后缀能看出是旧副本"这个信号非常罕见——`2500` 个私有段里只有 `18` 个带结构标记。**
   我先前用它论证"必须保留原名"，数据不支持。

但 `10.0%` 是**高估**：那 `83` 个"全程私有"里绝大多数是 `~/.cache/codex-runtimes/...`，
成因是我的词汇表没收 `.cache`。同理 `app`、`libs`、`modules`、`versions`、`dev`、`transformed`、
`prefab` 也被误判为私有段。

**这正是不推荐首版实现假名化的理由：词汇表的缺口会直接变成判断力的缺口，而这份表需要长期维护。**
误判成"私有"只是多脱敏一点（无害），误判成"公共"就是泄漏（有害），失败代价不对称——
但可用性会随词汇表老化持续劣化，而没有任何信号提示它正在劣化。

## 4. 结论

1. 整树不可发送，差 `25`–`123` 倍。证据装配是必须的，不是优化。
2. `≥128 MB` 绝对下限的骨架把 `2,025,446` 个节点压到 `1,084` 个、约 `14,200 token`，
   压缩比 `1740:1`。预算充裕，应当用来加厚每个节点的证据字段。
3. 不采用深度上限剪枝：它省得多但正好切掉第 5–7 层的工程产物。
4. 大残余块无需切开。深挖的触发条件应当是"模型认不出来"，由模型在第一段声明，
   而不是后端按体积判定。
5. 固定规则清单在本机够不到 `63.4%` 的字节，且缺口集中在未知应用缓存、项目内工程产物、
   git 膨胀和冷数据四类——前三类是"位置不固定"，第四类是"规则没有时间概念"。
6. 证据装配必须读现成快照，不得自己走盘。
7. `age_days` 必须夹紧，未来 mtime 单独标记。

## 5. 本次未验证

以下均**未做**，不得当作已知：

- **模型端一次也没跑过。** 提示词、结构化输出的稳定性、幻觉率、两段式的实际增益，
  全部没有测量。本记录只解决"送什么进去"，不解决"送进去之后有多准"。
- 校验层拦截率未测：模型返回的路径有多少比例是编造的、多少会被 `DeleteBlock` 拒绝，未知。
- token 数是 `字节/4` 的估算，未用真实分词器测量。
- `/System`、`/private/var` 未走，"全盘"是部分全盘。
- 只有一台机器、一种使用画像（见 §3.5）。
- 成本、时延、取消行为未测。
- 扩展名画像对判断力的**增益**未做对照实验——它在道理上有用，但没有证据。

## 6. 对设计的影响

| 结论 | 设计后果 |
| :-- | :-- |
| §3.1 整树发不出去 | `Advisor` 端口的输入是 `EvidencePack`，不是快照句柄，也不是节点数组 |
| §3.2 预算充裕 | 证据行带 `files/dirs/age/oldest/top_ext/biggest_file`，不只是大小 |
| §3.2 不用深度上限 | 剪枝只用绝对下限，默认 `128 MB`，随卷容量缩放 |
| §3.3 深挖由模型触发 | 第一段的输出契约里必须有 `needs_expansion: [node_id]`，上限 `8` |
| §3.4 四类缺口 | 提示词要显式点出这四类，few-shot 从这四类里取 |
| §3.4 规则仍必须存在 | 规则层不是可选项：它是证据包的一段输入，也是模型失灵时的下限 |
| §3.6 脏 mtime | 装配层夹紧并标记，不把清洗责任推给模型 |
| §3.7 判断力来自公共词汇 | 选择性假名化技术上成立，但因词汇表维护成本不进首版；首版靠可预览、可逐条排除、endpoint 自选 |
| §5 全部未验证 | 首个切片必须能在不接模型的情况下自证：证据包可导出、可人工审阅 |

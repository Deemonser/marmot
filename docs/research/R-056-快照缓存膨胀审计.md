# R-056 快照缓存膨胀审计

状态：已审计并修复泄漏（glob 缺陷已修 + 回归测试）；遗留 SQLite 的清理需新增 ADR

日期：2026-08-25

## 1. 问题

`~/Library/Caches/marmot` 增长到 **`10.4 GB`**，而缓存字节预算是 `512 MiB`。需要弄清每一部分是什么、
哪些是必要的、预算为什么完全没有起作用。

## 2. 环境与方法

本机 `~/Library/Caches/marmot`，当时目录里有 42 个文件。用 `du` / `ls` 逐项统计，用文件名与
`snapshot-N.manifest.json` 的存在性判断归属，再回到代码核对预算与剪除路径。

## 3. 证据

### 3.1 分项

| 项目 | 大小 | 判定 |
| :-- | --: | :-- |
| `snapshot-20.data` | `542 MB` | 必要——唯一事实源 |
| `snapshot-20.index.…0002` | `301 MB` | 必要——没有它重新打开结果就得重扫 |
| `snapshot-20.manifest.json` | `663 B` | 必要 |
| **38 个孤儿索引文件** | **`5.3 GB`** | **泄漏** |
| **`snapshots.db` + `-wal` + `-shm`** | **`4.6 GB`** | **孤儿**（ADR-0028 之前的 SQLite 存储） |
| `snapshot-20.index.…0001` | `3.4 KB` | 已被 manifest 取代，未清理 |
| `WebKit/` | `8 KB` | 必要——WebView 自己的缓存 |

目录里只有 **1 个 `.data`、1 个 manifest，却有 20 个快照的索引文件**：这些快照的数据文件与 manifest 都已
被删掉，索引却全部留下。真正需要的只有 `~843 MB`。

### 3.2 根因：printf 格式串被当成 glob 模式

```go
indexPattern: filepath.Join(directory, base+".index.%020d"),   // printf 格式
...
indexFiles, err := filepath.Glob(paths.indexPattern)           // 却传给了 Glob
```

`%020d` 里没有任何 glob 元字符，`filepath.Glob` 于是去匹配一个**字面名为 `snapshot-N.index.%020d`
的文件**——匹配不到，返回空切片，**且不返回错误**。这个错误出现在两处，互相放大：

1. `snapshotBytes()`：统计快照占用时**不计索引**，每个全盘快照少算约 `300 MB`；
2. `deleteSnapshotLocked()`：剪除时**不删索引**，只删 `.data` 与 `.manifest.json`。

于是预算以为存储很小、不触发剪除；即使触发，也只删掉小的那部分，最大的文件全部留下。
`512 MiB` 的预算下攒出 `6.1 GB` 索引。

**已修**：`snapshotPaths` 新增 `indexGlob`（`base+".index.*"`），两处调用点改用它；两个字段在注释里注明
不可互换及后果。回归测试 `TestPruneRemovesIndexFilesAndCountsThem` 断言"缓存尺寸包含索引字节"且"剪除后
目录里不留 `snapshot-*`"，并已验证：把 `indexGlob` 改回 `indexPattern`，测试立即报
`pruning left files behind`。

### 3.3 被取代的索引 generation 从未清理

`snapshot-20` 同时存在 generation 1（`3.4 KB`，首层发布索引）与 generation 2（`301 MB`，manifest 指向的
完整索引）。`Writer.Close` 只删 `.tmp` 文件，不删被取代的 generation。本例中 gen 1 很小，但机制上每次
重新发布都会留下一份。

**已修**：manifest 提交之后删除被取代的 generation。顺序是崩溃安全的——崩在中间只会留下一个多余文件，
绝不会出现 manifest 指向已删文件的情况；已持有该文件的 reader 句柄在 POSIX 下仍然有效。

### 3.4 遗留 SQLite 存储从未被生产代码打开，也没有任何代码清理它

`snapshots.db` 为 `4.57 GB`，`-wal` `38 MB`，修改时间是三天前（二进制存储接管之前）。
全仓检索生产代码中打开快照存储的位置只有一处：

```
main.go:112:  return binarysnapshot.OpenStore(filepath.Join(cacheDir, "marmot", "snapshots"))
```

`internal/infrastructure/snapshot`（SQLite 实现）仍在仓库中且被测试使用，但**生产链路不再打开它**。
没有任何代码会删除这些文件，它们会永久占用磁盘。这一项需要独立决策：让应用删除用户磁盘上的文件属于
需要明确边界的行为。进入 [ADR-0054](../adr/0054-遗留SQLite快照缓存清理.md)。

### 3.5 实际清理结果

按"manifest 不存在即为孤儿"的判据清理 38 个索引 + 被取代的 gen 1 + `snapshots.db*`：

```
清理前 10656 MB → 清理后 804 MB，释放 9852 MB
```

清理后重新打开应用，`snapshot-20` 正常载入（`238.5 GB`，条目完整），证明保留集合是充分的。

### 3.6 预算数值与单个快照体积不在同一量级

单个全盘快照实测 `843 MB`（`542` 数据 + `301` 索引），而 `snapshotCacheBudget` 是 `512 MiB`。
即修复之后稳态是**只保留一个快照**，每次新扫描都会挤掉上一个（ADR-0047 之后已保证不会挤掉最新的那个）。
产品形态只需要一个可重看的结果，因此行为可接受；但这个数字是在快照体积远小于现在时定的，与实际体积差
一个量级，需要单独复核。本记录不改它。

## 4. 结论

1. 缓存膨胀的根因是 printf 格式串被当作 glob 模式使用，且同一错误同时破坏了尺寸统计与删除；
2. 被取代的索引 generation 从未清理，机制上会持续泄漏；
3. `snapshots.db` 是 ADR-0028 遗留的孤儿，需要独立 ADR 决定清理边界；
4. 真正必要的缓存是"一个快照的 data + 当前 generation 索引 + manifest"，约 `843 MB`；
5. `512 MiB` 的预算与单快照 `843 MB` 不匹配，待单独复核。

## 5. 限制

- 单机单次审计；`snapshots.db` 的 `4.57 GB` 是本机历史扫描累积的结果，不代表其他机器的量级；
- 未测量修复后连续多次扫描的稳态占用（预期为一个快照，即 `~850 MB`，但未实测）；
- 第 3.6 节只指出预算与体积不匹配，没有给出应有的数值。

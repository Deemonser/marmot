# R-072：目录就地重读的可行性与代价

- 日期：2026-09-08
- 机器：8 核 / 16 GB / 内置 NVMe / APFS / macOS 26 (Darwin 25.5.0)
- 目的：为 [ADR-0070](../adr/0070-目录就地重读.md) 提供数据。本文只记测量与推翻的假设，不记决策。

## 1. 起因

R-071 之后，"对象已变化"的提示不再误报，但**报对了也无路可走**：`stale_node` 一出，该对象的所有文件操作
停用，唯一恢复手段是重扫整盘（本机 17-25 s）。使用方指出原版会持续更新（R-009 §键盘：`⌘R` 重扫当前目录），
而我们的 `⌘R` 只是从内存重查一遍，**不碰磁盘**。

SDD 14.5d 段落已明确拒绝 FSEvents 全盘监听（图会永远在抖）。本文要回答的是另一件事：**用户指着的一个目录**，
能不能在不重扫整盘的前提下从磁盘读一遍并接回内存树。

## 2. 树的结构允许什么

`memtree.tree` 以节点 ID 为记录表下标（ADR-0056 §1），子索引是按 `parentID` 计数排序得到的三段数组
（`childIDs / childStart / childCount`），`grouped=false` 时按需重建。ADR-0064 的 `removeSubtree` 已证明
两件事：把 `parentID` 置 0 即可把一棵子树从根摘下；祖先 roll-up 可以用差值算术就地修正。

重读需要的第三件事是**接入新节点**。子索引每个父的区间是连续的，无法就地扩容，所以接入必然触发一次
`group()` 重建。它有多贵：

| 树 | `group()` 用时（3 次） |
| :-- | :-- |
| 2,700,000 节点合成树（每目录约 4.5 个子项） | 76.6 ms / 64.6 ms / 65.9 ms |

**约 70 ms，且是分配 12 B/节点的临时数组。** 一次用户主动发起的重读可以承受。

## 3. 子扫描能给什么

`scanner.Scanner.ScanBatched(ctx, dir, emit, phase)` 接受任意目录作根：根节点 ID 为 1，其余从 2 起由
C 侧按批预留（`marmot_native_reserve_ids`），挂载边界照常跳过，firmlink 身份修正（SDD §13f）按绝对路径
生效。子扫描的编号与主树无关，接回时必须重编号。

两个必须知道的事实：

1. **`emit` 回调是多线程并发调用的。** 首版收集器用无锁 `append`，结果 873 个节点丢 1 个、且丢的可能是
   目录（"node 50 arrived before its parent 49"）。加锁后三轮 429,727 节点零丢失、无重号。这一条同样
   适用于任何新的 `BatchEmitter` 使用方。
2. **父先于子，按 ID 序成立。** 子项的 ID 在其父目录被列出时才预留，而父目录自己的 ID 更早预留。所以按 ID
   升序处理就能保证父先映射；**按到达顺序不成立**（并发 worker 会让子批先于父批到达，实测 873 节点里有 2 个）。

## 4. ID 该不该保留

前端到处拿着节点 ID：收集区行、面包屑、外环投影弧、hover 状态。若重读后全部换新 ID，收集区里的对象会与
轮盘脱钩、当前页的 `parentId` 失效。做法：**同一（已映射）父目录下同名同类的旧子项复用旧 ID**，新对象取
表尾新 ID，无人认领的旧记录置 `parentID=0`。实测对 4 个目录做无变化重读，`kept == nodes - 1`（减 1 是
目录自身），根字节数与节点数逐位不变——重读是幂等的。

顺带修正 `valid()`：原先"`parentID==0` 但名字非空"仍算有效，使被摘下的记录还能按 ID 查到并重建出一条
错误路径。改为 `id == root || parentID != 0`，摘下即"不存在"。ADR-0064 的回归测试全部通过。

## 5. 真实目录的代价

对 `/Users/deemo/AndroidStudioProjects`（429,727 节点，31.2 GB）扫描后，重读其前四个子目录：

| 目录 | 节点 | 重读用时 | 保留 / 新增 / 移除 | 之后首次 Map 查询 |
| :-- | --: | --: | :-- | --: |
| zymix-im-android-cloud | 206,958 | 1.396 s | 206,957 / 0 / 0 | 6 ms |
| android | 76,916 | 0.541 s | 76,915 / 0 / 0 | 6 ms |
| nook | 25,665 | 0.599 s | 25,664 / 0 / 0 | 6 ms |
| luffa2 | 95,267 | 0.739 s | 95,266 / 0 / 0 | 6 ms |

用时几乎全在子扫描本身（约 150k 节点/s，与全盘扫描同一量级）；接回与重建索引在 10 ms 量级。
4 次重读后根节点字节 `31,191,093,248` 与节点数 `429,727` 均与扫描时一致。

## 6. 上限

子扫描的节点在接回前以 `scan.Node`（含 `Path` 字符串，约 150 B/节点）暂存在内存里，接回前不能让读者看到
半新半旧的树，所以只能先攒齐再一次换入。取 **500,000 节点**为上限：约 3 s 重读、约 75 MB 暂存；再大的
目录已经是"盘"而不是"文件夹"，重扫整盘是诚实的工具。上限在收集回调里即时生效，不等扫完。

`SubtreeFacts.Nodes` 在 200,000 处饱和（`describeBound`），**不能**用来做预检——这条假设被测量推翻。

## 7. 结论

1. 目录就地重读可行：子扫描 + 按 ID 序重编号 + 同名复用 ID + 差值修 roll-up + 一次 `group()`。
2. 代价由子扫描决定，与全盘扫描同速率；接回是毫秒级。
3. 收集回调必须加锁；父先于子只按 ID 序成立。
4. 幂等：无变化的重读不改变任何数字与任何 ID。

## 8. 限制

- 没有测量变化量很大的重读（如删掉一半文件）的用时，预期与无变化相同，因为成本在读盘而不在接回。
- 含挂载卷节点（ADR-0052 §3 的 `kind=volume`）的目录拒绝重读，未寻找替代方案。
- 未做真实窗口的端到端验证。

## 9. 对 DDD/SDD 的影响与建议 ADR

- SDD：§8 用例表加"重读目录"；§13g 记录机制；14.5d 关于实时更新的段落补一句"用户主动的有界重读不在拒绝范围"。
- DDD：无新聚合；`SubtreeReplacement` 是与 `SubtreeRemoval` 同类的结果值对象。
- 建议 ADR-0070。

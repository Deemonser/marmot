# 技术预研

技术预研用于验证 SDD 中的高风险假设。预研结论必须写入记录，并通过 ADR 才能成为实现依据。

## 当前结论

- Wails 生产版不需要独立 HTTP 控制面，采用嵌入资源、类型化绑定和应用事件。
- 成熟产品普遍采用后台扫描、渐进展示、缓存/增量刷新、受限并发和按需展开。
- Mole 的扫描实现有可借鉴的并发、缓存、去重和取消设计，但当前 JSON 不是完整目录树协议。
- 固定的 Mole `V1.40.0` 提交是 MIT，可以在保留声明和来源记录的前提下复用扫描代码；当前 `main` 不在复用范围内。
- Marmot 采用五阶段扫描、设备感知并发、有限缓存和摘要事件；后端阶段结论由 ADR-0014 接受，扫描中窗口
  的前台切页部分由 ADR-0027 更新。
- Marmot 采用 `MapQuery`/`MapResult` 的当前层渐进查询，空间聚合项不能执行文件操作；结论已由 ADR-0013 接受。
- macOS 预览使用 Quick Look、Finder 定位使用 NSWorkspace，Collector 只映射为清理计划候选；结论已由 ADR-0015 接受。
- DaisyDisk 本机实机复核确认紧凑卷入口、当前目录列表、多层 Sunburst 和底部 Collector；结论已由 ADR-0016/0017 接受。
- DaisyDisk 视觉版式基线确认启动态与结果态必须使用不同窗口骨架；结论已由 ADR-0018 接受。
- Windows 暂不研究实现，只保留平台抽象。
- macOS APFS 目录扫描优先使用 `getattrlistbulk(2)` 批量元数据读取，`searchfs` 不作为首版主路径；结论已由 ADR-0021 接受。
- macOS 扫描预计算挂载边界、以单目录批量读取减少 cgo 往返，并以 2048 槽位有界 fd/openat 优先；结论已由 ADR-0022 接受。
- 本机 SSD 并发复测将单 SSD 预算更新为 8 worker；`15.22s` 和 `14.64s` 是旧 Go 扫描路径的历史基线，由 ADR-0024 接受。当前 Darwin 原生路径已接入，最新三次 `/` 纯扫描中位数约 `13.99s`；完整二进制终态中位数约 `20.87s`，两者继续分开测量。
- 快照缓存清理、历史数据库维护、事件限频和不确定进度已由 ADR-0023 接受；扫描中用户可见空间图刷新
  由 ADR-0027 更新，源页保持到终态。
- Application 与 SQLite 异步写入、批次和索引复测已由 ADR-0026 接受，现作为历史对照；纯扫描器与完整落盘耗时分开记录，
  当前完整 smoke 仍不宣称达到 `<15s`。
- DaisyDisk 扫描中保持磁盘选择页，前端不因后端首层发布而提前展示空间图；终态且最终 Map 查询成功后才进入结果页，结论已由 ADR-0027 接受。
- R-026 已确认 SQLite 不再适合作为首版扫描热路径和快照事实源；`SnapshotStore` 已接入 Darwin 原生批量扫描、
  追加式二进制快照和固定索引，结论由 ADR-0028 接受。原生纯扫描和真实 `/` 完整二进制终态 smoke 已通过，
  但完整终态中位数约 `20.87s`，15 秒目标尚未完成。旧 SQLite ADR 只保留历史基线，TTL、取消、部分结果和
  清理前身份校验语义继续有效。
- R-027 已通过真实 `/` profile 固定下一性能切片：原生 worker 复用 bulk/节点缓冲，按有效 bulk 页分配 ID，
  不改快照格式、完整性校验或设备并发预算；结论由 ADR-0029 接受。完整终态仍必须用三次中位数验收。
- R-029 基于符号化 profile 固定 FinishSnapshot 临时索引同步切片：只取消进程私有排序中间文件的
  `Sync`，保留数据帧、最终索引段、index 临时文件和 manifest 的同步/校验；结论由 ADR-0031 接受。
- R-034 已完成 Application 扫描状态记账有界化；真实 `/` 三次完整终态中位数为 `19.473s`，达到本切片
  `<=19.70s` 目标，但总 `15s` 门槛仍未完成；结论由 ADR-0034 接受。
- R-035 已实施外部排序归并小顶堆和排序块缓冲复用；真实三次 `/` 终态中位数为 `22.946s`，
  `FinishSnapshot` 中位数为 `4.884s`，未达到本切片目标；正确性实现保留，结论由 ADR-0035 接受。
- R-036 已实施 relation 归一化与最终 parent 排序合并；真实三次 `/` 终态中位数为 `19.651s`，
  `FinishSnapshot` 中位数为 `3.064s`，未达到本切片目标；正确性实现保留，结论由 ADR-0036 接受。
- R-037 已实施 Darwin 原生节点路径的已知长度转换和直接拼接；分配 profile 总量下降约 `2.9%`，
  纯扫描三次中位数 `13.069s` 达到子目标，但完整终态中位数 `25.493s` 未达标；保留完整
  `scan.Node.Path`、挂载边界、快照格式和清理契约，结论由 ADR-0037 接受。
- R-038 已通过真实 `/` profile 锁定 `FinishSnapshot` 外部固定记录排序器的反射交换和已排序检查复制为
  内部优化边界；目录字符串回读未形成稳定热点。已实施标准库 `slices.SortFunc` 和两个固定缓冲交换，
  排序累计 CPU 约从 `0.68s` 降至 `0.44s`，但真实 `/` 三次完整终态中位数 `29.727s`、`FinishSnapshot`
  中位数 `6.406s`，未达到本切片目标；正确性实现保留，结论由 ADR-0038 接受。
- R-040 已通过真实 `/` profile 锁定并实施 Darwin 回调的 `Name`/`Path` 双重分配削减：一次分配完整路径，
  名称从路径尾部复用；不引用 C 批次内存，不改变扫描节点、取消、挂载 boundary 或快照契约。实际累计分配
  下降约 `1.0%`，低于 `5%` 子目标；结论由 ADR-0040 接受，正确性实现保留。
- R-041 已实施：用一个私有状态值同时保存 `path` 和 `parentID`，两次同口径分配 profile 相对 R-040
  下降 `1.55%` 和 `3.20%`，不改变扫描事实、目录汇总或快照契约；结论由 ADR-0041 接受。
- R-042 已完成预研并锁定数据帧校验与问题索引单次遍历：保留每帧 header/footer/checksum 校验，消除
  `buildIssueSection` 的重复数据遍历；结论由 ADR-0042 接受。
- R-043 已完成预研并锁定节点 metadata/relation 联合临时记录：按 node ID 的初始外排从两路收敛为一路，
  继续保留 override 对齐、最终 parent 排序、checksum、manifest 和有界内存；结论由 ADR-0043 接受。
- R-044 已完成预研并锁定 parent 排序归并直接消费：保留固定记录块和有界 merge，直接生成 child/directory
  section，不落盘完整 normalized relation 中间流；结论由 ADR-0044 接受。
- R-045 已完成预研并锁定 Darwin 原生回调锁争用削减：parent path 快照和批内路径/节点转换移到全局锁外，
  每批只做一次状态合并，emitter 在锁外执行；不改变节点、硬链接、目录汇总、取消或快照契约，结论由
  ADR-0045 接受。
- R-046 已完成预研并锁定 relation 外排专用 `256K` run 块：只为 parent relation 外排放大固定 run，
  降低 run 数与临时文件读写，不改变快照格式、查询顺序或全量节点不入内存的约束；结论由 ADR-0046 接受。
- R-047 已完成预研并锁定用户可见终态解耦：扫描结束即由内存目录树投影应答空间图，`FinishSnapshot`
  转后台完成后再切回 `SnapshotStore` 作为查询权威。同时纠正了三个被沿用多轮的前提——`<15s` 只见于
  R-020/R-024 的推定表述；同机同卷原版三次实测为 `18s` / `16s` / `15s`，中位数 `16s`，真实差距约
  `5.25s` / `33%`，且 `15s` 错在口径（可见终态被当成 durable 完整终态）而不是数值；
  原版终态不是「首屏 + 后台补齐」，其扫描完成时整张图可见、可下钻五层，因此首层投影方案不构成追平；
  而全盘目录聚合树在扫描结束时已经在内存中（`scanner.go:136-138,337-345`、
  `native_darwin.go:902,949-964`），是已付成本。产品门槛改为用户可见终态 `<=18s` 且可下钻深度不低于
  原版五层，stretch `<=15s`，并冻结固定只读样本口径。中位数 `16s` 也使「只做 R-046 即与原版持平」
  失效——R-046 自身目标 `<=20.50s` 仍慢 `4.5s`，方案 A 因此是追平的必要条件。待 ADR-0047 决策。

- R-049 已完成预研并锁定投影条目精简：扇区密度差距的根因不是预算数值，而是每条弧携带完整 `MapEntry`
  （内嵌完整 `scan.Node`）。实测发现 ADR-0017 的 `256 KB` 载荷上限**在默认 `384` 预算下就已被突破**
  （`274 KB`），硬上限 `512` 时达 `384 KB`；精简 DTO 稳定小 `11` 倍，`2021` 个弧只需 `132.8 KB`。
  瓶颈在服务端装配（`2021` 弧 p95 `346.9ms`），编码只占 `2.5ms`。另发现 `maxPageSize = 1000` 会让预算
  抬不过 `1000`。方案为「先精简投影后代条目、跳过其路径重建、解除 `maxPageSize` 耦合，再按实测重定
  预算与 p95」；目标密度 `2000` 弧由产品决策给出，结论由
  [ADR-0048](../adr/0048-空间图投影条目精简与密度上限.md) 接受。**实施后两条门禁均达标**：`2021` 弧
  载荷 `235.2 KB`、p95 `66.2ms`（实施前 `1467.5 KB` / `346.9ms`）；路径重建假设被证实，但"小 11 倍"是
  理想编码上界，可交付形态为小 `6.2` 倍。

等待 durable」的方案被否掉——那只是把等待从进页面前挪到首次下钻。

关键可行性事实：两条扫描路径在扫描结束时都已为每个目录持有 path、parentID 和全深度 roll-up 后的聚合
尺寸（`scanner.go:136-138`、`:172-174`、`:337-345`；`native_darwin.go:902`、`:923-926`、`:949-964`、
`:764`），全盘目录聚合树是已付成本，已计入当前峰值 RSS；缺的只有子项排序列表和个体文件
条目。投影尺寸已实测定型（本机 `/` 探测：目录 `771,265`、文件 `2,737,195`；深度 `<=4` 只覆盖 `0.9%` 目录，
故按深度收口不可行；子项数 `p50=1`、`p90=5`、`p99=53`，故按目录做 top-K 很便宜）：**深度 `<=4` 保留
top-256，其余深度保留 top-8**，约 `74 MiB`，完整覆盖 `93.31%` 目录的全部子项。分层比纯 top-8 只多
`1.2 MiB`，却修掉了根目录 18 个子项被折掉 10 个的首屏残缺；top-16 多花 `15.8 MiB` 只换 `2.6` 个百分点。
超出 top-K 的部分复用已有的 `Remaining` / `ProjectionTruncated` 语义，不扩展 `MapQuery` /
`MapResult` 契约。`store.FinishSnapshot(...)`、`UpdateDirectorySizes` 和
`InsertIssues` 转后台，durable 就绪后 `SnapshotStore` 恢复为唯一权威。

目标为固定样本三次 **用户可见终态中位数 `<=16s`**（stretch `<=15s`）、**首屏五环图零等待且投影完整覆盖 `>=90%` 目录的
全部子项**（防止用加载态掩盖成本的硬性指标）、开始 → top-K 外首次下钻可用 `<=21.254s`、durable 发布
完成不回退超过 `3%`。内存改为显式预算：投影新增 `<=96 MiB`，总峰值 RSS `<=` 冻结样本重建基线加
`96 MiB`——原定 `5%` 门禁作废，因为 RSS 历史记录本身互不一致（ADR-0030 三次约 `584 MiB`、R-045 单次约
`420 MiB`）。原版基线仍需补足两次复测形成中位数。投影原型已用真实扫描器实测（真实目录 `589,497`、非空目录 `422,577`、保留条目 `1,159,430`）：可见终态
≈ `14.45s`（扫描 `14.390s` + finalize `62.3ms`），低于原版中位数 `16s` 与 stretch `15s`，构建耗时不构成
风险。但堆占用把估算推翻了——朴素 `map[int64][]childEntry` 为 `+295.1 MiB`（超 `96 MiB` 预算 3 倍，
明确拒绝），compact arena 为 `+62.0 MiB`（在预算内）。因此表示方式和「累加器按 `parent_id` 分片」
（emitter 在 R-045 之后由 8 个 native worker 并发调用，单 map 会 `concurrent map writes`）都升级为实现
约束。随后的原型 v2 实测了逐批 compact（native flush 是单父目录批次，实测 `multi_parent_batches=0`）：稳态
降到 `+58.9 MiB`（预算内，`sum(Total)=nodes-1` 精确通过），扫描期峰值贡献从 `295.1 MiB` 降到
`117.1 MiB`——但仍超 `96 MiB` 预算 `22%`，因为 arena 用 `append` 倍增扩容，缓解方向为 chunked arena。
另外定量了两个实现陷阱：名称必须排序裁剪后才复制（否则名称字节从 `19.2MB` 涨到 `62.0MB`），分片 map
预分配容量必须按实测定（`64` 个 `1<<13` 空 map 占 `26.7 MiB`）。随后两个假设被自己的测量推翻：**冻结样本不可行**（APFS 快照可建，但 Data 卷 `95%` 占用下
`deleted(8)` 在一轮测量结束前就回收，空间也不够复制语料）；**chunked arena 无效**（峰值约 `+127 MiB`
反而高于 `append` 的约 `+103 MiB`）。峰值超标的真因是 GC 锯齿余量随活跃堆等比放大，`GOGC=50` 下投影
峰值贡献降到 `+91.2 MiB`，进入预算——即峰值由 GC 策略而非数据结构决定。wall 时间在实时 `/` 上不可测：
六对交替中五对显示投影组「更快」，配对抵消无效（`WindowServer` `33%`、终端 `11%`、浏览器 `10%` 在竞争）；
改用 `user` CPU 后三对完全一致，投影成本为 **`+0.29s` user CPU（`+9.4%`）**，`sys` CPU 无变化，对 `16s`
门槛可忽略。因此 ADR-0047 第 4 条的「固定只读样本」已改为「相对成本用 CPU 时间判定、绝对 wall 门槛须在
静默环境测量，否则记为未验证」。最后，实测原版扫描期内存从 `300M+` 升到 `700M+` 并维持，说明原定的
`96 MiB` 投影预算是在没有产品标尺时凭空设的、过紧；预算改为总峰值 RSS `<=700 MiB`、投影新增
`<=160 MiB`，带投影的 Marmot 扫描期最大 RSS 为 `499`–`523 MiB`（无投影 `383`–`402 MiB`），仍比原版低约
`200 MB` 且终态后释放。`GOGC=50` 因此不再需要，ADR-0047 已无未量化成本项。测量纪律：`50ms` 采样在大堆下把 wall 从 `14.410s` 抬到 `22.869s`，
峰值与 wall 必须分两次运行测。
实施后真实 `/` 的 A/B 实测：用户可见终态中位数 `20.651s`（控制臂）→ `17.110s`（投影臂），对原版中位数
`16s` 的差距从 `5.25s` / `33%` 缩到 `1.1s` / `7%`；目录覆盖率 `92.86%`，投影与 durable 在真实数据上逐字段
一致，首屏 Map `29.6`–`90.8ms`，扫描速度约 `167,000 nodes/s`。峰值内存不升反降（`~893 MiB` 对
`~1013 MiB`），因此 ADR 中以原版 `700M+` 定的峰值预算被证伪并改为以自身控制臂基线表述。
扫描期按 `parent_id` 分桶增量索引作为 R-048 候选，本轮不采用。详见
[R-047 记录](R-047-用户可见终态解耦与内存目录树查询预研.md) 和
[ADR-0047](../adr/0047-用户可见终态解耦与内存目录树查询权威.md)。

### R-049 空间图投影密度与载荷成本

状态：已实施并实测（ADR-0048 已接受；密度目标 `2000` 弧达成）

原版空间图每个顶层楔形都长满细齿，我们只有最大的楔形有 3–4 环——因为 ADR-0017 的 `projectionLimit`
是**整个投影共享的总预算**（默认 `384`、硬上限 `512`），最大的楔形先吃光配额。实测真实 `/` 快照
（`snapshot-9`）：预算在 `512` 处饱和于 `533` 个弧；载荷约 `0.72 KB/弧`，因此**默认预算下就是 `274 KB`、
硬上限下 `384 KB`，ADR-0017 的 `256 KB` 上限一直在被突破**（与 R-047 的 `<15s` 同类：定数时没有实测）。
抬掉夹子后 `2021` 弧为 `1467.5 KB` / p95 `346.9ms`，`10000` 则被另一条独立上限
`maxPageSize = 1000` 直接拒绝。

关键发现是**瓶颈在每条弧的 DTO 而不是弧数**：投影后代当前携带完整 `scan.Node`（`Path`/`Device`/
`Inode`/`ModifiedAt`/`VolumeID` 加逐条字符串），换成「绘制一条弧实际需要的字段」后载荷稳定小 `11` 倍
（`2021` 弧 `1467.5 KB` → `132.8 KB`，落在 `256 KB` 内）；JSON 编码不是瓶颈（`1.4 MB` 仅 `2.48ms`），
服务端装配才是。因此方案是「先精简投影后代条目、跳过其路径重建、解除 `maxPageSize` 耦合，再由实测
重定预算与 p95」，而不是直接抬预算。路径重建是延迟主因这一点目前仍是**假设**，必须在实现切片实测确认。
目标密度 `2000` 弧由产品决策给出（R-049 只能给出量级估计，不反推目标）。详见
[R-049 记录](R-049-空间图投影密度与载荷成本预研.md) 和
[ADR-0048](../adr/0048-空间图投影条目精简与密度上限.md)。

### R-050 内存投影全保留与会话单一查询源

ADR-0047 把可见终态与 durable 发布拆开后留下了**两个查询源**：发布前由内存投影回答空间图，发布后改由
`Reader` 回答。后果是扫描完成几秒后扇区会"补充跳动"，而且投影的分层 top-K 只覆盖 `92.86%` 的目录，
"投影是权威"因此只能有条件成立。本预研在真实 `/` 上实测三档保留量：`256/8`（现状）覆盖 `92.86%`、
最大 RSS `895 MiB`；`256/64` 覆盖 `99.33%`、最大 RSS `966 MiB`；**全保留覆盖 `100%`、最大 RSS
`1098 MiB`**。两个关键结论：中间档 `256/64` **严格更差**（首屏 `444.68ms` 是全保留的 `2.3` 倍、
可见终态慢 `4s`，只省 `130 MiB`），所以"提高 K"不是折中方案；全保留的可见终态**没有回退**。
按全保留 + 会话单一查询源实施后端到端实测：覆盖率 `591344/591344`、**跨 durable 发布空间图逐字段一致**、
稳态 p95 `2.06ms`/`2.29ms`、载荷 `141.8 KiB`。代价是扫描结束后常驻 `410.8 MiB`——这是定价而非瑕疵，
且推翻了 ADR-0047 第 2.1 节的 `700 MiB` 总峰值预算（该预算在本轮之前就已不成立）。另有一个旧假设被
否证：`495 truncated / 800 deferred` 统计的一直是**密度耗尽**而不是投影保留缺口，字段因此改名为
`DensityTruncated`。详见 [R-050 记录](R-050-内存投影全保留与会话单一查询源预研.md) 和
[ADR-0049](../adr/0049-内存投影全保留与会话单一查询源.md)。

### R-053 空间数值与原版对齐复核

同机对照下我们与原版的数值全面对不上（容量 `228 GB` 对 `245.1 GB`、扫描总量 `190 GB` 对 `231.9 GB`、
原版有「隐藏空间 `9.3 GB`」我们没有）。本轮用 `diskutil apfs list` + `statfs` + 自建 `getattrlistbulk`
探针把差距拆成四条独立缺陷并让账闭合：**单位**（`formatBytes` 以 `1024` 为除数却标 `GB`，统一读低
`7.4%`；`245.1 GB` 就等于 `228.3 GiB`）；**卷组覆盖**（`newMountBoundaries` 无条件跳过根下每个挂载点，
漏掉同容器的 `VM 11.00 GiB` 与 `Preboot 8.36 GiB`；`/System/Volumes/Data` 必须继续跳过，其内容已由
firmlink 覆盖）；**口径**（`OwnedAllocated` 实测恒等于 `AllocatedSize`，"去重后实际占用"从未实现；补测
`ATTR_CMNEXT_PRIVATESIZE` 后确认**原版跟踪的也是 `allocated`**——`/Applications` `21.37` 对 `21.9`、
`/Library` `6.96` 对 `7.0`、`/usr` `1.05` 对 `1.02`，而 `privatesize` 差很远）；**平衡项**（原版按构造让
树总量等于 `statfs` 已用，残差进「隐藏空间」）。另一条关键约束：Preboot 的 cryptexes 是 APFS 克隆，
按 `allocated` 遍历得 `27.60 GiB` 而物理只有 `8.36 GiB`，若如此计入树总量会**超过**磁盘已用。详见
[R-053 记录](R-053-空间数值与原版对齐复核.md) 和
[ADR-0052](../adr/0052-空间数值口径与卷组覆盖对齐.md)。

### R-054 扫描进度条真实分母

原版扫描时是**有进度的**条，我们是不确定条——此前不做是因为没有可信分母（ADR-0027 §4、ADR-0050 §3 都
禁止用容器容量算百分比）。ADR-0052 之后前提变了：快照创建时就记录了卷已用字节，分母成了有实测出处的
真实值。本轮采样真实 `/` 的 `ScanProgress` 流（`76` 个样本）与挂钟对照：曲线**单调**，偏差 `-0.120` 到
`+0.098`（最大约 `12` 个百分点），**封顶 `95.9%`**——缺的 `4.1%` 是 `hidden_space`，只有树总量确定后才
算得出来，必须由终态补满而不能预估。一条关键约束：卷组辅助卷是枚举结束后一次性挂上的，不做前置计数时
最后一个十分位会跳 `26.7 GiB`（`12` 个点）；而它们的大小扫描前就从 `statfs` 已知，前置计入后跳变降到
`4` 个点。本轮还解开了 R-051 §5 的悬案：原版条纹段占轨道 `36%`——**条纹是"正在扫描"的质感、宽度是真实
进度**，两者不是二选一，`36%` 正落在本轮曲线 `t≈40%` 处。详见
[R-054 记录](R-054-扫描进度条真实分母预研.md) 和 [ADR-0053](../adr/0053-扫描进度条真实分母.md)。

### R-055 空间图配色与角度基准取样

三条反馈——扇区不够亮、起始角不对、小扇形堆成毛刺——都靠对原版截图**逐像素取样**定量解决（自建 Swift
取样器按极坐标读 sRGB/HSB）。三个实测结论：**亮度**，原版 HSB 亮度恒定 `97%`–`99%`、饱和度随深度

原版色相**按子项序号**分配（根层 `95/235/294/323/340`，步进 `140/59/29/17`，与角度不成比例）、整棵子树保持
该色相，而我们按角度位置取色。详见 [R-055 记录](R-055-空间图配色与角度基准取样.md)。

### R-056 快照缓存膨胀审计

`~/Library/Caches/marmot` 涨到 `10.4 GB`，而缓存预算是 `512 MiB`。审计出根因是一个 printf 格式串被当成
glob 模式用：`indexPattern` 是 `snapshot-N.index.%020d`，`%020d` 里没有 glob 元字符，`filepath.Glob` 于是
去匹配一个字面同名的文件、返回空切片**且不报错**。同一错误出现在两处并互相放大——`snapshotBytes()` 统计
时不计索引（每个全盘快照少算 `~300 MB`），`deleteSnapshotLocked()` 删除时也不删索引。于是预算以为存储很小、
不触发剪除；触发了也只删 `.data` 和 manifest，最大的文件全部留下：磁盘上 38 个孤儿索引共 `5.3 GB`。另外
被取代的索引 generation 从未清理，`snapshots.db` + `-wal`（`4.6 GB`，ADR-0028 之前的 SQLite 存储）也从未
被任何代码删除，而生产链路早已不打开它。真正必要的只有"一个快照的 data + 当前 generation 索引 + manifest"，
约 `843 MB`。前两项已修（含能抓到该 bug 的回归测试，已验证），SQLite 的清理由
[ADR-0054](../adr/0054-遗留SQLite快照缓存清理.md) 决定。实际清理 `10656 MB → 804 MB`。详见
[R-056 记录](R-056-快照缓存膨胀审计.md)。

### R-057 内存唯一事实源可行性预研

产品决策提出"不再缓存扫描结果，结果只存在内存，刚启动就只能重扫"。本预研只回答技术问题：内存能否自持有
一棵完整的树、代价多少——因为 ADR-0049 的投影是**故意只存偏移、名字从盘上重读**的，取消文件不是纯减法。
实测真实 `/`（`2,782,449` 节点）：**全部文件名合计只有 `55.7 MiB`**（均长 `21`），而
`kind`/`volumeID`/`sizeBasis`/`confidence` 四个字段的**真实基数只有 `3/1/2/1`**——
`"darwin_getattrlistbulk_native_v1"` 重复 278 万次、盘上白占 `84.9 MiB`，`"mount:/dev/disk3s1s1"` 占 `53.1 MiB`。
按 `56` 字节定长布局（**nodeID 用数组下标，不占空间**）+ 名字 arena + 子项索引 + 目录表推算，总计
**`237.4 MiB`**，**低于**现状的 `340–385 MiB`，而磁盘从 `843 MB` 降到 `0`。结论与直觉相反，原因是现行结构
为了"能从盘上重读"付了双份代价（两个偏移 `42 MiB` + 单独的 nodeID `21 MiB` + 每目录两个 Go string 与三个
切片头）——**"为了省内存所以从盘上重读"这个前提不成立**。风险如实记录：推算未实测、崩溃后不留任何结果。
详见 [R-057 记录](R-057-内存唯一事实源可行性预研.md)。

### R-057 内存唯一事实源可行性预研（已实施）

产品决策"不再缓存扫描结果、结果只存在内存、刚启动就只能重扫"的技术前提验证。ADR-0049 的投影是**故意只存偏移、
名字从盘上重读**的，所以取消文件不是纯减法。实测真实 `/`（`2,78x,xxx` 节点）：**全部文件名合计只有 `55.7 MiB`**
（均长 `21`），而 `kind`/`volumeID`/`sizeBasis`/`confidence` 的**真实基数只有 `3/1/2/1`**
（`"darwin_getattrlistbulk_native_v1"` 重复 278 万次、盘上白占 `84.9 MiB`）；**完整路径均长 `122` 字节、
全盘 `325 MiB`**，而旧投影根本不存路径。结论与直觉相反：**取消持久化后内存反而下降**——实施后留存堆
**`276.0 MiB`**（推算 `237.4`），低于原先 `340–385 MiB`，磁盘从 `843 MB` 归零，可见终态 `15.2s`（基线 `16.5s`）。
原因是旧结构为了"能从盘上重读"付了双份代价。三条如实记录的偏差：节点记录实际 **64 字节而非 56**
（漏算了三个 1 字节码）；**峰值 RSS `1113 MiB` 未达门禁 `400 MiB`**，超出部分是扫描管线逐节点 materialise
`scan.Node` ＋完整路径的瞬时垃圾，需另立 ADR；一次报出 `247.756s` 的采样被我误归因为机器换页，**真实原因是
卡在权限弹窗上等待用户点击**——阻塞在对话框上的样本是无效样本，不是性能数据。详见
[R-057 记录](R-057-内存唯一事实源可行性预研.md)。

### R-058 扫描到装配的分配峰值归因

使用方报告应用占用 `1.19 GB`。R-057 第 4c 节已证实其中只有 `258 MiB` 是扫描结果，且高水位在 Darwin 上
**事后不可回收**，因此唯一杠杆是不分配。本记录把一次全盘扫描的 `2530 MB` 分配量落到**具体行号**，
并推翻了先前两份实施报告里"原因是逐节点 materialise `scan.Node` 加完整路径"的归因——那只覆盖一半。
真正的结构性原因是**批次极小**：扫描器发出 `421,701` 个批次，平均 `6.6` 个节点，**`45.7%` 只有 1 个节点**，
而契约要求每批次交付一个独立拥有的 `[]scan.Node`，于是所有"每批次一次"的固定分配要付 42 万次
（含三个按 ID 索引的 map，合计 `428.95 MB`，其中 `directoryDeltas` 一项 `210.61 MB`）。契约总成本
`813.0 MiB`，而存储保留的唯一文本是名字 `55.7 MiB`，倍率 `14.6×`；文件路径 `263.4 MiB` 建完即弃，
父前缀被复制 278 万次共 `269.1 MiB`。**并如实推翻了我自己上一轮的结论**：ADR-0056 实施时引入的翻倍增长
＋`trim()` 是花 `737.54 MB` 分配量换 `110 MiB` 留存下降，在"高水位不可回收"前提下方向相反，分页数组
两头都能拿到。三条改法的隔离测量（每批次 `831.1 → 0.6 MiB`、持久 map `224.2 → 55.5 MiB`、
文件路径 `267.8 → 50.2 MiB`）与生产剖析交叉校验均在 `±10%` 内，推算合计 `2530 → ~626 MB`。
一条方法学纠正：第一版探针用普通计数器统计，跑出 `concurrent map writes` 才发现**扫描器的 emit 回调是
并发调用的**（实测并发 `2`）——挂在 emit 回调上的测量必须先假定并发。同时指出 ADR-0056 门禁 2 的
"峰值/稳态 `<=1.2`"**在 `GOGC=100` 下由构造决定就达不到**，与 churn 无关，是门禁本身的规格问题。**实施后实测**：分配量 `2530 MB → 650.1 MiB`（churn 比 `9.8× → 1.4×`）、峰值 `phys_footprint`
`1126.4 → 569.0 MiB`、留存堆 `256.7 MiB`、可见终态 `15.2 → 14.259s`，推算 `~626` 对实测 `650.1`，
差 `3.9%`。一条实施教训：中途有一版把分配量做到 `19934 MiB`（比改前差 20 倍），因为在回收路径上写了
"缓冲耗尽就新建一个"作为兜底，而自由链表基本总是空的——**以回收为目的的路径上写"分配一个新的"等于没有回收**，
且比不回收更糟。它是被下一次测量抓到的，不是被推理抓到的。详见
[R-058 记录](R-058-扫描到装配的分配峰值归因.md)。


### R-059 峰值与稳态之比和内存上限策略

ADR-0057 把扫描期分配量降了 `74%` 之后，峰值门禁**仍然**不通过。本记录验证了原因确实换了：
留存堆 `255.3 MiB`、峰值 footprint `568.5 MiB`、比值 `2.2`——**churn 降了 74% 而比值纹丝不动**，
因为它由 `GOGC=100` 的定义决定（堆涨到活跃量 `2×` 才回收），与 churn 无关。所以 ADR-0056 门禁 2 的
"峰值/稳态 `<=1.2`"不可实现，必须换成加法余量：比例门禁在更大的卷上会自动放宽，加法门禁不会。
同时重测了 R-057 §4c.4 判定 `GOMEMLIMIT` 为"危险旋钮"的那个拐点——**它随 churn 一起消失了**
（峰值随上限单调下降 `577.2 → 570.8 → 520.4 → 486.2 → 473.2`，代价只在 `300MiB` 出现、耗时 `+18%`）。
但**固定上限仍然不该用**：活跃集约 `92` 字节/节点，超过约 `4.3M` 节点的卷会顶穿 `400MiB`，
本机调好的常量会在更大的盘上变成纯粹的性能损失。推荐**自适应上限 `live + 100 MiB`**：
同一探针各 3 次中位数为无上限 `549.0` / 固定 `400MiB` `521.9` / 自适应 **`499.5 MiB`**，耗时无可测代价，
且把峰值与稳态的关系从比例变成加法常数。**一条方法学纠正**：自适应实验的第一版用
`/memory/classes/heap/objects:bytes` 当活跃集，该指标**含未清扫的死对象**，导致上限永远落在堆的当前
位置之上、四档 headroom 全部"无效果"，我差点据此判定方案不可行；正确指标是 `/gc/heap/live:bytes`。
同一个错误也解释了此前"扫描刚结束留存堆 `434.9 MiB`、静置后 `256.7 MiB`"的异常——不是真的多留，
是指标选错。**实施后实测**：峰值 `phys_footprint` `568.5 → 487.8 MiB`，峰值 `-` 稳态 `313.2 → 233.1 MiB`，
稳态 `254.7 MiB`。一个干净的 A/B（各六次不采样运行）同时证实两件事:自适应上限**没有可测的耗时代价**
（中位数 `13.727s` 对 `13.983s`）；以及**这台机器存在一个约 `20s` 的慢模式,与改动无关**——
开关限流器都是六次里两次。由此得到一条纪律：**本机的耗时判定必须给出多次采样**，单次数字有三分之一
概率落在慢模式上。详见 [R-059 记录](R-059-峰值与稳态之比和内存上限策略.md)。

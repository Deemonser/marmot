# R-068 存储源读取的原生化与身份缓存

- 日期：2026-09-01
- 触发：使用方「启动时页面会有一个正在读取存储源的状态,这个过程要多久?能否提速?」
- 结论：`GetStorageSources` 的全部耗时都在逐卷 `diskutil info` 的进程启动上;
  换成 `getattrlist` + statfs + 按卷 UUID 的身份缓存后,热态 **105µs**(原 390–450ms)。

## 1. 慢在哪

`ListVolumes` 每卷起一个 `diskutil info -plist` 子进程(~95ms 纯进程启动),十卷并发仍要
390ms;`ListMounts`(扫描启动路径)同样逐卷跑 diskutil,而且是**串行**。
代码注释早已写明正道:「原生查询取代子进程,或缓存,二者都不改变任何数字」。

## 2. diskutil 提供的五类信息,及各自的原生替代

| 信息 | 会变吗 | 原生替代 | 验证 |
| :-- | :-- | :-- | :-- |
| 卷自身已用字节 | 会 | `getattrlist ATTR_VOL_SPACEUSED` | 10 卷逐一与 diskutil 相等(±噪声) |
| 容器容量/剩余 | 会 | statfs(APFS 上报的就是容器) | `APFSContainerSize` 与 `Blocks×Bsize` 相等;`APFSContainerFree` 与 `Bavail` 差 1 块 |
| 卷名 | 几乎不 | 缓存(diskutil 首见学习) | — |
| 容器 ID / 卷组 ID | 不 | 缓存 | — |
| SSD/HDD | 不 | 缓存 | — |

关键前提仍是 R-054/ADR-0052 那条:**statfs 不能回答"卷自身用了多少"**——APFS 上它报容器
数字(Preboot/VM 各报 191.8 GB 的事故)。能回答的只有 `ATTR_VOL_SPACEUSED` 和 diskutil,
本次换的是回答者,不是答案。

## 3. 实现

- `getattrlist` 一次调用取 `ATTR_VOL_SPACEUSED` + `ATTR_VOL_UUID`(~10µs/卷)。
  **注意回复布局**:实测 SPACEUSED(8 字节)在 UUID(16 字节)**之前**,与位序相反——
  后加的属性按 man page 的组序排,不按 bitmask 位置。解析错时得到的是随机大数,
  对账测试当场拦住了它。
- 身份缓存 `~/Library/Application Support/marmot/volume-identity.json`:UUID →
  {名称, 容器, 卷组, 介质, 文件系统}。首见某卷时 diskutil 学一次,写穿;损坏读作未命中。
  改名的卷在缓存删除前显示旧名——身份里唯一可能过时的字段。
- `UsageBasis` 新值 `native_apfs_volume_v1` / `native_volume_v1`;statfs 兜底语义不变。
- UUID 拿不到或 SPACEUSED 不支持(网络卷等)→ 整体退回 diskutil 路径,和过去一样。

## 4. 实测

| | 之前 | 之后(热) | 之后(首次见到全部卷) |
| :-- | --: | --: | --: |
| `ListVolumes` | 390–450ms | **105µs** | ~370ms(diskutil 一次性学习) |

守门测试:逐卷对账(native vs diskutil,±2% 或 64MB)、缓存文件往返与损坏降级、
热态 `ListVolumes` < 50ms(比实测高一个量级,比被替换者低两个,不会抖动误报)。

## 5. 未验证 / 已知限制

- 外置 HFS+/exFAT 卷的 SPACEUSED 支持未在本机验证(无此类卷);不支持时走 diskutil 退路,
  行为与过去一致,只是慢。
- 启动的其余部分(webview 加载、React 首屏)未测量;本记录只覆盖"正在读取存储源"这一段。
